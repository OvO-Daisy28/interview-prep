## 撰写原则（以优秀简历为标准，写其他项目时同样适用）

1. **产出动词叙事**：部署、开发、诊断并修复、定位并解决、打通——不用「梳理 / 调研 / 做实验 / 验证」等过程动词。动词决定简历身份：测试工程师还是工程师。
2. **一条一个故事**：问题 → 动作 → 结果，两行以内。两个故事塞同一条必然超长。
3. **数字只放句尾做结果**：报告「快了多少、降了多少」，不报告「怎么测的」。控制变量、阶梯压测、p99/max 等方法论细节留给面试口述。
4. **不自我解释意义**：删「压测同时验证了……」式元叙事。数字自己说话，需要解释的数字不该出现在简历上。
5. **小规模数字不上广告位**：题集数量、图谱节点数、「百份」级时间不写——要么删，要么换倍数表述，要么留作面试口头弹药（存防守地图）。
6. **不主动立靶**：不写「满足 XX 指标」（除非实测真达标），写「提供基线 / 支撑可行性结论」；不声称自己没实测过的能力（如检索调优）。
7. **口径可对账**：每个数字被追问时能说清来源（脚本压测还是服务路径、CPU 还是 GPU 环境、哪批数据），简历 / 详细版 / 口头三层一致。
8. **数字分层有节奏**：性能与结果条用数字收尾，功能与修复条靠「解决了原生做不到的问题」叙事——不是每条都堆数字，留一两个口头弹药更有冲击力。

## 主版本（3 条密集段落）

2026.08–至今
核电央企采购文件知识库活化（基于 RAGFlow 二次开发）
RAG 算法实习生

内容：面向核电央企采购文件（设备运维手册、法规文档等，万级规模）数字化活化需求，基于 RAGFlow + MinerU 技术栈搭建文档解析入库、知识图谱构建与检索问答的端到端系统，需解决万级导入吞吐瓶颈、多文档 GraphRAG 建图抽取失败、以及问答时效（常规 ≤2s / 复杂 ≤5s）与准确率要求。

个人职责：独立部署 131 CPU 与 4×4090 GPU 两套 RAGFlow 集群，修复 Task Executor 队列假死故障（5 处内核补丁 + 全库数据治理），分层架构开发带进度可视化的批量导入服务（IngestPipeline 协议层 + 状态机 + 并发调度 + 失败隔离），主导性能评测与优化、GraphRAG 与端到端验证三项核心工作。

1. **性能评测与 GPU 迁移**：设计 100/1000/10000 份阶梯压测（控制变量法），以 p99/max 长尾分布而非均值定位 Embedding 为主要瓶颈（占总耗时 93.6%、单份 max 556s 堵塞并发槽导致万份吞吐下降 74%）；主导 4090 GPU 迁移，吞吐提升约 5 倍、长尾 556s→5.4s；对扫描版 PDF（MinerU）做 7 组实验定位真瓶颈为 API 固定开销而非 OCR

2. **GraphRAG 建图与检索**：解决多文档建图空图问题（根因为 LLM 结构化输出稳定性而非文档规模），经模型对比选型（Qwen3.8-27B）成功构建全局图谱（979 节点/719 边）；知识图谱检索较纯向量相似度提升 40%（局部问题，T1 双维对照实验）

3. **端到端问答验证与优化**：以真实核电设备手册打通全链路；落地流式响应+生成长度控制+上下文裁剪优化后，简单问答完整响应 1.0s（≤2s 达标）、流式首字 0.9s（≤2s/5s 双达标）；分层耗时分析定位瓶颈为 LLM 生成（占 96.5%）而非检索
