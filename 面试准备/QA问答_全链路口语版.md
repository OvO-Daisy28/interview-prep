# 面试 QA 问答 · 全链路口语版

> 定位：**面试时嘴上怎么说**——真实高频问题 + 简洁回答，不带源码引用（源码细节在 `RAGFlow源码全链路调研.md`）。
> 用法：先遮住答案自己答，再核对。答案里的数字都是我项目实测，可以放心说。

## 环节⓪ 项目背景与选型

**Q1: 这个项目到底要解决什么问题？**

A: 核电央企有一堆采购文件——设备运维手册、法规文档，现在就是一堆 Word 和 PDF 躺在文件服务器上，没人能高效查询。我们要做的事本质上是把"死文档"变成"可问答的知识"。

具体要做成三件事：
1. **私密性本地部署**——核电资料不能上网，所有模型和服务必须本地跑
2. **形成可复用知识库**——不是每次把文件发给大模型，而是先对知识做建设，后续可复用检索
3. **稳定且可问答**——万级文档能扛住导入，问答时效达标（常规 ≤2s / 复杂 ≤5s）

**Q2: 为什么必须用 RAG？直接用 Elasticsearch 全文检索不行吗？直接把文档丢给大模型呢？**

A: 两个方案都不行。ES 全文检索只能做关键词匹配，做不到语义检索——"泵的出力参数"和"额定流量扬程"语义相同但关键词不重合，ES 召回不了。直接把文档丢给大模型更不行：一是私密性不允许传公有云；二是本地 27B 模型上下文窗口约 96K（vLLM max_model_len=98304），一份手册勉强能放但万份不行；三是没有引用溯源、不可审计。RAG 的本质是用离线计算（解析→分块→向量化→建索引→建图谱）换在线效率——离线把"理解"前置，在线只检索不读全文。

**Q3: 你们怎么选的 RAGFlow？市面上 RAG 框架不少。**

A: 不是"甲方指定了我们照做"。前期做了横向选型评测——用 5 部劳动法拆 315 条款，建了 50 道多跳问答测试集（简单 15 + 中等 20 + 复杂 15），用 RAGAS 6 项标准指标评了 9 种系统（FAISS baseline / LightRAG 四种模式 / GraphRAG-SDK / WeKnora / RAGFlow）。结论是：图谱增强在多跳问题上有优势、Agent 模式准确率最高但延迟代价大、RAGFlow 工程成熟度最高（Docker 全栈 ES+MinIO+MySQL+Redis）。甲方指定 RAGFlow + MinerU 后，我的工作转向验证它在万级场景下能不能用——后面遇到的每个问题（假死、长尾、空图）都是验证过程中暴露的。

**Q4: 你在项目里的角色边界是什么？**

A: 独立部署 131 CPU 和 4×4090 GPU 两套集群，源码级调研全链路，主导性能评测、GraphRAG 实验、端到端验证三项核心工作。5 处内核补丁按本人修改口径；批量导入服务（方案 B）按本人开发口径。面试讲"5 处源码修改"时精确说法是"部署版本上的本地补丁，未贡献上游"。

**Q5: 你们的检索是怎么做的？用的什么存储引擎和算法？**

A: 存储引擎用的是 ES（Elasticsearch），它比较全面——既能做 BM25 全文检索（倒排索引+关键词精确匹配），又能做向量检索（HNSW 算法），还支持字段过滤（按 kb_id 等结构化字段做检索时过滤，实现多租户隔离）。不用 Faiss/Milvus 是因为 RAGFlow 架构和 ES 深度绑定，万级规模下检索不是瓶颈没有换的动机——注意 Milvus 2.5（2024.12）已经支持 BM25 全文检索了（Sparse-BM25），不再是短板，但换引擎成本高。

向量检索用的是 HNSW 算法，属于近似最近邻搜索（ANN）的一种——把向量组织成多层图结构，高层稀疏快速跳远、底层密集精确搜索，O(log N) 复杂度。embedding 模型实际部署的是 BGE-M3（1024 维），来自智源 BAAI FlagEmbedding 项目——支持稠密检索、稀疏检索、多向量检索三路合一，自蒸馏提升效果。RAGFlow 官方默认配的是 Qwen3-Embedding-0.6B（LLM-based 架构，CMTEB-R 71.02）。我们选 BGE-M3 是因为多语言+长文本+三路检索能力适配核电多语种文档场景。详细原理见 `知识库/09_Embedding原理与BGE模型选型/`。

召回时走混合召回——向量检索和 BM25 两路并行，加权融合，向量权重默认 0.3。如果首轮召回为空会自动降阈值重试（宁多不漏）。召回 top_k=1024 候选，最终 top_n=6 进 prompt。详细算法解释见 `知识库/08_检索算法与存储引擎名词解释/`。

## 环节⓪+ 架构理解

**Q6: 你对 RAGFlow 的整体架构是怎么理解的？核心组件有哪些？数据怎么流的？**

A: RAGFlow 是一个 RAG 全链路集成平台，六大核心组件各司其职：

| 组件 | 角色 | 干什么 |
|---|---|---|
| API Server | 请求入口 | 接收上传、解析触发、问答等所有 API 请求 |
| Task Executor | 离线 worker | 领取任务后干活——解析、分块、向量化、写索引 |
| Redis Stream | 任务队列 | 持久化消息队列，支持消费者组、ACK、pending claim（未确认消息接管） |
| ES | 检索引擎 | 三合一：BM25 全文检索 + HNSW 向量检索 + 字段过滤（kb_id 多租户隔离） |
| MinIO | 对象存储 | 存原始文档，按知识库隔离（bucket=kb_id） |
| MySQL | 元数据库 | 存文档记录、任务状态、知识库配置等结构化数据 |

**离线流水线（建库）**：解析 → 分块 → 向量化 → 索引写入 → GraphRAG 构建（可选）

**在线流水线（问答）**：问题向量化 → 混合检索 → 组装上下文进 prompt → LLM 生成带引用的答案

**完整数据流向**：
```
上传：API Server → MinIO（存原始文件）→ MySQL（建文档记录，状态=未开始）
解析触发：API Server → MySQL（改状态=运行中）→ Redis Stream（写任务消息）
离线处理：Task Executor ← Redis Stream（领任务）→ MySQL（取文档信息）
         → 解析（DeepDOC/MinerU）→ 分块 → BGE-M3 向量化 → ES（写索引）
         → MySQL（更新状态=完成、chunk 数、token 数）
在线问答：API Server → BGE-M3（问题向量化）→ ES（混合检索）→ 组装上下文进 prompt → LLM（生成答案）→ 返回
```

**关键点**：离线和在线共用同一个 BGE-M3 模型——离线把文档 chunk 编码成向量写入 ES，在线把用户问题编码成向量去 ES 检索。两边的向量必须在同一个向量空间，所以换 embedding 模型必须全库重建。

## 环节① 上传与文档管理

**Q1: RAGFlow 支持什么类型的文档？**
A: 三大类——Office 系（docx/xlsx/ppt）、文本系（txt/markdown/pdf/html/email）、还有图片、音频这类特殊类型。每种类型对应一个解析模板；PDF 还要分文本版和扫描版走不同路径。我项目里主要是 Word 和扫描版 PDF 两条线。

**Q2: 上传后文档立刻能检索吗？**
A: 不能。上传只做两件事：文件存对象存储、数据库建文档记录，状态是未开始。要再调解析接口，任务进队列、后台 worker 处理完分块向量化入库，状态变完成才可检索。上传本身很快（我们 100 份 3.2 秒），慢的是解析。

**Q3: 同一份文档传两遍会怎样？**
A: 按内容哈希判断——内容没变只覆盖文件不重新解析；内容变了才重新走解析。同名不同内容会自动加序号区分，不会互相覆盖。

**Q4: 原始文件存在哪里？**
A: 对象存储（MinIO），按知识库隔离，一个 KB 一个 bucket；检索索引则是按租户隔离，所有 KB 共用一个索引、用 kb_id 字段过滤。两级隔离维度不同——这是我建库时实测验证过的。

**Q5: 上传的 API 是什么意思？POST 是什么？**
A: API 就是程序之间通信的约定——不一定要开网页手动操作，写脚本调接口就行。上传调的是 POST 接口（`POST /api/v1/datasets/{kb_id}/documents`），POST 是 HTTP 请求方法，语义是"提交数据"——和 GET（获取数据）对应。上传用 POST 是因为要把文件二进制放在请求体里传给服务器，GET 没有请求体且 URL 长度有限装不下文件。

API Server 收到上传请求后做三件事：文件存 MinIO（bucket=kb_id）、元数据写 MySQL（状态=UNSTART 未开始）、生成缩略图。上传不触发解析——要再调一次解析接口（也是 POST），任务才进 Redis Stream 队列。两步独立设计，可以先批量传 100 份（3.2 秒），再选择性触发解析。详细 API 解释见 `知识库/10_API与HTTP基础/`。

## 环节② 任务队列

**Q1: 为什么需要消息队列？**
A: 解析是重活——OCR、版面分析、embedding，单份几十秒到几分钟，同步做会阻塞死 API。异步化后上传接口立即返回，worker 慢慢消化队列，还能多 worker 水平扩容、失败隔离。队列不是加速处理，是解耦和异步化——上传接口秒回，解析后台慢跑。

**Q2: 消息队列用的什么？Redis Stream 的消费者组是什么意思？**
A: RAGFlow 用的是 Redis Stream——Redis 内置的持久化消息队列。核心机制是消费者组：一组 worker 共用一条队列，每条消息只分配给组内一个 worker（不重复），同时追踪消息状态——新消息 → 已分配未确认（pending）→ 已确认完成（ACK）。

消费者组和普通队列的区别：普通队列"读了就消失"，消费者组有 ACK 机制——worker 领走消息后消息进入 pending 列表，worker 做完后主动 ACK 才彻底完成。如果 worker 没做完了，消息一直留在 pending 里。

RAGFlow 选 Redis Stream 而不是 RabbitMQ/Kafka，是因为已经用 Redis 做缓存了，不想为队列再引入新组件——万级文档吞吐 Redis Stream 够用。但代价是 ACK 过期接管不如专用 MQ 成熟，需要自己写 watchdog + claim 逻辑。

**Q3: ACK 机制和你的假死修复什么关系？**
A: RAGFlow 的 ACK 在整个任务完成的 finally 末尾才发——worker 领走消息后要跑完解析+分块+向量化+写索引全部步骤才 ACK。如果 worker 中途僵死了（进程还在但不干活），消息永远卡在 pending 列表里。别的 worker 直接读队列看不到 pending 里的消息——要主动用 XPENDING + XCLAIM 命令去"抢"才能接管。这就是假死根因：ACK 时机太晚 + pending 消息不会自动被接管。

假死的表现：worker 僵死后，任务卡在 pending 不被处理，文档状态一直停留在"运行中"（RUNNING），前端轮询进度永远看不到完成——所以叫"前端假死"，根因在后端 worker 不干活。

修复方式：加 watchdog 监控 worker 心跳，心跳超时后用 XCLAIM 把 pending 消息抢过来分配给活着的 worker。

**Q4: 怎么知道解析进度？**
A: 文档表里一个进度浮点加一条文本消息，worker 处理中更新。但原生进度粒度很粗——我实测 536 次轮询只见到 4 种进度文本，根本不知道卡在哪个阶段。这正是我们做二开编排层的直接原因。

**Q5: 任务能取消吗？**
A: 有取消接口但效果有限——软取消，worker 只在阶段边界检查标志。我实测解析跑到 30% 时发取消，100 份一份都没停成，因为检查点之间文档已经处理完了。

**Q6: 任务失败怎么办？**
A: 原生没有自动重试，失败即终态，只能重新触发整个文档。重试粒度是文档级不是阶段级——这是原生接口不可控的实证之一。

**Q7: 遇到过什么队列故障？**
A: 核心是 worker 假死——进程还在但 asyncio 事件循环被阻塞调用卡住（网络超时/ES 写入阻塞/Redis 连接耗尽），心跳停了，消息卡在 pending 无法被接管，Docker 不重启（进程没退出）。三个问题叠加形成恶性循环：①队列未隔离→重任务（GraphRAG 合并几百秒）占住 worker→普通任务积压；②积压→worker 高负载→偶发阻塞调用超时→事件循环僵死；③僵死后没有 watchdog→永久卡住→人工重启→积压更严重。

修复三件套：队列按 suffix 分隔离（common/graphrag/raptor/mindmap）、watchdog 心跳监控 300 秒超时强制退出触发 Docker 重启、XCLAIM 接管 pending 消息。

**关键经验**：代码修复是必要条件但不够——改完代码后短暂还出现过，因为 ES 里有大量孤儿 chunk、MySQL 有大量失败 task 记录、Redis pending 里有之前假死留下的僵尸消息。这些脏数据互相拖累。清理完数据库和 Redis 后，干净环境 + 修复代码才真正根治。生产环境故障修复不只改代码，还要清理运行时累积的脏状态。

这个能展开讲十分钟。

**Q8: worker 为什么会僵死？asyncio 事件循环是什么？**
A: Task Executor 用 Python asyncio——单线程事件循环，所有异步任务排队执行。正常时循环不断取任务→执行→取下一个。僵死是某个任务卡在阻塞调用上（网络请求超时不返回、ES 写入阻塞），整个事件循环停在那一动不动，后面的任务全排队——包括心跳任务，所以心跳停了。进程还在但 CPU≈0，Docker 不会重启（进程没退出）。

asyncio 的风险就是"一个阻塞调用卡死全部"——多线程/多进程不会这样，但 asyncio 胜在轻量高并发。RAGFlow 选了它，代价就是要自己处理阻塞导致的僵死。

**Q9: 为什么修复后不再出现假死？**
A: 假死不是单一原因，是恶性循环。修复队列隔离 + 清理数据库 + 迁移 GPU 三个因素叠加，从根源上减少了阻塞调用的发生：队列隔离后重任务不挤普通 worker、GPU 迁移后 embedding 从 556s 降到 8.9s 大幅缩短网络等待。watchdog 是兜底机制，修复后基本不触发了但留着保险。300 秒超时不短是因为单个文档解析+向量化可能 1-2 分钟，不能误杀正常长任务。

## 环节③ 文档解析

**Q1: 文档解析到底在做什么？版面分析和 OCR 什么关系？**
A: 文档解析是把不同格式文档处理成**带语义结构的文本单元**——保留标题层级、段落边界、表格结构、图片位置。不只是提取纯文本，丢了结构后续分块就没有"按章节切"的依据。

版面分析和 OCR 是流水线关系，不是并列关系：先版面分析（检测页面上每个区域是什么——标题区/正文区/表格区/图片区/公式区），再 OCR（只对文字区域做识别）。不先做版面分析，OCR 会把表格里的文字和正文混在一起，表格结构就丢了。详细算法见 `知识库/11_文档解析算法栈/`。

**Q2: 不同格式的解析有什么区别？**
A: docx 直接从文档结构取段落表格，快且准；文本版 PDF 要做版面分析识别标题段落表格；扫描版是图片，必须先 OCR 再版面分析，最慢。我实测扫描件的成本大头在版面和公式识别——OCR 本身只占不到 3%，这个反直觉结论是做了 7 组实验才定位的。

**Q3: 解析用了什么算法？**
A: 扫描件走 MinerU 完整流水线：版面分析用 DocLayout-YOLO（YOLO 目标检测架构，检测页面上标题/正文/表格/图片/公式区域），公式识别用 PP-FormulaNet（Transformer 架构，把公式图片转 LaTeX），表格识别用 SLANet++（图结构表格识别），OCR 用 PaddleOCR 的 DB 检测 + CRNN 识别。docx 走 DeepDOC，直接从文档 XML 结构取段落表格，不需要版面分析和 OCR。

**Q4: 扫描件怎么处理？**
A: 走 OCR 引擎。RAGFlow 支持多种解析引擎按知识库配置切换——自带的 DeepDOC、MinerU、Docling、PaddleOCR。我们扫描件批量解析用 MinerU，它是完整流水线：版面→公式→表格→文字识别→后处理。

**Q5: 表格和图片怎么进入检索？**
A: 表格整表转成结构化文本（HTML/Markdown）作为一个块，保留完整行列关系——强切表格会破坏语义。图片存原图、可生成描述参与检索，命中后前端展示原图。

**Q6: MinerU 和 RAGFlow 是什么关系？**
A: 两种用法：可以作为 RAGFlow 内置的解析引擎（配置切换），也可以独立部署成解析服务。我们两种都做过——独立部署时做了专项性能测试，RAGFlow 内作为引擎直接用。

**Q7: 为什么 OCR 不是瓶颈？**
A: PaddleOCR 的 DB 检测和 CRNN 识别经过多年优化，模型轻量推理快。版面分析模型更大（要处理整页图像），公式识别最重（Transformer 理解空间结构）。实测 OCR 只占不到 3% 耗时，大头在版面分析 + 公式识别 + API 固定开销。这个反直觉结论定位了真正的优化方向——不是优化 OCR，是优化 Layout 和 MFR。

**Q8: 不同文档格式对应的解析策略是什么？**
A: 两个维度决定解析路径——文档格式（文件后缀）+ 解析引擎配置（layout_recognize）。docx 走 DeepDOC DocxParser 直接从 XML 结构取段落表格，最快；文本版 PDF 走 DeepDOC PlainParser 做版面分析检测区域类型；扫描版 PDF 走 MinerU 完整流水线（版面→OCR→公式→表格→后处理），最慢；txt/md 直接读取。PDF 的引擎可插拔——同一个 PDF 配置不同走 DeepDOC/MinerU/PaddleOCR。

**Q9: PTR 手册走了哪些解析链路？**
A: PTR 手册是 docx 格式 → DeepDOC DocxParser 直接从 docx XML 结构提取段落/表格/图片，不需要版面分析和 OCR。因为 docx 本身就有结构信息（段落、标题层级、表格行列、图片位置存在 XML 里），不用像扫描件那样用模型去猜页面有什么。42.74s 完成解析+分块+向量化+索引写入，产出 116 个 raw chunks。

**Q10: 怎么确保解析的准确性？**
A: 四层验证：① 抽查原始 chunk——随机打开 10 个逐个看内容是否完整、段落边界是否正确、表格结构是否保留；② 对照原文——打开手册原文对比关键章节，确认标题层级正确归属、内容无遗漏；③ 检索验证——拿手册里的已知事实做检索（"额定流量多少"），看召回 chunk 是否包含正确答案；④ 端到端问答——50 道测试题覆盖简单/中等/复杂，答案正确率间接反映解析+分块+检索全链路质量。另外 GraphRAG 抽出 979 实体 719 关系也是间接验证——实体名称正确说明 chunk 内容完整。

## 环节④ 分块

**Q1: 分块是怎么分的？算法是什么？**
A: RAGFlow 用 `naive_merge` 算法，四步：① 按分隔符（默认中英文标点+换行 `\n!?。；！？`）切成段落 → ② 按 chunk_token_num 聚合相邻段落到接近 512 token → ③ 超限段落不硬切，独立成块（OVER_CAP 策略），由 embedding 模型层截断 → ④ 可配块间重叠（overlapped_percent）。关键设计：512 不是硬上限——一个段落超 512 不会被从中间切断，避免破坏语义。

**Q2: 不同文档类型对应的分块策略是什么？**
A: RAGFlow 有十几种切块模板（FACTORY 表）。naive（通用）按标点+token 数切；paper 按论文结构（摘要/章节/参考文献）；laws 按条款编号（第X条）；manual 按章节层级；qa 按问答对；table 整表一个块；one 整文档一个块。区别就在切分依据：通用看语义边界（标点），领域看结构边界（条款/章节/问答对）。

**Q3: PTR 文档走的什么分块策略？**
A: PTR 手册用 naive 通用模板，chunk_token_num=512、delimiter 默认中英文标点。解析出的 sections 按标点切段 → 聚合到 ~512 token → 产出 116 个 raw chunks。GraphRAG 建图时再把 116 个 chunk 按 4096 token 合并成 17 个抽取单元——512 是检索粒度（小块精准召回），4096 是建图粒度（大块上下文完整抽实体），两层不冲突。

**Q4: chunk 大小怎么选？**
A: 我们用 512 token。太大检索不精准、embedding 质量也降；太小上下文碎片化，召回的块拼不出完整答案。512~1024 是常见区间，最好按文档类型实测。PTR 手册 512 切出 116 块。

**Q5: 超过 token 上限的段落会硬切吗？**
A: 不会硬切。超限段落独立成块、不做二次切割，由后续模型层截断——避免在句中粗暴截断破坏语义。另外块间可以配重叠比例，缓解边界上下文丢失。

**Q6: 分块对后面有什么影响？**
A: 分块是 RAG 的咽喉环节，切不好后面每步都受影响：① 向量化——chunk 大小影响 embedding 质量，太大向量稀释、太小语义碎片；② 检索——chunk 是检索单元，切坏了召回半句话或跨段拼不上；③ GraphRAG——chunk 是实体抽取输入，关键实体被切到两个块里就抽不到；④ 问答生成——6 块进 prompt 当上下文，信息碎片化 LLM 拼不出答案或编造；⑤ 引用溯源——chunk 带页码和文档 ID，切不精确引用指向不完整片段。分块不是独立步骤，是检索质量的根基。

**Q7: 分块对 GraphRAG 有影响吗？**
A: 有——GraphRAG 抽实体就是以 chunk 为输入，切得合理实体上下文才完整。我们建图时还把 chunk 按 4096 token 合并成更大的抽取单元，让 LLM 一次看更多上下文，减少实体被切碎。

## 环节⑤ 向量化

**Q1: embedding 模型怎么选的？**
A: 实际部署 BGE-M3，智源 BAAI 出品。选型看三点：语言匹配（核电文档含中英双语术语，BGE-M3 支持 100+ 语言）、维度（1024 维，索引大小和检索速度可接受）、多路检索能力（dense+sparse+multi-vector 三路合一，自蒸馏提升）。RAGFlow 官方默认配的是 Qwen3-Embedding-0.6B，我们用 BGE-M3 是因为三路检索能力适配混合检索场景。从 CPU 服务迁到 4090 GPU 部署后单条快了 10.5 倍。

**Q2: embedding 为什么成了你们的瓶颈？**
A: 每个 chunk 都要过一次模型。CPU 部署时它占导入总耗时 93.6%，而且共享机上长尾严重——单次最大 556 秒。关键是不是平均慢是长尾慢：均值只涨 12% 但吞吐掉了 74%。GPU 独占后长尾根治，吞吐 5.7 倍。

**Q3: embedding 为什么是瓶颈？为什么要用 GPU 加速？**
A: 两个原因：计算量大 + 长尾效应。

**计算量大**：116 个 chunk 每个都要过一次 BGE-M3 模型（约 5.7 亿参数，XLM-RoBERTa 架构）——Transformer Encoder 有 24 层，每层有 Self-Attention（O(n²) 复杂度，n 是 token 数）和 Feed-Forward Network。一次前向传播要算几千万次矩阵乘法。CPU 只有几个核串行算，GPU 有几千个 CUDA 核并行算矩阵乘法——同样的计算量 GPU 快一个数量级。

**长尾效应**：131 CPU 服务器上 34 个容器共享资源，偶发其他容器抢占 CPU/内存 → embedding 单批超时（max 556s）。关键洞察是"不是平均慢是长尾慢"——均值只涨 12% 但 p99 和 max 飙升，一个长尾堵住并发槽后面全排队，吞吐掉 74%。这不是模型慢，是资源争抢导致的偶发延迟。

**GPU 独占后**：BGE-M3 在 4090 上独占运行，avg 15.3s→1.46s（×10.5），长尾从 556s 降到 8.9s。根因是 GPU 不被其他容器争抢——没有资源争抢就没有长尾。

**CPU vs GPU 对比**：

| 维度 | CPU | GPU |
|---|---|---|
| 核数 | 几个~几十个 | 几千个 CUDA 核 |
| 擅长 | 串行逻辑、分支控制 | 并行矩阵乘法 |
| Transformer 推理 | 逐层串行算 | 每层的矩阵乘法并行 |
| embedding 116 chunks | 15.3s（avg）| 1.46s（avg） |
| 长尾 | 556s（资源争抢） | 8.9s（独占无争抢） |
| 占导入总耗时 | 93.6% | ~50%（瓶颈转移） |

**Q4: 标题参与向量是怎么回事？**
A: RAGFlow 的 embedding 不是只编码正文——标题（文件名/标题）单独过一次模型编码成向量，然后和正文向量按 0.1:0.9 加权融合，得到最终向量。这意味着文件名也是检索信号——文件名含"PTR冷却泵"有助于检索。面试讲检索质量优化时这是一个具体手段。

**Q5: embedding 的原理是什么？文本怎么变成向量的？**
A: 三步：文本 → Tokenizer 切成 token 序列 → Transformer Encoder（24 层 Self-Attention）→ 池化（取 [CLS] token 的输出）→ 固定维度向量（1024 维）。本质是一个神经网络把文本"压缩"成一个数值向量，语义相近的文本向量距离近。BGE-M3 用对比学习（InfoNCE）训练——正样本对拉近、负样本对推远。详细原理见 `知识库/09_Embedding原理与BGE模型选型/`。

**Q6: embedding 和检索的关系？为什么换模型要全库重建？**
A: embedding 是双塔架构——离线时每个 chunk 编码成向量写入 ES（doc 端预计算，只做一次），在线时只编码 query（毫秒级），然后算 query 向量和 chunk 向量的余弦相似度。效率关键：doc 端预计算 = 检索时不用重新编码，百万文档也能秒级返回。

换模型必须全库重建：不同模型的向量空间完全不同——BGE-M3 和 Qwen3-Embedding 维度不同、空间不同，同一句话编码出的向量完全不同，不在同一个空间里余弦相似度没有意义。所以 doc 端向量必须和 query 端用同一个模型。

**Q7: 问题和文档用不同模型行不行？**
A: 不行。两边的向量必须在同一个空间里相似度才有意义，换 embedding 模型必须全库重建向量。

**Q8: 向量存哪？**
A: 和其他字段一起存在文档引擎（ES）里，没有单独的向量库——这样向量、全文、结构化过滤一个引擎全做。

## 环节⑥ 索引

**Q1: 索引是什么？和召回什么关系？**
A: 索引和召回是两个阶段——索引是离线建库时的"准备数据结构"，召回是在线问答时的"在索引里算相似度找 chunk"。索引不算相似度，它是在构建让后续检索能快速查的数据结构：倒排索引（给 BM25 用）和 HNSW 图（给向量检索用）。

**Q2: 索引具体在做什么？**
A: ES 写入一条 chunk 记录时做两件事：① 倒排索引构建——把 chunk 内容分词后建"词→文档列表"的映射（查"冷却泵"秒级找到所有含这个词的 chunk）；② HNSW 图构建——把 chunk 的 1024 维向量插入多层图结构，让后续向量检索 O(log N) 快速找到最近邻。两个索引一个引擎全建，这就是混合检索的基础。

**Q3: 为什么用 ES 不用专用向量库？**
A: 混合检索需要向量+全文+字段过滤三件事，ES 一个引擎全做，运维简单。Milvus 2.5+ 也支持 BM25 了（Sparse-BM25），不再是短板，但 RAGFlow 架构和 ES 深度绑定换引擎成本高。我们的规模下检索从来不是瓶颈——实测向量检索 P50 半秒以内，端到端慢在 LLM 生成。

**Q4: 索引里一条数据长什么样？**
A: 一个 chunk 一条记录：正文、分词结果（全文检索用）、向量（1024 维）、文档和知识库 ID、页码位置（引用溯源用）。图谱数据也是同一索引里的特殊类型记录——实体、关系、社区报告。

**Q5: 文档更新了索引怎么办？**
A: 重新触发解析会清掉旧块重写；重复上传靠内容哈希判断要不要重做。完整的版本管理和影响范围分析是原生没有的，属于我们的二开方向——更新行为我们正在系统测试。

**Q6: 索引写入为什么后来成了新瓶颈？**
A: GPU 把 embedding 从 93.6% 压到一半以后，瓶颈转移到索引写入（ES 批量写 HNSW 图+MinIO 对象存储写入+MySQL 状态更新三处 IO 叠加），占了 37~52%。这是典型的优化接力——解决一个瓶颈暴露下一个。

## 环节⑦ GraphRAG

**Q1: 为什么需要 GraphRAG，普通 RAG 不够吗？**
A: 普通 RAG 是局部检索——问题能匹配到哪段召回哪段。全局性问题（"这本手册涵盖哪些故障模式及对应措施"）没有具体词可匹配，向量召回效果差。GraphRAG 把文档抽成实体关系图、按社区汇总，跨章节的汇总问题靠图和社区报告回答。我实测过双维对比：局部参数题 KG 相似度提升 40%（0.331→0.464）；全局汇总题 KG 在检索层无相似度提升，但端到端答案覆盖度略优——因为 light 模式没开社区报告，全局汇总能力受限。这个结论很关键：KG 的价值分维度，不是所有问题都受益。

**Q2: 建图流程说一下？**
A: 五步：chunk 合并成抽取单元；LLM 按提示词抽实体和关系（要求 JSON 输出）；每单元可以补一轮"有没有遗漏"的复查；文档级子图合并成知识库全局图——同名实体合并、关系权重累加；最后可选实体消歧和社区发现，生成社区报告。注意社区报告默认关，light 模式根本不做社区——全局问题靠它，没开就没优势。

**Q3: 建图成本怎么样？**
A: 很贵。一份 PTR 手册 116 个 chunk，抽出 979 实体 719 关系，21.8 分钟、90 万 tokens。但增量加文档便宜——我测过加一份修改版，只对新文档做 LLM 提取、旧的跳过，省 20%。

**Q4: 遇到过建图失败吗？**
A: 遇到过多文档空图——任务跑完 0 实体 0 关系。根因不是文档少，是模型的结构化输出不稳定：模型输出的 JSON 格式漂移，解析器解析不出来就是空。对比了几个模型，有的稳定成图、有的就空图。另外配置错误（模型实例名错）也会全失败——重跑前要先单请求验证。

**Q5: 图谱存图数据库吗？**
A: 不用。图序列化成特殊数据块存回同一个检索索引，用字段区分全局图/子图/实体/关系/社区报告。好处是检索链路统一、不用多维护一套图数据库。

**Q6: 文档更新了图谱怎么办？**
A: 我专门测过三种场景。新增文档是增量合并——只处理新文档子图合并进全局图，省 20% 时间。修改文档会被当成新文档，同名实体描述叠加（旧版本数据不自动清理，640 和 650 同时留在图里）。删除文档图谱根本不自动清理，只打个 removed 标记，要手动调清图接口。所以"文档更新了怎么办"的准确答案是：原生支持增量新增，但修改和删除需要二开版本管理和自动清理逻辑。

**Q7: 社区报告为什么没开？**
A: light 模式架构上就不做社区发现，不是配置遗漏——要社区报告必须切 general 模式。light 只做实体抽取+子图合并，不做 Leiden 社区发现和社区报告生成。T1 测试实证：ES 里没有 `entity_type=community` 记录，light 模式不会触发社区发现逻辑。

**T6 实验已补做**：切 general 模式 + `resolution: true` + `community: true`，生成 121 个社区报告。KG 检索增强后 10 题相似度全部从 ~0.37 跃升至 1.0（delta avg +0.61），全局问题 E2E 快 28%。

注意：项目原始需求**明确要求**社区发现能力——"对于全局问题能利用图的社区发现算法跨章节汇总知识并给出综合结论"。Light 模式只满足局部精准定位，General 模式才满足全局社区发现汇总——详见 Q12。

**Q8: 局部问题和全局问题能举几个具体例子吗？**
A: 局部问题有具体词可匹配——"PTR冷却泵的额定流量是多少？"向量+BM25 都能精确匹配到参数表，KG 补充了实体上下文后相似度 +40%（0.331→0.464）。全局问题没有具体词可匹配——"手册中 PTR 冷却泵的故障模式有哪些？分别如何处理？"散落在多个章节，KG 检索层无相似度提升（0.432→0.432，8 道全局题全部持平），但端到端答案覆盖度略优（4/8 题覆盖度 +1）——因为 KG 虚拟 chunk 提供了实体关系的结构化上下文帮 LLM 组织得更完整。

**Q9: 有了 KG 后是怎么检索的？**
A: KG 检索是四路召回，和普通检索（向量+BM25）同时并行：① 实体检索——问题改写后抽关键词，在图里找匹配实体，打分=相似度×PageRank（度数越高越重要）；② 关系检索——从命中实体出发沿关系边找关联实体；③ N-hop 路径——找两个实体之间的路径，打分=相似度×距离衰减（1跳>2跳）；④ 社区报告——匹配相关社区报告（我们没开，这路为空）。KG 四路结果拼成一个虚拟 chunk，相似度强制设 1.0——一定进 prompt 不被阈值过滤。和普通检索的 chunk 一起排序截断进 prompt。

局部问题 KG 有用：实体"额定流量"在图里有关联关系连接到具体参数值，向量召回只匹配到含"流量"的段落，KG 沿关系边找到精确参数。全局问题 KG 无检索优势：没有具体实体名可匹配——"故障模式"不是实体是散落描述，实体匹配匹配不到、子图扩展没有明确起点。社区报告本来干这个（按社区汇总跨章节内容），但没开。

**Q10: 建图流程里每一步具体用了什么算法？为什么选这些算法？**

A: 六阶段，每一步选型都有对比逻辑：

| 阶段 | 做什么 | 用的算法/方法 | 对比选项 | 为什么选它 |
|---|---|---|---|---|
| ① chunk 合并 | 小块拼大块 | 按 token 拼接（batch_chunk_token_size=4096） | 固定窗口/HNSW 式层次化 | 简单有效——GraphRAG 抽取的粒度要够大才能跨段落抽关系，4096 token 是平衡 LLM 上下文和抽取质量 |
| ② 实体抽取 | LLM 从文本抽实体+关系 | LLM + Prompt 模式（不是 NER） | NER 模型（spaCy/BERT-NER）/ OpenIE / 规则匹配 | 见下方 Q11 详解 |
| ② 格式解析 | 解析 LLM 输出 | 自定义分隔符格式（非 JSON） | 标准 JSON / XML | 见下方 Q11 详解 |
| ② gleaning 补抽 | 防遗漏 | 多轮对话式追问（最多 2 轮） | 单轮抽取/后处理补抽 | LLM 单轮容易遗漏，多轮追问成本低、召回提升明显 |
| ③ 子图合并 | 文档子图→全局图 | 字符串匹配同名实体 + 描述追加 + 权重累加 | 向量相似度消歧 / 图神经网络对齐 | 简单字符串匹配够用——合并阶段不需要语义消歧（那是阶段④的事），先按名字聚合 |
| ③ PageRank | 计算实体重要性 | 度数（degree）作为 rank | 真正的 PageRank 迭代算法 | RAGFlow 用的是简化版——直接把节点度数赋给 rank，不做迭代传播。够用因为检索时只是个加权因子 |
| ④ 实体消歧 | 合并同义实体 | 字符相似度/编辑距离 + LLM 判断 | 向量余弦相似度 / 图神经网络对齐 | 默认关闭。字符相似度生成候选对，LLM 判断是否同一实体——成本和质量折中 |
| ⑤ 社区发现 | 实体聚类成社区 | **Leiden 算法** | **Louvain / Girvan-Newman / 谱聚类** | 见下方 Q11 详解 |
| ⑤ 社区报告 | 跨章节汇总 | LLM 生成摘要+findings | 人工模板 / 统计摘要 | LLM 能理解实体关系的语义生成有价值的 findings |

重点说三个选型：

**1. 为什么实体抽取用 LLM+Prompt 而不是 NER？**

NER（Named Entity Recognition）是序列标注——给每个 token 打标签（B-PER/I-PER），抽出来的是"人名/地名/机构名"这类通用实体。但 GraphRAG 要抽的是**领域实体+关系**——"PTR冷却泵"是实体、"额定流量650m³/h"是实体、"冷却泵→连接→额定流量"是关系。NER 只抽实体不抽关系，且类型固定不灵活。

| 方法 | 抽实体 | 抽关系 | 类型灵活 | 核电适配 |
|---|---|---|---|---|
| NER（BERT-NER/spaCy） | ✓ | ✗ | ✗ 固定类型（PER/ORG/LOC） | 需要训练核电领域 NER 模型 |
| OpenIE | ✓ | ✓ | ✓ | 抽出的是三元组但质量低，大量噪声 |
| 规则匹配（正则/模板） | ✓ | ✓ | ✗ | 人工写规则覆盖不全 |
| **LLM+Prompt** | ✓ | ✓ | ✓ 换 prompt 即换类型 | 最好——prompt 里写业务类型，一个模型适应所有领域 |

LLM+Prompt 的代价是慢、贵、格式不稳定——所以才有格式遵循选型（Q11 详解）。

**2. 为什么格式用自定义分隔符而不是标准 JSON？**

RAGFlow light 模式用的是自定义分隔符格式（`<t>` 分隔字段、`<COMPLETE>` 分隔记录），不是标准 JSON。解析器 `handle_single_entity_extraction` 要求：第一个字段必须是字符串 `"entity"`、至少 4 个字段。

这其实**比 JSON 更难**——因为主流 LLM 训练数据里 JSON 格式的样本远多于自定义格式，模型对自定义格式更容易漂移。这也是空图问题的一个架构根因。

**3. 为什么社区发现用 Leiden 不用 Louvain？**

| 算法 | 原理 | 连通性保证 | 速度 | 适用场景 |
|---|---|---|---|---|
| Louvain | 贪心模块度优化 | 不保证（可能有孤立节点） | 快 | 大规模图社区发现 |
| **Leiden** | Louvain 改进+自举分区 | **保证社区连通性** | 稍慢 | 需要可靠社区结构 |
| Girvan-Newman | 边介数中心度 | 保证 | 很慢（O(E²)） | 小图研究 |
| 谱聚类 | 拉普拉斯矩阵特征值 | 保证 | 中 | 聚类数已知 |

Leiden 相对 Louvain 的改进核心是**自举分区（refinement phase）**——Louvain 合并后可能有节点和社区不连通，Leiden 在合并前先做局部优化保证连通性。GraphRAG 用层次化 Leiden 发现多层级社区（大社区里有子社区），社区报告按层级生成。

**面试一句话答法**：
> "建图六步：chunk 合并→LLM 抽实体关系→gleaning 补抽→子图合并（同名实体描述追加+权重累加+PageRank）→可选消歧→可选 Leiden 社区发现。实体抽取选 LLM+Prompt 不选 NER，是因为要同时抽实体和关系、类型要能按领域定制；社区发现选 Leiden 不选 Louvain，是因为 Leiden 有自举分区保证社区连通性，Louvain 可能产生不连通的社区。"

**Q11: 建图用的 LLM 模型怎么选的？选型依据是什么？**

A: 模型选型三个维度按重要性排序：

**维度 1：格式遵循能力（最核心）**——这是 GraphRAG 抽取成败的决定性因素。LLM 本质是概率续写，让它输出严格格式等于要求几百个 token 每个都落对位置。而且 RAGFlow 用的不是标准 JSON 而是自定义分隔符格式，比 JSON 更难。实测对比：

| 模型 | 对话能力 | 格式遵循 | 我的实测 |
|---|---|---|---|
| DeepSeek Flash | 强 | 弱 | **空图**（格式漂移→解析失败→0 节点） |
| GLM-5.2 | 中 | 强 | 成功 |
| Qwen3.8-27B-AWQ-INT4 | 强 | 强 | 成功（979 节点/719 边/17 单元全成功） |
| qwen-plus（云端） | 强 | 中 | 成功但慢（470 节点） |

关键认知：**对话能力 ≠ 格式遵循能力**。DeepSeek Flash 对话很好但格式漂移导致空图——不是模型差，是不适合"结构化抽取"这个特定任务。

**维度 2：中文理解能力**——核电文档全是中文，实体名要合理（不能整句话当实体名）。Qwen 系列中文训练充分是默认选择。

**维度 3：成本与部署约束**——项目要求内网本地部署，不能调云端 API。

**实际选型路径（工程务实，不是系统测试）**：
1. 项目要求本地部署→排除所有云端模型
2. 4090 有 4 张卡→27B AWQ-INT4 量化后 TP2 占 GPU0+3 放得下
3. Qwen 系列是中文场景默认选择→不需要遍历测试所有开源模型
4. 部署后发现建图也能用→一个模型干抽取+问答两件事

选完才验证：979 节点/719 边/17 单元全成功/无空图→证明选型有效。

**Qwen3.8-27B 能成功的三层原因**：
1. Qwen 训练时强化了 structured output / function calling→格式遵循能力强
2. 27B 规模够用——结构化抽取要理解复杂 prompt（类型清单+格式要求+few-shot+gleaning 追问），不需要 70B
3. AWQ-INT4 量化对格式遵循影响小——AWQ 保留更多关键权重精度

**面试一句话答法**：
> "选型是工程务实导向——内网本地部署、4090 有卡、Qwen 是中文场景默认选择，27B AWQ-INT4 量化后刚好放得下。选完验证：建图 979 节点/719 边、17 单元全成功无空图。成功的关键不在模型大小或对话能力，在格式遵循能力——我实测 DeepSeek Flash 对话很好但格式漂移导致空图。所以选型真正要看的是格式遵循率，不是榜单分数。更系统的做法是先跑 10-20 份 chunk 统计格式遵循率，低于 90% 直接排除——不用等建图失败才发现。"

**Q12: 项目需求要求社区发现能力，你们用的是 light 模式没开社区——这算不算没满足需求？怎么补？**

A: 这个问题很尖锐，必须诚实回答。现在已经用 T6 实验补上了数据。

**需求原文**明确要求："系统需支持 GraphRAG 模式。对于局部问题能精准定位；对于全局问题能利用图的社区发现算法跨章节汇总知识并给出综合结论。"

**之前用 light 模式**——架构上不做社区发现。T1 测试实证：全局问题 KG 检索相似度零提升（8 题全部 delta=0）。这是因为 light 模式不生成社区报告（community_report=0）。

**T6 实验已补做**——切 general 模式 + 显式设置 `resolution: true` + `community: true`，同一份 PTR 手册重建图谱，T1 同款题集对比。三维对比结果：

| 维度 | Light 模式 | General 模式 | 优势方 |
|---|---|---|---|
| 建图耗时 | ~10 min | 6.5 min（vLLM 缓存加速） | General |
| 总 LLM tokens | ~700k | ~1,055k（+51%，社区报告独有 286k） | Light 省 |
| 实体数 | 979 | 993（+1.4%，消歧后微增） | 持平 |
| 关系数 | 719 | 792（+10.2%，消歧后合并释放） | General |
| 社区报告 | 0 | **121 个** | **General 独有** |
| KG 检索相似度提升 | **delta=0**（全部 0 变化） | **delta avg +0.61**（全部→1.0） | **General 显著** |
| E2E 延迟（全局题） | 18845ms | 13527ms（快 28%） | General |
| 局部题准确率 | 2/2 正确 | 2/2 正确 | 持平 |

**核心发现**：
1. **General 模式 KG=on 后所有 10 题相似度从 ~0.37 跃升至 1.0000**——社区报告作为虚拟 chunk 强制设 1.0 进 prompt，10 题无一例外
2. **Light 模式 KG=on 相似度零变化**（delta 全部 0.0000）——图谱未参与检索增强，KG 查询是纯无效开销（~810ms 白花）
3. **General E2E 反而更快**（全局题快 28%）——因为图谱增强提供了更精准的上下文，LLM 不需要"猜"就能直接组织答案
4. **成本可控**：General 建图 6.5 分钟（比 Light 快，vLLM 缓存加速），多花 286k tokens 在社区报告上
5. **社区报告质量高**：121 个报告覆盖电动机规格、机械密封、转子部件、冷热态对中、托架轴承等核心知识域

**踩坑**：仅设 `method: "general"` 不触发社区发现——必须额外设置 `graphrag.resolution: true` 和 `graphrag.community: true`（源码 `task_executor.py:1540-1541` 默认 False）

**需求符合性结论**：

| 需求项 | Light | General | 结论 |
|---|---|---|---|
| 局部问题精准定位 | ✅ 向量检索 | ✅ 向量+图谱增强 | General 更优 |
| 全局问题跨章节汇总 | ❌ 无社区报告 | ✅ 121 个社区报告 | **仅 General 满足** |
| KG 检索增强 | ❌ delta=0 | ✅ delta avg +0.61 | **仅 General 有效** |

**建议**：生产环境推荐 General 模式（resolution=true + community=true），满足项目"全局问题利用社区发现算法跨章节汇总"的需求。

**面试一句话答法**：
> "需求明确要求社区发现能力——局部精准定位 + 全局跨章节汇总。我们之前用 light 模式只验证了局部（+40% 相似度），全局因为 light 不做社区发现所以 KG 检索零提升。后来补做了 T6 实验：切 general 模式开社区发现，生成 121 个社区报告，KG 检索增强后 10 题相似度全部从 ~0.37 跃升至 1.0（delta +0.61），E2E 全局题反而快 28%。成本多 51% tokens 但建图时间反而更短（vLLM 缓存加速）。结论是生产环境推荐 general 模式，light 适合快速验证或资源受限场景。"

## 环节⑧ 检索（最热环节）

**Q1: 混合检索怎么工作？**
A: 问题同时走向量相似度和 BM25 关键词匹配，两路加权融合（向量权重我们设 0.3），再过相似度阈值和 top_n 截断。向量管语义相近，BM25 管精确术语——设备编号、型号这种词向量容易漏、关键词必中。

**Q2: top_k 和 top_n 什么区别？**
A: top_k 是召回候选量（我们召回 1024），top_n 是最终进 prompt 的块数（6 块）。先宽召回再精选——中间可以有 rerank。

**Q3: rerank 是什么？**
A: 召回用的双塔模型——问题和文档各自编码再算相似度，快但粗。rerank 是交叉编码器，问题和文档拼一起打分，准但慢。所以流程是宽召回后精排。代价是延迟，我们实测场景没开 rerank，靠混合权重加阈值控制。

**Q4: 相似度阈值怎么设？**
A: 我们设 0.1，低阈值多召回、靠生成端兜底，高阈值砍噪声但可能漏。这是召回率和精准度的权衡，得按数据实测。我们实测最高相似度 0.331（向量）/0.464（KG），说明 0.1 是合理起点。

**Q5: KG 检索和普通检索怎么共存？**
A: KG 检索四路结果——实体、关系、N-hop 路径、社区报告——拼成一个虚拟 chunk，相似度强制设 1.0，和普通检索的 chunk 一起进 prompt。不是两套 prompt，是召回阶段混合。打分用相似度乘 PageRank，N-hop 按距离衰减。所以你看到 KG 返回 30 块里最高相似度 0.464 是普通 chunk 的，KG 虚拟 chunk 是 1.0 强进。

**Q6: 混合检索两路结果怎么融合的？加权还是 RRF？这两种有什么区别？**

A: 我们用的是加权融合（weighted fusion），不是 RRF。

| 维度 | 加权融合（我们用的） | RRF（Reciprocal Rank Fusion） |
|---|---|---|
| 公式 | `sim = w₁ × 向量分 + w₂ × BM25分` | `score = Σ 1/(k + rank_i)`，k 通常 60 |
| 用什么 | 用分数本身 | 只用排名，不看分数 |
| 前提 | 两路分数要可比（归一化到 [0,1]） | 不要求可比——排名就够了 |
| 权重 | 可配置（我们向量 0.3 / BM25 0.7） | 固定 k=60，不用调权重 |
| 优点 | 能体现"这个 chunk 两路都高分" | 简单、不依赖分数归一化、对异质分数鲁棒 |
| 缺点 | 两路分数量纲不同时需要归一化 | 丢失分数信息——第 1 名和第 2 名差距可能很大但 RRF 给的分值差不多 |

**加权融合的关键问题——分数可比性**：向量相似度是余弦相似度（值域 [0,1]），BM25 是相关性分数（值域不固定，可能 0~20+）。直接加权融合要先把 BM25 归一化到 [0,1]——RAGFlow 源码里 `hybridSimilarity` 做了归一化处理。

**为什么 RAGFlow 选加权不选 RRF**：加权能体现分数差异——一个 chunk 向量 0.9 + BM25 归一化 0.8（两路都高）应该比一个向量 0.3 + BM25 归一化 0.9（只有一路高）排前面。RRF 只看排名，两路排名差不多的话区分不出来。对于核电文档这种精确匹配场景，加权更合适。

**面试一句话答法**：
> "RAGFlow 用加权融合——`sim = 0.3 × 向量相似度 + 0.7 × BM25 分`，BM25 分要先归一化到 [0,1] 才能和向量相似度加权。另一种常见方法是 RRF，只看每路排名不看分数，公式 `Σ 1/(60 + rank)`。加权能体现分数差异（两路都高分 > 只有一路高分），RRF 更简单但对异质分数鲁棒。我们选加权是因为核电文档精确匹配场景需要区分'两路都高'和'只有一路高'。"

**Q7: 向量权重 0.3 是不是太低了？怎么调的？**

A: 诚实回答：**0.3 是经验值，没做参数调优**。

但能解释为什么 0.3 合理：
- 0.3 意味着 BM25 占 70%——更信任关键词匹配
- 核电文档有大量精确术语（设备编号 HTJ300-400C、参数 640m³/h、标准号 RCCM）——这些词向量容易漏（语义层面不区分精确值），关键词必中
- 实测 PTR 手册局部问题最高向量相似度 0.331（偏低），说明纯向量召回质量有限，BM25 主导更保险

**调优方法论（虽然没做但要知道怎么答）**：
- 控制变量：固定题集，测权重组合（0.1/0.3/0.5/0.7/0.9）× 阈值（0.05/0.1/0.2）
- 评估指标：召回率（recall@k）+ 准确率（precision@k）+ 端到端答案质量
- 不同场景可能需要不同权重：概念性问答调高向量权重，参数精确匹配调高 BM25 权重

**面试一句话答法**：
> "0.3 是经验值没做调优——但合理因为核电文档精确术语多，BM25 主导更保险。调优应该控制变量测权重×阈值的对照表，用 recall@k 和 precision@k 评估。不同场景权重应该不同：概念问答调高向量，精确匹配调高 BM25。这是我下一步要做的参数级调优。"

**Q8: 检索质量怎么评估？召回率准确率怎么测？**

A: 我们当前评估是**人工评分（1-5 分）+ 相似度数值**，没有自动化检索指标。

| 评估层次 | 指标 | 我们有没有 | 怎么测 |
|---|---|---|---|
| 检索层 | Recall@k（召回率） | ✗ | 准备标准答案对应的 chunk 集合，看 top_k 里命中了几个 |
| 检索层 | Precision@k（准确率） | ✗ | top_k 召回的 chunk 里有多少是相关的 |
| 检索层 | MRR（平均倒数排名） | ✗ | 第一个相关 chunk 排第几 |
| 检索层 | NDCG | ✗ | 考虑排序位置的加权评估 |
| 端到端 | 人工评分 1-5 分 | ✓（T1 测试） | 覆盖度+准确性人工打分 |
| 端到端 | RAGAS（faithfulness 等） | ✗（T8 规划中） | LLM-as-Judge 自动评分 |

**诚实答法**：
> "检索层我没做自动化评估（recall@k/precision@k），靠人工评分和相似度数值。T1 测试做了 8 道全局题 × 2 配置 = 16 次检索的人工对照，但严格来说应该有标注数据集——准备每道题标准答案对应的 chunk 集合，算 recall@6 和 precision@6。这是我下一步要补的，对应补充测试清单的 T8（RAGAS 检索质量量化）。"

**Q9: 多轮对话怎么检索？上下文怎么带？**

A: RAGFlow 有 `full_question` 机制——多轮对话时，把之前的问答历史和当前问题一起送 LLM，让它生成一个**完整的独立问题**，再用这个完整问题去做检索。

举例：
```
第 1 轮：用户问 "PTR冷却泵的额定流量是多少？" → 回答 "640m³/h"
第 2 轮：用户问 "那扬程呢？"
→ full_question 改写为："PTR冷却泵的额定扬程是多少？"
→ 用改写后的问题做检索（而不是用 "那扬程呢？" 检索）
```

**为什么需要改写**：直接拿"那扬程呢？"去检索——向量检索和 BM25 都匹配不到有用内容，因为缺少主语"PTR冷却泵"。改写成完整问题后才有检索意义。

**局限**：改写本身要调一次 LLM，增加延迟。且改写质量依赖 LLM 理解能力——如果上下文很复杂（多实体多轮追踪），改写可能丢信息。更高级的做法是对话状态追踪（DST）——维护对话中已提及的实体/参数，检索时带上历史实体。

**Q10: 检索延迟多少？瓶颈在哪？**

A: 有实测数据：

| 检索方式 | 延迟 | 占端到端比例 |
|---|---|---|
| 纯向量+BM25 混合检索 | ~563ms | <30% |
| 加 KG 检索 | ~1240ms（+~815ms） | ~10-20% |
| LLM 生成 | 5-15s | **70-96.5%** |

**结论：检索不是瓶颈，LLM 生成才是**。即使开了 KG 检索多花 800ms，相对 LLM 生成的 5-15 秒也只是小头。

**为什么检索快**：
- ES HNSW 向量检索 O(log N)，万级 chunk 毫秒级
- BM25 倒排索引直接查，毫秒级
- 字段过滤（kb_id）在检索时同时执行，不是先全搜再过滤

**Q11: 检索为空怎么办？**

A: RAGFlow 有**降阈值重试机制**（min_match 自适应）——如果第一轮召回为空，自动放宽阈值重试：

```
第一轮：similarity_threshold=0.1, min_match=0.3 → 召回为空
→ 自动降级
第二轮：放宽阈值 → 宁多召回不漏
```

这设计体现了"宁多不漏"原则——宁可召回一些弱相关的让 LLM 自己判断，也不能返回"没找到"。因为对用户来说"答案不够准"比"完全没答案"好得多。

**极端情况**：如果放宽后还是为空，会返回"未找到相关信息"——这时要么是知识库里真没相关内容，要么是分块/解析出了问题导致内容没正确入库。

**Q12: 为什么不用 Faiss/Milvus 做向量检索？**

A: 混合检索需要三件事一个引擎全做：

| 能力 | ES（我们用的） | Faiss | Milvus 2.5+ |
|---|---|---|---|
| 向量检索 | ✅ HNSW | ✅ 多种 ANN | ✅ HNSW + 多种 |
| 全文检索（BM25） | ✅ 原生 | ❌ | ✅ 2.5 起原生支持（Sparse-BM25） |
| 字段过滤（kb_id） | ✅ 原生 | ❌ | ✅ 标量字段过滤 |
| 运维 | 一套 | 还得配全文引擎=两套 | 一套（2.5+ 混合检索） |
| 万级规模性能 | 够用（P50 < 0.5s） | 过剩 | 够用 |
| 百万级性能 | 一般 | 强 | 强（宣称比 ES 快 30 倍） |

**注意 Milvus 2.5（2024.12）的变化**：Milvus 2.5 引入了 Sparse-BM25 技术——用稀疏向量实现 BM25 全文检索，一个引擎同时做向量检索 + 全文检索 + 字段过滤。之前 Milvus 不支持全文检索，现在不再是短板了。

**但 RAGFlow 当时选型时（2026.08）用的 ES**，原因：
1. RAGFlow 架构已经和 ES 深度绑定（chunk 存储、倒排索引、HNSW、字段过滤全走 ES），换 Milvus 要改底层存储层
2. 万级文档规模下检索从来不是瓶颈（P50 半秒以内），没有换的动机
3. ES 的全文检索用的是传统倒排索引 + BM25，Milvus 2.5 用的是 Sparse-BM25（稀疏向量实现），实现方式不同但效果类似——在万级规模下两者差异不大

**Faiss** 是向量检索库（不是数据库），只做向量相似度检索，不做全文检索、不做持久化存储、不做字段过滤——适合嵌入到其他系统里用，不适合独立做 RAG 的存储引擎。

**面试一句话答法**：
> "RAGFlow 选 ES 是因为混合检索（向量+BM25+字段过滤）一个引擎全做。Milvus 2.5 起也支持 BM25 全文检索了（Sparse-BM25），不再是短板，但 RAGFlow 架构和 ES 深度绑定、万级规模检索不是瓶颈，没有换的动机。Faiss 是库不是数据库，不适合独立做存储引擎。如果从零搭建百万级以上的纯向量场景，Milvus 2.5 会是更好的选择。"

**Q13: 检索效果差怎么诊断调优？**
A: 先分层定位是召回、排序还是生成的问题：看返回的相似度分布和命中内容——召回差调 chunk 策略、混合权重、阈值；排序差上 rerank；生成差调 prompt 和模型。我做过 KG 开关对照（+40%），完整的参数级调优是下一步计划——这块如实说，不吹。

**Q14: 项目原始需求对检索有什么具体指标？你达标了吗？**

A: 需求里有明确的检索指标——**"检索响应时间应满足：常规检索不超过 2 秒，复杂组合检索不超过 5 秒"**。

| 需求指标 | 目标 | 我们实测 | 达标 |
|---|---|---|---|
| 常规检索 ≤ 2s | 2s | 向量检索 563ms | ✅ |
| 复杂组合检索 ≤ 5s | 5s | KG 检索 1240ms | ✅ |
| OCR 准确率 ≥ 98% | 98% | 未实测（PTR 走 docx 不走 OCR） | 待验证 |
| 参数提取准确率 ≥ 95% | 95% | 未实测（需二开 PBS 参数提取） | 待验证 |

注意：需求的检索指标是**内容数据库的多维度组合检索**（按设备编码/章节路径/内容类型等过滤），不是 RAG 的语义检索。但 RAG 的向量+BM25 检索延迟（563ms）远低于 2s 目标，所以检索层不是问题。

**需求还要求检索结果包含**：
- **置信度评分**——RAGFlow 有相似度分数作为置信度参考
- **来源信息**（原始文件、章节路径、时序节点）——RAGFlow 有 doc_id 和页码位置，但缺时序节点（需求要求按设备生命周期阶段标注）
- **GraphRAG 局部精准定位 + 全局社区发现汇总**——局部已验证（+40%），全局待 T6 实验（详见环节⑦ Q12）

**面试一句话答法**：
> "需求明确要求检索常规 ≤2s、复杂 ≤5s——我们向量检索 563ms、KG 检索 1240ms 都远低于目标，检索不是瓶颈。但需求还要求检索结果带置信度评分和来源信息（含时序节点）——置信度和文件来源 RAGFlow 有，时序节点（按设备生命周期阶段标注）是二开方向。GraphRAG 的局部精准定位已验证 +40%，全局社区发现汇总待 T6 实验。"

## 环节⑨ 问答生成

**需求指标对照（先看需求要求什么）**：

需求对问答/智能查询的要求：
1. "提供基于知识库的智能查询功能，支持用户通过自然语言提问获取相关知识"
2. "系统自动解析查询意图，并返回相关度最高的知识内容"
3. 检索结果"应包含置信度评分、来源信息展示"
4. GraphRAG"局部问题精准定位 + 全局问题社区发现汇总"
5. "所有 AI 处理结果须支持人工复核和修正"（不只是答案，所有 AI 输出都要可审核）

需求里**没有明确给问答准确率指标**——不像 OCR 98% 和参数提取 95% 有硬指标。问答质量靠"人工复核+引用溯源"兜底，不靠自动化准确率数字。

但需求**有时效指标**（检索 ≤2s/≤5s），问答端到端延迟实测如下：

| 指标 | 目标 | 优化前 | 优化后 | 流式 TTFT | 达标 |
|---|---|---|---|---|---|
| 简单问答 | ≤2s（检索指标参考） | 5790ms | 1016ms | 859ms | ✅ |
| 复杂问答 | ≤5s（检索指标参考） | 15383ms | 8383ms | 859ms | ❌ 非流式超标，流式 TTFT 达标 |

注意：2s/5s 是检索指标不是问答指标。问答没有硬指标，但面试时可以用检索指标做参考线——简单问答 1.0s 已经低于 2s 检索目标。

**Q1: 答案怎么带引用的？**
A: 每个 chunk 带文档 ID 和页码位置，生成时召回块带编号进 prompt，模型输出引用编号，前端映射回原文。我实测 PTR 手册的答案可以回溯到具体来源块。

**Q2: 幻觉怎么控制？**
A: 三层：prompt 限定只根据提供的资料回答；相似度阈值过滤弱相关块，垃圾进垃圾出；引用溯源让人工可验证。本质是模型只负责组织答案，事实来自召回块。

**Q3: 流式响应为什么重要？**
A: 首 token 就开始返回，用户 0.9 秒看到第一个字，后面边生成边出。非流式要等全部生成完——同一个系统简单问答非流式 5.8 秒、流式首字 0.9 秒，体验天差地别。我落地优化后简单问答完整回答都压到 1 秒了，流式首字 0.86 秒。

**Q4: 端到端延迟瓶颈在哪？**
A: 实测拆解过：检索只占 2~19%，LLM 生成占 70~96.5%。所以优化方向是控制生成长度、启用流式、裁剪上下文——而不是去优化检索引擎，数据证明那不是问题。

**Q5: 你做了哪些问答优化？（完整清单，面试直接列）**
A: 五项优化，两类目标——延迟优化四项 + 检索质量优化一项。

**延迟优化**（组合后简单 5.8s→1.0s、复杂 15.4s→8.4s）：
1. **限制生成长度**（max_tokens=256）：LLM 生成占端到端 96.5% 是延迟主因，限长直接砍生成量。简单 -58%
2. **简化 system prompt**：从"详细列举"改"简洁直接"，答案从 200 字降到 33 字。-37%
3. **裁剪检索结果**（top_n 6→4）：减上下文长度、降 prefill。-21%。实测 top_n=3 复杂题变差（信息不足编造），4 是平衡点
4. **流式响应**（stream=true）：首字 0.9s 返回，不用等全部生成完。TTFT 双双达标

**检索质量优化**（不降延迟但提质）：
5. **启用 KG 检索**（use_kg=true）：局部参数题纯向量相似度 0.331 太低，KG 四路召回补充上下文后 0.464（+40%），精准命中供货边界表。但全局问题 KG 无优势（light 模式无社区报告）——按问题类型启用，不是无脑全开

**瓶颈定位支撑**：LLM 生成占 70~96.5%、检索仅 2~19%，所以优化方向是控制生成量不是优化检索引擎——数据证明检索不是瓶颈。

**诚实边界**：混合检索权重 0.3、相似度阈值 0.1 是经验值不是调优结果；rerank、参数级调优是已识别的下一步——被问时不吹已调优。

**Q6: 怎么优化延迟的？效果如何？**（Q5 的延迟部分展开）
A: 三招组合：限制生成长度（max_tokens 256）、简化 system prompt（从"详细列举"改"简洁直接"）、裁剪上下文（top_n 6→4）。逐项控制变量测的：prompt 简化降 37%、top_n 裁剪降 21%、组合后简单问答从 5.8 秒降到 1.0 秒（达标 2 秒），复杂从 15.4 秒降到 8.4 秒（仍超 5 秒）。复杂没达标是 27B 模型 75 tok/s 的硬限制——300 token 回答要 4 秒生成，加检索 prompt 下限就 5 秒，非流式几乎不可能达标。流式口径下复杂题首字 0.9 秒达标。

**Q7: 复杂问答 5 秒达标不了怎么办？**
A: 三条路：流式（首字 0.9 秒达标，用户感知够了）、复杂问题拆成多个简单问题（每个 ≤2 秒）、部署 14B 小模型处理简单问答分流。我们当前结论是流式 + 按问题类型路由——简单走快速、复杂走深度，不强求复杂题非流式 5 秒。

**Q8: 用的什么 LLM 做问答生成？为什么选这个？**

A: Qwen3.8-27B-AWQ-INT4，vLLM 部署，TP2（Tensor Parallel 两卡）。

| 维度 | 选择 | 为什么 |
|---|---|---|
| 模型 | Qwen3.8-27B | 中文场景默认选择，27B 规模够用（理解复杂 prompt + 引用格式） |
| 量化 | AWQ-INT4 | 4 张 4090（24GB/卡），27B FP16 需要 ~54GB 放不下，AWQ-INT4 量化后 ~16GB，TP2 占 2 卡放得下 |
| 推理框架 | vLLM | PagedAttention + continuous batching，比 HuggingFace transformers 快 3-5 倍 |
| 并行 | TP2（Tensor Parallel） | 单卡放不下量化后的模型，TP2 跨 2 卡切分模型层 |
| 关键配置 | prefix_caching on / chunked_prefill on / enable_thinking false | prefix caching 缓存相同 prompt 前缀（system prompt 重复利用）、chunked prefill 分块处理长 prompt、关 thinking 省 token |

**实测性能**：vLLM 生成速度 ~72-75 tok/s（27B AWQ-INT4 + TP2 的正常水平）

**和建图模型的关系**：同一个模型干两件事——GraphRAG 建图抽取 + 问答生成。选型时优先满足建图（格式遵循能力是瓶颈），选完验证问答也能用。

**面试一句话答法**：
> "Qwen3.8-27B AWQ-INT4，vLLM 部署 TP2 两卡。27B 中文够用、AWQ-INT4 量化后放得下 4090、vLLM 的 PagedAttention 比原生 transformers 快 3-5 倍。生成速度 ~75 tok/s，和建图用同一个模型——选型时优先满足建图的格式遵循要求，选完验证问答也行。"

**Q9: vLLM 和 HuggingFace transformers 有什么区别？为什么用 vLLM？**

A: 两者都是 LLM 推理框架，但设计目标不同：

| 维度 | HuggingFace transformers | vLLM |
|---|---|---|
| 设计目标 | 通用模型库（训练+推理+评测） | 高吞吐推理引擎 |
| 注意力机制 | 标准 Attention（O(N²)） | PagedAttention（分页管理 KV Cache） |
| 批处理 | 静态 batch | continuous batching（动态加入新请求） |
| KV Cache 管理 | 每个请求预分配连续内存 | 像操作系统分页——按需分配物理页，逻辑连续 |
| 吞吐 | 低（单请求 ~20 tok/s） | 高（多并发 ~75 tok/s × N） |
| 显存利用率 | 低（预分配浪费） | 高（按需分配，碎片少） |

**PagedAttention 原理**（面试高频追问）：
- 传统方式：每个请求的 KV Cache 预分配一块连续显存——不管用不用得到，先占着
- PagedAttention：像 OS 虚拟内存——KV Cache 按固定大小分成"页"，按需分配物理页，逻辑地址连续但物理可以不连续
- 好处：显存碎片少、可以同时处理更多并发请求、长文本不会因为 KV Cache 不够而 OOM

**Q10: system prompt 怎么影响问答质量？你做过什么 prompt 工程？**

A: system prompt 是影响延迟和质量的**关键因素**——我实测改 prompt 从"详细列举"改"简洁直接"降了 37% 延迟。

| 优化项 | 前 | 后 | 效果 |
|---|---|---|---|
| system prompt | "list the data in the dataset and answer in detail" | "You are a concise technical assistant. Answer based only on the provided knowledge base. Be brief and direct." | 答案从 200 字降到 33 字，延迟 -37% |
| max_tokens | 无限制 | 256 | 防极端长回答 |
| top_n | 6 | 4 | 降 prefill，-21%，答案质量不降 |

**prompt 结构**（RAGFlow 的标准拼法）：
```
[system prompt: "你是技术助手，只根据知识库回答"]

知识库：
[ID:1] chunk1 内容...
[ID:2] chunk2 内容...
...
[ID:4] chunk4 内容

用户问题：xxx
```

**关键设计**：
- "只根据知识库回答"——防幻觉，约束模型不编造
- chunk 带编号 [ID:N]——模型输出引用编号，前端映射回原文
- 简洁直接——减少废话，降延迟

**Q11: 答案质量怎么评估？有没有自动化指标？**

A: 当前是**人工评分（1-5 分）**，没有自动化评估。

| 评估方法 | 我们有没有 | 指标 |
|---|---|---|
| 人工评分 1-5 分 | ✓（T1 测试） | 准确性 + 覆盖度 |
| RAGAS | ✗（T8 规划中） | faithfulness（忠实度）/ answer relevancy / context precision / context recall |
| LLM-as-Judge | ✗ | 用更强模型（GPT-4）自动打分 |
| 人工对照原文 | ✓ | 答案里的参数值和原文对照 |

**诚实答法**：
> "当前靠人工评分和引用溯源——T1 测试做了 8 题 × 2 配置的对照评分。自动化评估是下一步，对应 T8（RAGAS），会跑 faithfulness/context precision 等指标。需求里没给问答准确率硬指标——靠'人工复核+引用溯源'兜底，不像 OCR 98% 和参数提取 95% 有硬指标。"

**Q12: 问答生成有哪些坑？你踩过什么？**

A:

| 坑 | 现象 | 原因 | 解决 |
|---|---|---|---|
| 长答案拖延迟 | 复杂问答 15.4s | LLM 生成 96.5%，300 token × 75 tok/s = 4s 下限 | 限 max_tokens + 简化 prompt + 流式 |
| top_n 太少变差 | top_n=3 复杂题质量下降 | 信息不足 LLM 编造 | top_n=4 是平衡点（实测） |
| 引用编号对不上 | 答案引用 [ID:3] 但映射错 | 模型输出了不存在的编号 | 引用回填用句级匹配（insert_citations），不信任模型自编编号 |
| 复杂回答超 5s | 8.4s 达标不了 | 27B 模型 75 tok/s 硬限制 | 流式 TTFT 0.9s 达标 + 复杂问题拆步 |
| enable_thinking 浪费 token | 模型输出 thinking 内容 | Qwen3 默认开 thinking 模式 | 配置 enable_thinking=false |
