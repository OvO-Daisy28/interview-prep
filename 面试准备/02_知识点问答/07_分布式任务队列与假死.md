# 07 分布式任务队列与假死

> → 深度版见 [QA问答_全链路口语版.md](../QA问答_全链路口语版.md) 环节②（任务队列与假死）

## 一句话答案（电梯版）

RAGFlow 用 Redis Stream 做任务队列、Task Executor 做消费 worker、Redis 心跳做存活检测。我诊断过「进程活着但 worker 失联」的假死故障，根因是队列未隔离、ACK 时机、无 watchdog 三件事叠加，改了 5 处内核源码 + 清理了存量数据才修好。

## 2 分钟展开版

**任务系统的四个组件**：
```
Redis Stream（te.0.common / te.0.graphrag 等按任务类型分队列）
→ 消费者组 rag_flow_svr_task_broker
→ Task Executor worker（TASKEXE 集合注册 + ZSET 心跳，30s 一次，120s 判死）
→ MySQL task 表（run 状态 / progress / progress_msg 记录卡点阶段）
```

**排查三板斧**（我自己总结的命令级流程）：
1. `XINFO GROUPS / XPENDING`：lag 大 = 任务没人取；pending 大 = 取了没完成；consumer idle 大 = 卡死
2. `SMEMBERS TASKEXE` + `ZREVRANGE` 心跳：worker 还活着吗
3. MySQL `progress_msg` + 日志 grep doc_id/task_id：卡在哪个阶段

**假死案例完整链**（面试主故事，见故事 2）：
前端 0% → MySQL 任务已建 + Redis 已入队但 lag=1 → 两 worker 心跳停在前一天、进程在但 CPU≈0、线程 216/329 → 判定假死 → 4 个根因（队列后缀写死 .common 重任务互抢 / 180s 固定超时但任务实际 215s 且超时只包协程 / ACK 只在任务完成后执行导致消息无法接管 / 无 watchdog）→ 5 处源码修改。

## 深挖自测（先遮住答案）

**Q1: 为什么取消任务没生效？**
A: RAGFlow 是软取消——写 Redis 标志，executor 在阶段边界轮询 `has_canceled` 才停。串行 embedding 场景检查点之间文档已处理完，实测 100 份 0 份取消成功。

**Q2: watchdog 怎么设计的？**
A: 事件循环 300 秒无心跳 → 输出线程栈（留下尸检材料）→ 退出，由容器监督逻辑自动拉起新 worker。尸检 + 自愈两件事。

**Q3: pending 什么时候能被别人接管？**
A: 只有原 worker 心跳过期后才能 claim——防止两个 worker 同时处理同一消息。

**Q4: ack 不 XDEL 是什么问题？**
A: RAGFlow 的 `ack()` 只 ACK 不删除消息 → 消息永久残留在 Stream 里，XLEN 越积越大。上游缺陷，我们的对策是 XTRIM MAXLEN + 清理 runbook 化，没改上游代码。

**Q5: 修好后怎么验证的？**
A: ① 当场：卡住任务恢复完成（187 节点/200 边入库）、pending=0 lag=0；② 两周后：数据治理（删僵尸 task 验证 remaining=0、DELCONSUMER、全库重建）；③ 长期：万份 45 小时稳定，失败率 0.06%。
