# 故事 2：内核修复（队列假死 → 5 处源码 + 数据治理）

## 一句话版

GraphRAG 任务卡在 0%，但进程活着、任务在队列里——这是"假死"。我用 Redis 队列 lag/pending 与 worker 心跳交叉验证定位根因（队列未隔离、ACK 时机、无 watchdog），改了 5 处内核源码 + 清理存量数据才修好。

## 背景：什么是假死，为什么棘手

**现象**（2026-08-14 16:14）：GraphRAG 任务前端进度 0%，一动不动。但诡异的是——API 正常、MySQL 任务已建、Redis 已入队，进程也活着。

**棘手在哪**（读懂 [RAGFlow队列机制原理.md](../RAGFlow队列机制原理.md) 才能讲清）：

RAGFlow 的任务系统是"进程 + 心跳 + 队列"三层协作：worker 进程跑着、每 30 秒往 Redis ZSET 打心跳、从 Redis Stream 取消息处理完才 ACK。"假死"是这三层里**进程层活着、心跳层停了、队列层消息卡在 pending**——不是崩溃（崩溃会被容器监督重启，反而好处理），是进程还在但事件循环僵死，最隐蔽的故障。

**当时判定的三组证据**（交叉验证，不是猜）：
1. MySQL：任务已创建（`created task graphrag`）、progress=0
2. Redis：lag=1（任务没人领）、pending=3（3 条旧消息没 ACK）
3. 心跳：两个 worker 心跳停在前一日（17:17 / 15:59），但 `ps aux` 看进程还在、CPU≈0、线程数 216/329

→ 结论：进程活、worker 失联，任务停在 lag 里始终未开始。

## 方法：根因定位 + 两阶段修复

### 第一阶段：根因（vanilla 在重任务场景下的 4 个设计局限）

读完队列机制原理文档的补丁对照表，四条根因清晰了——**不是"bug"，是 vanilla RAGFlow 在重任务场景下的设计局限**：

1. **所有任务挤 .common 队列**（vanilla settings.py:157 硬编码）：vanilla 把所有任务类型放同一条 Stream，轻负载没问题。但 graphrag 合并要几百秒，占住 worker 就阻塞普通解析——重任务场景下互抢是设计局限。
2. **ACK 在任务完成才执行**（task_executor.py:1779，finally 之后）：vanilla 设计是整个任务处理完才 ACK。worker 中途僵死 → 消息永远在 pending → 别人无法接管。轻负载下任务快、不易僵死；重任务长跑下必然踩中。
3. **无 watchdog 自愈**：vanilla 没有 watchdog。进程不退出、容器监督不触发重启、心跳停了也没有自愈。轻负载下任务不易僵死；重任务下事件循环僵死就永久卡住。
4. **合并超时固定 180s**（index.py）：vanilla 固定超时。但 graphrag 合并实际需 215s（按节点边数量），超时只包协程、底层 embedding 线程取消不掉，重试产生重复计算。

**关键判断**：这些都是 vanilla 的合理设计（轻负载下简单有效），但项目是重任务场景（graphrag + 万份文档），设计局限暴露。团队的修复是**改进**（为重任务加隔离/自愈/动态超时），不是修 bug——这个区分面试很重要。

### 第一阶段：补丁（5 处本地源码，未贡献上游）

| 补丁 | 源码位置 | 对应局限 |
|---|---|---|
| 为 graphrag/raptor/mindmap 加专用队列（SPECIAL_TASK_QUEUE_SUFFIXES） | settings.py:136 | 局限 1 |
| 重任务专用 worker（单任务、embedding 并发限 4、异常自动重启） | entrypoint.sh:219-233 | 局限 1+3 |
| watchdog（事件循环 300s 无心跳→输出线程栈→退出→容器监督拉起） | task_executor.py:167 | 局限 3 |
| pending 接管（原 worker 心跳过期后才能 claim，get_stale_unacked_iterator） | redis_conn.py:487 | 局限 2 |
| 合并超时按 embedding 工作量动态计算（_effective_merge_timeout_seconds） | index.py:122 | 局限 4 |

**补丁归属**：打在部署的 v0.26.1 上，**未贡献上游**。vanilla v0.26.4（GitHub）仍是原设计——所以本地 v0.26.4 源码读到的是硬编码 .common，部署版 v0.26.1 读到的是已打补丁的代码。面试讲"5 处源码修改"时，精确说法是"在部署版本上打的本地补丁，未贡献上游"。

**watchdog 的精妙**：300s 无心跳→先输出线程栈（faulthandler.dump_traceback，留下"尸检材料"便于排查）→再 os._exit(70) 退出。退出后 entrypoint.sh 的 while 循环拉起新 worker——把"僵死不退出"变成"僵死能退出→被重启"，自愈闭环。

### 第二阶段：数据治理（两周后，09-03 起，我亲手执行）

源码修好只防"再假死"，**修之前烂掉的存量还在**：7 月 22 日遗留的僵尸 task（progress=0 挂了两周）、僵尸消费者、ack 不 XDEL 留下的消息残骸。清理方式风险受控：

1. **删僵尸 task**：`DELETE FROM task WHERE progress=0 AND begin_at < DATE_SUB(NOW(), INTERVAL 7 DAY)`——先 SELECT 确认范围、删后 `SELECT COUNT(*) remaining_zombie` 验证归零
2. **清僵尸消费者**：`XGROUP DELCONSUMER` 清掉 recovery2 等失联消费者
3. **裁剪队列**：`XTRIM te.0.common MAXLEN 10000`（注意：MAXLEN 不删 pending，只删已 ACK 的历史）
4. **全库重建**：TRUNCATE 6 表（file/document/task/knowledgebase/file_commit*）+ 逐表 COUNT 验证归零 + 显式保留 canvas_template

**机制级发现**（清理过程中挖出来）：RAGFlow 的 `ack()` 只 ACK 不 XDEL（redis_conn.py:45 调 XACK 不调 XDEL）→ 消息永久残留在 Stream。上游缺陷，我们没改它（影响面大），选择把清理 runbook 化成为常规动作（09-13/14 又清过一轮）。

## 结果：源码修复让特定任务恢复，但系统还会卡——清理完才真正不卡

**这是关键修正**：源码修复 ≠ 系统不卡。修源码只治了"机制病"（防再假死），但修之前积压的垃圾还在，继续干扰新任务。**真正不卡是 09-03 数据清理完之后**。

### 08-14 源码修复后：那个特定任务恢复，但系统还会卡

- 卡住任务恢复完成：187 节点 / 200 边 / 389 图谱 chunk 入库，合并耗时 215s（正好超过旧 180s 固定超时——根因 4 的实证）
- Redis：pending=0、lag=0（那一刻通畅）
- Redis 接管测试通过（模拟 worker 失联→消息被别的 worker claim）
- **但系统还会卡**：因为积压的僵尸 task（7 月 22 日遗留、progress=0 挂两周）、ack 不 XDEL 留下的消息残骸、僵尸消费者，这些垃圾继续干扰新任务

### 09-03 数据清理后：真正不卡

- 僵尸 task 清零（`SELECT COUNT(*) remaining_zombie` → 0，有手跑验证）
- 全库重建（TRUNCATE 6 表）后逐表 COUNT 归零
- 清理后实测批量上传 5 份 word 正常走完——**链路干净、不再卡**

### 长期（稳定性证明）

- 万份 45 小时压测稳定，失败率 0.06%（6/10000）——这是 131 CPU 上的，慢（吞吐 0.046 份/s）但不卡

### 卡 vs 慢的区分（面试易混，必须讲清）

| | 卡（假死） | 慢（长尾） |
|---|---|---|
| 现象 | 任务 0%、进程活心跳停、消息卡 pending | 任务在跑、不卡 0%，但吞吐崩塌 |
| 解决 | 源码修复（机制）+ 数据清理（存量） | GPU 迁移（硬件） |
| 时间 | 08-14 + 09-03（131） | 09-11（4090） |

**4090 不卡的主因不是 GPU**——是 131 上已经做了源码修复+数据清理（机制和存量都治了，带过去的代码/配置在新环境生效，且 4090 没积压垃圾）。GPU 解决的是"慢"（长尾吞吐），不是"卡"（假死）。

## 追问与接法

- **"到底是改源码修好的还是清库修好的？"** → 两个动作治两个病：改源码治机制（防再假死），清库治存量（修之前烂掉的僵尸数据）。缺一不可，且是两个阶段隔了两周。
- **"什么是假死？"** → 进程活着、心跳停了、消息卡在 pending。不是崩溃（崩溃会被容器重启反而好处理），是事件循环僵死——最隐蔽的故障。
- **"怎么发现的？"** → 三组交叉验证：MySQL 任务已建、Redis lag=1 没人领、心跳停在前一日但进程还在。三组证据合起来才判定假死，单一指标看不出来。
- **"队列为什么没隔离？"** → vanilla 把所有任务放 .common 队列，对轻负载是合理设计；重任务场景（graphrag 合并几百秒）下重任务和普通解析互抢。团队为 graphrag/raptor/mindmap 加了专用队列。这是改进设计局限，不是修 bug。
- **"补丁贡献上游了吗？"** → 没有，打在部署的 v0.26.1 上，是本地补丁。vanilla v0.26.4 仍是原设计。
- **"watchdog 为什么是 300s？"** → 心跳 30s 的 10 倍余量，避免误杀慢任务；判死 120s 是原生心跳阈值参照。
- **"清库不怕误删吗？"** → 风险受控：先 SELECT 圈范围、和 leader 对齐、删后验证计数、canvas_template 显式保留。
- **"ack 不 XDEL 是什么？"** → RAGFlow 的 ack 只 ACK（从 pending 移除）不 XDEL（不从 Stream 删消息），消息永久残留。上游缺陷，我们用 XTRIM+定期清理对策。
- **"怎么验证修好了？"** → 三层：当场任务恢复（08-14）/ 两周后清理+实测链路干净（09-03）/ 长期 45h 稳定性。
- **"修完源码就不卡了吗？"** → 不是。修源码让那个特定任务恢复，但系统还会卡——因为积压的僵尸 task 和 ack 残留消息没清。真正不卡是 09-03 数据清理完之后。机制病靠源码、存量病靠清理，缺一不可。
- **"4090 不卡是源码修复的功劳吗？"** → 部分是。4090 不卡主因是 131 上做了源码修复+数据清理（机制和存量都治了，带过去生效，且 4090 没积压垃圾）；GPU 解决的是"慢"（长尾吞吐），不是"卡"（假死）。卡和慢是两个病，别混。
