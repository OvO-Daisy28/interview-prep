# 故事 3：二开批量导入 + 压测验证

## 一句话版

项目经理 5 项可控性需求（每阶段计时、随时启停、失败重试、读写队列状态、提供接口），RAGFlow 原生接口实测只满足 1 项。我设计并开发了带进度可视化的批量导入服务——协议化分层（编排层独立于 RAGFlow 内核），四阶段精确计时，并发调度+失败隔离，万份压测验证稳定性。

## 背景：5 项需求 vs 原生 1 项满足

### 项目经理的 5 项可控性需求（2026-08-13 原话）

1. 批量上传支持**每个阶段的时间记录**
2. **随时开始、随时停**（启停）
3. **失败重试**
4. **读取和修改队列里的状态**
5. 最后能**提供一个接口**出来

### 原生接口实测（100 份纯真 docx，量化缺陷）

| 需求 | 原生满足度 | 实测证据 |
|---|---|---|
| 每阶段计时 | ❌ | 536 次轮询 progress_msg 去重仅 4 种文本（排队类），前 483s 进度几乎不动 |
| 随时启停 | ❌ | 30% 时发取消，最终 0 份 CANCEL 全部 DONE（软取消只在阶段边界轮询） |
| 失败重试 | ❌ | retry_count 字段存在但内核不消费，失败即终态 |
| 读写队列状态 | ❌ | 无对外接口，仅文档级 task 进度查询 |
| 提供接口 | ✅ | 有 4 个 HTTP API |

**满足度 1/5**——这是团队放弃原生路线转自建的实证依据。

## 方法：协议化分层设计 + 自建管线

### 核心设计原则：不动 RAGFlow 内核，建外置编排层

代码实证（`code/ingest/`，20+ 单元测试）：编排层完全独立于 RAGFlow 内核，通过协议（Protocol）适配——这是"外置治理"而非"改内核"。

### 四层架构（代码对应）

```
REST API（rest_api.py）    对外接口：POST /ingest/jobs、GET /jobs/{id}、pause/resume/retry/cancel
   ↓
Scheduler（scheduler.py）  并发调度 + 失败隔离：ThreadPoolExecutor(max_concurrent)，默认 3
   ↓
Orchestrator（orchestrator.py） 状态机 + 阶段映射：驱动单任务 upload→parse→graph_build，轮询+推送阶段
   ↓
Pipeline（pipeline.py）    协议层：IngestPipeline Protocol，两个后端实现
   ├─ ChunksPipelineAdapter  调 RAGFlow HTTP API（方案 A）
   └─ SelfRunPipeline        自建四阶段 parse→chunk→embed→index（方案 B，当前）
   ↓
Repository（repository.py） 状态持久化：PostgreSQL（job/task/stage 三表）
```

### 关键设计点（代码实证）

**1. 协议化——后端可替换**（pipeline.py:43 `IngestPipeline` Protocol）：
- 两个后端实现同一协议：HTTP 适配器（调 RAGFlow）和自建管线（自己跑四阶段）
- **A/B 对比公平性基础**：同一协议、同一编排层，只换 pipeline 实现
- 注释原文："swapping backends must not touch the state machine, the scheduler, the REST API, or their tests"

**2. 状态机独立**（state.py：6 状态 7 动作）：
- pending/running/succeeded/failed/cancelled/paused——`paused` 是编排层独有（RAGFlow 没有），支持软暂停（graceful，边界退出）和硬暂停（force，调 DELETE /chunks）
- 状态机在 PostgreSQL，不在 RAGFlow 内核——注释原文"RAGFlow kernel is never touched"

**3. 四阶段精确计时**（selfrun_pipeline.py:157-189）：
- 每阶段 `t0 = time.time()` → 跑完 `stage(name, status, pct, dur_ms, detail)` 回调
- `on_stage` 回调**推送真实阶段边界**（不是从 progress_msg 文本猜）——这是进度可视化的核心
- orchestrator.py:168 `on_stage` 接收并写库（started_at/finished_at/duration_ms）

**4. 并发调度 + 失败隔离**（scheduler.py:91 `run_batch`）：
- `ThreadPoolExecutor(max_workers=max_concurrent)`，默认 3（代码注释：RAGFlow 单 worker 是真瓶颈，高并发只会堆队列）
- **每任务独立 try/except**（:122）：单份失败只标 failed，兄弟任务继续——PM 原型"单份失败不影响批量"
- BatchResult 返回 per-task 明细（succeeded/failed/skipped），不聚合成单一 flag

**5. PM 5 步投影**（orchestrator.py:76 `_pm_steps_view`）：
- `stages` 是真实发生的（truth），`pm_steps` 是面向 PM 原型的 5 步投影（presentation）
- 设计原文："stages is what actually happened; pm_steps is the prototype-facing projection"

### 过程中修的两个 bug

**1. MySQLRepository 并发连接 bug**：
- `threading.local()` 每线程一连接，在 ThreadPoolExecutor 并发下连接断开
- `--persist --concurrency 3` 万份任务 7 份成功后全卡死（`'NoneType' object has no attribute 'status'`）
- 定位为连接非线程安全，测试期切 InMemory 绕开完成万份测试，给出连接池/per-task 连接修复方向

**2. 文件名超长 500**：
- 上传暂存名 `{uuid8}_{原文件名}` 遇法律文档超长文件名超 Linux 255 字节上限（OSError Errno 36）
- 暂存名改纯 uuid（32 字符），原文件名仅存 job 元数据

## 结果：满足 5 项需求 + 万份稳定性

### 5 项需求满足度（从 1/5 到 5/5）

| 需求 | 满足方式 |
|---|---|
| 每阶段计时 | ✅ 四阶段 time.time() 精确计时写库，on_stage 推送真实边界 |
| 随时启停 | ✅ 软暂停（边界退出）+ 硬暂停（DELETE /chunks）+ resume 清 abort flag |
| 失败重试 | ✅ retry 状态转换 + graph_build 重试时 DELETE /graph 避免 'already merged' |
| 读写队列状态 | ✅ GET /ingest/jobs/{id} 总览 + GET /ingest/queue 队列状态 |
| 提供接口 | ✅ REST API（POST /ingest/jobs 等） |

### 压测验证（双作用：验证接口 + 定位系统瓶颈）

| 实验 | 结果 |
|---|---|
| 并发 1/3/6 标定 | 3 最优（吞吐 0.180 份/s，2.1× 串行），6 无收益且长尾暴涨 60% |
| 万份 45 小时 | 9994/10000 成功、6 份失败（0.06%），失败隔离生效，进程零崩溃 |

### 压测同时定位了系统瓶颈（故事 1 的入口）

并发标定发现 embedding 占总耗时 93.6%——压测不只是验证接口，**同时定位了系统瓶颈**，直接推动了 GPU 迁移决策。这是"接口开发 + 压测 + 优化"连成一条线的实证。


## 追问与接法

- **"进度可视化怎么实现的？"** → 自建管线四阶段每阶段 time.time() 计时，on_stage 回调推送真实阶段边界（不是从 progress_msg 文本猜），orchestrator 接收写库。去 `code/ingest/selfrun_pipeline.py:157` 复习。
- **"为什么并发 3 最优？"** → embedding 占 93.6%，3 个并发刚好喂饱 CPU embedding 服务；6 个纯争抢（embed avg 翻倍 15→30s、长尾 +60%）。代码注释原文"RAGFlow's single worker is the real bottleneck, high number buys nothing but queue depth"。
- **"和原生的公平对比怎么做？"** → 同一 IngestPipeline 协议、同一批文档、同一 embedding 服务，只换 pipeline 实现——协议化分层保证公平性。
- **"你发现过什么 bug？"** → 两个：MySQL 并发连接 bug（threading.local 线程不安全，万份 --persist 7 份成功后全卡死，建议连接池）；文件名超长 500（uuid 暂存名隔离用户输入）。
- **"为什么不动 RAGFlow 内核？"** → 决策 8：先外置治理/编排，确需才改 worker。编排层独立于内核，通过协议适配——内核升级不影响编排层。
- **"pause 和 cancel 区别？"** → pause 可恢复（paused→resume→running），cancel 终态不可恢复；pause 分软（边界退出）和硬（DELETE /chunks）。
- **"压测和接口开发什么关系？"** → 压测双作用：验证接口稳定性（万份 0.06%）+ 定位系统瓶颈（embedding 93.6%），后者直接推动 GPU 迁移。
