## 逐项分析

### 1a/1b: max_tokens 限制

- max_tokens=128 和 256 对简单问答效果一致（~2440ms），因为简单问题答案短（~200字），128 tokens 就够了
- 复杂问答 128 和 256 也基本一致（~13000ms），因为复杂回答仍未被 max_tokens 截断就自然结束
- **max_tokens 不是主要瓶颈**，但限制了极端情况下的输出长度上限

### 2: 简化 prompt（关键优化）

- 简单问答从 ~2440ms 降到 ~1546ms（-37%），因为简洁 prompt 让 LLM 直接回答而非详细列举
- 答案长度从 ~200 字降到 ~33 字（"额定流量为640m³/h"直接回答）
- 复杂问答从 ~13000ms 降到 ~9942ms（-23%）
- **system prompt 是影响延迟的关键因素之一**

### 3: top_n 6→4

- 简单问答从 ~1546ms 降到 ~1216ms（-21%）
- 复杂问答从 ~9942ms 降到 ~8022ms（-19%）
- 减少 2 个 chunk 的上下文，减少 prefill 时间和 prompt 构造时间

### 4: top_n 6→3

- 简单问答 1212ms，与 top_n=4 持平
- 复杂问答 9465ms，比 top_n=4 略差（检索信息不足导致更多"编造"）
- **top_n=3 对复杂问答有负面影响，top_n=4 是最佳平衡点**

### 5: 最优组合（max_tokens=256 + 简化prompt + top_n=4）

- **简单问答：1016ms**，首次低于项目目标 2s ✅
- 复杂问答：8383ms，仍超目标 5s，但已从 15.4s 降到 8.4s（-45%）
- 流式 TTFT：859ms，远低于目标 ✅

## 复杂问答未达标的原因分析

复杂问答优化后 avg 8383ms，离 5000ms 目标还差 3383ms。主要因为：
1. 复杂问题（"常见故障+如何预防"）需要长篇回答，LLM 生成 ~700-1000 字（约 200-300 tokens）
2. vLLM 生成速度 ~75 tok/s，300 tokens 需要 ~4000ms 生成时间
3. 加上检索 ~560ms + prompt 构造 ~300ms + TTFT ~150ms = ~5060ms 下限
4. **结论：当前 27B 模型 + 复杂回答需求下，5s 目标在非流式模式下几乎不可能达到**

### 流式模式下的复杂问答

流式 TTFT ~859ms，用户 0.9 秒就能看到首字。按项目"时效"如果指首字响应，复杂问答已达标。

## 最优配置推荐

```json
{
  "llm_setting": {
    "max_tokens": 256
  },
  "top_n": 4,
  "top_k": 1024,
  "similarity_threshold": 0.1,
  "vector_similarity_weight": 0.3,
  "prompt_config": {
    "system": "You are a concise technical assistant. Answer the question based only on the provided knowledge base. Be brief and direct.\n      Knowledge base:\n      {knowledge}"
  }
}
```

| 配置项 | 原值 | 推荐值 | 理由 |
|--------|------|--------|------|
| max_tokens | 无限制 | 256 | 防止极端长回答，256 足够 |
| top_n | 6 | 4 | 减少上下文长度，对答案质量无显著影响 |
| system prompt | 详细回答型 | 简洁直接型 | 减少生成内容量，降延迟 37% |
