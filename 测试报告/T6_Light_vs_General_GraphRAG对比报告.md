## 一、测试目的

验证项目原始需求："系统需支持 GraphRAG 模式。对于局部问题能精准定位；对于全局问题能利用图的社区发现算法跨章节汇总知识并给出综合结论。"

之前 T1 测试结论为：Light 模式下全局问题 KG 检索无提升——因为 Light 模式不做社区发现，community_report = 0。本次 T6 切换 General 模式并启用社区发现，验证社区报告对全局问题的价值。

## 六、配置踩坑记录

### 问题 1：method=general 不触发社区发现

**现象**：设置 `method: "general"` 后重建，community_report = 0。

**根因**：`task_executor.py:1540-1541`：
```python
with_resolution = graphrag_conf.get("resolution", False)
with_community = graphrag_conf.get("community", False)
```
这两个字段默认 False，必须在 KB 的 `parser_config.graphrag` 中显式设置 `resolution: true` 和 `community: true`。

**修复**：在 KB 配置中添加这两个字段（前端 UI 对应"实体归一化"和"社区报告生成"复选框）。

### 问题 2：peewee JSONField 双重序列化

**现象**：通过 `KnowledgebaseService.update_by_id()` 更新 parser_config 后，task handler 拿到的 `kb_parser_config` 是 string 而非 dict，报错 `'str' object has no attribute 'get'`。

**根因**：RAGFlow 使用 peewee ORM 的 JSONField，`update_by_id` 在序列化 dict → JSON string 时被 DB 层再次转义，导致双重 JSON 编码。

**修复**：使用 raw SQL 绕过 peewee 序列化层：
```python
DB.execute_sql("UPDATE knowledgebase SET parser_config = %s WHERE id = %s", (json_str, kb_id))
```
同样需要对 document 表执行同样操作。

## 七、结论与建议

### 核心结论

1. **General 模式 + community=true 成功生成 121 个社区报告**，填补了 Light 模式的架构短板
2. **KG 检索增强效果显著**：
   - General 模式：KG=on 后所有 10 题相似度从 ~0.37 跃升至 1.0000，delta 平均 +0.61
   - Light 模式：KG=on 后相似度零变化（delta=0.0000），图谱未参与检索
3. **成本可控**：General 完整建图 6.5 分钟（含社区报告），比 Light 多约 50% tokens（+286k），但绝对时间因 vLLM 前缀缓存反而更快
4. **社区报告质量高**：121 个报告覆盖了电动机规格、机械密封、转子部件、冷热态对中、托架轴承等核心知识域，具备跨章节汇总能力
5. **E2E 问答 General 更快**：全局题平均延迟 13527ms vs Light 18845ms（快 28%），但答案字数略短（806 vs 1072）
6. **配置门槛**：需显式设置 `resolution: true` + `community: true`，仅设 `method: "general"` 不够

### 项目需求符合性评估

| 需求项 | Light 模式 | General 模式 | 结论 |
|--------|-----------|-------------|------|
| 支持 GraphRAG 模式 | ✅ 基础图谱 | ✅ 完整图谱+社区 | 两者均支持 |
| 局部问题精准定位 | ✅ 向量检索 | ✅ 向量检索+图谱增强 | General 更优 |
| 全局问题跨章节汇总 | ❌ 无社区报告 | ✅ 121 个社区报告 | **仅 General 满足** |
| KG 检索增强 | ❌ delta=0 | ✅ delta avg +0.61 | **仅 General 有效** |

### 建议

- **生产环境推荐 General 模式**（resolution=true + community=true），满足项目"全局问题利用社区发现算法跨章节汇总"的需求
- Light 模式适用于快速验证或资源受限场景（不生成社区报告，tokens 节省 51%）
- KG 检索增强带来 ~800ms 额外延迟，在可接受范围内（E2E 总延迟仍优于 Light）

- **检索 API**：`POST /api/v1/retrieval`，body 传 `dataset_ids`（注意不是 `datasets_ids` 或路径参数 `/api/v1/datasets/{id}/retrieve`）
- **问答 API**：`POST /api/v1/chats/{chat_id}/completions`，body 传 `dataset_ids` + `question`
- **`use_kg` 参数**：在 retrieval body 中传 `use_kg: true/false` 控制是否启用图谱增强
