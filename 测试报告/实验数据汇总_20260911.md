### 实验 4 的存储说明

- 实验 4 用的是 **mentor 常驻服务**（不是我们的脚本），数据写进 **MySQL `gcn_ingest` 库**（ingest_job / ingest_task / ingest_step 三表）。

- 实测发现：库里 **job 35 / job 37 的记录已丢失**，只剩一条 job 39（10000 份，9987 成功/10 失败/3 卡 running）——且 job 39 并非本实验（可能是更早的 `--persist` 残留）。

- 所以实验 4 的数值**无法从数据库取回**，只能引用报告 HTML 中的数字。


### 方案B 两种存储后端的区别

- `mentor_b_bench.py` 有 `--persist` 开关：给了写 MySQL（`MySQLRepository`），不给走内存（`InMemoryRepository`）。

- 我们所有压测（实验 3/5）**都没给 `--persist`** → 走 InMemory，因为 `MySQLRepository` 用 `threading.local()`，在 ThreadPoolExecutor 并发下连接会断导致任务全失败（已知 bug）。

- 实验 4 是 mentor 服务自己跑的（走 MySQL），和我们的脚本压测是**两条独立路径**。


## 三、贯穿性结论

1. **embedding 是绝对瓶颈**：各实验占比 87%–96%，131 的 bge-base 跑在 CPU 上。
2. **单份 embed 随并发升高而变慢**：并发1 11.0s → 并发3 15.3s → 并发6 29.7s（CPU 争抢），并发收益被抵消。
3. **规模放大后吞吐下降（同一服务内）**：方案B（InMemory 并发3）从 50 份的 0.180 份/s 降到 1 万份的 0.046 份/s（**降 74%**）；而 mentor demo 服务在 161→1000 份区间吞吐稳定（0.24→0.25），说明退化发生在更长的运行时长上。**千份时曾预测万份约需 11 小时，实际跑了 59.7 小时（偏差 5.4 倍）**。
4. **对照组（4090 GPU）**：GPU 上 bge 单条文本 embedding 实测 **0.030 秒**（131 CPU 单份文档 embed 17.1 秒）。两者口径为「文档级」近似（文档大小与批处理行为不同），量级上 GPU 快约 **500 倍**，是 4090 上 GPU 部署的核心依据。
5. **取消能力缺失**：RAGFlow 原生不支持真正取消（实验 2），是 PM 5 项需求中未满足的一项。


## 四、数据缺口与可信度

- **实验 1/2/3/5**：由脚本产出 JSON，数值经程序化交叉校验（16/16 项通过），可信度高。

- **实验 4**：mentor 服务跑的，数据写 MySQL 但**记录已丢失**（库里只剩无关的 job 39）；表内数值引自报告 `批量导入规模验证_20260907.html`，无法再核对原始记录。

- **阶段数据归属更正**：报告里那张阶段表（embed 7.67s / 96%）标注为「千份级（job 37）」专有，不适用 job 35——本表 job 35 的阶段字段已留空。

- **4090 GPU 对照**：单条 embedding 0.030s 为 bge-gpu 容器日志实测；与 131 CPU 17.1s 是「文档级」近似对比（文档大小与批处理行为不同），量级结论可信。


## 五、万份变慢根因分析

> 数据来源：`bench_c3.json`（50 份并发3）与 `bench_10k.json`（1 万份并发3），同一脚本、同一并发、同一知识库（`2f84a97a`），仅规模不同。


### 5.1 反直觉：单份只慢 20%，吞吐却掉 74%

同口径对比单份阶段耗时（源：各实验 `stage_ms` 字段）：


| 指标 | 50 份（源 bench_c3） | 1 万份（源 bench_10k） | 变化 |

|---|---|---|---|

| embed 单份 avg | 15.31s | 17.11s | +12% |

| embed p50（中位数） | 12.93s | 13.35s | +3% |

| 单份阶段合计 avg | 16.35s | 19.73s | +21% |

| **吞吐** | **0.1797** | **0.0465** | **-74%** |


**矛盾点**：单份阶段合计只涨 21%，吞吐却掉了 74%。若瓶颈是「每份变慢」，吞吐应只降 21% 左右。这说明**主因不在单份耗时**，而在别处。


### 5.2 真正的主因：embedding 长尾堵塞并发槽

看 embed 的长尾（源：`stage_ms.embed` 排序统计）：


| embed 耗时 | 50 份 | 1 万份 |

|---|---|---|

| p50（中位数） | 12.93s | 13.35s |

| p90 | 33.78s | 33.33s |

| p99 | 72.80s | 74.51s |

| **max** | **72.8s** | **556.0s（9.3 分钟）** |

| max 是 avg 的几倍 | 4.8x | **32.5x** |


长尾分布（源：1 万份 embed 各区间计数）：


| embed 耗时区间 | 1 万份数量 | 占比 |

|---|---|---|

| >30s | 1235 份 | 12.4% |

| >60s | 187 份 | 1.9% |

| >120s | 27 份 | 0.3% |

| >180s | 5 份 | 0.1% |

| >300s | 2 份 | 0.0% |


**堵塞机制**：并发只有 3 个槽。50 份时 >60s 的只有 2 份（4%），最慢 72.8s——一个慢文档最多占住一个槽 1 分钟；1 万份时最慢一份要 556.0s（9.3 分钟），占住一个槽期间该槽完全停摆，并发 3 退化成 2。12.4% 的文档超 30s，意味着约 1235 份会反复堵塞并发槽——这是吞吐崩塌的直接原因。


**墙钟去哪了（验证）**：理论墙钟 = 单份合计 × 文档数 / 并发 = 19.73 × 9994 / 3 = 65735s（18.3h）。实际墙钟 215054s（59.7h，源 bench_10k wall_seconds），差额 149318s（41.5h，占实际墙钟的 **69%**）——这 69% 的时间都消耗在等长尾上。

- 50 份的实际/理论吞吐量比 = 97.9%（几乎无空耗）；1 万份 = **30.6%**（近 69% 时间在等长尾）。这一组对比是长尾堵塞的铁证。


### 5.3 长尾本身的来源

embedding 长尾来自 **131 是共享机 + CPU embedding 服务**：

- **外部 embedding 服务超时**：1 万份的 6 份失败，错误信息全部是 `HTTPConnectionPool(host='192.168.80.1', port=18001): Read timed out. (read timeout=180)`（源：bench_10k 的 tasks[].error）。说明 embedding 服务是 `192.168.80.1:18001` 这台外部机器，网络抖动时直接 read timeout=180s，是服务稳定性问题，非 RAGFlow 本身。

- **CPU 争抢**：131 是 34+ 容器混跑的共享机（VLLM、langflow、weknora……），bge-base 在 CPU 上推理，其他容器负载一抖动单次 embed 就被拖长。50 份只跑 5 分钟，撞上抖动概率低；1 万份跑 60 小时，必然反复撞上，长尾累积。

- **单份 embed 略变慢**：avg 15.31→17.11s（+12%），推测是 CPU 长时间运行的热节流/内存压力，属次要因素。


### 5.4 parse 长尾是次要因素

parse 也有长尾（源：`stage_ms.parse`）：1 万份 parse avg=1.78s、max=79.4s、>30s 的有 131 份；parse 占总耗时比例从 50 份的 0.2% 升到 1 万份的 9.0%。但 parse 本身耗时小（avg 1.78s vs embed 17.11s），不是吞吐崩塌的主因。


### 5.5 三因素贡献拆分


| 因素 | 贡献 | 证据来源 |

|---|---|---|

| **① embedding 长尾堵塞并发槽** | **主因（~69%）** | max 556s、12.4% 文档 >30s、墙钟 69% 在等长尾、实际/理论吞吐 30.6% |

| ② 单份 embed 略变慢 | 次要（~12%） | avg 15.31→17.11s |

| ③ parse 长尾 | 边际 | parse 占比 0.2%→9.0%，max 79.4s |


### 5.6 GPU 为何能根治

| | 131 CPU | 4090 GPU | 来源 |

|---|---|---|---|

| 单条 embed | 15.3-17.1s | **0.030s** | 131：bench_10k stage_ms；4090：bge-gpu 容器日志 |

| 长尾来源 | CPU 争抢 + 外部服务超时 | GPU 独占，无争抢 | 131：34 容器混跑；4090：bge-gpu 独占 GPU2 |

| 长尾倍数 | max 是 avg 的 32.5x | （待端到端实测） | bench_10k stage_ms |


GPU 不仅把单条快了约 500 倍，更重要的是**消除了 CPU 争抢导致的长尾**——长尾才是万份吞吐崩塌的真凶。这也解释了为什么「只看单条提速」会低估 GPU 价值：GPU 对吞吐的提升远大于单条提速比例。


### 5.7 一句话结论

万份变慢的主因**不是「每份变慢」**（单份只慢 21%），而是 **embedding 在 CPU 共享机上的长尾**（max 556s、12.4% 文档超 30s）**堵塞了并发槽**，叠加单份略慢（12%）和 parse 长尾。墙钟 69% 的时间在等长尾。GPU 通过消除 CPU 争抢根治长尾，是万份吞吐问题的解药。
