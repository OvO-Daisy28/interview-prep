## T1 全局/跨章节问题的 GraphRAG 检索对比（P0）

**为什么测**：项目需求原文要求「局部问题精准定位 / 全局问题用社区发现算法跨章节汇总」。当前只验证了局部参数问题（额定流量/扬程，KG 相似度 0.331→0.464）。全局维度零数据——这是 GraphRAG 价值的另一半。

**前置确认**：当前 PTR 图谱构建时社区报告（community）是否开启——RAGFlow 默认**关闭**社区。若未开启：先开启 community 重建图谱，单独记录社区发现与社区报告生成的耗时、token 消耗、社区数量。

**步骤**：
1. 设计 6~10 个全局/跨章节问题，覆盖三类：
   - 汇总类：「手册中 PTR 冷却泵的故障模式有哪些，分别如何处理？」
   - 归纳类：「维护 PTR 冷却泵需要哪些专用工具和备件？按章节归纳」
   - 关联类：「PTR 冷却泵与哪些系统/部件存在运行关联？」
2. 同一题集、同一 chat 配置，`use_kg=false` 与 `use_kg=true` 各跑一遍
3. 每题记录：答案全文、人工评分（1~5，评估覆盖度与准确性）、引用 chunk 的来源章节分布（是否跨章节）、最高相似度、检索耗时、端到端耗时

**验收标准**：得出「局部问题 KG +40%，全局问题 KG ±X%」的双维结论；若全局问题 KG 无优势，分析原因（社区报告质量/题集设计）并如实记录。

**产出**：题集 JSON、双配置结果 JSON、对比报告 md（含每题答案原文与评分依据）。

## T2 P0 优化落地 + 延迟复测（P0）

**为什么测**：延迟基准报告给出的 P0 优化（启用流式、限制 max_tokens、简化 prompt）目前是**方案未落地**。落地复测后，「简单问答完整回答 X s」才有实测数字。

**步骤**：
1. 保存当前 chat 配置（基线已有：非流式简单 5.79s / 复杂 15.4s）
2. 逐项落地并单独复测（控制变量，一次只改一项）：
   a. `llm_setting` 限制 max_tokens（简单问答 128，长问答 256）
   b. system prompt 简化（要求简短直接回答）
   c. top_n 6→4
3. 组合全部优化后跑完整复测：简单/复杂题各 8~10 轮，流式与非流式都测

**验收标准**：优化前后延迟对比表；目标参考：简单 ≤2.5s、复杂 ≤6s（预计值，非硬性）。

**产出**：每项优化的单独效果 + 组合效果对比表（JSON+md）。

## T3 文档更新 / 删除后的图谱行为（P0）

**为什么测**：项目经理原话「文档更新了怎么办」，需求中删除/修订是明确条款，但从未实测。需要回答：文档更新后图谱是全量重建还是增量合并？删除文档后图谱残留什么？

**重要**：本测试在**新建副本 KB** 上执行（复制 PTR 手册进新 KB 重建图），不得污染主库。

**步骤**：
1. 副本 KB 建图，记录基线：nodes/edges、实体清单抽样
2. **更新场景**：复制手册、修改 2~3 处参数（如额定流量 640→650、增删一个章节段落），作为 v2 上传同 KB 并解析 → 触发 GraphRAG → 检查：总 nodes/edges 变化？同名实体是被替换/合并/翻倍？新实体的 source_id 指向？旧版本实体是否残留？
3. **删除场景**：删除 v1 文档 → 检查图谱：对应实体/关系是否清理？ES 中 knowledge_graph_kwd=graph 记录的变化？
4. 全程记录每步耗时与 token 消耗

**验收标准**：明确结论「更新 = 全量重建 / 增量合并 / 部分增量」+「删除后图谱 = 清理 / 残留」，并给出对「文档更新了怎么办」的回答（原生行为 + 需要二开什么）。

**产出**：图谱快照对比（更新前后 entity/relation 抽样）、结论报告。

## T4 万份压测收尾（P1）

**为什么测**：万级数字（45h/0.06%）目前全部来自 131 CPU；4090 GPU 只验证到千份。「GPU 无规模退化」结论差万份最后一档。

**步骤**：
1. 新建 KB `GPU测试_10000_<日期>`
2. 按预案分批上传：2000 份 × 5 批（浏览器单次 fetch 上限），走前端真实路径
3. 每批记录：上传耗时、解析墙钟、embed/index 占比、失败数
4. 汇总：总吞吐、失败率、与百份/千份的吞吐曲线对比（0.786 → 1.406 → ?）

**验收标准**：万份吞吐 ≥ 千份吞吐的 80%（warm-up 摊薄后应持平或更高）；失败率 <1%。

**产出**：完整阶梯曲线（100/1000/10000）+ 每批 JSON + 报告。

## T5 多文档图谱合并 + 多知识库问答（P1）

**为什么测**：4090 上只有单份手册建图；「多份文档合并为一张全局图」只在 131 小规模验证过。PM 问过「一次问答能基于多个数据库吗」——未验证。

**步骤**：
1. **多文档建图**：新 KB 放入 PTR 手册 + 2~3 份其他文档（法规或另一份设备资料），完整建图。检查：跨文档同名实体是否合并（各文档子图 → 全局图的合并行为）、图规模、建图总耗时与 tokens
2. **多 KB 问答**：创建 chat assistant 绑定 2 个 dataset（PTR KB + 法规 KB），提问「PTR 冷却泵的维护要求要遵守哪些法规条款？」验证回答是否综合两个库、引用是否双库来源

**验收标准**：跨文档实体合并的实例证据（合并前后对比）；多 KB 问答可行性结论。

**产出**：合并行为报告 + 多 KB 问答结果。

## T6 Light vs General 建图模式对比（P2）

**前置**：先确认 PTR 主库（979/719）实际使用的抽取模式（light / general），写入报告。

**步骤**：同一手册在副本 KB 用另一种模式重建（若主库是 light 则跑 general），固定其余配置。记录：建图耗时、tokens、nodes/edges、社区数（若开）、T1 同款题集的问答效果。

**验收标准**：得出本环境下的模式选型结论（成本 vs 图质量 vs 问答效果），与 131 的历史结论（Light 快 33.76% 但图稀疏）对照。

## T7 扫描版手册端到端全链路（P2）

**为什么测**：MinerU 性能测试（解析）和 docx 端到端问答是两条没串起来的线。「覆盖 Word 与扫描版 PDF」目前只有解析性能证据，缺端到端。

**步骤**：
1. 将 PTR 手册 docx 转为图片版/扫描版 PDF（打印为图片或工具转换，记录转换方式）
2. 新 KB：上传扫描版 → MinerU 解析 → 建图 → 问答，跑通全链路
3. 用 T1 同款题集（局部+全局）对比 docx 路径与扫描路径的：chunk 数、图谱规模、答案质量评分、延迟

**验收标准**：扫描版全链路可行性 + 相对 docx 的质量损失量化。
