# RAGFlow 文档解析卡死排查汇报

| 项目 | 内容 |
|---|---|
| 日期 | 2026-09-03 ~ 2026-09-04 |
| 环境 | 服务器 docker 部署 RAGFlow v0.26.1 |
| 汇报人 | 小zhu |

---

## 一、背景与目的

**遇到的问题**：在 RAGFlow Web 端批量上传文档时，前端文档解析进度长时间卡住不动，无法判断后端是否在正常处理，影响文档活化的上线验证。

**需求来源**：Leader 要求基于 RAGFlow 源码，搞清楚四件事——数据如何存放、后端如何处理队列、如何自己查找队列卡住的原因、如何找到每一步的耗时。

**本次目的**：用文档实测跑通完整解析链路，在过程中学会用数据库和服务器命令定位卡死，并产出根因结论与排查方法。

---

## 二、结论（先行）

批量卡死的真根因**不是队列产能，而是 litellm logging_worker 死锁**：

> worker 处理完文档后，`LLMBundle.close()` 调 litellm 的 `logging_worker.flush()`，`flush()` 用无界 `queue.join()` 等待队列排空；当存在失效模型（Ollama 连不上）时，litellm 调用失败重试，logging task 挂起在队列里永远不完成，导致 `queue.join()` 死等、worker 永久 hang、common 队列停摆、后续所有工单堆积。

**证据链**：用 `py-spy dump` 抓到 worker 堆栈稳定卡在 `close → flush → queue.join → wait`，定位到 litellm 源码 `logging_worker.py` 的 `flush()` 实现是无界 `queue.join()`。

**处置与验证**：清理僵尸工单 + 删除失效 Ollama 模型 + 重启 worker。验证：20 个 docx 批量上传 **54 秒全部完成，零卡死**（清理前同样场景卡 17~62 分钟）。

---

## 三、排查方法

核心思路：**Redis 队列状态 + MySQL 任务表 + progress_msg 时间戳 + py-spy 线程堆栈** 四个视角交叉定位。

| 想回答的问题 | 用什么 | 看什么 |
|---|---|---|
| 队列有没有积压 | `XINFO GROUPS te.0.common` | `lag`（>0=有工单没人取）、`pending`（取走未 ACK） |
| worker 健不健康 | `XINFO CONSUMERS` + `ps` | idle 异常大、进程名对不上=僵尸 |
| 工单卡在哪一步 | MySQL `task.progress` + `progress_msg` | progress 停在哪个区间=卡在哪步 |
| 每步耗时多少 | `progress_msg` 的时间戳 | 相邻两行时间差=该步耗时 |
| 是否被重试过 | `task.retry_count` | >1=被 PEL 重投过 |
| worker 卡在哪个函数 | `py-spy dump --pid <PID>` | 堆栈顶的函数=卡死位置 |

> 关键认知：`XLEN`（Stream 历史消息总数）**不等于积压**，判断积压看 `lag` 和 `pending`。

## 四、排查过程与发现

### 4.1 数据存放与队列机制（摸清架构）

| 数据 | 存放 | 容器 |
|---|---|---|
| 文件二进制 | MinIO，bucket=知识库ID | docker-minio-1 |
| 文档元数据+状态 | MySQL `document` 表 | docker-mysql-1 |
| 任务工单 | MySQL `task` 表 + Redis Stream | docker-mysql-1 / docker-redis-1 |
| 向量+全文索引 | Elasticsearch | docker-es01-1 |

- 队列技术：Redis Stream（valkey），队列 key `te.0.common`/`te.1.common`，消费组 `rag_flow_svr_task_broker`。
- worker：`task_executor.py` 单进程 asyncio，`XREADGROUP` 消费，完成后 `ack()`。
- 并发：common worker 默认 1 个进程，进程内 `MAX_CONCURRENT_TASKS=5`，chunk/embedding 各限 1。

### 4.2 第一层发现：产能与僵尸积压（表层原因）

| 发现 | 证据 |
|---|---|
| common worker 只有 1 个 | `ps` 显示 `-t common` 进程仅 1 个 |
| 历史僵尸工单积压 43 天 | `task` 表 `progress=0` 的工单 `begin_at=2026-07-22`，age_min=61884 |
| 僵尸消费者残留 | `XINFO CONSUMERS` 有 `recovery2`，idle 25h+，`ps` 无对应进程 |
| Redis Stream 不清理 | `XLEN=28` 为已处理未清理的历史消息，非积压 |
| 重试副作用 | `retry_count=2` 的页段，第一轮已 `Task done` 仍被重投重跑（ACK 时序缺陷） |

### 4.3 第二层发现：定位死锁（真根因，py-spy 堆栈）

worker 处理到第 5 个文档后 hang，日志停在 `LLMBundle.encode`，idle 涨到 25 分钟不动。用 `py-spy dump` 抓堆栈：

```
wait (threading.py:359)        ← 永远等
join (queue.py:105)
flush (litellm/logging_worker.py)   ← litellm 日志队列 flush
close (api/db/services/tenant_llm_service.py:545)   ← self.mdl.close()
close (api/db/services/llm_service.py:99)
__exit__ (api/db/services/llm_service.py:107)       ← with 语句退出
handle (task_handler.py:144)
```

**根因链**：
```
任务处理完 → with __exit__ → LLMBundle.close()
  → self.mdl.close()                    ← litellm 模型实例关闭
  → litellm logging_worker.flush()      ← 清空日志队列
  → while not queue.empty(): queue.join()   ← 无界等待
  → 队列里有挂起的 logging task（失效模型调用失败重试）
  → queue.join() 永不返回 → worker 永久 hang
```

源码佐证：litellm 的 `logging_worker.py` 的 `flush()` 实现是 `while not self._queue.empty(): await self._queue.join()`，无超时保护。RAGFlow 源码 `tenant_llm_service.py:538` 的注释也承认 `flush() blocks on an unbounded queue.join()`。

### 4.4 触发因素：失效模型

| 失效模型 | 地址 | 失败原因 |
|---|---|---|
| Ollama qwen2.5:7b | 192.168.80.1:11434 | Cannot connect（端口不通） |
| qwen-plus@Tongyi-Qianwen | — | Access to model denied（权限被拒） |
| gpt-5.5/gpt-5.4 等 | — | model not found |

这些失效模型导致 litellm 调用失败重试，logging task 挂起在队列，触发 `flush()` 死锁。

## 六、处置与验证

### 处置步骤
1. **清理僵尸工单**：删除 `progress=0` 且超 7 天的 401 条 + `0<progress<1` 的漏网僵尸。
2. **清理僵尸消费者**：`XGROUP DELCONSUMER` 删除 `recovery2`。
3. **清理 Redis Stream 残留**：`XTRIM` 控制长度。
4. **删除失效 Ollama 模型**：从 `tenant_model`/`tenant_model_provider`/`tenant_model_instance` 删除连不上的 Ollama 配置。
5. **B 档全量清理**（重置环境）：ES 索引 + 37 个 MinIO bucket + MySQL 业务表（knowledgebase/document/task/file/file2document）+ 聊天记录/智能体 + Redis 队列。
6. **重启 worker**：`docker restart docker-ragflow-cpu-1`。

### 验证结果（20 个 docx 批量上传）

| 指标 | 清理前 | 清理后 |
|---|---|---|
| 5 文档总耗时 | 17~62 分钟（卡死） | 20 秒 |
| 20 文档总耗时 | 无法完成 | **54 秒** |
| Embedding 波动 | 6.4s↔57.66s（9倍） | 0.57s↔3.54s（稳定） |
| worker 死锁 | 频繁发生 | 零发生 |
| retry_count | 多个为 2 | 全为 1 |

20 个文档全部 `Task done`，零卡死、零重试、embedding 耗时稳定。**死锁问题解决**。

## 七、遗留与建议

### 已解决
- 批量卡死（删失效模型 + 重启）
- 僵尸工单/消费者堆积
- 历史数据清理

### 遗留（治本，建议提 issue）
1. **litellm logging_worker flush 死锁**：`flush()` 用无界 `queue.join()` 无超时，建议给 litellm 提 issue 加超时保护。
2. **RAGFlow close 时序**：`tenant_llm_service.py:566` 调 `self.mdl.close()` 可加 try/except + 超时，避免单个模型 close 卡死整个 worker。
3. **ACK 时序缺陷**：`set_progress(1.0)` 写库后、`ack()` 前崩溃会导致已完成任务被重跑，建议加幂等保护。
4. **Redis Stream 不主动 XTRIM**：长期有内存涨满风险，建议加定时清理。

### 运维纪律
1. 多套 RAGFlow 不要共用 Redis（队列名固定，会串消费）。
2. 不要配连不上的模型（失效模型是死锁触发因素）。
3. common worker 偏少（1 个），批量场景建议 `--workers=2~4` 水平扩展。
4. 定期清理僵尸工单和 Stream 残留。

-- 找卡住的工单
SELECT id,doc_id,progress,LEFT(progress_msg,300) AS msg,begin_at,
       TIMESTAMPDIFF(SECOND,begin_at,NOW()) AS elapsed_sec
