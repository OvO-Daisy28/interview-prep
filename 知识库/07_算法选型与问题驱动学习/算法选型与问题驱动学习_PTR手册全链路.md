# 算法选型与问题驱动学习（PTR 冷却泵手册 × 4090 全链路实测）

> 定位：**以 PTR 手册真实数据为锚点**，逐环节讲清楚每个算法"解决了什么问题、解决不了什么、什么时候该用、怎么改"。不是算法百科，是"问题→算法→边界→二开"的决策文档。
> 数据来源：端到端验证完整报告（4090 PTR 手册）+ RAGFlow 源码全链路调研 + GraphRAG 全流程原理 + MinerU 实习报告 + 压测实验报告。
> 阅读方式：沿九环节顺序读，每个环节看「PTR 真实场景 → 算法选择 → 算法原理 → 能解决什么/不能解决什么 → 二开方向」五段式。

## 环节① 上传与元数据

### PTR 真实场景
PTR 冷却泵手册是一个 docx 文件，上传后系统做了三件事：文件存 MinIO、MySQL 建 document 记录（含 content_hash）、生成缩略图。上传仅 3.2s（100 份），不触发解析。

### 算法/技术选择
这里没有传统"算法"，但有两个关键机制：

| 机制 | 技术选择 | 为什么 |
|---|---|---|
| 幂等判断 | xxhash128 内容哈希 | 同一文件重复上传时 hash 不变 → 跳过解析；内容变了才重走全流程 |
| 存储隔离 | MinIO bucket=kb_id / ES 索引=租户级 | 两级隔离维度不同：对象存储按知识库隔离，检索索引按租户共享 |

### 能解决什么 / 不能解决什么

**能解决**：
- 重复上传不浪费解析资源（hash 判断）
- 跨知识库的 doc_id 冲突自动跳过
- 损坏 PDF 预修复（`read_potential_broken_pdf`）

**不能解决**：
- 同名文件内容不同时，`duplicate_name()` 加序号但不做语义去重——"PTR手册v1.docx"和"PTR手册v2.docx"内容 90% 相同也会各解析一次
- 不判断文档是否适合当前知识库的主题——垃圾进垃圾出

### 二开方向
- **语义级去重**：上传时先做一次 embedding，与库内文档做相似度比对，高相似度时提示用户"是否替换"而非新建
- **文档质量预检**：上传前做页数/字数/token 预估，给用户"这份文档预计解析 X 分钟、产出约 N 个 chunk"的前馈

## 环节② 任务队列（Redis Stream）

### PTR 真实场景
PTR 手册上传后调解析接口，系统把文档拆成 task 写入 Redis Stream，Task Executor 消费后才真正开始解析。你遇到过最严重的队列故障——worker 假死，进程活着但心跳停了，任务堆在队列没人领。

### 算法/技术选择

| 问题 | 技术选择 | 替代方案 | 为什么选这个 |
|---|---|---|---|
| 异步解耦 | Redis Stream | RabbitMQ / Kafka | RAGFlow 已集成 Redis；Stream 支持消费者组+持久化+回溯，够用 |
| 任务分发 | 消费者组（Consumer Group） | 简单队列 | 多 worker 水平扩容、各自领活各自确认 |
| 消息确认 | XACK（整任务完成才确认） | 每步确认 | 简化设计但代价大——僵死时消息无法被接管 |

### 能解决什么 / 不能解决什么

**能解决**：
- 异步化：上传接口立即返回，worker 慢慢消化
- 多 worker 水平扩容
- 失败隔离：单 task 失败不影响其他

**不能解决（你的实测验证）**：
- **进度可见性**：536 次轮询只见到 4 种进度文本——进度是一个浮点+一条 msg，不告诉你卡在解析/分块/embedding 哪一步
- **取消生效**：软取消只在阶段边界检查，串行 embedding 时检查点间文档已处理完 → 0 份生效
- **worker 假死**（你的核心故障）：队列后缀写死 `.common` 导致重任务互抢、ACK 太晚导致僵死消息无法接管、事件循环僵死无 watchdog
- **自动重试**：失败即终态，只能重新触发整个文档

### 算法原理速记

Redis Stream 的三条消息生命周期：
```
new（新消息）→ XREADGROUP 消费者取走 → pending（待确认）→ XACK 确认 → acked
```

- `lag` 大 = 消息没被取走（worker 不够或挂了）
- `pending` 大 = 取走了没确认（worker 卡住了）
- `consumer idle` 大 = 消费者没活动（假死信号）

### 二开方向（你已做的 + 可继续的）

**你已做的 5 处内核修复**：
1. 队列按任务类型拆分（graphrag/raptor/mindmap 独立）
2. 重任务专用 worker（单任务执行、异常退出自动重启）
3. watchdog（事件循环 300s 无心跳输出线程栈退出）
4. pending 接管（原 worker 心跳过期后可 claim）
5. 合并超时动态计算

**可继续**：
- 阶段级进度上报：在 task_executor 的每个阶段（parse→chunk→embed→index）插入 `set_progress(msg="embedding: 45/116")`——你的自研导入服务已实现四阶段计时，可以反哺到 RAGFlow 内核
- 优先级队列：当前只有 0/1 两级，可按文档大小/用户优先级动态调整

## 环节③ 文档解析

### PTR 真实场景
PTR 手册是 docx 格式 → DeepDOC 的 DocxParser 直接从文档结构取段落/表格/图片，42.74s 完成。如果手册是扫描版 PDF → 必须走 MinerU 完整管线（Layout→MFR→Table→OCR→Seal→Processing）。

### 算法选择矩阵

| 文档类型 | 解析引擎 | 核心算法 | PTR 场景 |
|---|---|---|---|
| docx | DeepDOC DocxParser | XML 结构解析（段落/表格/图片直接从 docx XML 取） | PTR 手册走这条 |
| 文本版 PDF | DeepDOC PlainParser | 版面分析（标题/段落/表格 bbox 检测） | — |
| 扫描版 PDF | MinerU / PaddleOCR | 版面检测 + OCR + 公式/表格识别 | 你的 MinerU 7 组实验 |

### MinerU 的 7 阶段管线与算法原理

```
PDF → Layout Predict → MFR Predict → Table → OCR-det → OCR-rec → Seal → Processing → 输出
```

| 阶段 | 算法 | 模型 | 解决什么 | 解决不了什么 |
|---|---|---|---|---|
| Layout Predict | 目标检测（YOLO 系） | DocLayout-YOLO | 检测页面区域类型（标题/正文/图片/表格/公式）并给 bbox | 手写标注/非标准版面可能漏检 |
| MFR Predict | 图像→LaTeX 序列生成 | PP-FormulaNet | 把图片中的数学公式转成 LaTeX | 复杂嵌套公式可能出错 |
| Table | 表格结构识别 | SLANet++ | 识别表格方向、无边框表格行列结构 | 合并单元格/跨页表格 |
| OCR-det | 文本检测（DB 算法） | PaddleOCR DB | 检测文字块的位置（bbox） | 密集排版的文字块粘连 |
| OCR-rec | 文本识别（CRNN+CTC） | PaddleOCR CRNN | 识别文字内容 | 生僻字/特殊字体识别率降 |
| Seal | 专用检测模型 | — | 识别印章/公章 | — |
| Processing | 规则+后处理 | — | 整理结果生成 Markdown/JSON | — |

### PTR 实测中的反直觉发现

**MinerU 7 组实验的核心结论**：
- OCR 仅占 <3% 不是瓶颈 ← 反直觉！
- 真瓶颈是 API 通信固定开销（~6s/份，占 42%）+ Layout/MFR 推理
- 批量提交摊薄固定开销（-26%）
- 双 Worker 共享单卡加速 1.7-2.0×（pipeline 显存仅 ~2.5G/Worker，分时复用）

**为什么 OCR 不是瓶颈**：现代 OCR（PaddleOCR DB+CRNN）在 4090 上推理极快（<0.5s/页），慢的是版面分析（DocLayout-YOLO 推理）和公式识别（PP-FormulaNet 推理），以及每次 API 调用的固定通信开销。

### 能解决什么 / 不能解决什么

**DeepDOC（docx 路径）能解决**：
- 直接从 docx XML 取结构化内容（段落、表格、图片），准确率高
- 保留文档固有层级（标题→正文→子标题）

**MinerU（扫描件路径）能解决**：
- 图片版 PDF 的完整结构化（版面→公式→表格→文字→印章）
- 表格转 HTML/Markdown 保留行列关系

**都解决不了**：
- 跨页表格拼接：表格被分页截断时无法自动合并
- 图表的语义理解：识别出"这是一个流程图"但不知道流程图表达什么
- 复杂排版（多栏、文本框环绕）的阅读顺序

### 二开方向

| 问题 | 原生方案 | 二开方向 |
|---|---|---|
| 跨页表格 | 各页独立识别 | 后处理规则：检测表格在页面底部未闭合 → 下一页表格首行是否是续行 → 合并 |
| 业务实体识别 | 只做通用版面分析 | 在版面分析后加一层业务实体标注（设备名/参数/部件号）——可用 NER 模型或 LLM prompt |
| 图表语义 | 只识别"是图表" | 对图表做 caption 生成（VLM 模型或 LLM 看 OCR 结果生成描述） |

## 环节④ 分块（Chunking）

### PTR 真实场景
PTR 手册 DeepDOC 解析后产出 116 个 raw chunks（chunk_token_num=512）。GraphRAG 建图时把这 116 个 chunk 按 batch_chunk_token_size=4096 合并成 17 个抽取单元。

### 算法选择

| 分块策略 | 算法 | 适用场景 | PTR 场景 |
|---|---|---|---|
| 通用模板（naive） | delimiter 切段 + token 数聚合 + 超限独立成块 | 通用文档 | PTR 手册走这条 |
| 法规模板（laws） | 按条款/章节结构切 | 法规文档 | 你的法规库实验 |
| 手册模板（manual） | 按章节层级切 | 设备手册 | PTR 可选但用了 naive |
| QA 模板（qa） | 按问答对切 | FAQ 文档 | — |
| 表格模板（table） | 整表为一个 chunk | 表格密集文档 | — |

### naive_merge 算法原理（源码级）

```
① delimiter 切段（默认 "\n!?。；！？"，中文标点优先）
② 按 token 数聚合成块（_merge_paragraph_groups，策略=OVER_CAP）
③ 超限段落独立成块，不二次切（"model layer truncates oversize units"）
④ 块间重叠（overlapped_percent，默认配置）
⑤ tokenize_chunks 生成 content_ltks 分词（BM25 索引基础）
```

**关键设计决策**：chunk_token_num 不是硬上限。段落超限时独立成块，由 embedding 模型层截断（`truncate(c, max_length - 10)`）——避免在句中粗暴截断破坏语义。

### 能解决什么 / 不能解决什么

**能解决**：
- 大多数文档的合理切分（512 token 在 PTR 手册上产出 116 块，粒度适中）
- 块间重叠缓解边界上下文丢失
- 表格整表保存（tokenize_table，不破坏行列关系）

**不能解决**：
- **跨页语义关联**：一个操作步骤跨了第 3 页和第 4 页，切在第 4 页开头 → 第 3 页的块缺少步骤结尾，第 4 页的块缺少步骤开头
- **层级语义断裂**：手册的"3.1.2 故障诊断"被切到只包含"3.1.2"的上下文，丢失了"3.1 维护规程"和"3 运行管理"的层级上下文
- **参数-描述分离**：设备参数表（640m³/h、36m）和参数的说明文字被切到不同块

### GraphRAG 抽取单元合并（两层分块）

PTR 手册的关键设计：116 个 512-token chunks → 合并成 17 个 4096-token 抽取单元。

**为什么合并**：LLM 抽实体时一次看更多上下文，减少实体被切碎（"PTR冷却泵"在第 5 块出现但完整描述在第 12 块 → 合并后 LLM 一次看到完整上下文）。

**代价**：token 成本翻倍（90 万 tokens 的主要来源之一）。

### 二开方向

| 问题 | 原生方案 | 二开方向 |
|---|---|---|
| 跨页语义 | 纯按 token 切 | 章节感知分块：检测章节边界，不在章节内切分；跨页段落用 overlap 补 |
| 层级上下文 | chunk 只有自身内容 | 层级注入：每个 chunk 带上父标题链（"3 运行管理 > 3.1 维护规程 > 3.1.2 故障诊断"） |
| 参数表分离 | 表格整表成块 | 表格+紧邻描述文字合并成块（检测表格下方紧邻的"注："段落） |

## 环节⑤ 向量化（Embedding）

### PTR 真实场景
116 个 chunks 每个经 BGE-M3 模型生成 1024 维向量，写入 ES 的 `q_1024_vec` 字段。标题单独编码后与正文向量按 0.1:0.9 加权融合。131 CPU 上 embedding 占总耗时 93.6%（max 556s），4090 GPU 迁移后 avg 15.3s→1.46s（×10.5）。

### 算法选择

| 模型 | 架构 | 维度 | 选择理由 |
|---|---|---|---|
| BGE-M3 | XLM-RoBERTa（Encoder-only）+ 对比学习 + 自蒸馏 | 1024 | 多语言（100+语言）、三路检索（dense/sparse/multi-vec）、8192 token 长文本、可本地部署、C-MTEB 高排名。RAGFlow 默认配 Qwen3-Embedding-0.6B（LLM-based），我们选 BGE-M3 是因为三路检索能力适配混合检索场景 |

### 算法原理

**双塔模型（Bi-Encoder）**：
- query 和 doc 各自独立编码成向量 → 计算余弦相似度
- 优势：doc 端可离线编码入库，在线只编码 query → 快
- 劣势：query 和 doc 交互不充分 → 召回准但不够精

**对比学习训练目标（InfoNCE）**：
- 正样本对（相似 query-doc）拉近向量距离
- 负样本对（不相似 query-doc）推远向量距离
- 困难负样本挖掘：用看起来相似但语义不同的样本训练 → 模型学会细粒度区分

### 能解决什么 / 不能解决什么

**能解决**：
- 语义相似度匹配："泵的额定流量" 和 "设备的标准输出参数" 向量距离近
- GPU 独占后长尾根治（max 556s→8.9s）
- 标题参与向量（filename_embd_weight=0.1）→ 文件名也是检索信号

**不能解决**：
- **精确术语匹配**：设备编号"HTJ300-400C"、参数"640m³/h"这种精确值 → 向量检索召回差，靠 BM25 补
- **跨语言**：纯中文模型对英文/混合语言的检索效果会降（BGE-M3 多语言支持缓解此问题，但极端低资源语言仍可能不足）
- **数值推理**："流量大于 600 的设备" → 向量不理解"大于"的语义

### PTR 实测中的关键发现

**标题参与向量**（源码 task_executor.py:744-749）：
```python
vects = title_w * tts + (1-title_w) * cnts  # title_w 默认 0.1
```
PTR 手册的文件名"PTR冷却泵设备运行与维修手册"被编码后融合进向量 → 文件名含"PTR冷却泵"有助于检索。这就是"文件名起得规范有助于检索"的源码原因。

**长尾不是均值问题**：
- 万份测试 embed avg 涨 12% 但吞吐崩 74%
- 真相：max 556s 的长尾堵塞并发槽（并发 3 退化成 2）
- **方法论**：用 p99/max 看性能不用均值——你的差异化优势

### 二开方向

| 问题 | 原生方案 | 二开方向 |
|---|---|---|
| 精确术语召回 | 向量+BM25 混合 | 已解决（混合检索），但权重 0.3 是经验值 → 需参数级调优 |
| 跨语言 | 换多语言模型 | bge-m3 支持多语言，但需全库重建 |
| 数值推理 | 不支持 | 结构化字段提取（PBS 二开方向）：把"640m³/h"抽成结构化字段，检索时按字段过滤 |

## 环节⑥ 索引写入

### PTR 真实场景
116 个 chunk + 向量写入 ES（租户级索引 `ragflow_<tenant>`），图谱数据（graph/subgraph/entity/relation）也写同一索引，用 `knowledge_graph_kwd` 字段区分类型。GPU 迁移后 index 写入成新瓶颈（42.7%）。

### 算法/技术选择

| 问题 | 技术选择 | 替代方案 | 为什么 |
|---|---|---|---|
| 向量索引 | ES HNSW（近似最近邻） | Faiss / Milvus 2.5+ | RAGFlow 架构与 ES 深度绑定，万级规模检索不是瓶颈 |
| 全文检索 | ES BM25（倒排索引） | Milvus 2.5 Sparse-BM25 | 设备编号/型号精确匹配；Milvus 2.5+ 也支持了 BM25 但换引擎成本高 |
| 图谱存储 | ES 特殊 chunk（不落 Neo4j） | Neo4j | 统一检索链路、省一套运维 |

### HNSW 原理速记
层次化可导航小世界图：把向量组织成多层图结构，高层稀疏（快速跳远）、底层密集（精确搜索）。查询时从高层开始逐层下降，找到最近邻。优势：查询快（O(log N)）、支持并发查询；劣势：内存占用大、构建慢。

### 能解决什么 / 不能解决什么

**能解决**：
- 混合检索：向量相似度 + BM25 全文匹配 + 字段过滤一个引擎全做
- 图谱与普通 chunk 共存（`knowledge_graph_kwd` 区分）
- 租户级索引共享（建 KB 不 init ES，按 kb_id 过滤）

**不能解决**：
- 超大规模（百万级文档）时 ES 查询规划变慢
- 实时更新图谱的增量清理（T3 测试：删除文档图谱不自动清理）

### 二开方向

| 问题 | 原生方案 | 二开方向 |
|---|---|---|
| 修改文档图谱残留 | 描述追加不替换 | 版本管理：修改文档时先删旧实体→清图→重建 |
| 删除文档图谱不清理 | 标记 removed_kwd=Y | 自动清理：删除文档时自动调 DELETE /index?type=graph |
| index 写入瓶颈 | ES bulk + MinIO + MySQL 三处 | ES 批量大小调优 + MinIO 异步写 + MySQL 批量更新 |

## 环节⑦ GraphRAG 构建（核心算法层）

### PTR 真实场景
116 chunks → 合并成 17 个抽取单元 → Qwen3.8-27B 逐单元抽实体+关系 → 979 nodes / 719 edges / 90 万 tokens / 21.8 分钟。子图合并成全局图（同名实体描述追加、关系权重累加、PageRank 重算）→ 1700 graph chunks 写回 ES。

### 六阶段全流程与算法

```
① chunk 合并（4096 token 单元）
② LLM 抽实体+关系（gleaning 补抽）→ 解析格式 → 文档子图
③ 子图合并成全局图（同名实体追加、关系权重累加、PageRank 重算）
④ 可选：实体消歧（默认关）
⑤ 可选：Leiden 社区发现 + 社区报告（默认关）
⑥ 在线检索：query 改写 → 四路召回
```

### 阶段② LLM 实体关系抽取

**算法选择**：用 LLM 做 zero-shot 信息抽取（IE），而非传统 NER 模型。

| 方法 | 优势 | 劣势 | PTR 场景 |
|---|---|---|---|
| 传统 NER（BERT 微调） | 快、准（在训练域内） | 需标注数据、泛化差、只抽实体不抽关系 | 核电领域无标注数据 |
| LLM zero-shot IE | 无需标注、可抽实体+关系+描述 | 慢、贵（90 万 tokens）、格式不稳定 | PTR 走这条 |

**LLM 抽取的 prompt 格式（非标准 JSON）**：
```
("entity"<t>实体名<t>实体类型<t>实体描述<COMPLETE>)
("relationship"<t>源实体<t>目标实体<t>关系描述<t>关键词<COMPLETE>)
```

**为什么不用标准 JSON**：RAGFlow light 模式用自定义分隔符格式。解析器要求首字段是 `"entity"`（带引号）、至少 4 个字段、entity_type 必须在配置清单里。

### 空图根因（你的核心发现）

**两条空图路径（源码实证）**：

| 路径 | 原因 | 现象 | 你的实测 |

| ① 格式解析失败 | LLM 输出 JSON 格式漂移，`handle_single_entity_extraction` 返回 None | 0 nodes | DeepSeek Flash 空图 |

**模型对比结论**：

## 环节⑧ 在线检索

### PTR 真实场景
问题"PTR冷却泵的额定流量和扬程是多少？" → 向量检索最高相似度 0.331（偏低）→ 开启 KG 检索后 0.464（+40%），精准命中供货边界表（640m³/h、36m）。全局问题 KG 无检索优势（8 题相似度 0 变化）。

### 两条检索链路

**普通 RAG（Dealer）**：
```
问题 → BM25 关键词匹配 + 向量相似度 → 加权融合（向量权重 0.3）→ 相似度阈值过滤 → top_n 截断
```

**KG 检索（KGSearch）**：
```
问题 → LLM query 改写（抽查询实体+推断类型）→ 四路并发召回：
  a. 实体向量召回（按 keywords）
  b. 实体类型召回（按 PageRank 排序）
  c. 关系向量召回
  d. N-hop 路径扩展（沿关系图遍历邻居，按距离衰减 sim/(2+i)）
→ 打分：score = sim × pagerank → 排序截断 → 拼成虚拟 chunk（similarity=1.0 强进 prompt）
```

### 算法选择矩阵

| 问题类型 | 最佳检索方式 | PTR 实测 | 为什么 |
|---|---|---|---|
| 局部参数题 | 向量 + KG | KG +40%（0.331→0.464） | 问题含具体实体名 → KG 实体匹配精准命中参数表 |
| 全局汇总题 | 向量（KG 无优势） | 8 题相似度 0 变化 | 全局问题不含具体实体 → KG 匹配不到；社区报告未开 → 无跨章节汇总 |
| 精确术语 | BM25 | — | 设备编号/型号向量容易漏、关键词必中 |

### 打分公式（源码级）

**普通 RAG 混合打分**：
```python
sim = hybridSimilarity(ans_embd, ins_embd, ans, inst)
# = vtweight * 向量相似度 + tkweight * BM25 词权重
# vtweight = vector_similarity_weight（用户可配，RAGFlow 默认 0.3）
# tkweight = 1 - vtweight = 0.7
# 实际配置：vtweight=0.3, tkweight=0.7（向量 30% + BM25 70%）
```

**KG 打分**：
```python
score = sim × pagerank
# 实体：sim *= 2 若同时被类型命中
# 关系：sim *= (类型命中加分 + N-hop加分 + 1)
# N-hop：sim / (2+i)，i 是跳数
```

### 能解决什么 / 不能解决什么

**能解决**：
- 局部问题精准检索（KG +40%）
- 精确术语匹配（BM25）
- 混合检索一个引擎全做（ES）
- 检索延迟达标（向量 563ms / KG 1240ms，非瓶颈）

**不能解决**：
- **全局汇总问题**（light 无社区报告）
- **参数级调优**：权重 0.3 / 阈值 0.1 是经验值，未做对照测试
- **rerank 精排**：未启用
- **query 意图识别**：不区分"这台泵的参数"（局部）和"所有泵的故障模式"（全局），都走同一检索路径

### 二开方向

| 问题 | 原生方案 | 二开方向 |
|---|---|---|
| 全局问题无优势 | light 无社区报告 | 切 general 模式开社区发现；或二开 query 分类路由：全局问题走社区报告检索，局部走 KG |
| 参数级调优 | 经验值 | 控制变量测权重（0.1/0.3/0.5/0.7）× 阈值（0.05/0.1/0.2）对照表 |
| rerank | 未启用 | 加 bge-reranker：召回 top_k=1024 → rerank 精排 → top_n=6 |
| 查询意图识别 | 无 | LangGraph 意图路由（你第一周做过原型）：局部/全局/精确 → 不同检索路径 |

## 环节⑨ 问答生成

### PTR 真实场景
问题"PTR冷却泵的额定流量和扬程是多少？" → Qwen3.8-27B 回答准确（640m³/h、36m、型号 HTJ300-400C、转速 1480r/min），带 [ID:1][ID:2] 引用可溯源。优化后简单问答 1.0s 达标、流式 TTFT 0.9s 双达标。瓶颈在 LLM 生成（占 70~96.5%），不在检索。

### 算法/技术选择

| 问题 | 技术选择 | PTR 配置 | 为什么 |
|---|---|---|---|
| 推理引擎 | vLLM | TP2（GPU0+3）、max_num_seqs=8、prefix_caching on | PagedAttention + prefix caching 加速 |
| 生成控制 | max_tokens=256 | 限制生成长度 | LLM 生成占 96.5%，限长直接砍生成量 -58% |
| prompt 工程 | 简化 system prompt | "Be brief and direct" | prompt 从"详细列举"改"简洁直接" → 答案 200字→33字 -37% |
| 流式响应 | stream=true | SSE | TTFT 0.9s，用户 0.9s 看首字 |
| 上下文裁剪 | top_n 6→4 | 减少 prefill | -21%（4→3 复杂题变差，4 是平衡点） |
| 引用回填 | insert_citations | 句级匹配 | 答案按句子切分，每句匹配最相似 chunk 编号 |

### vLLM 推理优化原理

**PagedAttention**：把 KV Cache 按"页"管理（类似 OS 虚拟内存），消除显存碎片，提高 GPU 利用率。

**prefix caching**：相同 prompt 前缀的 KV Cache 复用（RAG 场景下 system prompt + 知识上下文的前缀可复用）→ 减少 prefill 计算量。

**chunked prefill**：把长 prefill 拆成 chunk 分批计算，与 decode 交替执行 → 降低 TTFT。

### PTR 实测中的关键发现

**system prompt 是关键因素**（不是 max_tokens）：
- max_tokens 128 和 256 效果一致 → 不是生成长度限制
- prompt 从"详细列举"改"简洁直接" → 答案从 200 字降到 33 字 → 生成量受 prompt 控制而非硬截断
- **结论**：prompt 工程比参数调优更有效

**复杂问答 5s 不可达**：
- 27B 模型 75 tok/s × 300 token 回答 = 4s 生成下限
- 加检索 + prompt = 5s 下限
- **硬限制**：非流式几乎不可能达标；流式口径首字 0.9s 达标

### 能解决什么 / 不能解决什么

**能解决**：
- 简单问答 1.0s 达标（≤2s）
- 流式 TTFT 0.9s 双达标
- 引用溯源（句级回填到 chunk ID）
- 幻觉控制（三层：prompt 限定 + 阈值过滤 + 引用验证）

**不能解决**：
- **复杂问答非流式 5s 达标**（27B 75tok/s 硬限制）
- **多轮对话的上下文管理**：full_question 改写但有信息损失
- **答案质量评估**：人工评分（1-5 分），无自动化评估

### 二开方向

| 问题 | 原生方案 | 二开方向 |
|---|---|---|
| 复杂问答超标 | 流式兜底 | 复杂问题拆步：用 LangGraph 编排，把"手册涵盖哪些故障及对应措施"拆成 N 个局部问题各走快速检索 |
| 简单/复杂不分流 | 同一模型处理所有问题 | 大小模型分流：14B 处理简单问答（2× 提速），27B 处理复杂问答 |
| 无自动化评估 | 人工评分 | 加 LLM-as-Judge：用更强模型（如 GPT-4）对生成答案做自动评分 |
| 多轮上下文损失 | full_question 压缩 | 对话状态追踪（DST）：维护对话中已提及的实体/参数，检索时带上历史实体 |
