## 一、总览（一句话结论）

以真实核电设备手册在 4090 打通了「解析→分块→向量化→索引→GraphRAG 建图→检索→问答」全链路。知识图谱检索在**局部问题上相似度提升 40%**，全局问题无检索优势（light 模式无社区报告）；落地流式+长度控制+上下文裁剪优化后，**简单问答完整响应 1.0s 达标（≤2s）、流式首字 0.9s 双双达标**；瓶颈定位在 LLM 生成（占 70~96%），非检索。

## 五、端到端问答延迟与优化（T2）

### 5.0 优化全景（问题 → 方法 → 结果）

**五项优化，两类目标**：

#### 延迟优化（4 项，组合后简单问答 5.79s→1.0s）

| # | 问题 | 方法 | 结果 |
|---|---|---|---|
| 1 | LLM 生成长篇回答，生成占端到端 96.5% | llm_setting 限制 max_tokens=256 | 简单 -58%（5790→2441ms） |
| 2 | system prompt 要求"详细列举"导致长篇 | 改"简洁直接型"（Be brief and direct） | -37%，答案 200 字→33 字 |
| 3 | top_n=6 上下文长，prefill 耗时 | top_n 6→4（实测 4→3 复杂题变差，4 是平衡点） | -21% |
| 4 | 非流式要等全部生成完才返回 | API 加 stream=true | TTFT 0.9s，用户 0.9s 看首字 |

**组合效果**：简单 5790→1016ms（-82%）、复杂 15383→8383ms（-45%）、流式 TTFT 859ms（双双达标）

#### 检索质量优化（1 项，不降延迟但提质）

| # | 问题 | 方法 | 结果 |
|---|---|---|---|
| 5 | 纯向量检索局部参数问题召回精度不够（相似度 0.331） | 开启 use_kg=true，KG 四路召回（实体/关系/N-hop/社区）拼虚拟 chunk 补充上下文 | 相似度 0.331→0.464（**+40%**），精准命中供货边界表 |

**T1 边界结论**：全局问题 KG 检索无优势（light 模式无社区报告），所以不是无脑全开，是按问题类型启用。

#### 瓶颈定位（为什么这么优化）

LLM 生成占简单问答 70%、复杂 96.5%（vLLM 72~75 tok/s 属正常）。检索仅 563~1240ms（2~19%）。**所以优化方向是控制生成量，不是优化检索引擎**——数据证明检索不是瓶颈。

#### 诚实边界：配置项 vs 主动调优

| 配置 | 值 | 性质（面试别说"我调优了"） |
|---|---|---|
| vector_similarity_weight | 0.3 | 经验值，未做对照测试 |
| similarity_threshold | 0.1 | 默认低阈值，未做对照 |
| top_k | 1024 | RAGFlow 默认值 |

被问"混合检索权重怎么调的"——诚实答"当前 0.3 是经验值不是调优结果；完整参数级调优是已识别的下一步"。

#### 已识别未落地的优化（讲"下一步"用）

| 优化 | 预期 | 状态 |
|---|---|---|
| rerank | 召回后精排 | 未启用 |
| 复杂问题分步回答 | 拆成多个简单题 | 未落地 |
| 14B 小模型处理简单问答 | 生成 2× 提速 | 未落地 |
| 参数级检索调优 | 权重/阈值对照 | 未做 |

### 5.2 T2 逐项优化效果（控制变量）

| 优化项 | 简单问答 | 复杂问答 | 简单降幅 | 复杂降幅 |
|---|---|---|---|---|
| 基线（无优化） | 5790ms | 15383ms | - | - |

- 最优组合：max_tokens=256 + 简化prompt + top_n=4

## 六、各阶段耗时分解

### 6.1 简单问答（流式，总 ~3s）

| 环节 | 耗时 | 占比 |
|---|---|---|
| 向量检索 | ~563ms | 19% |
| RAGFlow prompt 构造+调度 | ~186ms | 6% |
| vLLM TTFT（首 token） | ~150ms | 5% |
| LLM 生成（~26 tokens） | ~2100ms | **70%** |
| 总计 | ~2999ms | 100% |

### 6.2 复杂问答（流式，总 ~27.6s）

| 环节 | 耗时 | 占比 |
|---|---|---|
| 向量检索 | ~563ms | 2% |
| RAGFlow prompt 构造+调度 | ~287ms | 1% |
| vLLM TTFT | ~150ms | 0.5% |
| LLM 生成（~200+ chunks） | ~26632ms | **96.5%** |
| 总计 | ~27632ms | 100% |

### 6.3 瓶颈定位

**LLM 生成是绝对瓶颈**：简单问答占 70%、复杂占 96.5%。vLLM 生成速度 ~72-75 tok/s，在 27B AWQ-INT4 + TP2 配置下属正常水平。问题出在生成内容量——复杂问答生成 200+ streaming chunks（几百 token 长篇回答）。

**检索不是瓶颈**：向量 563ms、KG 1240ms 均合理，top_n=6 上下文可控。

## 八、关键发现汇总

1. **KG 检索在局部问题上价值明确**（+40% 相似度），建议开启
2. **全局问题 KG 在检索层无优势**，但 E2E 答案质量和延迟略有改善——社区报告缺失是根因
3. **流式 TTFT 是达标关键路径**：简单/复杂首字均 ~0.9s，远低于目标
4. **非流式复杂问答 5s 不可达**：27B 生成 75 tok/s × 300 token 回答 = 4s 生成下限 + 检索 prompt = 5s 下限
5. **优化三招有效**：max_tokens + 简化 prompt + top_n=4，简单问答达标
6. **瓶颈在 LLM 生成不在检索**：数据证明检索已达标，优化方向是控制生成量
