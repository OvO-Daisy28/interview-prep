# 压测实验调研报告：原理 · 方法 · 结果

> 定位：把分散在 131/4090 多份记录里的压测工作，整理成"为什么做、怎么做、得出什么"的完整叙事，支撑面试深挖。
> 数据来源：[实验数据汇总_20260911.md](../../测试报告/实验数据汇总_20260911.md)（131 五组实验）+ [4090_GPU压测_20260911.md](../../测试报告/4090_PTR端到端验证_延迟基准.md)（4090 对照）。

---

## 一、原理：为什么做这件事

### 1.1 业务驱动

项目经理的核心诉求（2026-08-13 原话）：批量上传支持每阶段计时、随时启停、失败重试、读写队列状态、提供接口——5 项可控性需求。但先要回答一个前置问题：**RAGFlow 原生批量导入到底能不能扛住客户上万份文档？慢在哪？**

两件事驱动了压测：
1. **评估可行性**：客户真实数据上万份（太平岭一期 30 万+），要知道吞吐曲线、失败率、规模退化
2. **支撑选型**：团队存在两条技术路线（原生接口 vs 自建管线），压测给出实测对比证据

### 1.2 技术原理：为什么要拆阶段计时

RAGFlow 的导入链路是 `上传 → 解析(parse) → 分块(chunk) → 向量化(embed) → 索引(index)` 多个异步阶段串起来。原生接口只给一个进度浮点+一条文本（536 次轮询只见到 4 种文本），**不告诉你时间花在哪一步**。

不拆阶段就无法定位瓶颈——这是为什么自建管线（方案 B）给每阶段加 `time.time()` 精确计时写库。不是炫技，是诊断的前提。

### 1.3 性能分析方法原理：为什么用长尾不用均值

**核心方法论**：用 p50/p90/p99/max 分布看性能，而不是只看平均值。

原因（实测验证）：万份测试里 embed 平均值只涨 12%（15.31→17.11s），但吞吐掉了 74%。如果只看均值会得出"每份慢了一点所以整体慢了"的错误结论。真相是：**max 从 72.8s 飙到 556s（9.3 分钟），12.4% 的文档（1235 份）超 30 秒**——这些长尾堵塞了并发槽（并发 3 退化成 2），才是吞吐崩塌的真凶。

**墙钟差额法**验证：理论墙钟 = 单份合计 × 文档数 / 并发 = 19.73 × 9994 / 3 = 65735s（18.3h），实际 215054s（59.7h），差额 41.5h 占实际墙钟的 **69%**——这 69% 纯在等长尾。50 份时这个比是 97.9%（几乎无空耗），对比是铁证。

## 二、方法：怎么做的

### 2.1 实验设计总览（5 组 131 + 1 组 4090）

| # | 实验 | 方案 | 文档数 | 并发 | 目的 |
|---|---|---|---|---|---|
| 1 | 方案A 原生上传 | RAGFlow 原生 API | 100 | 内部 | 量化原生接口性能 + 进度可见性 |
| 2 | 方案A 取消测试 | 原生 API + 中途取消 | 100 | 内部 | 验证取消能力 |
| 3 | 方案B 并发1/3/6 | 自建管线（脚本） | 50 | 1/3/6 | 标定最优并发 |
| 4 | mentor 服务 baseline | 常驻服务（前端） | 161/1000 | 3 | 真实用户路径 + 规模曲线 |
| 5 | 1万份稳定性 | 自建管线（脚本） | 10000 | 3 | 长时间稳定性 + 规模退化 |
| 6 | 4090 GPU 对照 | 自建管线（脚本） | 100 | 3 | GPU 消除长尾后提速验证 |

### 2.2 控制变量法

每次只改一个变量：
- 实验 3 三档（1/3/6）固定文档/模型/分块，只改并发 → 得出并发 3 最优
- 50 份 vs 1 万份：同一脚本、同一并发、同一 KB，仅规模不同 → 隔离规模效应
- 131 vs 4090：同脚本、同并发、同文档，仅 embedding 服务不同（CPU vs GPU）→ 隔离硬件效应

### 2.3 数据可信度控制

- **脚本产出 JSON 程序化交叉校验**（实验 1/2/3/5：16/16 项通过）
- **脏数据预筛**：原始 451 份 DOCX 经 `unzip -t` 逐文件核验，89 份损坏剔除；万份扫描 12184 份、python-docx 预筛出 10000 份纯真（约 20% 是 .doc 改名的假 docx）——排除脏数据对失败率的干扰
- **数据缺口诚实标注**：实验 4（mentor 服务）的 MySQL 记录已丢失，数值引自报告 HTML 无法再核对，明确标注可信度降级

### 2.4 两条口径分离

- **脚本压测口径**：`mentor_b_bench.py` 直调，测流水线极限（1.029 份/s）
- **服务前端口径**：走 demo 网页真实上传路径（0.786 份/s，-24%）
- 两条口径分开度量——测的是不同东西，不能混着报

### 2.5 工程保障（跨平台踩坑沉淀）

- Windows/PowerShell 引号嵌套不可行 → 本地写脚本 scp 传容器
- Windows tar ≠ Linux tar → Python zipfile 打包（顺带处理中文 UTF-8 文件名）
- `docker exec -d` 后台执行 + 日志文件 + `python3 -u` 解决输出缓冲
- 长任务与 ssh 会话解耦：断线不影响后台测试

## 三、结果：得出什么

### 3.1 五组核心数据

| 指标 | 131 并发3(50份) | 131 万份(并发3) | 4090 GPU(100份) |
|---|---|---|---|
| 吞吐 | 0.180 份/s | 0.046 份/s（-74%） | **1.029 份/s（×5.7）** |
| embed avg | 15.31s | 17.11s（+12%） | 1.46s（×10.5） |
| embed max | 72.8s | **556s** | **8.9s** |
| embed 占比 | 93.6% | 86.7% | 51.2% |
| index 占比 | 6.1% | 4.1% | **42.7%（新瓶颈）** |
| 失败率 | 0% | 0.06%（6/10000） | 0% |

### 3.2 三层结论

**第一层：瓶颈定位**
- embedding 是 131 上的绝对瓶颈（占 87~96%）
- 长尾（max 556s）堵塞并发槽是万份吞吐崩塌的真凶——不是单份变慢（只涨 12%）
- 墙钟 69% 在等长尾（差额法验证）

**第二层：GPU 迁移效果**
- 单条 embed ×10.5，但吞吐只 ×5.7——Amdahl 定律：瓶颈占比 93.6% 决定理论上限 6.5×，差值在 index 写入
- 长尾根治（max 556s→8.9s），131 的规模退化在 4090 不存在
- 瓶颈转移：embedding 93.6%→51.2%，index 升至 42.7% 成新瓶颈

**第三层：可控性缺陷实证**
- 进度黑盒：536 次轮询只 4 种文本
- 取消失效：实测 0 份取消成功（软取消只在阶段边界轮询）
- 无暂停/重试：5 项 PM 需求满足度 1/5
- → 直接驱动了自建管线（方案 B）的开发

### 3.3 过程中的 bug 发现

- **MySQLRepository 并发 bug**：`threading.local()` 每线程一连接，在 ThreadPoolExecutor 并发下断连（万份 --persist 7 份成功后全卡死）→ 定位为连接非线程安全，测试期切 InMemory 绕开
- **文件名超长 500**：法律文档文件名超 Linux 255 字节上限 → 暂存名改纯 uuid
- **1.3 万份之谜**：RAGFlow 页面显示 1.3 万份已解析——自研 writer 直写 document 表 run=DONE 绕过 task_executor + 历史残留，数字含累积不能直接用

### 3.4 方法学沉淀

1. **长尾分布 > 均值**：性能分析看 p50/p90/p99/max，均值会掩盖长尾
2. **差额法**：理论墙钟 vs 实际墙钟的差额定位"时间花在哪"
3. **控制变量 + 三重证据**：源码 + 设计文档 + 实测交叉验证
4. **脏数据预筛**：20% 假 docx 不是系统 bug，预筛排除干扰
5. **两条口径分离**：极限压测 vs 真实用户路径分开度量

## 四、面试深挖地图

| 预判问题 | 答案位置 |
|---|---|
| 吞吐提升 5.7 倍怎么测的 | §3.1 + 口径备注（脚本口径，非服务） |
| 为什么不是 10 倍 | Amdahl：瓶颈占比 93.6%，上限 6.5×，差值在 index |
| 为什么不用均值 | §1.3：均值只涨 12% 但吞吐掉 74%，长尾才是真凶 |
| 长尾怎么定位的 | §1.3 + §3.2：p99/max 分布 + 墙钟差额法（69% 在等长尾） |
| 并发为什么是 3 | §2.2：1/3/6 标定，3 最优，6 无收益且长尾暴涨 60% |
| 万份失败率 | 0.06%（6/10000），失败隔离生效 |
| 发现什么 bug | §3.3：MySQL 并发连接 + 文件名超长 |
| 原生接口为什么不行 | §3.2 第三层：进度黑盒+取消失效+5项需求满足1项 |
| index 成新瓶颈怎么办 | §3.2 第二层：ES bulk+MinIO+MySQL 三表写入，下一阶段方向 |

## 五、诚实边界

- 万份 45h/0.06% 是 131 CPU 口径；4090 GPU 只验证到千份，万份未跑（T4 待执行）
- "GPU 无规模退化"目前到千份实证，万份是推论
- 实验 4（mentor 服务）MySQL 记录已丢失，数值引自报告无法再核对
- 4090 GPU 单条 0.030s 与 131 17.1s 是"文档级"近似对比（批处理行为不同），量级结论可信但非严格同口径
