## 一、文档解析在做什么

把不同格式的文档（Word/PDF/扫描件）处理成**带语义结构的文本单元**——保留标题层级、段落边界、表格结构、图片位置。

**不是纯文本提取**：如果只提取纯文本丢了结构，后续分块就失去了"按章节切"的依据，检索质量严重下降。

### 三类文档的解析路径

| 文档类型 | 路径 | 速度 | 原因 |
|---|---|---|---|
| docx / xlsx / ppt | 直接从文档 XML 结构取段落表格 | 最快 | 不需要版面分析和 OCR，结构信息已在文件里 |
| 文本版 PDF | 版面分析（识别标题/段落/表格区域） | 中等 | PDF 有文字层但无语义结构，需要版面分析识别区域类型 |
| 扫描版 PDF（图片） | 版面分析 → OCR → 表格识别 → 公式识别 → 后处理 | 最慢 | 本质是图片，所有信息都要模型识别 |

---

## 二、完整解析流水线（以扫描版 PDF 为例）

```
PDF 输入
  → 预处理：PyMuPDF 检测文件类型、语言、是否扫描件
  → 版面分析（Layout）：检测页面上每个区域是什么——标题区/正文区/表格区/图片区/公式区
  → 公式检测（MFR-det）：检测行内公式和展示公式的位置
  → 公式识别（MFR-rec）：把公式图片转成 LaTeX
  → 表格识别：把表格图片转成 HTML/Markdown（保留行列结构）
  → OCR 检测（OCR-det）：检测文字块的位置
  → OCR 识别（OCR-rec）：识别文字内容
  → 印章识别：检测和提取印章
  → 后处理：内容排序（从上到下从左到右）、去重、BBox 修正
  → 输出：Markdown / JSON 结构化文本
```

**关键顺序**：版面分析是第一步——它告诉系统"页面上哪里有字、哪里有表格、哪里有图"。OCR 只对"文字区域"做识别。如果不先做版面分析，OCR 会把表格里的文字和正文混在一起，表格结构就丢了。

## 三、各阶段算法详解

### 3.1 版面分析（Layout Detection）

**做什么**：检测页面上每个区域的类型和边界——标题、正文、图片、表格、公式、页眉页脚等。

**算法本质是目标检测（Object Detection）**：把页面上每个区域当成一个"物体"来检测，输出每个区域的类型 + 矩形坐标（BBox）。

#### 目标检测算法横向对比

| 算法 | 系列 | 原理 | 速度 | 精度 | 文档解析用没用 |
|---|---|---|---|---|---|
| **YOLO** | 单阶段检测 | 一次前向输出所有框 + 类别 | **最快** | 中高 | ✅ MinerU 用 YOLOv8/v10、DocLayout-YOLO |
| **DETR** | Transformer 检测 | 用 Transformer 直接预测框 | 慢 | 高 | 少用 |
| **Faster R-CNN** | 两阶段检测 | 先生成候选框再分类 | 慢 | 高 | 早期方案 |
| **LayoutLM** | 文档理解专用 | 结合文本 + 布局 + 图像三模态 | 中 | **最高（文档场景）** | ✅ MinerU 论文用 LayoutLMv3 |

**MinerU 的版面分析演进**：

| 版本 | 模型 | 架构基础 |
|---|---|---|
| MinerU 论文版（v0.8） | LayoutLMv3-SFT | LayoutLMv3 + YOLOv10，21K 标注数据微调 |
| MinerU v3.4.5（我们部署版） | DocLayout-YOLO | YOLO 架构，专做文档版面 |

**LayoutLM vs YOLO 的区别**：

| 维度 | LayoutLMv3 | YOLO（DocLayout-YOLO） |
|---|---|---|
| 输入 | 文本 token + 布局坐标 + 图像（三模态） | 纯图像 |
| 优势 | 结合文本语义，对模糊区域判断更准 | 纯视觉检测，速度快 |
| 劣势 | 需要文本输入，扫描件无文本层时受限 | 不利用文本信息 |
| 适合 | 文本版 PDF（有文字层） | 扫描件/图片（无文字层） |

#### YOLO 为什么适合版面分析

YOLO（You Only Look Once）的核心思想：把图片分成网格，每个网格一次性预测"这个位置有没有物体、是什么类型、框在哪"。不需要像 Faster R-CNN 那样先生成候选框再逐个分类——一次前向就出结果，所以快。

文档版面分析恰好适合 YOLO：页面上区域类型固定（标题/正文/表格/图片/公式），区域边界相对清晰，和"检测图片里的猫狗汽车"是同类问题。

### 3.2 OCR（光学字符识别）

**做什么**：把图片中的文字识别成文本。分两步：

```
OCR 检测（OCR-det）：检测图片上哪里有文字——文字块的矩形坐标
  → 模型：PaddleOCR 的 DB（Differentiable Binarization）算法
  → 原理：基于分割的文字检测——对图片每个像素预测"是文字边缘的概率"，再二值化得到文字块

OCR 识别（OCR-rec）：把每个文字块的图片识别成文本
  → 模型：PaddleOCR 的 CRNN（CNN + RNN + CTC）
  → 原理：CNN 提取图像特征 → RNN 捕捉序列关系 → CTC 解码成文字（不需要逐字符标注）
```

#### OCR 算法横向对比

| 算法 | 原理 | 优势 | 代表 |
|---|---|---|---|
| **DB + CRNN**（PaddleOCR） | 分割检测 + 序列识别 | 成熟、快、多语言 | MinerU / RAGFlow |
| **CRAFT + TPS+ResNet+BiLSTM** | 字符级检测 + 识别 | 轻量 | StarNet |
| **TrOCR**（Microsoft） | Transformer 端到端 | 手写体、低质量图片效果好 | 学术 |
| **Surya OCR** | Transformer 端到端 | 多语言、布局感知 | 新兴 |

**为什么 OCR 不是瓶颈**（你的反直觉发现）：PaddleOCR 经过多年优化，DB 检测和 CRNN 识别都很轻量，推理快。版面分析模型更大（LayoutLMv3 或 DocLayout-YOLO），公式识别最重（UniMERNet/PP-FormulaNet）——所以实测 OCR 只占不到 3% 耗时。

### 3.3 公式识别（Formula Recognition）

**做什么**：把公式图片转成 LaTeX 文本。

**这是最难最慢的阶段**——公式结构复杂（上下标、分式、根号、积分），需要理解二维空间布局转成一维序列。

#### MinerU 的公式识别演进

| 版本 | 模型 | 架构 | 训练数据 |
|---|---|---|---|
| MinerU 论文版 | **UniMERNet** | 自研网络 | UniMER-1M（100 万公式） |
| MinerU v3.4.5 | **PP-FormulaNet** | PaddlePaddle | 飞桨公式识别 |

#### 公式识别 vs OCR 的区别

| 维度 | OCR | 公式识别 |
|---|---|---|
| 输入 | 文字块图片 | 公式图片 |
| 输出 | 纯文本 | LaTeX（结构化标记） |
| 难点 | 字符识别 | 二维结构 → 一维序列的转换 |
| 模型 | CRNN（轻量） | Transformer/ViT（重） |
| 速度 | 快 | **慢（模型大）** |

**为什么慢**：公式识别需要理解"这个符号在另一个符号的上方"这种空间关系，普通的 CNN 做不到，需要 Transformer 做 attention 来捕捉全局空间关系——模型大、推理慢。

### 3.4 表格识别

**做什么**：把表格图片转成 HTML/Markdown，保留行列结构。

#### MinerU 的表格识别

| 版本 | 模型 | 架构 | 训练数据 |
|---|---|---|---|
| MinerU 论文版 | TableMaster + StructEqTable | 四子任务（结构识别+文本检测+文本识别+框分配） | PubTabNet v2.0 |
| MinerU v3.4.5 | SLANet++ | 基于图结构的表格识别 | — |

### 3.5 后处理（Post-Processing）

**做什么**：把前面所有阶段的输出整理成有序的文本。

核心问题：版面分析输出的 BBox 可能重叠（文字框被图片框包含），顺序可能乱（双栏排版从左到右还是从上到下）。

后处理规则：
- **包含关系**：被图片/表格包含的文字框移除
- **部分重叠**：收缩文字框避免覆盖
- **排序**：按"从上到下、从左到右"的人类阅读顺序，双栏排版分割成多个列区域

| 方案 | 版面分析 | OCR | 公式识别 | 表格识别 | 特点 |
|---|---|---|---|---|---|
| **DeepDOC**（RAGFlow 内置） | 自研模型 | 自带 | ❌ 不支持 | 自带 | 轻量、默认引擎、docx 直接解析 |

**DeepDOC vs MinerU**（RAGFlow 最常用的两个引擎）：

| 维度 | DeepDOC | MinerU |

| 公式识别 | ❌ 不支持 | ✅ UniMERNet/PP-FormulaNet |

## 五、实测发现（7 组实验的核心结论）

### 瓶颈定位

| 阶段 | 耗时占比 | 说明 |
|---|---|---|
| API 固定开销 | ~42% | 请求初始化、模型加载等 |
| Layout + MFR | ~55% | 版面分析 + 公式识别是大头 |
| OCR（det + rec） | **<3%** | 反直觉——OCR 不是瓶颈 |

### 为什么 OCR 不是瓶颈

- PaddleOCR 的 DB 和 CRNN 经过多年优化，模型轻量推理快
- 文字区域多但每个区域识别很快（毫秒级）
- 版面分析模型更大（YOLO/LayoutLM 要处理整页图像）
- 公式识别最重（Transformer 架构理解空间结构）

### 容量规划公式

```
T(N) = a + b×N
  a = 固定开销（API 初始化、模型加载）
  b = 每份文档边际耗时
  N = 文档数量
```

### 优化手段

| 手段 | 效果 | 代价 |
|---|---|---|
| 批量提交（vs 逐份） | -26% | 需要改调用方式 |
| 双 Worker 并发 | 1.7~2.0× 吞吐 | 需要额外 GPU 显存 |

## 六、面试口径

### "文档解析用了什么算法？"

> 扫描件走 MinerU 完整流水线：版面分析用 DocLayout-YOLO（YOLO 目标检测架构，检测页面上标题/正文/表格/图片/公式区域），公式识别用 PP-FormulaNet（Transformer 架构，把公式图片转 LaTeX），表格识别用 SLANet++（图结构表格识别），OCR 用 PaddleOCR 的 DB 检测 + CRNN 识别。docx 走 DeepDOC，直接从文档 XML 结构取段落表格，不需要版面分析和 OCR。

### "为什么 OCR 不是瓶颈？"

> PaddleOCR 的 DB 和 CRNN 经过多年优化，模型轻量推理快。版面分析模型更大（要处理整页图像），公式识别最重（Transformer 理解空间结构）。我实测 7 组实验发现 OCR 只占不到 3% 耗时，大头在版面分析 + 公式识别 + API 固定开销。这个反直觉结论定位了真正的优化方向——不是优化 OCR，是优化 Layout 和 MFR。

### "YOLO 是什么？为什么用在文档解析？"

> YOLO 是目标检测算法——一次前向就输出图片上所有物体的位置和类别，比两阶段检测（Faster R-CNN）快。文档版面分析和"检测图片里的猫狗"是同类问题——页面上区域类型固定（标题/正文/表格/图片），区域边界相对清晰，所以 YOLO 适合。MinerU 用 DocLayout-YOLO 专门在文档数据上微调。

### "公式识别为什么慢？"

> 公式识别要把二维图片转成一维 LaTeX 序列——需要理解"这个符号在另一个符号上方"这种空间关系。CNN 做不到全局空间理解，需要 Transformer 做 attention 捕捉全局关系——模型大推理慢。OCR 只需要逐字符识别（CRNN 足够），所以快。

### "DeepDOC 和 MinerU 什么关系？"

> 两个解析引擎，RAGFlow 可插拔切换。DeepDOC 是 RAGFlow 自带的轻量引擎，docx 直接从 XML 结构取段落表格（不需要版面分析），但不支持公式识别。MinerU 是完整流水线重引擎（版面+公式+表格+OCR+印章），适合扫描件和学术论文。我们 PTR 手册 docx 走 DeepDOC，扫描件批量解析走 MinerU。
