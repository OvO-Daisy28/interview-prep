## 二、技术背景

### 2.1 MinerU 是什么

MinerU 是一个开源 PDF 文档解析工具，能把 PDF（包括扫描件、图片版）转成 Markdown/JSON 结构化文本。支持版面分析、表格识别、公式识别、OCR 等功能。

本次测试使用 v3.4.5 版本，pipeline 模式（轻量通用模式）。

### 2.2 Pipeline 流水线

pipeline 模式把 PDF 解析拆成多个步骤依次执行，像工厂流水线：

```
PDF 输入 → 版面分析(Layout) → 公式识别(MFR) → 表格识别 → OCR检测 → OCR识别 → 印章识别 → 后处理 → 输出
```

| 阶段 | 作用 | 模型 |
|------|------|------|
| Layout Predict | 检测页面区域（标题/正文/图片/表格/公式） | DocLayout-YOLO |
| MFR Predict | 把图片中的数学公式转成 LaTeX | PP-FormulaNet |
| Table orientation/wireless | 识别表格方向和无边框表格 | SLANet++ |
| OCR-det | 检测文字块的位置 | PaddleOCR (DB) |
| OCR-rec | 识别文字内容 | PaddleOCR (CRNN) |
| Seal Predict | 识别印章/公章 | 专用模型 |
| Processing pages | 整理结果，生成 Markdown/JSON | - |

### 2.3 部署架构

4090 服务器上的 MinerU 部署架构：

```
用户请求 → Router (端口 18002) → 分发到两个 Worker
                                ├── Worker 1 (容器 gpu0, GPU2)
                                └── Worker 2 (容器 gpu1, GPU2)
```

两个 Worker 共享同一张 GPU2（24GB），Router 的 `max_concurrent_requests=2` 可并行分发 2 个请求。

### 2.4 GPU 资源分布

| GPU | 显存占用 | 用途 |
|-----|---------|------|
| GPU0 | 22.6/24.6 GB | vLLM（大语言模型推理） |
| GPU1 | 0/24.6 GB | 空闲但未绑定 |
| GPU2 | 5.4/24.6 GB | **MinerU 双 Worker + bge-gpu** |
| GPU3 | 22.6/24.6 GB | vLLM |

MinerU 只能用 GPU2，余量约 19GB。

## 三、实验方法

### 3.1 科学方法论

- **控制变量法**：每次只改变一个自变量，固定其他所有变量
- **重复测量**：每组实验至少 3 轮，第 1 轮丢弃当预热（模型冷启动），取后续轮次中位数
- **假设检验**：明确假设 H1-H6，预设接受/拒绝标准，用数据验证
- **线性回归**：批量吞吐用最小二乘法拟合，报告 R² 值评估拟合质量

### 3.2 测试数据

从 OmniDocBench v1.6（HuggingFace 公开数据集，CVPR 2025）下载图片，用 PyMuPDF 转成 PDF。

**单文档测试集（D1-D7）**：

| 编号 | 类型 | 页数 | 文件大小 | 用途 |
|------|------|------|---------|------|
| D1 | 纯文字 | 1 | 0.3 MB | 固定开销测量 |
| D2 | 纯文字 | 10 | 61.2 MB | 基线 + 批量测试基准 |
| D3 | 纯文字 | 50 | 300.6 MB | 页数扩展性 |
| D4 | 含表格 | 10 | 110.5 MB | 表格类型影响 |
| D5 | 含公式 | 10 | 3.6 MB | 公式类型影响 |
| D6 | 手写笔记 | 5 | 12.2 MB | 手写内容影响 |
| D7 | 纯文字 | 100 | 430.5 MB | 长文档 + 并发边界 |

**异构批量测试集**：100 份各自不同的单页 PDF，来自 OmniDocBench 的 6 种文档类型（book/research_report/note/PPT2PDF/academic/colorful_textbook）。

### 3.3 实验设计

| 实验 | 维度 | 自变量 | 因变量 | 方法 |
|------|------|--------|--------|------|
| 0 | 阶段确认 | - | tqdm 阶段序列 | 单页解析，确认 7 阶段 |
| 1 | 基线 Profiling | 文档类型(6种) | 总耗时 + 阶段耗时 | 6 PDF × 5 轮 |
| 2 | hybrid-engine | backend 类型 | 耗时 | 尝试 VLM 模式（失败） |
| 3 | 页数扩展性 | 页数(1/10/50) | 总耗时 | 复用实验 1 数据 |
| 4 | 并发吞吐 | 串行 vs 并发 | 加速比 | D2+D4 并发，5 轮 |
| 5 | 批量队列 | N(10/30/60) | 总耗时 T(N) | 同构 D2 副本，3 轮 |
| 6 | 并发显存边界 | 页数(10/50/100) | 加速比 + OOM | D2×2/D3×2/D7×2，3 轮 |
| 7 | 异构批量 | 内容多样性 | 每份耗时 | 100 份不同单页，3 轮 |

### 3.4 CLI 调用方式

```bash
# 单文档解析（复用已有 API 服务，避免 ~4s 临时服务启动开销）
mineru -p /data/bench/D2.pdf \
  -o /data/bench/results/exp1/D2_r1 \
  -m ocr -b pipeline \
  --api-url http://127.0.0.1:8000

# 目录模式（批量解析目录下所有 PDF）
mineru -p /data/bench/batch_100_pdf/ \
  -o /data/bench/results/exp7/r1 \
  -m ocr -b pipeline \
  --api-url http://127.0.0.1:8000

# 通过 Router 并发提交（自动分发到两个 Worker）
curl -s -X POST http://10.148.4.21:18002/tasks \
  -F "files=@/data/bench/D2.pdf" \
  -F "backend=pipeline" -F "parse_method=ocr" -F "lang_list=ch"
```

### 3.5 耗时提取方法

| 数据类型 | 提取方法 | 精度 |
|---------|---------|------|
| 总耗时 | CLI stderr 两行时间戳差值（Submitting → Completed） | 秒级 |
| 阶段耗时 | `docker logs` grep tqdm 100% 最终速率换算 | 秒级 |
| 并发耗时 | Router `GET /tasks/{id}` 轮询 wall-clock | 秒级 |

## 四、实验过程与结果

### 4.1 实验 0：单页日志确认

**目的**：确认 3.4.5 的实际 tqdm 阶段序列。

**结果**：确认 7 个阶段——Layout Predict、MFR Predict（可选）、Table orientation、Table-wireless、OCR-det ch、OCR-rec Predict、Seal Predict、Processing pages。纯文字页 MFR 不出现，无表格页 Table 阶段为 0it。

### 4.2 实验 1：基线 Profiling

**目的**：6 类文档 × 5 轮，测量单文档总解析耗时和阶段级耗时。

**结果**：

| PDF | 页数 | 类型 | 中位数(s) | 每页成本(s) |
|-----|------|------|----------|------------|
| D1 | 1 | 纯文字 | 7.15 | 7.15 |
| D2 | 10 | 纯文字 | 14.13 | 1.41 |
| D3 | 50 | 纯文字 | 53.42 | 1.07 |
| D4 | 10 | 含表格 | 20.67 | 2.07 |
| D5 | 10 | 含公式 | 25.21 | 2.52 |
| D6 | 5 | 手写笔记 | 6.50 | 1.30 |

**关键发现**：
- D1 单页 7.15s，其中 ~6s 是 API 通信固定开销，实际推理仅 ~1s
- 页数扩展性近线性：10→50 页（5x），耗时 14→53s（3.8x）
- 文档类型影响显著：同样 10 页，纯文字 14s → 表格 21s(+46%) → 公式 25s(+78%)
- OCR 仅占 <3%，不是瓶颈

### 4.3 实验 2：hybrid-engine 对比

**结果**：15 次全部 EXIT=1 失败，错误：`Local path for repo_mode 'vlm' is not configured.`

**原因**：当前 4090 部署只配置了 pipeline 模式模型路径，未配置 VLM（视觉语言模型）路径。

**结论**：当前环境只支持 pipeline 模式。hybrid-engine 需运维补配 VLM 模型路径 + GPU 资源。

### 4.4 实验 4：双 Worker 并发吞吐

**目的**：测试同一张 GPU2 上两个 Worker 并发提交 2 份 PDF 是否有吞吐收益。

**结果**：

| 轮次 | 串行(s) | 并发(s) | 加速比 |
|------|---------|---------|--------|
| r1（丢弃） | 52.0 | 21.3 | 2.44x |
| r2 | 38.8 | 22.5 | 1.73x |
| r3 | 33.5 | 21.1 | 1.59x |
| r4 | 35.6 | 21.6 | 1.65x |
| r5 | 33.9 | 21.2 | 1.60x |
| **中位数** | **34.7** | **21.4** | **1.62x** |

**关键发现**：
- 并发确实有效，加速 1.62x，节省 38% 时间
- 并发耗时稳定（标准差 0.6s vs 串行 2.1s）
- r1 串行偏高（52s vs ~34s）因 Worker 2 冷启动加载模型

### 4.5 实验 5：批量队列吞吐

**目的**：验证大批量 PDF 队列吞吐的线性性，建立容量规划公式。

**结果**：

| N（份数） | 中位数(s) | 每份耗时 |
|----------|----------|---------|
| 10 | 110 | 11.00s |
| 30 | 322 | 10.75s |
| 60 | 630 | 10.50s |

线性回归：**T(N) = 7.89 + 10.39 × N**，R² = 0.9999

**关键发现**：
- 吞吐完全线性（R²=0.9999），队列调度开销仅 7.89s
- 批量提交比逐份快 26%（10.39s/份 vs 单份 14.13s）
- 假设 H3 被拒绝：b=10.39s ≠ 14.13s，批量模式有额外优化

### 4.6 实验 6：并发显存边界

**目的**：测试并发 2 份不同页数 PDF 的显存边界和加速比变化趋势。

**结果**：

| 并发对 | 页数 | 并发中位数(s) | 串行基线(s) | 加速比 |
|--------|------|-------------|-----------|--------|
| D2×2 | 10 | 16.5 | 28.3 | **1.71x** |
| D3×2 | 50 | 57.5 | 106.8 | **1.86x** |
| D7×2 | 100 | 98.5 | 198.0 | **2.01x** |

**关键发现**：
- 加速比随页数增大**不降反升**（1.71→1.86→2.01），与预期（下降）完全相反
- 原因：pipeline 模式显存占用极低（~2.5G/Worker），22G 余量充裕，瓶颈不在显存而在 GPU 计算单元
- 页数越多，两 Worker 并行重叠时间越长，时分复用损耗占比越小
- D7×2 达到 2.01x（完美并行），并发 98.5s ≈ 单份串行 99s
- 无 OOM，2×100 页也不触发显存溢出

### 4.7 实验 7：异构批量验证

**目的**：实验 5 用同一份 PDF 副本，担心 GPU 缓存效应。实验 7 用 100 份各自不同的单页 PDF 验证真实异构批量。

**结果**：

| 轮次 | 总耗时(s) | 每份耗时 | EXIT |
|------|----------|---------|------|
| r1（丢弃） | 145 | 1.45s | 0 |
| r2 | 139 | 1.39s | 0 |
| r3 | 138 | 1.38s | 0 |
| **中位数** | **138.5** | **1.39s/份** | **0** |

**关键发现**：
- 线性模型对异构批量同样有效，内容多样性未显著影响吞吐
- MinerU pipeline 不做跨文档缓存，实验 5 不存在缓存作弊
- 批量提交比逐份快 5.2x（7.15s→1.39s/份，固定开销摊薄 81%）

## 五、综合结论

### 5.1 瓶颈定位

| 瓶颈层级 | 占比 | 优化方向 | 可行性 |
|---------|------|---------|--------|
| API 通信固定开销 | 单份 42%（6/14.13s） | 批量提交摊薄 | ✅ 立即可行 |
| Layout Predict 推理 | ~15% | 升级模型或换 GPU | 需硬件投入 |
| MFR 公式识别 | 含公式文档 +78% | 如不需要可关闭 | 中等 |
| OCR 文字识别 | **<3%** | **非瓶颈，无需优化** | - |
| 队列调度开销 | <1%（a=7.89s） | 可忽略 | - |

### 5.2 优化建议

按收益从高到低排序：

| 优化措施 | 预期收益 | 实施难度 |
|---------|---------|---------|
| 批量提交（CLI 目录模式） | 每份 -26%（14→10.4s） | 低，改 `-p` 参数即可 |
| Router 并发提交 2 份 | 1.71-2.01x 加速 | 低，走 18002 端口 |
| 100 页文档走并发 | 接近 2x | 低，两 Worker 充分利用 |
| 关闭公式识别（如不需要） | -78%（含公式场景） | 中，需改配置 |
| 配置 VLM 跑 hybrid-engine | 质量提升，速度未知 | 高，需运维配合 |

**立即可行的组合优化**：批量提交 + Router 并发，100 份 10 页 PDF 从 ~24 分钟降到 ~9 分钟，无需改代码、无需额外 GPU。

### 5.3 容量规划公式

```
单份文档串行耗时（单 Worker）：
  T(P) ≈ 6 + 1.1 × P    （P=页数，纯文字）
  T(P) ≈ 6 + 1.5 × P    （P=页数，含表格）
  T(P) ≈ 6 + 1.9 × P    （P=页数，含公式）

批量队列串行吞吐（单 Worker，目录模式）：
  T(N) = 7.89 + 10.39 × N    （N=份数，10 页纯文字）
  T(N) ≈ 7.89 + 1.39 × N     （N=份数，单页异构）

批量并发吞吐（双 Worker，Router 模式）：
  T_concurrent(N) ≈ T_batch(N) / 1.7~2.0

实测参考：
  100 份 10 页纯文字：串行 17.4min / 并发 8.7-10.3min
  100 份单页异构：串行 2.3min / 并发 1.2-1.4min
```

### 5.4 实验验证的假设检验

| 假设 | 结果 | 说明 |
|------|------|------|
| H1: T(N)=a+b×N 线性 | ✅ 接受 | R²=0.9999 |
| H2: 每份耗时随 N 递减 | ✅ 接受 | 11.0→10.75→10.5s |
| H3: b≈14.13s（单份） | ❌ 拒绝 | b=10.39s，批量更快 26% |
| H4: 并发≈max(T_a,T_b) | ✅ 接受 | D7×2 并发 98.5s≈单份 99s |
| H5: 加速比随页数下降 | ❌ 拒绝 | 1.71→1.86→2.01，反而上升 |
| H6: 2×50 页不 OOM | ✅ 接受 | 2×100 页也不 OOM |
| H7: 异构批量线性性 | ✅ 接受 | 内容多样性不影响吞吐 |

## 六、踩坑经验

### 6.1 `--api-url` 模式下 tqdm 在 docker logs 而非 CLI stderr

传 `--api-url` 时 CLI 只是客户端，tqdm 进度条在 API 服务端日志（`docker logs`），CLI stderr 只有 Submitting/Completed 两行时间戳。

应对：总耗时从 CLI 时间戳差值算，阶段耗时从 `docker logs` grep 提取。

### 6.2 容器内缺少 `bc` 命令

实验 4 脚本用 `echo "$a-$b" | bc` 做浮点运算，但容器没有 `bc`。

应对：改用 `date +%s` + 整数运算 `$((end-start))`。

### 6.3 Router 端口 18002 从 localhost 不可达

`curl http://127.0.0.1:18002` 返回 Connection refused。必须用 `http://10.148.4.21:18002`（host IP）。

### 6.4 hybrid-engine 需要 VLM 模型路径

`-b hybrid-engine` 报 `Local path for repo_mode 'vlm' is not configured`。当前容器只配了 pipeline 模式。

### 6.5 重复进程竞争 GPU

修复脚本后重新部署时，旧进程可能还在跑，新旧进程同时竞争 GPU。需先 `kill -9` 清理。

### 6.6 OmniDocBench 图片路径需要 `images/` 前缀

JSON 里 `image_path` 是 UUID 文件名，HuggingFace 仓库实际路径是 `images/{filename}`。

### 6.7 HuggingFace 网络超时

从国内直连 HuggingFace 会超时。应对：利用之前下载 D1-D7 时缓存的 123 张图片离线构建 100 份异构测试 PDF。

5. **分析数据**：线性回归建模（R²=0.9999），假设检验（H1-H7），瓶颈定位，容量规划公式
6. **交付文档**：实验记录（600+ 行）、性能报告（面向领导）、复现指南（面向接手人）、术语对照表

- **工程实践**：Docker 容器操作、SSH 远程执行、日志提取、脚本自动化
- **文档习惯**：边做边记，踩坑即记录，让结果可复现
