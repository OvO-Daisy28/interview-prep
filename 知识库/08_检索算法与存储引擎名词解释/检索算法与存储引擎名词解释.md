# 检索算法与存储引擎名词解释

> 定位：把 RAG 项目里涉及的检索算法和存储概念讲清楚——不是百科，是"在这个项目里它是什么、怎么工作、为什么选它"。
> 阅读顺序：倒排索引 → BM25 → 向量检索 → HNSW → 混合检索 → 字段过滤 → ES 的定位 → Faiss/Milvus vs ES → bge embedding 模型

---

## 一、倒排索引（Inverted Index）

### 是什么

倒排索引是一种数据结构：**从词出发找文档**，而不是从文档出发找词。

- **正排索引**：给你文档 ID，列出它包含哪些词。像翻书的目录——你知道是第几章，想知道这章写了什么。
- **倒排索引**：给你一个词，列出哪些文档包含它。像书后面的索引页——你找一个关键词，它告诉你出现在哪几页。

### 怎么建的

```
文档 1: "PTR冷却泵额定流量640"
文档 2: "冷却泵扬程36m"
文档 3: "额定转速1480"

分词后建倒排索引：
  "PTR"      → [文档1]
  "冷却泵"    → [文档1, 文档2]
  "额定"      → [文档1, 文档3]
  "流量"      → [文档1]
  "640"      → [文档1]
  "扬程"      → [文档2]
  "36m"      → [文档2]
  "转速"      → [文档3]
  "1480"     → [文档3]
```

搜索"冷却泵流量"时：查"冷却泵"→[文档1,文档2]，查"流量"→[文档1]，取交集→文档1。不需要翻所有文档。

### 在 RAGFlow 里对应什么

ES 里每个 chunk 的 `content_ltks` 字段就是分词结果——ES 用这个字段建倒排索引，支持 BM25 全文检索。

---

## 二、BM25 打分

### 是什么

找到了包含关键词的文档后，BM25 给每个文档打一个相关性分数，用来排序。

### 公式核心两个因素

**IDF（逆文档频率）**：衡量一个词"有多稀有"。

- 公式简化版：IDF = log(总文档数 / 包含该词的文档数)
- "PTR冷却泵"只出现在 3 份文档里 → IDF 大 → 权重高
- "的"出现在所有文档里 → IDF ≈ 0 → 权重为零
- **直觉**：越稀有的词越能区分文档，越常见的词越没用

**TF（词频饱和）**：衡量一个词在这份文档里出现多少次。

- 不是简单的"出现越多越好"——BM25 用饱和函数，出现 10 次不一定比 5 次好 2 倍
- 公式里有 k1 参数（默认 1.2~2.0）控制饱和速度
- **直觉**：出现 1 次说明相关，出现 5 次说明更相关，但 10 次和 5 次差距不大了

### 在 RAGFlow 里对应什么

RAGFlow 的混合检索里，BM25 是其中一路——问题分词后匹配 chunk 的 `content_ltks` 字段，BM25 打分。设备编号"HTJ300-400C"这种精确术语，向量检索容易漏（因为向量是语义层面的），但 BM25 关键词必中。

### BM25 的局限

只认字面词。"泵的出力参数"和"额定流量扬程"——语义相同但字面不重合，BM25 召回不了。这就是为什么需要向量检索补上语义匹配能力。

---

## 三、向量检索

### 是什么

把文本通过 Embedding 模型变成一个固定长度的数字向量（比如 1024 维），然后在向量空间里找"距离最近"的文档。

### 怎么做的

1. **离线阶段**：每个 chunk 的正文经 BGE-M3 模型编码成 1024 维向量，存入 ES 的 `q_1024_vec` 字段
2. **在线阶段**：用户的问题也经同一个模型编码成 1024 维向量
3. **检索**：在所有 chunk 向量里找和问题向量"余弦相似度"最高的 top_k 个

### 余弦相似度

两个向量的夹角余弦值。值域 [-1, 1]，越接近 1 越相似。

- 不关心向量长度（长短不影响），只关心方向（语义方向）
- "泵的出力参数"和"额定流量扬程"虽然字面不同，但语义方向接近 → 向量夹角小 → 相似度高

### 向量检索 vs BM25 的分工

| 能力 | BM25 | 向量检索 |
|---|---|---|
| 精确术语匹配 | ✅ 强 | ❌ 弱（语义层面不区分精确值） |
| 语义相似匹配 | ❌ 弱（只认字面） | ✅ 强 |
| 速度 | 快（倒排索引直接查） | 稍慢（要算所有向量距离） |
| 适用场景 | 设备编号、型号、参数值 | 概念性、描述性、换种说法的查询 |

**这就是为什么要混合检索**：两路各有所长，加权融合后两类需求都能满足。

## 四、HNSW 算法（向量检索引擎）

### 为什么需要它

如果每次检索都把用户问题向量和库内所有 chunk 向量逐一计算余弦相似度——万份文档约 116 万个 chunk，每次检索算 116 万次距离，太慢了。

**暴力检索（Flat/Brute-force）**：算所有距离，准但慢。O(N) 复杂度。
**近似最近邻搜索（ANN）**：不追求绝对最优，用空间结构加速查找，牺牲一点点精度换大幅提速。

HNSW 是 ANN 的一种实现，ES 用它做向量检索。

### HNSW 是什么

**层次化可导航小世界图（Hierarchical Navigable Small World）**。

核心思想：把所有向量组织成一个**多层图结构**——

```
Layer 2（最稀疏）:  A -------- F              ← 快速跳远
                     |
Layer 1（中等密度）:  A --- C --- F            ← 逐步缩小范围
                     |    |    |
Layer 0（最密集，全部节点）: A-B-C-D-E-F-G-...   ← 精确搜索
```

- **高层稀疏**：只有少量节点，节点间距离远——查询时从最高层开始，快速跳到目标区域附近
- **底层密集**：包含所有节点——从高层降到底层后，在小范围内精确搜索最近邻
- **类比**：像查地图找一家店——先看全国地图确定是哪个城市（高层），再看城市地图确定哪条街（中层），最后看街道地图找到具体门牌（底层）。不用从全国每条街逐个比对。

### 查询过程

1. 从最高层的一个随机入口节点开始
2. 在当前层找到离查询向量最近的节点
3. 如果这个层不是底层，下降到下一层，从上一步找到的节点附近继续搜索
4. 重复直到到达底层
5. 底层做局部精确搜索，返回 top_k 个最近邻

### 优势与代价

| | 优势 | 代价 |
|---|---|---|
| 查询速度 | O(log N)，比暴力检索快几个数量级 | 不保证找到绝对最优解（近似） |
| 并发 | 支持并发查询 | 内存占用大（要存图结构） |
| 构建 | — | 构建慢（每个向量插入时要和邻居建边） |

### 在 RAGFlow 里对应什么

ES 7.x+ 原生支持 dense_vector 字段类型 + HNSW 索引。RAGFlow 的 chunk 向量存在 `q_1024_vec` 字段（BGE-M3 1024 维），ES 自动用 HNSW 构建向量索引。检索时 ES 对该字段做 KNN 查询（k-Nearest Neighbors），返回 top_k 个最相似的 chunk。

## 五、混合检索（Hybrid Search）

### 是什么

同时走向量检索和 BM25 全文检索，两路结果加权融合。

### RAGFlow 怎么做的

```
用户问题
  ├─→ 向量检索：问题 embedding → HNSW KNN 查询 → top_k=1024 候选
  ├─→ BM25 检索：问题分词 → 倒排索引匹配 → top_k=1024 候选
  ↓
  加权融合：sim = vtweight × 向量相似度 + tkweight × 词权重
  （vector_similarity_weight=0.3 是这里的配置）
  ↓
  相似度阈值过滤（similarity_threshold=0.1）
  ↓
  top_n=6 截断（最终进 prompt 的块数）
```

### 加权融合的权重

`vector_similarity_weight=0.3` 意思是：向量相似度占 30%，BM25 词权重占 70%。

这个权重是经验值，不是调优结果——表示在这个场景下更信任关键词匹配。不同场景可能不同：如果是概念性问答（用户换种说法问），应该调高向量权重；如果是参数精确匹配，应该调高 BM25 权重。

### 加权融合 vs RRF（Reciprocal Rank Fusion）

两种主流的混合检索融合方法对比：

| 维度 | 加权融合（RAGFlow 用的） | RRF |
|---|---|---|
| 公式 | `sim = w₁ × 分数₁ + w₂ × 分数₂` | `score = Σ 1/(k + rank_i)`，k 通常 60 |
| 用什么 | 用分数本身 | 只用排名，不看分数 |
| 前提 | 两路分数要可比（归一化到 [0,1]） | 不要求可比——排名就够了 |
| 权重 | 可配置 | 固定 k 值，不用调权重 |
| 优点 | 能体现"两路都高分" > "只有一路高分" | 简单、不依赖分数归一化、对异质分数鲁棒 |
| 缺点 | 两路分数量纲不同时需要归一化 | 丢失分数信息——第 1 名和第 2 名差距可能很大但 RRF 给的分值差不多 |
| 适用场景 | 分数质量高、需要区分分数差异 | 分数不可靠或量纲不一致 |

**为什么 RAGFlow 选加权不选 RRF**：加权能体现分数差异——一个 chunk 向量 0.9 + BM25 归一化 0.8（两路都高）应该比一个向量 0.3 + BM25 归一化 0.9（只有一路高）排前面。RRF 只看排名，两路排名差不多的话区分不出来。核电文档精确匹配场景需要这种分数区分。

### 空结果降级

如果召回为空，RAGFlow 会自动放宽阈值重试（min_match 0.3→0.1，similarity 0.1→0.17）——宁多召回不漏。

## 六、字段过滤（Filter）

### 是什么

在向量检索或 BM25 检索的结果上，按结构化字段做过滤——"只在某些文档里搜"。

### 在 RAGFlow 里对应什么

ES 索引是**租户级共享**的——所有知识库的 chunk 都存在同一个 `ragflow_<tenant>` 索引里。那检索时怎么只搜某个知识库？靠 `kb_id` 字段过滤。

```
检索条件 = 向量相似度 > 0.1  AND  kb_id = "目标知识库ID"
```

这就是字段过滤：不是把所有租户的 chunk 都搜一遍再筛选，而是在 HNSW 向量检索的同时按 `kb_id` 字段做过滤——ES 支持"向量检索 + 结构化过滤"同时执行，不先全搜再过滤。

### 为什么重要

如果不做字段过滤，A 知识库的用户问"PTR 冷却泵"会搜到 B 知识库里的法规文档——数据隔离就破了。字段过滤是**多租户场景下的数据隔离手段**。

### 常见过滤字段

| 字段 | 作用 |
|---|---|
| `kb_id` | 只搜某个知识库 |
| `doc_id` | 只搜某份文档 |
| `knowledge_graph_kwd` | 只搜图谱类型（graph/entity/relation/community_report）|
| `available_int` | 排除已软删除的 chunk |

## 七、ES 到底是什么——存储引擎还是向量库

### 纠正一个常见误解

ES **不是**"专门的向量库"（如 Faiss、Milvus 那样），也不是"一种算法"。ES 是一个**搜索引擎/存储引擎**，它能同时做：

| 能力 | 实现 | 对应 RAG 场景 |
|---|---|---|
| 全文检索 | 倒排索引 + BM25 | 关键词精确匹配（设备编号/型号） |
| 向量检索 | HNSW 算法（7.x+ 原生支持） | 语义相似检索 |
| 结构化过滤 | 字段查询 | 多租户隔离、文档级过滤 |
| 聚合分析 | Aggregation | 统计分析（RAGFlow 较少用） |

### 为什么 RAGFlow 选 ES 而不选 Faiss/Milvus

| 维度 | ES | Faiss | Milvus 2.5+ |
|---|---|---|---|
| 向量检索性能 | 够用（万级 chunk，P50 < 0.5s） | 更强（百万级优化） | 更强（百万级优化，宣称比 ES 快 30 倍） |
| 全文检索（BM25） | ✅ 原生（倒排索引+BM25） | ❌ 不支持 | ✅ 2.5 起原生支持（Sparse-BM25 稀疏向量实现） |
| 字段过滤 | ✅ 原生 | ❌ | ✅ 标量字段过滤 |
| 运维复杂度 | 一套 | 还得配全文引擎=两套 | 一套（2.5+ 混合检索） |
| RAGFlow 集成 | 深度绑定 | 需改底层 | 需改底层 |

**注意**：Milvus 2.5（2024.12）引入了 Sparse-BM25 技术——用稀疏向量实现 BM25 全文检索，一个引擎同时做向量+全文+过滤。之前"Milvus 不支持全文检索"的结论已过时。

**RAGFlow 选 ES 的实际原因**：
1. 架构已和 ES 深度绑定（chunk 存储、倒排索引、HNSW、字段过滤全走 ES），换 Milvus 要改底层存储层
2. 万级文档规模下检索从来不是瓶颈（P50 半秒以内），没有换的动机
3. ES 全文检索用传统倒排索引+BM25，Milvus 2.5 用 Sparse-BM25（稀疏向量实现），万级规模下两者差异不大

### Faiss 是什么

Faiss 是 Facebook（Meta）开源的**向量检索库**——它只做向量相似度检索，不做全文检索、不做结构化过滤、不持久化存储（是库不是服务）。适合纯向量场景或嵌入到其他系统里用，不适合独立做 RAG 的存储引擎。

### Milvus 是什么

Milvus 是开源的**专用向量数据库**——专门为向量检索设计，支持持久化、分布式、多种 ANN 算法（包括 HNSW）。比 Faiss 更完整（是数据库不是库）。

**Milvus 2.5（2024.12）的重要更新**：
- 引入 Sparse-BM25 技术：通过 `Function(FunctionType.BM25)` 把文本字段自动转成稀疏向量，用 `SPARSE_INVERTED_INDEX` 索引实现全文检索
- 一个引擎同时做向量检索 + 全文检索 + 字段过滤，不再是"只做向量"的短板
- 官方宣称百万级数据检索 6ms（vs ES 200ms），性能提升 30 倍
- 适合百万级以上大规模场景，或从零搭建需要混合检索的新项目

## 八、Embedding 模型（BGE-M3 / Qwen3-Embedding）

### 和 ES 的关系——别混

| 概念 | 是什么 | 选了什么 |
|---|---|---|
| 存储引擎 | 向量存哪、怎么检索 | ES（HNSW） |
| Embedding 模型 | 把文本变成向量的模型 | BGE-M3（1024 维，实际部署） |

ES 是"仓库"——存向量、检索向量。Embedding 模型是"翻译机"——把文本翻译成向量。两个是不同的东西，别混。

### 为什么选 BGE-M3

1. **多语言**：BGE-M3 支持 100+ 语言，核电文档含中英双语术语，纯中文模型（如 bge-base-zh）对英文/混合语言效果会降
2. **可本地部署**：核电私密性要求，不能用 OpenAI 的 embedding API
3. **三路检索**：BGE-M3 支持 dense（稠密向量）、sparse（稀疏检索，类似学习版 BM25）、multi-vector（ColBERT 式多向量）三路合一，且有自蒸馏提升
4. **长文本**：支持 8192 token，适配长手册分块
5. **标题参与向量**：RAGFlow 的 embedding 会把标题单独编码后和正文向量加权融合（权重 0.1）——文件名含"PTR冷却泵"有助于检索

> RAGFlow 官方默认配的是 Qwen3-Embedding-0.6B（LLM-based 架构，CMTEB-R 71.02，32K 上下文），我们选 BGE-M3 是因为三路检索能力适配混合检索场景。详细原理见 `知识库/09_Embedding原理与BGE模型选型/`。

### 为什么换模型要全库重建

问题和文档的向量必须在**同一个向量空间**里相似度才有意义。BGE-M3 和 Qwen3-Embedding 是两个不同的模型、两个不同的向量空间——同一句话在两个模型里编码出来的向量完全不同。所以换 embedding 模型 = 所有 chunk 重新编码 = 全库重建。

## 九、检索全链路串起来（PTR 手册为例）

```
用户问："PTR冷却泵的额定流量是多少？"

1. 问题 embedding：BGE-M3 把问题编码成 1024 维向量
2. 向量检索：ES 用 HNSW 在所有 chunk 向量里找余弦相似度最高的 1024 个
   → 同时按 kb_id 字段过滤（只搜目标知识库）
3. BM25 检索：问题分词后查倒排索引，BM25 打分取 1024 个
   → 同时按 kb_id 字段过滤
4. 加权融合：向量相似度 ×0.3 + BM25 ×0.7
5. 阈值过滤：相似度 < 0.1 的丢弃
6. top_n 截断：取前 6 个进 prompt
7. [可选] KG 检索：LLM 改写问题抽实体 → 实体/关系/N-hop 四路召回 → 拼虚拟 chunk
8. 上下文组装：6 个 chunk（+ KG 虚拟 chunk）按格式拼进 system prompt
9. LLM 生成：vLLM 生成答案
10. 引用回填：答案按句子切分，每句匹配 chunk ID → [ID:1][ID:2]
```

PTR 实测：纯向量检索最高相似度 0.331（偏低），开启 KG 后 0.464（+40%），精准命中供货边界表（640m³/h、36m）。
