# 实习工作记录：RAGFlow 批量上传测试（2026-09-07 ~ 09-11）

> 项目：中广核「采购文件活化项目」，RAGFlow v0.26.1 作为知识库/图谱后端
> 环境：131 服务器（10.126.2.131，CPU，34 容器混跑共享机）；后期启动 4090 服务器（10.148.4.21，4×RTX 4090）部署
> 测试数据：law_data 法律法规文档（zip 内 29346 份，约 20% 是 .doc 老格式改名 .docx 的脏数据）

---

## 一、背景与任务演进

项目经理对「批量上传」的核心要求：**可管理**——每阶段计时、随时暂停/重试、读写队列状态、提供接口。

团队存在两条技术路线，我的任务是给出实测对比证据：

| | 方案 A（RAGFlow 原生） | 方案 B（mentor 自建） |
|---|---|---|
| 解析流程 | 调 RAGFlow API，task_executor 干活 | 自己 parse→chunk→embed→index |
| 存储 | 原生 | 复用 RAGFlow 的 MinIO/ES/MySQL |
| 可控性 | 弱 | 强（暂停/重试/计时全有） |

任务在实际执行中按 mentor 安排演进了四步：
1. 方案 A vs 方案 B 对比实验设计与执行
2. 聚焦单独测试方案 A 原生接口（性能 + 进度可见性 + 可控性）
3. 方案 B 接口压测机器最好性能 + 重新标定并发数（embedding 服务被清理重置过）
4. 1 万份大规模稳定性测试；期间启动 4090 GPU 服务器部署

## 二、架构认知（源码级探查，3 个并行 agent 读 mentor 代码 + RAGFlow 源码验证）

**方案 A 调用链**（4 个 HTTP API）：
```
POST   /datasets/{kb}/documents   批量上传（multipart，只存文件+登记，不解析）
POST   /datasets/{kb}/chunks      启动解析（只是入 Redis Stream 队列，立即返回）
GET    /datasets/{kb}/documents   轮询进度（run / progress / progress_msg / process_duration）
DELETE /datasets/{kb}/chunks      取消解析
```
真正干活的是容器内 `task_executor` 进程，默认 `MAX_CONCURRENT_CHUNK_BUILDERS=1`——**embedding 阶段串行**，这是方案 A 慢的根源。

**方案 B** 在 mentor 进程内同步跑四阶段，每阶段 `time.time()` 精确计时写库；`Scheduler(max_concurrent=N)` 控制并发。两方案最终都调同一个 bge-base embedding 服务。

**关键架构事实**：两方案共享同一 `IngestPipeline` 协议 + `Orchestrator`，唯一差异是 pipeline 实现——这是对比实验公平性的基础。

## 三、测试 1：方案 A 纯原生接口（100 份纯真 .docx）

**方法**：写 `native_upload_test.py`，只调上述 4 个 API，不走 mentor 任何代码。数据先用 python-docx 预筛（剔除 .doc 改名/空文件），保证 100% 是可解析的真 docx。

**结果**：

| 指标 | 值 |
|---|---|
| 批量上传 100 份 | **3.2s**（上传本身很快） |
| 解析墙钟 | **1104s（18.4 分钟）** |
| 吞吐 | **0.091 份/s** |
| 成功率 | 100/100 |

**进度可见性（硬伤实证）**：全程 536 次轮询采样，`progress_msg` 去重后只有 4 种文本——`Task is queued...` / `N tasks are ahead in the queue...`。没有任何 parse/chunk/embed 阶段信息，progress 浮点前 483 秒几乎不动（0.0049）。无法回答"现在跑到哪个阶段、哪份文档拖后腿"。

## 四、测试 2：方案 A 取消能力实测

**方法**：跑到整体 30%（30 份 DONE、70 份 RUNNING）时发 `DELETE /chunks`，继续轮询观察。

**结果**：**最终 0 份变 CANCEL，100 份全部正常 DONE**——取消完全没生效。

**根因**（结合源码）：RAGFlow 取消是软取消（写 Redis 标志，task_executor 在阶段边界轮询 `has_canceled` 才停），串行 embedding 场景下检查点之间文档已被处理完。且原生无 pause 状态，无单份重试（失败即终态，`retry_count` 字段存在但内核不消费）。

**PM 5 项需求方案 A 满足度：1/5**（只满足"提供接口"）——这是 mentor 当初放弃原生路线转自建的实证依据。

## 五、测试 3：方案 B 并发压测（1/3/6 三档 × 50 份）

**背景**：embedding 服务被清理重置，mentor 要求重新标定并发数。用 `mentor_b_bench.py`（基于 m2_batch_run.py 改造为读真 .docx）。

| 并发 | 墙钟 | 吞吐 | embed avg | embed max |
|---|---|---|---|---|
| 1 | 594s | 0.084 份/s | 11s | 47s |
| **3** | **278s** | **0.180 份/s** | 15s | 73s |
| 6 | 275s | 0.182 份/s | **30s** | **118s** |

**结论（与清理前一致，甜点区未变）**：
- 并发 3 是最优：吞吐 2.1 倍于串行，接近理论上限
- 并发 6 无收益：吞吐持平（+1%），但单份 embed 翻倍、长尾暴涨 60%——纯争抢开销
- **embedding 占总耗时 93~95%，parse+chunk+index 合计 <7%**，编排层无优化空间；提速正解是 GPU/独立部署，不是加并发

## 六、测试 4：1 万份稳定性测试

**过程**：
1. 筛 10000 份纯真 docx（扫描 12184 份），zip 279MB 传入容器
2. 第一次尝试 MySQL 持久化（`--persist`）**失败**——暴露 mentor 代码真实 bug（见第八节），退回 InMemory 模式
3. `docker exec -d` 后台跑（09-08 17:25 启动），脱离 ssh 会话，日志 `/tmp/bench_10k.log`
4. 约 45 小时跑完（09-11 收尾出报告），期间用 `tail` 远程跟踪

**观察到的现象**：
- **吞吐随时间衰减**：0.12 → 0.078 → 0.054 份/s（131 共享机负载累积所致，但进程零崩溃、线性增长）
- **失败率极低**：全程仅 6 份失败（≈0.06%），失败隔离生效，不拖累其他文档
- **长时间稳定性验证通过**：InMemory 模式跑 45 小时无崩溃

**附带发现——"RAGFlow 页面 1.3 万份已解析"之谜**：查 document 表发现 KB 里累积 13189 份、全部 run=DONE/progress=1.0、按小时分桶全部落在万份测试时间段。根因：**方案 B 的 writer 跑完四阶段后直接往 RAGFlow document 表写 run=DONE**（绕过 task_executor，chunks 直写 ES），所以 RAGFlow 页面显示"已解析"并不代表 task_executor 干的活；且多次测试残留从未清理，数字含历史累积。教训：**demo 页/服务查的 MySQL gcn_ingest 表和测试脚本 InMemory 是两个数据源，数字对不上是正常的**。

## 七、核心结论汇总

1. **方案 A「能用但不可管」**：功能完整（上传→解析→检索），适合轻量一次性导入；进度只能猜（单浮点+排队文本）、取消实测不生效、无暂停/重试
2. **方案 B 满足 PM 全部 5 项需求**，吞吐约为方案 A 的 2 倍（0.18 vs 0.091），代价是放弃 RAGFlow 解析引擎、自维护全链路（复杂版面/扫描件解析质量待验证）
3. **embedding 是两方案共同瓶颈**（93-95%），并发 3 是当前 CPU 环境的最优点，1 万份推算需 15-23 小时——不配 GPU 无法满足 PM 期望 → 直接引出 4090 部署任务
4. 三重证据（RAGFlow 源码 + mentor 设计文档 + 实测数据）交叉验证，结论可复现

## 八、发现的问题与踩坑记录（全部实测验证）

### 反馈给 mentor 的 bug
- **MySQLRepository 并发连接 bug**：`threading.local()` 每线程一个 MySQL 连接，在 `ThreadPoolExecutor` 并发下连接断开，`get_task` 返回 None，task 全失败（`'NoneType' object has no attribute 'status'`）。复现：`--persist --concurrency 3` 万份任务 7 份成功后全卡死；InMemory 不受影响。建议加连接 ping/重连。**这影响生产路径**（service.py 长驻服务用的就是 MySQLRepository）。

### RAGFlow API 层面（写脚本前不知道、踩出来的）
| 坑 | 真相 |
|---|---|
| run 状态码 | 是**单词字符串** `"RUNNING"/"DONE"/"FAIL"/"CANCEL"/"UNSTART"`，不是数字 0-4。搞错导致脚本两次"秒退"（把 RUNNING 全算成已结束） |
| 删文档参数 | `DELETE /documents` 用 `ids`，不是 `document_ids`（后者报 code:101 Extra inputs are not permitted）；而 `DELETE /chunks` 用 `document_ids`——两个接口参数名不一致 |
| 容器内端口 | RAGFlow API 容器内是 **9380**，9388 是宿主映射，容器内 curl 9388 不通 |
| 列表分页 | `GET /documents` page_size 上限 100 |
| 停止解析 | 对已 DONE 的文档 stop 报 `DOC_STOP_PARSING_INVALID_STATE`（不影响删除） |
| KB 权限 | 默认 KB_NORMAL 属别的 tenant（code:102 lacks permission），要确认 KB 归属再选 |

### 跨平台工程层面
- **PowerShell 引号嵌套是死路**：`ssh "docker exec ... python -c "...""` 层层嵌套必然解析错。可靠模式：**本地写 .py 脚本 → scp → docker cp → 容器内执行**
- **Windows tar ≠ Linux tar**（bsdtar vs GNU 格式），流式传输报 "does not look like a tar archive"。可靠模式：**Python zipfile 打包 → 传 zip → 容器内 Python zipfile 解压**（顺带正确处理中文 UTF-8 文件名）
- **Python 输出缓冲**：docker exec 跑长任务"终端没反应"多半是 stdout 缓冲，用 `python3 -u` 解决；后台任务输出重定向日志文件 + 进度线程定期打印
- **scp 源在 F: 盘必须在本机 PowerShell 跑**，在 131 ssh 会话里跑必报 `Could not resolve hostname f`
- **`docker exec -d` 启动的进程脱离 ssh 会话**，ssh 断线不影响后台测试

## 十、收获与能力沉淀

1. **对比实验方法论**：控制变量（同一批文档、同一编排层只换 pipeline）、三重证据交叉（源码/文档/实测）、预筛数据排除干扰（脏数据导致的 20% 失败不是系统 bug）
2. **读懂了 RAGFlow 内核**：Redis Stream 队列派活、task_executor limiter 并发模型、set_progress/has_canceled 机制、document 表字段——从"会用 API"到"能从源码解释行为"
3. **性能测试的严谨性**：单次测量在共享机上不可信（吞吐随负载衰减 0.12→0.054）；"最优并发"依赖环境，换环境必须重标定；长尾（max/avg 比）比均值更能暴露问题
4. **远程服务器工程能力**：跨机文件搬运的可靠模式、后台任务与 ssh 会话解耦、进度可观测性（日志+轮询双通道）
5. **发现并定位了 mentor 生产代码的真实并发 bug**——大规模测试的价值不只是性能数字，还有稳定性问题暴露
