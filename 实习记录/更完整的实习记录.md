# 第一部分：LightRAG 实验与运行问题

## 1. 实习目标

本阶段围绕 RAGFlow 的 LightRAG 能力开展调研，目标是回答：

1. 多份法律法规文档如何上传、解析、分块、向量化并生成知识图谱；
2. 每份文档与全局图的关系，以及一个知识库能否把多份文档合并成一张图；
3. 在当前部署、模型和 CPU 条件下，解析速度、图谱生成速度、问答速度和问答准确率如何；
4. 大批量上传时应如何分批、失败后如何重试；
5. 后续如何通过更大规模压测估计单图可容纳的文档量。

## 2. 我实际完成的工作

### 2.1 熟悉 RAGFlow 的核心链路

已跑通并观察过以下流程：

`上传文档 → 文档解析 → 分块 → Embedding 向量化 → LLM 实体/关系抽取 → 子图处理 → 全局图合并 → 图谱检索/问答`

对源码和运行链路的认识：

- RAGFlow 的 API 服务负责接收请求和维护任务状态；`task_executor.py` 是独立的后台执行器，消费 Redis 队列并执行解析、分块和图谱任务。
- 普通文档解析与 LightRAG 图谱任务不是同一个进程阶段；前者产生 chunks，后者基于可用 chunks 调用 LLM 抽取实体和关系。
- 每份文档先形成自己的局部/子图，随后进行实体解析、关系合并和全局图构建；因此不是“每份文档直接独立成为最终图”，而是“文档级抽取后合并为知识库级全局图”。
- 页面/API 的图谱展示存在返回上限；节点和边总数必须以 Elasticsearch 中 `knowledge_graph_kwd=graph` 的实际记录核验。

## 3. 已解决或定位的问题

### 3.1 89 个 DOCX 损坏

通过逐文件 `unzip -t` 核验，89 个 DOCX 确认损坏。它们与后续“模型调用超时/队列阻塞”问题要分开处理：损坏文件属于输入质量问题，不能用来解释所有解析失败。

### 3.2 任务进度卡在 60% 或 80%

实际运行中出现过文档长时间停在约 80% 或图谱进度不变。已确认需要区分三类状态：

1. 文档解析任务未完成，通常与执行器消费、模型请求或队列状态有关；
2. 文档虽有 chunks，但实体/关系抽取返回空结果；
3. 图谱全局合并仍在执行，页面进度条不能细粒度反映内部处理。

因此，不能只看前端百分比判断是否卡死，应同时检查任务状态、执行器进程、Redis pending、后端日志和 ES 结果。

### 3.3 取消任务后队列仍占用

已观察到取消任务后 Redis pending 中仍可能保留消息，旧执行器进程继续占用任务或消费状态未及时释放，导致后续任务排队。处理原则是：

- 先确认任务是否真的取消；
- 检查 common/special executor 是否存活；
- 检查 Redis stream pending 和后端日志；
- 只在确认 common executor 异常时处理对应 executor，不随意重启 RAGFlow、Redis 或删除全部数据；
- 失败重试只针对失败文档，不重复提交整批文档。

### 3.4 图谱中出现 0/0 子图

“0 nodes, 0 edges”不能直接解释为“文档实体太少”。目前更稳妥的判断是：模型返回为空、输出格式未被解析器识别、抽取调用失败，或原文确实缺少可抽取信息，都可能导致 0/0。必须结合原文、模型原始响应和后端日志进一步区分。

## 4. 模型与配置方面学到的知识

### 4.1 Embedding model 与 indexing/生成模型的区别

- Embedding model 把文本转换为向量，用于向量检索和相似度计算；它不负责生成实体、关系或自然语言答案。
- LLM/生成模型负责实体关系抽取、图谱摘要和问答回答。
- indexing 在 RAGFlow 语境中通常指把 chunks、向量、关键词和图谱记录写入索引；它不是一个与 embedding 完全等价的“第二个模型”。
- `bge-base` 适合作为当前向量化模型，但最终效果仍取决于语料、分块和检索配置。

### 4.2 Qwen、DeepSeek 与本地模型的使用经验

- 云端模型必须同时验证模型标识、Base URL、API 权限、余额和实际请求；页面中“已添加”不等于可调用。
- `qwen-plus` 的图谱实验可以提交，但其问答请求实际返回 `Access to model denied`，说明模型权限/账户状态需要单独确认。
- `deepreasoning-qw-3.8-max` 已完成单文档解析验证：1 份 DOCX 成功生成 9 chunks，耗时约 19.5 秒，可进入后续分批测试。
- 本地 Windows 环境曾核验 Ollama 运行中，已有 `qwen2:7b` 和 `gpt-oss:20b`；但机器为 NVIDIA GeForce GT 705、2GB 显存，主要走 CPU，不适合按高吞吐规划。该本地环境与服务器上的 RAGFlow 不是同一运行环境。

## 5. 目前可以给出的结论

1. RAGFlow LightRAG 可以把多份文档先生成文档级子图，再合并为一个知识库级全局图；10 份文档已经实际生成过全局图。
2. 当前没有完成“最大文档数”压测，因此不能声称 LightRAG 一张图最多支持多少文档。10 份只能作为已验证样本规模，不能作为上限。
3. 在当前 CPU、队列和模型调用条件下，建议先按 1～2 份文档分批解析；批次大小应通过逐步压测调整。
4. 解析失败时，应只重试失败文档，并先检查执行器、Redis pending 和日志。
5. QW 完整知识库的已验证问答指标为：平均 8.028 秒、P95 10.097 秒、准确率 90%。这是该 QW 知识库/固定题集的结果，不应泛化为所有数据集和所有模型。
6. 严格的 QW 与 DeepSeek Flash A/B 结果当时仍未完成；Flash 早期实验存在取消文档和重复 chunks，不能直接拿来比较。

## 10. 已确认的 RAGFlow 运行架构

RAGFlow 后端使用 Quart，不是 FastAPI。系统主要由 API Server 和 Task Executor 两类进程组成：

```text
Quart API Server
    → 接收上传、解析、检索和索引请求
    → 创建文档和任务
    → 查询任务状态

Task Executor
    → 从 Redis 队列消费任务
    → 从对象存储读取原始文件
    → 调用解析器、切块器和 Embedding 模块
    → 将结果写入文档引擎
```

核心架构文件：

- [CLAUDE.md](/data/zwt/ragflow/CLAUDE.md)
- [api/apps/__init__.py](/data/zwt/ragflow/api/apps/__init__.py)

## 11. 文档上传、解析和入库流程

### 11.1 文件上传

文档上传接口为：

```text
POST /api/v1/datasets/{dataset_id}/documents
Content-Type: multipart/form-data
```

上传流程：

```text
客户端上传 Word / PDF
    → Quart 接收 multipart/form-data
    → FileService.upload_document()
    → 原始文件写入 MinIO / S3 等对象存储
    → DocumentService.insert()
    → MySQL / PostgreSQL 保存文档元数据
    → 返回 document_id
```

上传接口主要负责“保存文件和创建文档记录”，不代表解析已经完成。

关键代码：

- [api/apps/restful_apis/document_api.py](/data/zwt/ragflow/api/apps/restful_apis/document_api.py:367)
- [api/db/services/file_service.py](/data/zwt/ragflow/api/db/services/file_service.py:458)

### 11.2 启动解析

文档解析接口为：

```text
POST /api/v1/datasets/{dataset_id}/documents/parse
```

请求体示例：

```json
{
  "document_ids": ["document_id_1", "document_id_2"]
}
```

解析流程：

```text
客户端提交 document_ids
    → 校验文档归属
    → 清理旧 chunk
    → 更新文档状态为 RUNNING
    → DocumentService.run()
    → TaskService.queue_tasks()
    → 任务写入 Redis 队列
    → HTTP 接口返回任务已提交
```

因此，RAGFlow 的解析接口通常是“提交异步任务”，不是同步返回完整解析文本。

关键代码：

- [api/apps/restful_apis/document_api.py](/data/zwt/ragflow/api/apps/restful_apis/document_api.py:1431)
- [api/db/services/task_service.py](/data/zwt/ragflow/api/db/services/task_service.py:358)

### 11.3 后台 Worker 执行解析

后台任务执行器的主要流程为：

```text
Task Executor 获取任务
    → 根据 document_id 获取对象存储地址
    → 读取原始二进制文件
    → 根据 parser_id 选择解析器
    → 识别章节、段落、表格和图片
    → 文本切块
    → 图片和表格裁剪图入对象存储
    → 生成 Embedding
    → chunk 写入文档引擎
    → 更新文档解析状态
```

核心函数：[rag/svr/task_executor.py](/data/zwt/ragflow/rag/svr/task_executor.py:272)

## 12. Word、PDF 和扫描版 PDF 的解析结论

### 12.1 Word / DOCX

```text
DOCX
    → DocxParser
    → 段落、图片、表格
    → 统一为 JSON 或 Markdown 结构
    → 切块
    → Embedding
    → 写入文档引擎
```

DOCX 解析结果会区分文本、图片和表格，例如：

```json
{
  "text": "段落内容",
  "image": null,
  "doc_type_kwd": "text"
}
```

表格可能被转成 HTML 或其他文本结构，并标记为 `table`。相关代码：[rag/flow/parser/parser.py](/data/zwt/ragflow/rag/flow/parser/parser.py)

### 12.2 文本版 PDF

```text
文本版 PDF
    → DeepDOC / PlainParser / MinerU / Docling
    → 版面、文本、表格和图片识别
    → section / bbox 结构
    → 归一化为 text / table / image
    → 切块
    → Embedding
    → 写入文档引擎
```

Pipeline Parser 可以在解析阶段输出 JSON 或 Markdown，但最终普通 RAG 使用的是切块后的 chunk，不是整份 JSON 或 Markdown 文件。

相关代码：

- [rag/flow/parser/parser.py](/data/zwt/ragflow/rag/flow/parser/parser.py)
- [rag/app/naive.py](/data/zwt/ragflow/rag/app/naive.py)
- [deepdoc/parser/pdf_parser.py](/data/zwt/ragflow/deepdoc/parser/pdf_parser.py)

### 12.3 扫描版 PDF

```text
扫描版 PDF
    → 页面图像
    → OCR / VisionParser / MinerU / PaddleOCR
    → 文字识别
    → 版面分析
    → 标题、段落、表格和图片识别
    → section / bbox
    → 切块
    → Embedding
    → 写入文档引擎
```

当前代码中没有发现默认把完整 OCR 中间结果额外保存成独立 `.txt` 或 `.json` 文件的逻辑。OCR 结果主要在解析流程中传递，最终进入 chunk。

如果项目需要保存 OCR 原文、坐标、置信度或页面级中间结果，需要单独增加持久化模型和存储逻辑。

```text
原始 Word / PDF / 扫描版 PDF
    → 对象存储

```

MySQL / PostgreSQL 保存：

```json
{
  "id": "chunk_id",
  "doc_id": "document_id",
  "kb_id": "kb_id",
  "content_with_weight": "正文内容",
  "content_ltks": "分词后的正文",

```

```text
图片 / 表格裁剪图
    → 对象存储

PDF outline / 文档级元数据
    → 文档元数据服务

```

## 14. 普通 RAG 数据流

### 14.1 普通 RAG 建库

```text
上传 Word / PDF / 扫描版 PDF
    → 原文件写入对象存储
    → MySQL 创建文档元数据
    → 提交解析任务
    → Redis 任务队列
    → 后台 Worker
    → PDF / DOCX / OCR 解析
    → 章节、段落、表格和图片识别
    → chunk 切分
    → 图片和裁剪图保存
    → chunk Embedding
    → 普通 chunk 写入文档引擎
    → 普通 RAG 索引完成
```

### 14.2 普通 RAG 问答

```text
用户问题
    → 问题预处理
    → 问题 Embedding
    → 向量检索 + 全文 / BM25 检索
    → 混合相似度计算
    → 可选 Rerank
    → Top-K 普通 chunk
    → 拼接知识上下文
    → 生成 Prompt
    → LLM 回答
    → 引用匹配和来源回填
```

普通 RAG 以文本 chunk 为中心，适合局部事实、段落问答、参数附近原文检索和操作步骤查询。

## 15. GraphRAG 数据流

### 15.1 GraphRAG 的输入

GraphRAG 不直接从原始 PDF 建图，而是读取普通 RAG 已经生成的 chunk：

```text
原始文件
    → 普通解析
    → 普通 chunk
    → GraphRAG 实体和关系抽取
```

因此，GraphRAG 是建立在普通 RAG chunk 之上的结构化检索层。

### 15.2 GraphRAG 任务触发

接口形式为：

```text
POST /api/v1/datasets/{dataset_id}/index?type=graph
```

调用链：

```text
客户端发起 GraphRAG 索引请求
    → dataset_api_service.run_index()
    → 创建 graphrag 任务
    → 任务写入 Redis 队列
    → 后台 Worker 消费任务
    → run_graphrag_for_kb()
    → 从文档引擎读取普通 chunk
```

### 15.3 实体和关系抽取

```text
普通 chunk
    → 按 token 合并为 GraphRAG 抽取批次
    → light / general LLM 抽取，或 ner 抽取
    → 实体名称、类型、描述和来源
    → 实体之间的关系、描述、关键词、权重和来源
    → 合并同一文档内重复实体和关系
```

当前支持的方法：

```text
light
    → 轻量 LLM 抽取，默认方法

general
    → 更完整的 GraphRAG 风格 LLM 抽取

ner
    → spaCy / NER 路径
```

主要代码：

- [rag/graphrag/general/graph_extractor.py](/data/zwt/ragflow/rag/graphrag/general/graph_extractor.py)
- [rag/graphrag/light/graph_extractor.py](/data/zwt/ragflow/rag/graphrag/light/graph_extractor.py)
- [rag/graphrag/ner/graph_extractor.py](/data/zwt/ragflow/rag/graphrag/ner/graph_extractor.py)
- [rag/graphrag/general/extractor.py](/data/zwt/ragflow/rag/graphrag/general/extractor.py)

### 15.4 文档子图

```text
实体记录 + 关系记录
    → 创建 NetworkX Graph
    → 实体成为节点
    → 关系成为边
    → 加入 entity_type、description、source_id 等属性
    → 清理无效节点和关系
    → 生成文档级子图
```

子图转为 NetworkX node-link JSON，并作为特殊 chunk 写入文档引擎：

```json
{
  "knowledge_graph_kwd": "subgraph",
  "source_id": ["document_id"],
  "content_with_weight": "node-link JSON"
}
```

### 15.5 知识库级全局图合并

```text
文档 A 子图
    + 文档 B 子图
    + 文档 C 子图
    → 获取知识库级锁
    → 读取已有全局图
    → 合并同名实体
    → 合并实体描述和来源
    → 合并相同实体对之间的关系
    → 累加关系权重
    → 重新计算 PageRank
    → 形成知识库级全局图
```

全局图作为特殊 chunk 保存：

```json
{
  "knowledge_graph_kwd": "graph",
  "source_id": ["doc_a", "doc_b"],
  "content_with_weight": "global node-link JSON"
}
```

### 15.6 图节点、边和子图转为检索数据

```text
全局图
    → graph chunk
    → subgraph chunk
    → entity chunk
    → relation chunk
    → 为实体和关系生成向量
    → 计算 PageRank
    → 计算 N-hop 邻居路径
    → 写入文档引擎
```

GraphRAG 使用的特殊类型包括：

```text
graph
    → 知识库全局图

subgraph
    → 文档级子图

entity
    → 单个实体记录

relation
    → 单条关系记录

community_report
    → 社区摘要报告
```

RAGFlow 当前主流程没有使用 Neo4j 保存 GraphRAG 主图，而是将图数据序列化后写回同一个文档引擎，通过 `knowledge_graph_kwd` 区分普通 chunk 和图数据。

### 15.7 实体消歧

实体消歧由 `resolution=true` 开启，默认配置为关闭：

```text
全局图
    → 按实体类型分组
    → 字符相似度 / 编辑距离生成候选实体对
    → 过滤数字差异明显的实体
    → 候选实体对批量送入 LLM
    → LLM 判断是否为同一实体
    → 合并同义实体或别名节点
    → 重连关系并合并重复边
    → 删除重复节点
    → 重新计算 PageRank
    → 更新 graph / entity / relation chunk
```

消歧过程的 checkpoint 保存在 Redis 中，支持任务中断后恢复。

主要代码：

- [rag/graphrag/entity_resolution.py](/data/zwt/ragflow/rag/graphrag/entity_resolution.py)
- [rag/graphrag/checkpoints.py](/data/zwt/ragflow/rag/graphrag/checkpoints.py)

### 15.8 社区发现和社区报告

社区阶段由 `community=true` 开启，默认配置为关闭：

```text
消歧后的全局图
    → Leiden / hierarchical Leiden 社区发现
    → 得到多个层级的社区
    → 收集社区实体和内部关系
    → 将实体表和关系表发送给 LLM
    → 生成社区摘要和 findings
    → 形成 community_report chunk
    → 写入文档引擎
```

社区报告典型结构：

```json
{
  "knowledge_graph_kwd": "community_report",
  "docnm_kwd": "冷却系统核心设备",
  "content_with_weight": {
    "report": "社区摘要文本",
    "evidences": "社区证据文本"
  },
  "entities_kwd": ["主循环泵", "蒸汽发生器"],
  "weight_flt": 0.82
}
```

主要代码：

- [rag/graphrag/general/leiden.py](/data/zwt/ragflow/rag/graphrag/general/leiden.py)
- [rag/graphrag/general/community_reports_extractor.py](/data/zwt/ragflow/rag/graphrag/general/community_reports_extractor.py)

### 15.9 GraphRAG 在线检索

```text
用户问题
    → KGSearch
    → LLM 分析查询实体和答案类型
    → 检索 entity chunk
    → 按实体类型和 PageRank 筛选
    → 检索 relation chunk
    → 对命中实体进行 N-hop 扩展
    → 检索 community_report
    → 综合实体、关系和社区结果
    → 生成 GraphRAG 虚拟 chunk
    → 加入 Prompt
    → LLM 生成答案
```

GraphRAG 检索上下文主要由三部分组成：

```text
Entities
    → 实体名称、描述和分数

Relations
    → 起点实体、终点实体、关系描述和分数

Community Reports
    → 社区标题、摘要和证据
```

检索器代码：[rag/graphrag/search.py](/data/zwt/ragflow/rag/graphrag/search.py)

## 16. 解析器与 FastAPI 的关系

本次分析确认：解析器不是一个独立 HTTP API，而是后台 Worker 调用的 Python 组件。

完整链路为：

```text
HTTP 上传请求
    → 保存原文件和文档元数据
    → HTTP 解析请求
    → 创建 Redis 任务
    → 后台 Worker
    → 调用 PDF / DOCX / OCR 解析器
    → chunk 切分
    → Embedding
    → 文档引擎
```

FastAPI 学习内容可以映射到 RAGFlow：

| FastAPI 概念 | RAGFlow 对应 |
| --- | --- |
| `@app.post()` | `@manager.route(..., methods=["POST"])` |
| `UploadFile` | Quart 的 `request.files` |
| Pydantic 请求模型 | RAGFlow 的请求校验模型和校验工具 |
| `BackgroundTasks` / Celery | Redis 任务队列 + Task Executor |
| `/docs` | QuartSchema / OpenAPI |
| `async def` / `await` | Quart 异步接口和后台异步逻辑 |

需要特别区分：

```text
async def
    ≠ 自动进入后台任务
```

耗时的 OCR、LLM 抽取和 Embedding 通常需要采用：

```text
API 接收请求
    → 创建 task_id
    → 立即返回
    → Worker 后台执行
    → 前端轮询任务状态
```

# 第三部分：甲方需求与二次开发边界

## 17. RAGFlow 原生或部分具备的能力

已确认具备或部分具备：

- Word / PDF 上传；
- 批量上传接口；
- PDF、DOCX 和扫描版 PDF 的基础解析；
- 章节、段落、表格和图片识别；
- OCR / 视觉解析；
- 文本切块；
- Embedding；
- 向量检索、全文检索和 Hybrid Search；
- Rerank；
- GraphRAG 实体关系抽取；
- 文档子图和知识库全局图；
- 可选实体消歧；
- Leiden 社区发现；
- 社区报告；
- GraphRAG 检索；
- 基础图谱可视化接口。

## 18. 明确需要二次开发的能力

### 18.1 工程化批量导入编排

甲方要求的不只是“可以批量上传”，还包括：

```text
批量导入编排
    → 分批处理
    → 并发控制
    → 失败自动重试
    → 指数退避
    → 断点续传
    → 限流
    → 进度监控
    → 失败隔离
```

这些需要在现有任务机制之上补充工程化编排服务。

### 18.2 参数提取

当前 RAGFlow 的 chunk 和通用 GraphRAG 实体关系抽取，不能直接满足工程参数结构化要求：

```text
参数名称
参数值
单位
适用条件
所属设备 / 部件
专业维度
来源章节
审核状态
```

需要建设：

```text
LLM 参数抽取
    + 规则引擎
    + 单位标准化
    + 复合参数拆分
    + 参数类型识别
    + 参数置信度
```

例如：

```text
“额定流量 640m³/h，额定扬程 36m”
    → 额定流量 = 640 m³/h
    → 额定扬程 = 36 m
```

### 18.3 PBS 和 SNS

当前 GraphRAG 默认实体类型不是核电设备层级模型，不能直接满足：

```text
核电站
    → 系统
        → 子系统
            → 设备
                → 部件
                    → 零件
```

需要补充：

- PBS 树模型；
- 系统、设备和部件识别；
- 参数到 PBS 节点的关联；
- 操作步骤、故障和备件到 PBS 节点的关联；
- SNS 编码生成和校验；
- PBS 与 SNS 的对应关系。

### 18.4 表格语义解析

RAGFlow 可以识别表格区域并转换为文本、HTML 或 Markdown，但以下业务语义需要二开：

- 故障现象—可能原因—处理措施三元组；
- 备件清单；
- 螺栓力矩表；
- 检查项表；
- 验收数据表；
- 参数对照表。

目标不是只保存表格文本，而是将其转换为结构化记录。

### 18.5 信息块

普通 chunk 不等于甲方要求的信息块。

信息块至少应包含：

```text
PBS 对象
    + 专业维度
    + 信息类型
    + 具体内容
    + 来源文档 / 章节 / 页码
    + 审核状态
    + 版本号
```

需要新建：

- 参数类信息块；
- 文档类信息块；
- 关系类信息块；
- 信息块与 PBS 对象的关联；
- 信息块的审核、修改和版本管理。

### 18.6 人工审核闭环

当前 RAGFlow 没有直接满足甲方要求的完整工程审核界面，需要开发：

```text
原文
    ↔ 解析结果
    → 人工确认 / 修改
    → 审核通过或驳回
    → 保存修改记录和版本
```

审核对象包括：

- 参数记录；
- 表格结构化记录；
- PBS 关联；
- 专业维度；
- 来源章节和页码。

## 19. 当前 GraphRAG 的边界

以下结论已经通过代码阅读确认：

1. GraphRAG 的主存储不是 Neo4j，而是同一文档引擎中的特殊 chunk。
2. 默认 GraphRAG 配置中，实体消歧和社区报告都关闭。
3. GraphRAG 的默认实体类型是通用类型，不是 PBS / SNS 专用类型。
4. 当前实体和关系的 `source_id` 主要记录到文档级，不能天然保证追溯到章节、页码、表格单元格和原始坐标。
5. 社区报告是 LLM 生成的摘要，适合主题概括，不应直接替代原始工程参数和验收数据。
6. GraphRAG 仍然依赖普通 RAG chunk 作为原始证据。

## 21. 尚未完全确认的事项

以下内容不作为已经完成的结论，后续需要继续验证：

1. `ty2ents` 类型到实体样本映射在当前建库流程中的完整写入位置尚未明确找到；检索侧存在读取逻辑，但需要确认实际生成方。
2. 扫描版 PDF 的 OCR 准确率不能只根据代码确认，需要用项目实际中文扫描文档进行评测。
3. RAGFlow 原生参数抽取不能直接保证甲方要求的 95% 准确率，需要建立测试集并评估。
4. 不同 API 是否同时执行普通 RAG 和 GraphRAG，需要根据具体接口和配置判断，不能假设所有入口都会自动混合检索。
5. 图谱节点、关系和社区报告是检索结构，不等同于已经人工审核通过的工程主数据。

## 22. 可直接复述的最终结论

```text
RAGFlow 的解析器不是独立 HTTP API，而是后台 Worker 调用的内部 Python 组件。

文件上传接口负责保存原文件和创建文档元数据；
解析接口负责创建异步任务；
后台 Task Executor 才真正调用 PDF、DOCX、OCR 等解析器。

普通 RAG 的主链路是：
文件 → 解析 → chunk → Embedding → 向量 / 全文检索 → LLM。

GraphRAG 的主链路是：
普通 chunk → 实体关系抽取 → 文档子图 → 全局图合并
→ 可选实体消歧 → 可选社区发现 → 实体 / 关系 / 社区检索 → LLM。

RAGFlow 已具备通用文档解析、OCR、切块、向量检索和 GraphRAG 能力，
但核电工程项目还需要补充参数提取、PBS、SNS、表格语义解析、信息块、
人工审核、版本管理和精确来源追溯等业务能力。
```
