# RAGFlow 文件活化实习工作记录

记录时间：2026-09-24  
项目背景：参与基于 RAGFlow 的文件活化项目，重点验证“文档上传、解析、分块、向量化、知识图谱生成、问答测评”全链路，并学习后端队列、任务执行、数据存储和故障排查方法。

> 本文只记录本次对话和实验中已经通过源码、后端状态或实际测试验证过的内容；不记录 API Key、临时闲聊和未验证猜测。

## 1. 我做过的工作

### 1.1 调研 RAGFlow 后端架构

阅读并确认了 RAGFlow 的核心运行结构：

- RAGFlow 后端主要分为 API Server 和 Task Executor 两类进程。
- API Server 负责接收前端/API 请求，例如创建知识库、上传文档、启动解析、启动图谱。
- Task Executor 是后台 worker，负责从 Redis Stream 队列取任务并执行真正的解析、分块、向量化、知识图谱抽取等耗时操作。
- 队列使用 Redis Stream，消费者组名为：

  ```text
  rag_flow_svr_task_broker
  ```

源码依据：

- `CLAUDE.md`：说明 API Server 与 Task Executor 是两类独立进程。
- `common/constants.py`：定义 `SVR_CONSUMER_GROUP_NAME = "rag_flow_svr_task_broker"`。
- `common/settings.py`：定义队列名格式，例如 `te.0.common`、`te.1.common`。
- `rag/svr/task_executor.py`：worker 消费 Redis 队列并处理任务。

### 1.2 验证文档上传、解析、入库流程

确认了一份文档从上传到可检索的大致链路：

1. 前端或 API 上传文件。
2. 后端 API 接收 multipart 文件。
3. 文件内容写入对象存储。
4. 数据库创建 document 记录。
5. 启动解析时，后端创建 task 记录。
6. task 被写入 Redis Stream 队列。
7. Task Executor 从队列取任务。
8. worker 读取文件内容。
9. parser 解析文档内容。
10. chunker 分块。
11. embedding 模型向量化。
12. chunk 写入文档索引存储。
13. document 状态变为完成。

关键源码位置：

- `api/apps/restful_apis/document_api.py`：上传接口。
- `api/db/services/file_service.py`：上传文档、创建文件和文档记录。
- `api/db/services/document_service.py`：启动解析、写入队列。
- `api/db/services/task_service.py`：任务创建、队列投递、重试相关逻辑。
- `rag/svr/task_executor.py`：任务消费和执行。
- `rag/svr/task_executor_refactor/task_handler.py`：重构后的任务处理入口。

### 1.3 验证知识图谱生成流程

确认知识图谱不是“上传文档后自动必然生成”，而是一个独立任务。

实际结论：

- 上传文档只负责创建文档记录，不直接生成图谱。
- 文档解析完成后才有 chunks。
- GraphRAG 图谱任务依赖已经存在的 chunks。
- 前端点击“生成知识图谱”后，会调用：

  ```text
  POST /api/v1/datasets/{dataset_id}/index?type=graph
  ```

- 后端将 `graph` 映射为 `graphrag` 任务，并写入专门的图谱任务队列。

源码依据：

- `api/apps/restful_apis/dataset_api.py`：`POST /datasets/<dataset_id>/index` 入口。
- `api/apps/services/dataset_api_service.py`：`run_index(..., index_type="graph")` 创建图谱任务。
- `api/db/services/document_service.py`：`queue_raptor_o_graphrag_tasks(..., ty="graphrag")` 将图谱任务写入 Redis。
- `rag/graphrag/general/index.py`：图谱任务读取 document chunks，进行实体关系抽取和图合并。
- `web/src/pages/dataset/dataset/generate-button/hook.ts`：前端按钮调用 `runIndex(id, 'graph')`。

实践建议：

- 为了追踪每一步耗时，应该先上传并解析文档，等文档分块完成后，再手动启动知识图谱。
- 不建议在排查阶段混在一起做，否则很难判断耗时来自解析、向量化、LLM 抽取还是图谱合并。

## 2. 实验与问题处理记录

### 2.1 批量上传与解析卡住问题

现象：

- 批量上传文档后，前端解析进度卡住。
- 有时 Redis 队列中存在大量旧任务或 pending 任务。
- 低优先级队列 `te.0.common` 曾经存在较多历史队列任务，影响后续测试判断。

排查结论：

- 前端卡住不一定是前端问题，本质上通常是后端 task 没完成。
- 要先看 Redis 队列的 `lag` 和 `pending`：
  - `lag` 大：任务还没有被 worker 取走。
  - `pending` 大：任务已经被 worker 取走，但没有 ACK，可能正在执行或卡死。
  - `pending=0` 但一直不动：要看 worker 是否还活着、是否有消费者。
- `XLEN` 很大不一定代表当前堵塞，因为 Redis Stream 可能保留历史消息；更关键的是消费者组里的 `lag` 和 `pending`。

### 2.2 Redis 队列和 worker 状态排查

已确认的队列类型：

- 普通解析队列：

  ```text
  te.0.common
  te.1.common
  ```

- 图谱/重任务相关队列：

  ```text
  te.0.graphrag
  te.1.graphrag
  te.0.raptor
  te.1.raptor
  te.0.mindmap
  te.1.mindmap
  ```

已确认的 worker 心跳机制：

- worker 会把自己注册到 Redis 集合：

  ```text
  TASKEXE
  ```

- 每个 worker 会用自己的名字作为 ZSET key 写心跳。
- worker 默认每 30 秒写一次心跳。
- 源码里死亡 worker 的清理阈值默认是 120 秒。
- 健康检查会读取最近 30 分钟的心跳。

相关源码：

- `rag/svr/task_executor.py`
- `api/utils/health_utils.py`

### 2.3 旧 pending / 历史队列任务处理

曾遇到的问题：

- 旧任务残留在低优先级队列中，造成后续测试时难以判断当前任务是否真的卡住。
- 后续目标变成“清掉旧 pending，不再复用旧任务，只保证当前 11 号知识库知识图谱任务生成”。

处理原则：

- 测试前先确认 Redis 队列是否健康。
- 对旧的、确认不再需要的 pending 或历史任务进行清理。
- 清理前必须确认目标队列和任务范围，避免误删当前正在执行的有效任务。
- 清理后重新上传/重新解析/重新生成图谱，保证实验链路干净。

### 2.4 知识图谱抽取失败与模型差异

现象：

- 使用某些模型生成知识图谱时，任务跑完但前端没有出现有效图谱。
- 曾经使用 `qwenplus` 抽取虽然慢，但可以形成图。
- 使用 `dsv4flash` 时曾出现无法有效抽取实体关系的问题。
- 后来使用 `glm5.2` 可以抽取实体和关系，并成功形成知识图谱。

已经核实的重要点：

- 不能把“问答模型”和“图谱抽取模型”混为一谈。
- 某次正式测试中：
  - 知识库解析/图谱抽取模型确认是 `glm5.2`。
  - 问答 chat assistant 模型是 `ds-v4flash`。

背后原因：

- GraphRAG/light 方法依赖 LLM 按提示词抽取实体和关系。
- 如果模型不能稳定按要求输出格式，后端解析不到有效实体/关系，就可能形成空图。
- 这不是单纯“文档数量太少”的问题，更多与模型对结构化抽取任务的稳定性、JSON/格式遵循能力、中文理解能力和提示词适配有关。

相关源码：

- `rag/graphrag/light/graph_extractor.py`
- `rag/graphrag/light/graph_prompt.py`
- `rag/graphrag/general/index.py`
- `rag/svr/task_executor_refactor/task_handler.py`

## 3. 我学到的后端知识

### 3.1 前端卡住时，后端可能发生了什么

前端显示“解析中”或进度不动，本质上通常是后端任务状态没有完成。可能原因包括：

- 任务还在 Redis 队列里没有被 worker 取走。
- 任务已被 worker 取走，但 worker 卡在某一步。
- worker 进程挂了，没有消费者。
- OCR / 版面分析 / parser 很慢。
- embedding 模型调用慢、限流或失败。
- ES / Infinity / OpenSearch 写入慢或失败。
- GraphRAG 调用 LLM 抽取实体关系慢、超时或输出格式不符合要求。
- 图谱任务启动太早，文档还没有成功分块，导致没有可用 chunks。

### 3.2 Redis 队列排查方法

连接 Redis 后，先查普通解析队列：

```redis
XLEN te.0.common
XLEN te.1.common

XINFO GROUPS te.0.common
XINFO GROUPS te.1.common

XINFO CONSUMERS te.0.common rag_flow_svr_task_broker
XINFO CONSUMERS te.1.common rag_flow_svr_task_broker

XPENDING te.0.common rag_flow_svr_task_broker
XPENDING te.1.common rag_flow_svr_task_broker
```

查图谱队列：

```redis
XLEN te.0.graphrag
XLEN te.1.graphrag

XINFO GROUPS te.0.graphrag
XINFO GROUPS te.1.graphrag

XINFO CONSUMERS te.0.graphrag rag_flow_svr_task_broker
XINFO CONSUMERS te.1.graphrag rag_flow_svr_task_broker

XPENDING te.0.graphrag rag_flow_svr_task_broker
XPENDING te.1.graphrag rag_flow_svr_task_broker
```

判断方法：

- `lag` 大：任务还没被取走。
- `pending` 大：任务被取走但没完成。
- 某个 consumer 的 `pending` 多且 `idle` 很大：对应 worker 可能卡住。
- `pending=0` 但任务一直不动：检查 worker 是否存在、是否有心跳、是否消费了正确队列。

### 3.3 worker 排查方法

查看 worker 注册情况：

```redis
SMEMBERS TASKEXE
```

查看某个 worker 的心跳：

```redis
ZREVRANGE task_executor_common_xxx_0 0 2 WITHSCORES
ZREVRANGE task_executor_special_xxx_0 0 2 WITHSCORES
```

容器内查看进程：

```bash
docker exec -it ragflow-server ps aux | grep task_executor
```

正常应看到类似：

```text
python rag/svr/task_executor.py -i xxx -t common
python rag/svr/task_executor.py -i xxx -t special
```

### 3.4 数据库排查方法

查知识库下文档状态：

```sql
SELECT
  id,
  name,
  run,
  progress,
  progress_msg,
  process_begin_at,
  process_duration,
  update_time
FROM document
WHERE kb_id = '<知识库ID>'
ORDER BY create_time DESC;
```

查普通文档任务：

```sql
SELECT
  id,
  doc_id,
  task_type,
  progress,
  progress_msg,
  retry_count,
  begin_at,
  process_duration
FROM task
WHERE doc_id = '<文档ID>'
ORDER BY create_time DESC;
```

查图谱任务：

```sql
SELECT
  id,
  doc_id,
  task_type,
  progress,
  progress_msg,
  retry_count,
  begin_at,
  process_duration
FROM task
WHERE task_type = 'graphrag'
ORDER BY create_time DESC
LIMIT 20;
```

状态理解：

- `run = 0`：未开始
- `run = 1`：运行中
- `run = 3`：完成
- `run = 4`：失败
- `progress = -1`：失败
- `progress_msg`：最关键字段，可用于判断任务停在哪一步

### 3.5 日志排查方法

按文档 ID 或 task ID 搜日志：

```bash
grep -R "<doc_id>" docker/ragflow-logs/
grep -R "<task_id>" docker/ragflow-logs/
```

图谱任务优先查：

```bash
grep -R "<task_id>" docker/ragflow-logs/task_executor*graphrag*.log*
grep -R "<doc_id>" docker/ragflow-logs/task_executor*graphrag*.log*
```

常见卡点：

- `Layout analysis`：OCR 或版面分析阶段慢。
- `Generate embedding`：embedding 模型调用慢、失败、限流。
- `Indexing`：写入索引存储慢或失败。
- `GraphRAG chunk_list returned 0`：文档没有可用 chunks，可能解析未完成或失败。
- `extracting entities / relations`：LLM 实体关系抽取阶段慢或失败。

## 4. 形成的关键结论

### 4.1 上传、解析、图谱是不同阶段

不能把“上传文件”等同于“解析完成”，也不能把“解析完成”等同于“知识图谱完成”。

更准确的链路是：

```text
上传文件
→ 创建 document
→ 创建解析 task
→ Redis 队列
→ worker 解析
→ 分块
→ embedding
→ chunks 入库
→ 手动启动 GraphRAG
→ 图谱任务队列
→ LLM 抽取实体关系
→ 合并图
→ 图谱数据入库
```

### 4.2 排查卡住问题要分层

遇到卡住时，不能只看前端。应该按顺序判断：

1. Redis 队列是否积压。
2. worker 是否存活。
3. document/task 表中的状态和进度。
4. 日志中具体异常。
5. 如果是图谱任务，再看 chunks 是否存在、LLM 是否能稳定抽取实体关系。

### 4.3 大批量上传时要谨慎

批量上传本身支持多个文件，但真正耗时在解析、OCR、embedding 和图谱抽取。

实践建议：

- 排查阶段不要一次性上传太多文件。
- 先用少量文档验证链路。
- 队列健康、worker 正常后再逐步增加数量。
- 上传失败或解析失败时，应根据 document/task 状态和日志定位，不要盲目重复上传。

### 4.4 知识图谱对 LLM 的结构化输出能力要求高

GraphRAG/light 的效果依赖模型能否稳定完成实体关系抽取。

经验结论：

- `qwenplus` 曾经可以抽取并形成图，但速度较慢。
- `dsv4flash` 曾出现实体关系抽取失败或空图问题。
- `glm5.2` 在本次地方法规测试中成功抽取实体和关系，并生成知识图谱。

因此，图谱失败时不能只怀疑文档数量，也要重点检查：

- 抽取模型是否适合结构化输出。
- 模型是否稳定遵守提示词格式。
- 后端是否解析到了实体和关系。
- 是否有 chunks 可供图谱任务读取。

## 5. 我的收获

### 5.1 技术能力收获

通过这次排查，我初步理解了 RAGFlow 文件活化的后端机制：

- 知道了文档上传、解析、分块、向量化、图谱生成不是一个同步接口完成的，而是多个异步任务串起来的。
- 学会了从 Redis Stream 的 `lag`、`pending`、consumer idle 判断任务是未消费、执行中还是卡死。
- 学会了用 `TASKEXE` 和 worker 心跳判断 task executor 是否活着。
- 学会了通过 `document` 和 `task` 表的 `progress_msg` 定位任务阶段。
- 学会了通过 task_id/doc_id 搜 task_executor 日志。
- 明白了知识图谱失败可能来自模型抽取能力，而不是单纯后端 bug。

### 5.2 工程排查方法收获

这次最大的收获是排查思路：

以前看到前端进度卡住，只能认为“系统坏了”。现在可以把问题拆成：

```text
请求是否发出？
任务是否入库？
任务是否进入 Redis？
worker 是否取走？
worker 是否 ACK？
任务卡在哪个 progress_msg？
日志里有没有异常？
模型输出是否符合后端解析要求？
```

这是一条比较完整的后端排查链路。

### 5.3 对 RAGFlow 的理解

RAGFlow 不是简单的“上传文件问答工具”，它背后包括：

- 文件存储
- 数据库元数据
- Redis 异步队列
- 后台 worker
- 文档解析器
- 分块策略
- embedding 向量化
- 文档索引存储
- LLM 抽取
- GraphRAG 图谱构建
- 检索和问答链路

这次实习工作让我从“只会点前端按钮”推进到了“能看后端状态、读源码、定位队列和任务问题”。

## 6. 后续建议

后续如果继续做文件活化项目，建议补充以下工作：

1. 做一份标准化排查脚本，只读状态，不自动删除任务。
2. 建立批量上传压测方案，记录不同文件数量、大小、类型下的解析耗时。
3. 分别统计上传耗时、解析耗时、embedding 耗时、图谱抽取耗时、图谱合并耗时。
4. 为常见失败场景整理错误码和日志关键字。
5. 对不同 LLM 的图谱抽取效果做对比测试，重点看实体数量、关系数量、空图率、耗时和失败率。
6. 在正式测试前固定模型、固定文档集、固定知识库配置，避免变量太多导致结论不清。
