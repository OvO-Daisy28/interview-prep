# RAGFlow / LightRAG 实习工作记录

> 记录范围：2026-08-31 至 2026-09-01 的 RAGFlow LightRAG 调研、实验和运行问题处理。  
> 记录原则：只保留聊天记录、实验日志和实际运行结果中能够核验的内容；未完成或证据不足的内容单独标注。

## 1. 实习目标

本阶段围绕 RAGFlow 的 LightRAG 能力开展调研，目标是回答：

1. 多份法律法规文档如何上传、解析、分块、向量化并生成知识图谱；
2. 每份文档与全局图的关系，以及一个知识库能否把多份文档合并成一张图；
3. 在当前部署、模型和 CPU 条件下，解析速度、图谱生成速度、问答速度和问答准确率如何；
4. 大批量上传时应如何分批、失败后如何重试；
5. 后续如何通过更大规模压测估计单图可容纳的文档量。

## 2. 我实际完成的工作

### 2.1 熟悉 RAGFlow 的核心链路

已跑通并观察过以下流程：

`上传文档 → 文档解析 → 分块 → Embedding 向量化 → LLM 实体/关系抽取 → 子图处理 → 全局图合并 → 图谱检索/问答`

对源码和运行链路的认识：

- RAGFlow 的 API 服务负责接收请求和维护任务状态；`task_executor.py` 是独立的后台执行器，消费 Redis 队列并执行解析、分块和图谱任务。
- 普通文档解析与 LightRAG 图谱任务不是同一个进程阶段；前者产生 chunks，后者基于可用 chunks 调用 LLM 抽取实体和关系。
- 每份文档先形成自己的局部/子图，随后进行实体解析、关系合并和全局图构建；因此不是“每份文档直接独立成为最终图”，而是“文档级抽取后合并为知识库级全局图”。
- 页面/API 的图谱展示存在返回上限；节点和边总数必须以 Elasticsearch 中 `knowledge_graph_kwd=graph` 的实际记录核验。

### 2.3 实验 A：qwen-plus 图谱与问答基线

- 知识库 ID：`890879fca52311f18159250f5cd0de4c`
- 图谱任务 ID：`75083b52a52a11f18a58f7d18c13f4d6`
- 抽取模型：`qwen-plus@1@Tongyi-Qianwen`
- 解析结果：10/10 DONE，共 92 chunks
- 首轮解析批次墙钟时间：约 33 分 36 秒；其中 3 份文档首轮停在约 80%，取消后重试成功
- 图谱抽取与合并耗时：567.19 秒（约 9 分 27 秒）

- 图谱失败数：5/10（按“未形成非空子图”统计）
- 解析失败数：0/10（以最终状态统计）

问答阶段：

- qwen-plus 对话请求 10 次均返回 DashScope `Access to model denied`，因此问答助手切换为已配置的 DeepSeek Flash 模型。
- 10 道固定问题答对 9 道，准确率 90%
- 平均端到端响应时间：9.786 秒
- P95：13.212 秒
- 唯一错误是答案没有命中标准答案要求的“表彰/奖励”，而是回答了相关待遇；属于答案生成/判定偏差，不是检索接口报错。

重要结论：

- 解析和图谱数据可以作为 qwen-plus 抽取基线。
- 问答速度和准确率不能归属于 qwen-plus，因为问答阶段实际使用的是 DeepSeek Flash。
- qwen-plus 当前不可作为后续实验模型；后续实验应先做单请求连通性和权限测试。

## 3. 已解决或定位的问题

### 3.1 89 个 DOCX 损坏

通过逐文件 `unzip -t` 核验，89 个 DOCX 确认损坏。它们与后续“模型调用超时/队列阻塞”问题要分开处理：损坏文件属于输入质量问题，不能用来解释所有解析失败。

### 3.2 任务进度卡在 60% 或 80%

实际运行中出现过文档长时间停在约 80% 或图谱进度不变。已确认需要区分三类状态：

1. 文档解析任务未完成，通常与执行器消费、模型请求或队列状态有关；
2. 文档虽有 chunks，但实体/关系抽取返回空结果；
3. 图谱全局合并仍在执行，页面进度条不能细粒度反映内部处理。

因此，不能只看前端百分比判断是否卡死，应同时检查任务状态、执行器进程、Redis pending、后端日志和 ES 结果。

### 3.3 取消任务后队列仍占用

已观察到取消任务后 Redis pending 中仍可能保留消息，旧执行器进程继续占用任务或消费状态未及时释放，导致后续任务排队。处理原则是：

- 先确认任务是否真的取消；
- 检查 common/special executor 是否存活；
- 检查 Redis stream pending 和后端日志；
- 只在确认 common executor 异常时处理对应 executor，不随意重启 RAGFlow、Redis 或删除全部数据；
- 失败重试只针对失败文档，不重复提交整批文档。

### 3.4 图谱中出现 0/0 子图

“0 nodes, 0 edges”不能直接解释为“文档实体太少”。目前更稳妥的判断是：模型返回为空、输出格式未被解析器识别、抽取调用失败，或原文确实缺少可抽取信息，都可能导致 0/0。必须结合原文、模型原始响应和后端日志进一步区分。

## 4. 模型与配置方面学到的知识

### 4.1 Embedding model 与 indexing/生成模型的区别

- Embedding model 把文本转换为向量，用于向量检索和相似度计算；它不负责生成实体、关系或自然语言答案。
- LLM/生成模型负责实体关系抽取、图谱摘要和问答回答。
- indexing 在 RAGFlow 语境中通常指把 chunks、向量、关键词和图谱记录写入索引；它不是一个与 embedding 完全等价的“第二个模型”。
- `bge-base` 适合作为当前向量化模型，但最终效果仍取决于语料、分块和检索配置。

### 4.2 Qwen、DeepSeek 与本地模型的使用经验

- 云端模型必须同时验证模型标识、Base URL、API 权限、余额和实际请求；页面中“已添加”不等于可调用。
- `qwen-plus` 的图谱实验可以提交，但其问答请求实际返回 `Access to model denied`，说明模型权限/账户状态需要单独确认。
- `deepreasoning-qw-3.8-max` 已完成单文档解析验证：1 份 DOCX 成功生成 9 chunks，耗时约 19.5 秒，可进入后续分批测试。
- 本地 Windows 环境曾核验 Ollama 运行中，已有 `qwen2:7b` 和 `gpt-oss:20b`；但机器为 NVIDIA GeForce GT 705、2GB 显存，主要走 CPU，不适合按高吞吐规划。该本地环境与服务器上的 RAGFlow 不是同一运行环境。

## 5. 目前可以给出的结论

1. RAGFlow LightRAG 可以把多份文档先生成文档级子图，再合并为一个知识库级全局图；10 份文档已经实际生成过全局图。
2. 当前没有完成“最大文档数”压测，因此不能声称 LightRAG 一张图最多支持多少文档。10 份只能作为已验证样本规模，不能作为上限。
3. 在当前 CPU、队列和模型调用条件下，建议先按 1～2 份文档分批解析；批次大小应通过逐步压测调整。
4. 解析失败时，应只重试失败文档，并先检查执行器、Redis pending 和日志。
5. QW 完整知识库的已验证问答指标为：平均 8.028 秒、P95 10.097 秒、准确率 90%。这是该 QW 知识库/固定题集的结果，不应泛化为所有数据集和所有模型。
6. 严格的 QW 与 DeepSeek Flash A/B 结果当时仍未完成；Flash 早期实验存在取消文档和重复 chunks，不能直接拿来比较。

## 6. 仍需继续验证的内容

- Flash 干净知识库重建的最终图谱节点数、边数、失败数和图谱耗时；
- 同一套问题下 Flash 的问答平均耗时、P95 和准确率；
- 10、50、100、1000 份文档的分批压测，确定单图规模和吞吐曲线；
- 不同批次大小下的成功率、队列积压和重试成本；
- 模型超时、空响应、解析器格式不兼容等失败原因的统计占比；
- 生产环境需要的执行器数量、Redis pending 告警和任务取消回收机制。

## 7. 对我能力提升的总结

通过本次工作，我掌握了：

- RAGFlow 从文档入库到 LightRAG 图谱和问答的完整链路；
- API 服务、后台执行器、Redis 队列、Elasticsearch 索引之间的职责关系；
- 如何区分解析失败、LLM 抽取失败、队列积压和前端进度显示不准确；
- 如何用任务状态、日志、Redis pending 和 ES 实际数据交叉验证，而不是只看页面进度条；
- 如何设计可复现实验：固定文档、模型、Embedding、分块参数、批次大小和问答题集；
- 如何识别“数据不完整、模型发生切换、队列重放”等会破坏实验公平性的因素；
- 云端模型的可用性必须通过真实请求验证，不能只看配置页面中的模型名称。
