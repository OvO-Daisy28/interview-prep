# RAGFlow 可行性评估项目经理汇报结论

> 汇报对象：项目经理内部评审
> 评估对象：RAGFlow v0.26.1 + MinerU，131 服务器现有部署
> 评估材料：PTR 冷却泵设备运行与维修手册、RAGFlow 源码归档、API/ES/Chat 实测证据
> 当前阶段：招投标前技术可行性评估与方案边界确认
> 结论状态：可行性评估阶段完成；规模专项与生产化专项待立项

## 一、先给结论

**RAGFlow 可以继续作为客户指定的主平台，但总体判断只能是“部分满足”，不能承诺原生 RAGFlow 已经具备上万份或 30 万份文档的稳定 GraphRAG 生产能力。**

当前已经证明：

- 普通 RAG 的导入、解析、分块、混合检索、问答和引用链路可用。
- RAGFlow 内置 GraphRAG 的实体/关系抽取、图合并、实体消歧、社区报告、KG 检索和 Chat 链路，在一份 PTR 手册上已完成闭环验收。
- RAGFlow 有图谱 API、Web 展示基础、源码、API、Python SDK 和 Apache-2.0 开源许可，具备二次开发前提。
- 普通 RAG 应作为默认检索链路；GraphRAG 应按问题类型和业务域按需启用，不应所有问题默认走最重路径。

当前没有证明：

- 需求背景的上万份或 30 万份同规模存储、建图、查询和长期稳定性。
- 采购要求的常规 2 秒、复杂 5 秒端到端问答目标。当前主要瓶颈在外部 LLM 调用、排队、网络往返和答案生成，不是单纯的 ES/图谱检索。
- GraphRAG 删除、修订、回滚后可以自动保持图谱、社区和引用的一致性。删除相关文件需要重新生成图谱，生产上需要版本治理和任务编排。
- 图谱导出、业务版本/时序节点/结构化置信度等完整治理能力。

因此项目可以收束在以下阶段目标：

> **完成 RAGFlow 招投标前的技术可行性评估、能力边界确认和二次开发路线设计。**

不再把法律域外部模型问题、独立 LightRAG 对比或 30 万份实测作为当前汇报前置条件。

## 二、项目经理四个问题的直接回答

### 1. RAGFlow 能不能承载几百、上万甚至 30 万份文档？

**普通 RAG：架构上可行，但本项目尚无同规模压测，不能给容量承诺。** RAGFlow 已具备批量导入、异步解析、chunk、embedding、全文/向量索引和检索 API。真正的容量边界取决于 chunk 总量、embedding 吞吐、文档引擎容量、内存、磁盘 I/O、worker 数量、并发和索引刷新策略。

**GraphRAG：架构上可以做，但原生直接承诺不足。** GraphRAG 还要承担实体/关系抽取、节点和关系 embedding、子图合并、实体消歧、社区发现和社区报告生成。文档规模扩大后，图合并、实体去重、社区重算和 LLM token 成本会成为主要风险。

建议生产方案采用：

```text
RAGFlow 主平台
  + 外置版本治理
  + 批量任务编排
  + 按设备/系统/专业分域
  + GraphRAG 分批构建
  + 必要时外置图存储
  + 统一检索路由与引用适配
```

### 2. 检索效率如何？

当前 72 条正式基准（12 题 × 2 轮 × 普通 RAG/General/Light）全部完成，结果如下：

| 系统 | E2E P50 | E2E P95 | E2E P99 | 独立检索 P50 | 规则覆盖率 |
|---|---:|---:|---:|---:|---:|
| 普通 RAG | 15.61s | 39.39s | 40.12s | 1.58s | 99.2% |
| GraphRAG General | 23.16s | 36.50s | 50.21s | 1.97s | 99.0% |
| GraphRAG Light | 22.56s | 58.86s | 76.23s | 2.38s | 88.3% |

采购目标是常规不超过 2 秒、复杂不超过 5 秒，**当前端到端目标未满足**。

但独立检索 P50 为 1.58～2.38 秒，说明当前主要瓶颈不是文档引擎查询本身，而是外部 LLM 的模型排队、网络往返、首 Token 等待、上下文组装和答案生成。`E2E - 独立检索` 只是诊断残差，不是服务端精确 Trace。

建议后续优先做：

- 查询路由：局部事实优先普通 RAG，关系/因果题按需启用 KG，全局汇总才使用 General 社区报告。
- LLM 服务并发、限流、缓存和流式首 Token 优化。
- 服务端 Trace，拆分检索、重排、KG 上下文、首 Token 和生成耗时。
- 按 1/10/100/1000/10000 份执行独立容量专项，而不是用单份 Demo 外推。

### 3. 文档更新怎么办？

- 普通 RAG 新增：上传后异步解析、分块、embedding 和索引，原生链路相对直接。
- GraphRAG 新增：可以触发数据集图谱更新，但要完成抽取、子图合并、消歧、社区处理，完成时间和失败风险不可忽略。
- GraphRAG 删除：不会自动完成图谱一致性更新，需要重新生成图谱。
- 文档修订：生产上应保存新版本、版本号、生效时间和来源关系，不建议直接覆盖旧文件。
- 回滚：需要版本治理层、影响范围分析和重建任务，RAGFlow 原生证据不足。

结论：**新增可接入，删除/修订/回滚属于部分满足，需要二次开发。**

### 4. 原生能力不足能不能在 RAGFlow 上二开？KAG 要不要替换？

**可以在 RAGFlow 上二开，不建议当前换主平台。** RAGFlow 有源码、API、Python SDK、前端和容器部署资产，建议先做外置治理和编排，再按瓶颈改 GraphRAG worker 或增加外置图存储。

优先二开模块：

| 优先级 | 模块 | 目标 |
|---|---|---|
| P0 | 版本治理 | 文档/设备/版本/生效时间/来源、审核、回滚、影响范围 |
| P0 | 导入编排 | 批量、断点、重试、限流、失败隔离 |
| P0 | GraphRAG 任务 | 分域、分批、增量子图、删除后重建、社区健康检查 |
| P0 | 容量观测 | 队列、token、节点/边/社区、索引占用、P95/P99、失败率 |
| P1 | 检索适配 | 普通向量/BM25 与图局部/全局融合、统一引用 |
| P1 | Web 展示 | 版本/时序过滤、来源回溯、任务状态和导出 |

KAG/OpenSPG 适合规则、数值、时序和强 Schema 推理，是独立平台，不是 RAGFlow 插件。它需要 Java、OpenSPG、MySQL、Neo4j、MinIO 等第二套技术栈，与当前 2 秒/5 秒目标方向也不一致。建议列入观察/备选名单；只有业务明确提出强规则推理且 RAGFlow 实测不达标时，再立项最小 PoC。

## 三、已经完成的 PTR 证据

PTR GraphRAG 修复后完成三层验收：

| 层次 | 结果 |
|---|---|
| 任务层 | `progress=1.0`、`ok=1`、`failed=0`，GraphRAG 合并 17 个输入块，总耗时约 1255 秒 |
| 图主体 | Graph API：256 个节点、128 条边；ES：614 个 entity、292 个 relation、1 个 graph、1 个 subgraph |
| 社区层 | 43 个 Leiden 候选社区；41 条社区报告成功落库；41/41 ID 唯一；`kb_id/source_id` 正确；已知污染词 0 |
| 检索层 | `use_kg=false` 返回 0 个社区块；`use_kg=true` 返回 1 个 `Related content in Knowledge Graph` 聚合块 |
| 问答层 | 固定题集 7/7 API/答案级成功；三系统正式基准 72/72 成功 |
| 内容层 | Q5 能回答泵盖、泵体、托架、机械密封、转子部件关系；Q6 能汇总 11 类故障特征 |

压力题虽然接口成功，但答案出现原文数据截断边界，不能把它表述为“所有故障清单完整覆盖”。

RAGFlow Light 的 A/B 结果：建图约 831 秒，比 General 的约 1255 秒快 33.76%，但图从 256/128 降至 36/27，社区从 41 降至 3，问答规则覆盖率为 88.3%。因此 Light 目前只能定位为成本较低但图更稀疏的候选模式，不建议作为默认模式，也不能等同于完整独立 LightRAG。

## 四、项目是否发生方向偏移？

**没有发生实质性方向偏移，但过程上曾经出现“继续跑实验、没有及时收束”的偏移。**

原始目标是评估 RAGFlow 能否支撑普通 RAG + GraphRAG，以及规模、效率、更新、二开和 KAG 选择。后来增加的普通 RAG 数据结构、GraphRAG 抽取/消歧/社区/可视化问题，是把“能不能用”细化成“如何存、如何追溯、如何解释、如何展示、如何问答”，与原目标一致。

当前已经达到合理收束节点：

- 平台选型：可以继续使用 RAGFlow。
- 单文档能力：普通 RAG 和 GraphRAG 闭环已验证。
- 性能结论：2 秒/5 秒未满足，瓶颈方向已定位。
- 规模结论：普通 RAG 具备架构可行性；GraphRAG 需要分域、编排和专项压测；万份/30 万份未验证。
- 更新结论：新增可触发；删除/修订/回滚需要治理层。
- 二开路线：明确，不需要先换平台。
- KAG 定位：观察/备选，不替换主链路。

## 五、建议项目状态与正式汇报话术

建议项目状态标记为：

```text
可行性评估阶段完成
整体结论：部分满足
规模专项与生产化专项：待立项
```

建议对项目经理直接说：

> RAGFlow 可以作为本项目普通 RAG + GraphRAG 的主平台继续推进。我们已经在 PTR 真实手册上验证了普通 RAG、GraphRAG 图谱、社区报告、KG 检索、问答和引用链路。GraphRAG 不是简单开关，单文档建图已经体现出较高的 LLM 和任务编排成本。当前端到端 2 秒/5 秒目标没有达到，上万份和 30 万份也没有做同规模实测，所以不能给生产容量承诺。推荐采用“RAGFlow 主平台 + 外置版本治理和任务编排 + 分域图谱 + 查询路由”的路线。删除、修订、回滚和版本/时序/置信度治理列为二次开发。KAG 先作为规则推理方向的备选，不建议现在替换 RAGFlow。

## 六、后续只保留两个专项

### 专项 A：规模与性能专项

目标：回答“几百、上千、上万份是否能稳定运行”。

最低范围：1/10/100 份；如资源允许再做 1000 份。指标包括导入成功率、chunk/实体/关系/社区增长、构建耗时、P50/P95/P99、资源峰值、失败率和索引占用。万份和 30 万份在容量规划前不承诺实测。

### 专项 B：生产化治理专项

目标：把 Demo 能力变成可运行系统。优先实现文档版本治理、批量任务状态机、删除/修订影响范围、图谱分域和重建、权限/引用隔离、服务端 Trace 和固定镜像发布。

当前不再作为本阶段前置条件的工作：

- 无限等待法律域外部 LLM 网关；
- 不断切换模型以跑通一份法律 GraphRAG；
- 用法律域五份文档替代规模压测；
- 把独立 LightRAG 或 KAG 的能力写成 RAGFlow 已完成能力；
- 未授权地继续删除 131 图谱、重启 worker 或覆盖运行时源码。
