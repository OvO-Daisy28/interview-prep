# RAGFlow 二开候选清单

> 定位：**哪些地方值得改 RAGFlow、改的收益与代价**。依据[决策 15](../../memory/decisions.md)——目标是交付好用的批量上传，RAGFlow 是手段不是约束。
> 判断标准：收益 vs 维护成本，不预设"不能改"，也不为改而改。
> 优先级由**真实性能数据**驱动（M2 批量实测后确定），当前排序是基于 M1 单份实测的初步判断。
> 最后更新：2026-08-19

## 一、判断框架

| 类型 | 判断 | 做法 |
|---|---|---|
| 编排层能做好的 | **不改内核** | 批量排队、优先级、失败隔离、状态聚合——本就是编排层职责 |
| 收益大 + 改动局部 | **直接改** | 例：`set_progress` 多报字段，风险低收益高 |
| 收益大 + 改动深 | **先隔离验证再改** | 例：worker 加暂停检查点，涉及任务生命周期 |
| 收益不明 | **等数据** | 先量化痛点再决定 |

所有内核改动必须满足[决策 10](../../memory/decisions.md) 工程约束：完整追踪调用链（避免坑#5 类漏改）、合入源码分支、回归测试、固定镜像、回滚路径。

## 二、候选清单（按初步优先级）

### C1. 结构化进度上报（收益大 / 改动局部）★★★

**痛点**（M1 实测）：RAGFlow 只暴露单浮点 `progress` + 累积文本 `progress_msg`，编排层被迫用正则"猜"当前阶段。为此修了 4 个 bug（关键词吃单、累积日志误判、漏 index 阶段、丢弃真实耗时），逻辑脆弱——RAGFlow 升级改一句日志文案就可能全线失效。

**现状代码**：`rag/svr/task_executor.py::set_progress(task_id, prog, msg)` 写 `Document.progress/progress_msg`。

**改法**：worker 在阶段切换时额外写结构化字段（新增 `Task.stage` / `Task.stage_started_at` / `Task.stage_duration_ms`，或写一个 JSON 列），编排层直接读，不再解析文本。

**收益**：消灭全部猜阶段逻辑；阶段与耗时变成契约而非日志格式的副产品；RAGFlow 升级不再随机打破映射。

**代价**：改 `set_progress` 调用点（约 20 处）+ DB 迁移加列。风险低——纯增量，不改既有行为。

**替代方案**：维持现状的文本解析（已实现，有 22 个真实样本回归测试兜底）。

---

### C2. Embedding 性能（收益最大 / 非源码改动）★★★

**痛点**（M1 实测）：单份 3.7MB docx 总耗时 130~166s，**embedding 占 60%+（81~115s）**，index 占 25%，真正的解析只占 6%。131 是 `docker-ragflow-cpu-1` —— **纯 CPU 部署无 GPU**。

外推：30w 份 × 165s ≈ 57 天（串行）。编排层限流做得再好，也是给慢引擎排队。

**改法（多选，成本递增）**：
1. **GPU 部署 embedding**（不改代码，改部署形态）——最直接
2. 换更快的 embedding 模型 / 换外部 embedding 服务
3. 调 `EMBEDDING_BATCH_SIZE`（`task_executor.py` 已有此配置）
4. 多 worker 并发（RAGFlow 默认单 worker，坑#1）

**收益**：直接决定 30w 份能否落地。这是**最值钱的一项**。

**代价**：1、4 是部署/配置层面，无源码风险；2 涉及模型评测（换模型要验证检索质量不降）。

**待验证**：131 能否上 GPU？多 worker 实际吞吐提升多少？→ M2 批量实测 + 阶梯压测回答。

---

### C3. 真正的暂停/恢复（收益中 / 改动深）★★

**痛点**：RAGFlow 无暂停能力，只有 `has_canceled` 硬取消（阶段边界轮询）。编排层只能提供：
- 软停：等当前 RAGFlow 任务跑完（GraphRAG 建图 21 分钟，暂停要等 21 分钟）
- 硬停：`DELETE /chunks` 取消，恢复时整份重跑（已跑的进度全废）

两者都不是业界意义上的"暂停"。

**改法**：worker 主循环（`task_executor.py` 的 chunk/embed/index 各阶段）加暂停检查点：检测到暂停标志时**保存 checkpoint 并挂起**，恢复时从 checkpoint 继续。

**收益**：真暂停真恢复，长任务（GraphRAG 建图、大文档 embedding）不用推倒重来。

**代价**：**高**。涉及任务生命周期、中间状态持久化、Redis 消息 ack 语义。需隔离验证。坑#5 的教训（改一处漏一处导致数据丢失）在这里风险最大。

**替代方案**：维持"软停 + 硬停"双模式（已实现）。多数场景够用——真正需要"暂停超长任务且不丢进度"的场景有多频繁，待业务确认。

---

### C4. 自动重试（收益中 / 改动局部）★★

**痛点**：`Task.retry_count` 字段在 DB 里存在，但 `task_executor.py` **无消费逻辑**——RAGFlow 从不自动重试，失败即终态。编排层只能重新触发整个流程。

**改法**：worker 捕获可重试错误（网络抖动、模型限流、临时 IO 失败）时按退避策略自动重试，写 `retry_count`。

**收益**：瞬时故障不再需要人工/编排层介入。大批量场景下，偶发失败率 × 30w 份 = 大量人工干预。

**代价**：中。要区分**可重试错误**（网络/限流）和**不可重试错误**（文件类型不支持——M1 实测遇到过）。误重试不可恢复错误会浪费大量算力。

**替代方案**：编排层重试（已实现），代价是整份重跑。

---

### C5. 事件推送替代轮询（收益中 / 改动中）★★

**痛点**：编排层每 2~3 秒 HTTP 轮询一次文档状态。M1 实测一份文档轮询了 140 次。批量 100 份并发时轮询压力线性增长，且状态更新有延迟。

**改法**：worker 阶段切换时发事件（Redis pub/sub 或 webhook），编排层订阅。

**收益**：状态实时、无轮询开销、大批量下省大量请求。

**代价**：中。要处理事件丢失（需保留轮询兜底）、顺序、重复。

**替代方案**：维持轮询 + 动态调整轮询间隔（长任务降频）。

---

### C6. 队列可观测（收益中 / 可能无需改内核）★

**痛点**：RAGFlow 的 Redis Streams 队列对外不可见，编排层只能维护自己的状态视图，无法回答"RAGFlow 内部还积压多少"。

**改法**：`rag/utils/redis_conn.py` 已有 `queue_info` / `get_pending_msg` / `get_unacked_iterator` 等完备能力（源码已确认），**可能只需加一个只读 API 暴露出来**，不用改内核逻辑。

**收益**：批量导入时能看到真实积压深度，限流可以基于真实队列水位而非固定并发数。

**代价**：低——只读接口。

---

## 三、当前不打算改的

| 项 | 理由 |
|---|---|
| 批量排队 / 优先级 / 失败隔离 / 状态聚合 | 编排层职责，改内核反而耦合 |
| 换主平台（迁移到别的 RAG 框架） | 甲方指定 RAGFlow + MinerU；换栈须证明指标不低于并经评审 |
| GraphRAG 算法本身（社区发现、消歧策略） | POC 已验证可用；当前瓶颈不在算法质量 |

## 四、下一步

1. **M2 批量实测**（10 份）→ 拿到并发下的真实数据：吞吐、队列积压、失败率、embedding 占比
2. 用数据确定 C1~C6 的**真实优先级**（当前排序是单份数据的初步判断）
3. 高优先级项逐个：隔离验证 → 改 → 回归测试 → 固定镜像（决策 10）

**原则**：不拍脑袋改，也不因"决策 8 说过不改"而绕路。数据说话。
