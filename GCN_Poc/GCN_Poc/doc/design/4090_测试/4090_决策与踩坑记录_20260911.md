# 4090 GPU 压测与服务部署：决策与踩坑记录

> 日期：2026-09-11 · 关联报告：`4090_GPU压测_20260911.md` · 范围：4090 上跑 GPU 压测 + 部署 mentor 常驻服务前端上传对比

本文记录 2026-09-11 在 4090（10.148.4.21）上做 GPU 压测和 mentor 服务部署过程中的关键决策与踩坑，作为后续万份测试和二开的参考。

---

## 一、决策记录

### D1. embedding 指向用 `--embed-url` 参数，不改脚本常量

**背景**：`mentor_b_bench.py` 构造 `SelfRunPipeline` 时没传 `embed_url`，用默认值 `http://192.168.80.1:18001/v1`（131 的 CPU embedding）。4090 上跑会错误指向 131。

**决策**：给 `mentor_b_bench.py` 加 `--embed-url` argparse 参数，默认保留 `http://192.168.80.1:18001/v1`（131 兼容），4090 跑时传 `http://bge-gpu:18001/v1`。KB/tenant 用现成的 `--kb-id`/`--tenant-id` 参数传，不改 `KB_NORMAL`/`TENANT` 常量。

**为什么**：向后兼容，不污染 131 基准脚本。131 和 4090 用同一份代码，只差启动参数。改动只 2 行（加 argparse + 传参）。

### D2. mentor 服务用 in-memory 模式，不用 MySQL

**背景**：`service.py` 默认用 `MySQLRepository` 持久化。但 `MySQLRepository` 用 `threading.local()`，在 ThreadPoolExecutor 并发下连接会断导致任务全失败（已知 bug，交接文档记录）。

**决策**：`service.py --in-memory` 跑，用 `InMemoryRepository`。和脚本压测同口径，绕开 MySQL 并发 bug。

**为什么**：用 MySQL + 并发3 会全失败，没有可用的对比数据。in-memory 和脚本压测（也走 InMemory）口径一致，能直接对比出服务层开销。状态不持久化是代价（重启丢进度），但 100 份测试一次跑完，不需要断点恢复。

**后续**：若要万份长跑 + 断点恢复，必须先修 `MySQLRepository` 的 `threading.local()` bug（改成连接池或 per-task 连接），或用并发1（不真实）。

### D3. fastapi + annotated-doc 走 docker relay，不走 pip

**背景**：4090 容器缺 fastapi（mentor 服务依赖）。4090 对持续大文件下载普遍卡死（pip/uv/PyPI 都卡，吞吐 0，交接文档「4090 网络结构性限制」明确警告）。

**决策**：从 131 容器（跑过完整 mentor 服务，fastapi 齐全）docker relay。torch 5.2G relay 已验证此路径可行，fastapi 是纯 Python 小包，秒级完成。

**为什么**：torch relay（131→本机→4090 容器）是 4090 上唯一可靠的搬大文件路径。pip 赌小包不卡不靠谱（交接文档说"普遍卡死"）。

### D4. 端口暴露用 demo_forward.py 转发，不改容器端口映射

**背景**：mentor 服务在容器内监听 9800，但 4090 的 `docker-ragflow-gpu-1` 容器没映射 9800 端口。重建容器改 compose 会中断 RAGFlow 服务。

**决策**：在 4090 宿主机跑 `demo_forward.py`（stdlib only，兼容系统 python3.10），转发 `0.0.0.0:9800 → 容器172.22.0.6:9800`，不动容器。

**为什么**：131 就是这么做的（`demo_forward.py` 转发 host:9800 → 容器:9800），验证过的低风险方案。重建容器有中断 RAGFlow 的风险（6 容器 unless-stopped，重启连锁）。

### D5. 每次测试新建独立 KB，避免数据污染

**背景**：第一次脚本压测用了 `--kb-id 1e427314…`（「9.10测试」KB，原 1 份文档），跑完 100 份后变 101 份，脏了。后续对比无法区分哪批数据。

**决策**：写 `create_kb.py` 脚本，每次测试前建新 KB。走 RAGFlow 自己的 service 层（`create_with_name` + 继承租户默认 `embd_id` + `save`），和 web 界面建库一致。

**为什么**：干净基线是对比的前提。建库走 service 层（不走 HTTP API，不需要 API key；不直接插 MySQL，避免漏关联表）。

### D6. KB 共用 tenant 级 ES index，建库无需 init ES

**背景**：`SelfRunPipeline` 写 chunk 时假设 ES index 已存在（`selfrun_writer.bulk_index_chunks` 注释）。

**决策**：调研 RAGFlow 建库流程（`dataset_api_service.py`），确认建 KB 只需 `create_with_name` + 设 `embd_id` + `save` 插 knowledgebase 表，**无 init_kb / create_bucket 步骤**。ES index 是 tenant 级别（`index_name(tenant_id)` = `ragflow_<tenant>`），新 KB 共用，按 `kb_id` 字段过滤。MinIO bucket=kb_id 在首次写数据时自动建。

**为什么**：直接插 knowledgebase 表不 init ES 会导致 SelfRunPipeline 写 chunk 失败。用 RAGFlow service 层建库保证 ES index 已存在（tenant 之前有 KB，index 已建）。

## 二、踩坑记录

### P1. `mentor_b_bench.py` 默认 embed_url 指 131，4090 跑会调 131 CPU

**现象**：脚本 `SelfRunPipeline` 默认 `embed_url = "http://192.168.80.1:18001/v1"`（131 的 CPU embedding 服务）。交接文档说"压测脚本要改指向 4090 的 RAGFlow：改成 http://10.148.4.21:9388 + API key"——**这个说法是错的**，脚本不走 HTTP API，是在容器内直接调 Python 模块。

**根因**：交接文档作者误以为脚本走 HTTP API（像 `native_upload_test.py`），实际 `mentor_b_bench.py` + `SelfRunPipeline` 是容器内自建流水线，embedding 走 `embed_url` 的 HTTP 调用（但调的是 embedding 服务，不是 RAGFlow API）。

**解法**：加 `--embed-url http://bge-gpu:18001/v1` 参数（见 D1）。交接文档的"改 API + key"说法是误导，实际改的是 embedding 服务地址。

### P2. ingest 包不在 4090 容器内

**现象**：`docker exec ... ls /ragflow/ingest/*.py` 返 0 个文件。4090 是新部署的 RAGFlow，没有 ingest 包。

**根因**：ingest 包是本地开发的（`f:\byh\…\code\ingest\`），131 容器有（之前传过），4090 没有。

**解法**：`tar --exclude='__pycache__' -C code/ingest -cf - . | ssh 4090 "docker exec -i ... tar -C /ragflow/ingest -xf -"`。秒传（约 300KB py）。依赖（requests/docx/xxhash/pymysql）4090 容器全有，import 不缺包。

### P3. fastapi 缺失 + 依赖链逐个踩坑

**现象**：relay fastapi 后 import 失败 `No module named 'annotated_doc'`。

**根因**：fastapi 0.141.1（131 上的版本）引入了新依赖 `annotated-doc`。其他依赖（starlette/pydantic/anyio/h11/click 等）4090 全有，但 `annotated-doc` 和 `typing-inspection` 是 4090 没有的。实际查下来 `typing-inspection` 4090 有（0.4.2），只缺 `annotated-doc`。

**解法**：用 `importlib.metadata.requires("fastapi")` 查完整依赖树，对比 131/4090 两边，只 relay 缺的 `annotated-doc`（+ dist-info）。教训：不要逐个 import 踩坑，先用 `requires()` 一次性查清依赖树。

### P4. ssh nohup 后台进程持有 stdout 导致 ssh 挂起

**现象**：`ssh root@4090 "nohup python3 demo_forward.py > log 2>&1 & sleep 1 && echo started"` 超时 120s。实际进程已启动（"forward started" 已输出），但 ssh 不退出。

**根因**：nohup 后台进程的 stdout/stderr 继承自 ssh 的通道，ssh 会等所有持有 stdout 的进程退出才关闭连接。`&` 后台 + `sleep` + `echo` 的组合让 ssh 认为还有输出。

**解法**：分步做——先 scp 文件，再单独 `ssh ... "nohup ... &"` 启动，用 `</dev/null` 重定向 stdin 或 TaskStop 掉挂起的 ssh（nohup 已 detach，进程不会被杀）。后续启动后台进程用 `nohup ... </dev/null >log 2>&1 &`。

### P5. `demo_forward.py` 的 TARGET_HOST 要改容器 IP

**现象**：直接用 131 的 `demo_forward.py`，TARGET_HOST = `192.168.80.6`（131 容器 IP），转发到错误地址。

**根因**：131 和 4090 的 RAGFlow 容器 IP 不同。4090 容器 IP = `172.22.0.6`（`docker inspect ... --format '{{.IPAddress}}'`）。

**解法**：`sed -i 's/192.168.80.6/172.22.0.6/' /root/demo_forward.py`。启动前用 `docker inspect` 确认容器 IP，不要照搬 131 的。

### P6. `TenantService` 的 import 路径不在 `tenant_service`

**现象**：`from api.db.services.tenant_service import TenantService` → `ModuleNotFoundError`。

**根因**：RAGFlow 的 `TenantService` 在 `api.db.services.user_service`（和 UserService/UserTenantService 一起）。

**解法**：`grep -n "TenantService" dataset_api_service.py` 找到正确 import：`from api.db.services.user_service import TenantService`。

### P7. `api_token` 表无 id 列，租户没生成过 API key

**现象**：`SELECT id FROM api_token` → `Unknown column 'id'`。查 token 也为空。

**根因**：`api_token` 表主键是 `token`（无 id 列）。且 admin's Kingdom 租户从没在 web 上生成过 API key。

**解法**：放弃用 RAGFlow v1 HTTP API 建 KB（需要 API key）。改用容器内 Python service 层建 KB（`create_with_name` + `save`），不走 HTTP、不需要 API key。

### P8. 脚本压测写数据会污染 KB

**现象**：「9.10测试」KB 从 1 份变 101 份。

**根因**：`mentor_b_bench.py --kb-id <KB>` 的 `SelfRunPipeline` 直接把 chunk 写进该 KB 的 ES index + MinIO bucket + MySQL document 表。没有"每次测试新建 KB"的机制。

**解法**：见 D5，写 `create_kb.py`，每次测试前建新 KB。这是用户明确要求，也是对比测试的基本卫生。

### P9. mentor 服务 worker 吞吐比脚本慢 24%

**现象**：mentor 服务前端上传 100 份，吞吐 0.786 份/s，脚本压测 1.029 份/s，慢 24%。

**根因**（分析）：worker 每 2s 轮询 + `run_batch(limit=3)` 反复创建/销毁 ThreadPoolExecutor（100 份分 34 批）+ REST 上传文件落地到 `/tmp` 再建 job 的开销。embed 本身反而更快（warm-up 启动时付了）。

**解法**（待定）：若要提升服务吞吐，优化 worker 模型——改成常驻线程池（不每次创建）+ 上传后直接提交（不落地 tempfile）+ 降低轮询间隔。当前 0.786 份/s 对 demo 够用，优化优先级低于万份实测。

### P10. 前端上传 HTTP 500：文件名超长触发 ENAMETOOLONG

**现象**：千份前端上传报 `HTTP 500`，service.log 报 `OSError: [Errno 36] File name too long: '/tmp/gcn_uploads/baeeb966_1994-11-07_最高人民法院…问题的答复.docx'`。

**根因**：`rest_api.py` upload 暂存逻辑用 `{uuid前8位}_{原文件名}` 做磁盘文件名。法律文档名常超 255 字节（如「1994-11-07_最高人民法院、最高人民检察院、公安部、劳动人事部研究室关于对无期徒刑犯减刑后原审法院发现原判决确有错误予以改判，原减刑裁定应如何适用法律条款予以撤销问题的答复.docx」），加前缀后超过 Linux 文件名 255 字节上限（ENAMETOOLONG）。单份文件名超长就让整个上传请求 500。

**解法**：`rest_api.py` upload 暂存名改用**纯 uuid**（`f"{uuid.uuid4().hex}.docx"`，32 字节固定短），原文件名只存进 `staged` 的 `name` 字段（pipeline 用 name 做 doc_name，不依赖磁盘文件名）。改后传容器 + 重启服务，千份上传 1000/1000 成功。

**教训**：用户上传的文件名不可控，做磁盘暂存时不要用原文件名做路径，用 uuid 隔离。百份时没触发是因为那 100 份文档名较短。

## 三、关键命令速查（4090，可复用）

```bash
# 建新 KB（每次测试前跑）
ssh root@10.148.4.21 "docker exec docker-ragflow-gpu-1 /ragflow/.venv/bin/python3 \
  /ragflow/ingest/create_kb.py --name '测试_<日期>' --tenant-id 8a0845faace211f1850e49f1b996babd"

# 启动 mentor 服务（in-memory, GPU, 并发3）
ssh root@10.148.4.21 "docker exec -d docker-ragflow-gpu-1 bash -c \
  'export GCN_TENANT_ID=8a0845faace211f1850e49f1b996babd \
   EMBED_BASE_URL=http://bge-gpu:18001/v1 GCN_MAX_CONCURRENT=3 PYTHONPATH=/ragflow; \
   cd /ragflow && nohup /ragflow/.venv/bin/python3 -m ingest.service \
   --host 0.0.0.0 --port 9800 --in-memory > /ragflow/ingest/service.log 2>&1 &'"

# 启动端口转发（宿主机）
ssh root@10.148.4.21 "nohup python3 /root/demo_forward.py > /tmp/demo_forward.log 2>&1 </dev/null &"
# 前端访问 http://10.148.4.21:9800/demo

# 脚本压测（容器内，GPU embedding）
ssh root@10.148.4.21 "docker exec docker-ragflow-gpu-1 /ragflow/.venv/bin/python3 \
  /ragflow/ingest/mentor_b_bench.py \
  --kb-id <新KB> --tenant-id 8a0845faace211f1850e49f1b996babd \
  --embed-url http://bge-gpu:18001/v1 \
  --docs-dir /ragflow/ingest/_abtest_docs --docs-json /ragflow/ingest/ab_doc_list.json \
  --count 100 --concurrency 3 --label gpu_c3 --out /ragflow/ingest/bench_gpu_c3.json"
```
