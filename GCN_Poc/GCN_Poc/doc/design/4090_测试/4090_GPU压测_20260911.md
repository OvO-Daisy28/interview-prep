# 4090 GPU 批量导入压测报告

> 环境：4090 服务器（10.148.4.21，RAGFlow v0.26.1，GPU bge-base on GPU2 cuda:0，bge-gpu 容器 18001）· 日期：2026-09-11
> 对照：131 服务器（CPU bge-base，embedding 服务 192.168.80.1:18001）的 bench_c3（50 份并发3）

## 一、背景

131 的 CPU 压测已收尾，结论：embedding 是绝对瓶颈（占 87%–96%），万份吞吐因 embedding 长尾堵塞并发槽崩塌至 0.046 份/s（比 50 份降 74%）。4090 上 bge-gpu 已部署完成（GPU2，device=cuda:0），本阶段跑 GPU 压测，验证 GPU 消除长尾后端到端吞吐能提多少。

## 五、核心结论

1. **GPU 把 embedding 从绝对瓶颈拉下来了**：占比 93.6% → 51.2%，avg 15.3s → 1.46s（快 10.5 倍）。长尾 max 72.8s → 8.9s（降 8.2 倍），GPU 独占无争抢的效果兑现——这正是 131 万份吞吐崩塌的真凶被根治的直接证据。

2. **吞吐快 5.7 倍而非 10.5 倍，符合 Amdahl 定律**：embed 占 93.6% 时提速 10.5×，理论吞吐提升 = 1/(0.064 + 0.936/10.5) ≈ 6.5×，实际 5.7×。差距来自 **index 写入（ES bulk + MinIO + MySQL）成了新瓶颈，占比从 6.1% 升到 42.7%**。下一阶段若要进一步提升吞吐，优化方向已从 embedding 转向 index。

3. **GPU 的价值远大于单条提速比例**：单条 embed 快 10.5×，但吞吐受 index 瓶颈约束只快 5.7×；而 131 万份崩塌的根因（embed 长尾 max 556s 堵塞并发槽）在 GPU 上被消除（max 8.9s），这意味着 **万份长跑下 GPU 的吞吐优势会随规模放大而扩大**，不会出现 131 那种 74% 的退化——但这需要万份实测确认。

## 五之二、mentor 服务 vs 脚本压测（同 GPU，验证服务层开销）

在 4090 上把 mentor 的常驻服务（`service.py` + REST API + worker）部署起来，前端 demo 上传 100 份，与脚本压测（`mentor_b_bench.py`）同口径对比，看服务层引入多少开销。

| 指标 | 脚本压测（mentor_b_bench） | mentor 服务（前端上传） | 差异 |
|---|---|---|---|
| 墙钟 | 97.2s | 127.2s | +31% |
| **吞吐** | 1.029 份/s | 0.786 份/s | **-24%** |
| embed avg | 1.46s | 1.21s | 更快（warm-up 启动时已付） |
| embed max | 8.90s | 5.74s | 长尾更小 |
| embed 占比 | 51.2% | 45.4% | — |
| index avg | 1.22s | 1.375s | +13% |
| index max | 10.22s | 14.43s | +41% |
| **index 占比** | 42.7% | **51.6%** | 成绝对瓶颈 |
| parse 占比 | 6.0% | 3.0% | — |

**结论**：

1. **服务层有 ~24% 吞吐损失**（0.786 vs 1.029）。来源：worker 每 2s 轮询 + `run_batch(limit=3)` 反复创建/销毁 ThreadPoolExecutor（100 份分 34 批）+ REST 上传文件落地到 `/tmp` 再建 job 的开销。
2. **embed 本身反而更快**（avg 1.21 vs 1.46，max 5.74 vs 8.9）：service 启动时一次性付了 16s warm-up，每份文档不再承担冷启动。
3. **index 是新的绝对瓶颈（51.6%）且长尾更大**（max 14.4 vs 10.2）：service 模式下 worker 轮询让 ES bulk 的刷新间隔更碎片化，document + file + file2document 三行 MySQL 的写入也更分散。

**一句话**：GPU 把 embedding 拉下神坛后，**index 写入（ES bulk + MinIO + MySQL 三表）是新的绝对瓶颈**，脚本/服务模式都占 43%–52%。服务层额外引入 ~24% 吞吐损失，来自 worker 轮询模型而非 embedding。

**服务部署方式**（详见决策与踩坑记录）：
- in-memory 模式（绕开 MySQLRepository 并发 bug），`EMBED_BASE_URL=http://bge-gpu:18001/v1`，并发3。
- 宿主机 `demo_forward.py` 转发 `0.0.0.0:9800 → 容器172.22.0.6:9800`，不改容器端口映射。
- fastapi + annotated-doc 从 131 容器 docker relay（4090 pip 装包卡死）。
- 独立 KB「GPU服务测试_0911」（`8892ca7c…`），保证干净基线。

## 六、待实测（万份）

用户暂缓万份，当前结论基于 100 份。万份需验证的关键假设：

| 假设 | 预期 | 风险 |
|---|---|---|
| embed 长尾不随规模放大 | max 应维持在 ~10s 级（131 万份 max 556s） | bge-gpu 容器 GPU 独占，无 CPU 争抢，长尾应稳定 |
| index 是否出现长尾退化 | index 100 份 max 10.2s，万份待测 | index 走 ES bulk + MinIO + MySQL，长跑下 ES 刷新/MySQL 连接可能抖动 |
| 吞吐是否随规模退化 | 100 份 1.029 份/s，万份应接近（131 从 0.180 退到 0.046，降 74%） | 若 index 成新长尾源，可能仍有退化 |
