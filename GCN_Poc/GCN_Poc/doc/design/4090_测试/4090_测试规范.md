# 4090 GPU 测试规范

> 制定于 2026-09-11 · 适用 4090 服务器（10.148.4.21）GPU bge-base 部署完成后的规模测试
> 关联：`4090_GPU压测_20260911.md`（已完成的 100 份 baseline）、`4090_决策与踩坑记录_20260911.md`（部署踩坑）

## 一、测试目标

131 CPU 测试已收尾，结论：embedding 是绝对瓶颈（87%–96%），万份吞吐因 embedding 长尾（max 556s）堵塞并发槽崩塌至 0.046 份/s（比百份降 74%）。

4090 测试要回答：**GPU 消除 embedding 长尾后，规模放大下吞吐能否守住？** 具体验证：

1. GPU embedding 长尾是否消除（100 份已验证：max 8.9s vs 131 的 72.8s）
2. 规模放大（100 → 1000 → 1 万）下吞吐是否退化（131 从 0.180 退到 0.046，降 74%）
3. index 写入成新瓶颈（42.7%）后，长跑下 index 是否有长尾退化
4. mentor 服务端到端吞吐（含 REST API + worker + 前端上传开销）vs 131 的对比

## 四、测试前准备（每次必做）

### 4.1 确认服务状态
```bash
ssh root@10.148.4.21 "docker ps --format '{{.Names}} {{.Status}}' | grep -iE 'ragflow|bge-gpu|es01|mysql|minio|redis'"
# 期望：6 容器全 running
# 确认 bge-gpu device
ssh root@10.148.4.21 "docker exec bge-gpu python3 -c 'import urllib.request;print(urllib.request.urlopen(\"http://127.0.0.1:18001/health\").read().decode()[:90])'"
# 期望 device:cuda:0
```

### 4.2 确认 mentor 服务在跑
```bash
ssh root@10.148.4.21 "docker exec docker-ragflow-gpu-1 bash -c 'ps aux | grep ingest.service | grep -v grep'"
# 若不在跑，启动（见决策与踩坑记录的命令速查）
```

### 4.3 新建知识库（避免数据污染）
```bash
ssh root@10.148.4.21 "docker exec docker-ragflow-gpu-1 /ragflow/.venv/bin/python3 \
  /ragflow/ingest/create_kb.py --name 'GPU测试_<档位>_<日期>' \
  --tenant-id 8a0845faace211f1850e49f1b996babd"
# 输出 KB id，记录下来，前端选这个 KB
```
**每次测试必须新建 KB**——131 踩过坑（100 份压测写进已有 KB 污染数据）。KB 命名规则：`GPU测试_百份_0912`、`GPU测试_千份_0912`、`GPU测试_万份_0912`。

### 我的统计（测试中 + 测试后）

**测试中盯进度**（长跑必备，万份可能 1-3h）：
```bash
# 查 job 状态（succeeded/running/pending 计数）
curl -s http://10.148.4.21:9800/ingest/jobs/<job_id> | python -c "..."
# 查 service.log 实时进度
ssh root@10.148.4.21 "docker exec docker-ragflow-gpu-1 tail -20 /ragflow/ingest/service.log"
```

**测试后提取阶段统计**：
```bash
curl -s http://10.148.4.21:9800/ingest/jobs/<job_id> > /tmp/job_<档位>.json
# 从 job 的 tasks[].stages 提取 parse/chunk/embed/index 的 duration_ms
# 计算 avg/p50/p90/p99/max/占比，墙钟（最早 started_at → 最晚 finished_at），吞吐
```

job 返回的 stages 数据结构（每个 task 有 stages 列表，含 step_name/duration_ms/started_at/finished_at），够出：墙钟、吞吐、各阶段 avg/p50/p90/p99/max/占比、失败明细。

## 七、对比基准（131 同口径）

| 指标 | 131 bench_c3（50份） | 131 bench_10k（万份） | 4090 要对比的 |
|---|---|---|---|
| 吞吐 | 0.180 份/s | 0.046 份/s | 4090 各档位 |
| embed avg | 15.31s | 17.11s | 4090 embed avg |
| embed max | 72.80s | 555.99s | 4090 embed max（核心：是否维持 ~10s） |
| embed 占比 | 93.6% | 86.7% | 4090 embed 占比（预期 ~50%，index 成新瓶颈） |

**核心判定标准**：
- 4090 万份吞吐若接近 100 份的 0.786 份/s（不降 74%）→ GPU 根治了长尾退化
- 4090 万份 embed max 若维持 ~10s 级（不是 131 的 556s）→ 长尾消除

## 八、风险与避坑

| 风险 | 应对 |
|---|---|
| in-memory 无 checkpoint | 服务进程稳定能跑完（131 万份 in-memory 跑了 59.7h 证明）。断了重跑，新建 KB 避免重复 chunk |
| 前端上传 1 万份浏览器卡 | 1000 份已验证可行；1 万份若浏览器卡，分批上传到同一 job（或退回脚本，但优先试前端） |
| mentor 服务 worker 轮询开销 | 已测 100 份服务层 -24% 吞吐，对比时标注 |
| 4090 大文件下载卡死 | 测试数据已传容器内，不涉及下载；服务依赖已在容器内 |
| KB 污染 | 每次新建 KB（4.3） |
