# Demo 范围与验收基线

> 文档性质：项目经理验收与可行性评估的现在时单一来源。
> 更新日期：2026-08-05。
> 结论规则：所有结论标注证据等级；没有同规模实测时不得写成规模验收结论。

## 1. 交付目标

本次交付不是证明 GraphRAG 必然优于普通 RAG，而是回答项目经理的四个决策问题：

1. RAGFlow 普通 RAG 和内置 GraphRAG 能否覆盖目标需求，尤其是局部精准定位、全局跨章节汇总、图谱可视化和来源追溯。
2. 文档规模从单份扩展到几百份、上万份时，RAGFlow 的索引构建、存储和查询是否具有工程可行性。
3. 当原生能力不足时，RAGFlow 是否支持源码级二次开发，以及应复用哪些开源组件和方法。
4. 新增、删除或修订文档时，普通索引和 GraphRAG 图谱是否容易增量更新，哪些操作需要重建或治理层补充。

最终截止日期：2026-08-04。允许结论为“部分满足”，但必须列出已满足项、未验证项、当前失败项、风险和可执行的补强方案。

## 3. 本次 Demo 的最小交付形态

### 3.1 现场入口

- 入口：RAGFlow Web 界面。
- 数据：PTR 冷却泵设备运行与维修手册，真实材料无需脱敏。
- 界面路径：知识库文档状态 → GraphRAG 配置/图谱 → 普通 RAG 会话 → GraphRAG 会话 → 引用来源。
- 后台辅助：只负责健康检查、批量问答、延迟统计、结构化留证，不额外开发替代 RAGFlow 的前端。

### 3.2 演示问题

固定问题仍保留为界面证据，但不再作为规模可行性结论的唯一依据：

- Q1 额定流量、扬程和转速：验证普通 RAG 已足够的局部事实。
- Q2 泵组主要部件/系统：验证实体与部件召回。
- Q3 无法启动的原因和措施：验证故障链路。
- Q4 不出液的原因和措施：验证表格行的成对覆盖。
- Q5 泵盖与部件的装配、密封和支承关系：验证关系题。
- Q6 表2.1的11类故障特征汇总：验证全局类别汇总。
- 压力题：列出所有故障现象及处理措施，观察长答案完整性，但不纳入固定题平均覆盖率。

固定题每套最多运行 3 轮，记录完整答案、引用、失败状态、单题耗时和时间戳。GraphRAG 只有同时满足 `progress=1`、`nodes>0`、`edges>0`、社区报告数量可核对、报告内容与当前领域一致、问答引用/上下文出现社区报告这六项，才可把问答结果称为有效 GraphRAG 结果。仅有任务成功日志或 `mind_map` 非空/为空都不够。

## 4. 可行性评估方法

### 4.1 证据等级

- **A：官方事实**：RAGFlow 官方文档/源码、采购需求原文、官方开源项目文档。
- **B：131 实测**：当前部署、日志、配置和已有评测结果。
- **C：工程外推**：基于处理链路和已有小规模数据的趋势判断，不等同于压测。
- **D：待验证**：需要在 131 或隔离环境执行的实验。

### 4.2 必须记录的指标

对普通 RAG 和 GraphRAG 分别记录：

- 文档数、文档总页数、文本 token 数、chunk 数。
- 实体数、关系数、社区数、图谱构建成功率。
- 首次构建耗时、增量新增耗时、删除/修订后的重建耗时。
- 查询总耗时及 P50、P90、P95、P99；区分局部题、全局题和复杂组合题。
- 召回 chunk 数、引用来源数、答案完整性、关键事实覆盖率、严重错误数。
- CPU、内存、磁盘、ES/Infinity 索引大小、LLM 调用次数和 token 消耗。

### 4.3 规模实验矩阵

当前截止日先交付单份 PTR 的可操作演示和可解释的工程边界；若 131 资源允许，再执行最小阶梯实验：

| 档位 | 文档数 | 目的 | 结果要求 |
|---|---:|---|---|
| S0 | 1 | 复现当前 PTR 基线 | 普通 RAG 可问；GraphRAG 四项健康检查 |
| S1 | 10 | 验证批量导入与图谱跨文件合并 | 成功率、构建时间、节点/边增长 |
| S2 | 100 | 观察百份规模趋势 | 查询 P50/P95、资源峰值、失败任务 |
| S3 | 1,000 | 评估上千份工程可行性 | 仅在资源和时间允许时执行，必须独立环境 |
| S4 | 10,000 | 形成万份规划依据 | 不在今天承诺实测；需容量规划和分批/分域方案 |

合成扩展数据只能验证容量与调度趋势，不能证明领域问答质量；领域质量必须使用真实手册样本和人工金标。

## 5. 当前事实与判断

### 5.1 RAGFlow 原生能力

| 能力 | 结论 | 证据与边界 |
|---|---|---|
| 几百/上万份普通 RAG 文档管理 | **原则上支持，需容量规划** | 官方提供批量文档导入、异步解析、向量/全文检索；没有本项目硬件上的万份压测证据 |
| 几百/上万份 GraphRAG | **架构上可做，原生直接承诺不足** | RAGFlow 将多个文件的图谱合并为数据集级统一图；官方同时警告高内存、计算和 token 成本；131 的 747 节点合并已超时 |
| 局部问题 | **单份 PTR 已通过演示验收** | 修复后 Q1-Q5 均返回有效答案和引用；Q5 可说明泵盖与泵体、托架、机械密封和转子部件的关系 |
| 全局社区汇总 | **单份 PTR 修复后通过有效性验收** | 发现 43 个 Leiden 候选社区，成功生成并索引 41 条报告；41/41 ID 唯一、来源正确、污染词为 0；Q6 正确列出 11 类故障 |
| 图谱 Web 可视化 | **原生具备** | 官方文档/博客明确提供节点、关系、社区和 mind map 可视化 |
| 来源追溯 | **普通问答部分满足** | RAGFlow 有 chunk 引用；GraphRAG 图数据保存 source_id；精确到业务版本/时序节点需额外建模 |
| 图谱导出 | **原生不满足** | 官方 FAQ 明确不支持导出已生成知识图谱 |

### 5.2 131 修复后实测终态

已确认的 PTR GraphRAG 事实：

- 普通存储层：162 个唯一 chunk；数据库 `chunk_count=324` 是历史重复解析造成的累计计数，不代表实际索引重复。
- GraphRAG 任务：`progress=1.0`、`ok=1`、`failed=0`，17 个合并 chunk，总耗时 1255.08 秒。
- 抽取与图处理：615 个节点、297 条边进入 embedding，51 对实体消歧候选，43 个 Leiden 候选社区。
- Graph API：256 nodes / 128 edges。
- Elasticsearch：614 entity、292 relation、41 community_report、1 graph、1 subgraph。
- 社区报告：41 条成功生成并索引，41 个唯一 ID，`kb_id/source_id` 正确，三个已知污染词命中为 0。
- KG 检索对照：`use_kg=false` 返回 4 个普通 chunk、0 个社区块；`use_kg=true` 返回 5 个 chunk，其中首个为 `Related content in Knowledge Graph` 社区聚合块。
- 修复后固定题集：7/7 API/答案级成功，P50=13.381 秒，P90=26.971 秒，平均引用 6.71；Q5/Q6 相比修复前明显改善。
- 三系统正式基准（2026-08-05）：72/72 全部成功（12 题 × 2 轮 × normal/general/light）。普通 RAG 规则覆盖率 99.2%、General 99.0%、Light 88.3%。普通 RAG E2E P50=15.61s 最快，Light P99=76.23s 最差。普通 RAG 24 次全成功等效覆盖原定 14 次重复性要求。详见 `test/results/2026-08-05/`。
- 压力题 P1 虽接口成功，但答案在“电机过载”后声明原文数据截断，不能判为所有故障完整覆盖。
- RAGFlow Light 隔离数据集重建通过三条件验收：`progress=1.0`、日志无失败标记、36 nodes / 27 edges；得到 3 个社区，总耗时 831.47 秒。
- 同一 PTR 的 General 基线为 1255.11 秒、256 nodes / 128 edges / 41 communities。Light 快 33.76%，但图明显更稀疏，建图速度不能替代关系覆盖和问答质量验收。
- RAGFlow Light 只是 LightRAG 风格抽取方法，图存储、KG retrieval 和 Chat 仍属 RAGFlow，不等同于独立 LightRAG 全链路。

已有法律域的历史评测只能说明评测脚本和延迟统计可复用，不能外推 PTR 或 GraphRAG：历史 RAGFlow 评测未开启知识图谱，且数据域、硬件、配置均不同。

### 5.3 查询效率趋势

普通 RAG 查询主要受向量/全文检索、重排、LLM 生成和并发影响。文档数增加时，合理的倒排/向量索引通常不会让查询时间与文档数线性增长，但索引规模、缓存命中率、内存压力、磁盘 I/O 和并发排队会使 P95/P99 变差。该结论是工程外推，必须用 S1-S3 阶梯实验验证。

GraphRAG 查询增加实体/关系/社区上下文组装和更大的 LLM prompt。局部题通常可控；全局题的社区摘要选择和生成上下文更重。规模增长后，构建成本和存储成本通常比普通 RAG 更敏感，查询延迟也更依赖图索引、社区报告数量、top-k、上下文 token 上限和 LLM 服务吞吐。本次 PTR 实测还发现，社区报告可能残留跨领域历史文本，因此必须把报告内容领域一致性作为问答验收前置条件。

需求阈值是常规检索不超过 2 秒、复杂组合检索不超过 5 秒。三系统正式基准（72 条）端到端 P50 均超过 15 秒，未达到阈值。但独立检索 P50 仅 1.58～2.38 秒，生成残差占 E2E 约 86%～91%，说明主要瓶颈在外部 LLM 调用而非 ES/图谱检索。`generation_residual` 来自两次独立顺序请求相减，仅作诊断方向。

## 6. 新增、删除和修订文档

### 6.1 普通 RAG

- 新增文档：RAGFlow 原生支持上传后异步解析、分块、embedding 和索引，流程相对直接。
- 删除文档：原文档和对应 chunk 可按平台流程删除，但必须验证引用、缓存和会话是否立即一致。
- 修订文档：建议以新文档版本导入，保留 `document_id`、版本号、生效时间和来源元数据；不要只覆盖原文件而丢失可追溯性。

### 6.2 GraphRAG

- 新增文档：官方说明新文件开始解析时，数据集级图谱会自动更新；实际仍需要等待实体/关系抽取、合并、消歧和社区任务完成。
- 删除文档：官方明确不会自动更新图谱，必须重新生成图谱；因此删除和大规模修订不是低成本实时操作。
- 实体消歧/社区：新文档可能改变实体连接和社区结构，不能简单只追加一条边；需要局部或全局重新计算并做一致性校验。
- 当前 131 证据说明合并 747 节点就可能超时，新增文档的“易更新”只能定义为“可触发”，不能定义为“快速完成且无需重建”。

## 7. RAGFlow 二次开发判断

### 7.1 可行性

RAGFlow 官方仓库是 Apache-2.0 开源项目，包含前端、API、文档解析、RAG、GraphRAG、SDK、Docker/Helm 等源码。因此可以进行：

- API/SDK 集成：在 RAGFlow 外部增加任务编排、版本元数据和评测服务。
- 后端定开：改 GraphRAG worker、任务状态、图谱合并、删除重建和检索上下文组装。
- 前端定开：增加图谱过滤、来源/版本/时序展示、任务监控和治理界面。
- 存储定开：保留 RAGFlow 文档引擎，同时把规范化实体关系同步到 Neo4j、PostgreSQL/AGE 或其他图存储。
- 部署定开：将容器内运行时补丁纳入源码分支和镜像构建，消除版本漂移。

### 7.2 建议的定开边界

| 层 | 定开内容 | 优先级 |
|---|---|---:|
| 数据治理层 | 文档/设备/版本/生效时间/来源 ID；去重、审核、回滚和影响范围 | P0 |
| 导入编排层 | 批量任务、断点、重试、限流、分批图谱构建、失败隔离 | P0 |
| GraphRAG 层 | 增量子图、实体消歧、受影响社区重算、删除后重建、健康检查 | P0 |
| 检索适配层 | 普通向量/BM25 + 图局部/全局检索融合；统一引用和置信度 | P1 |
| Web 层 | 图谱筛选、版本/时序过滤、任务状态、引用回溯、导出 | P1 |
| 容量与观测层 | P50/P95、队列长度、LLM token、ES/Infinity 占用、worker/GPU 监控 | P0 |

不建议今天直接修改 131 生产容器源码。先保存补丁 diff 和配置快照，复制到受控分支，在隔离环境验证，再构建固定版本镜像。

## 8. 可复用开源路径

| 方案 | 可复用能力 | 与 RAGFlow 的关系 | 建议定位 |
|---|---|---|---|
| RAGFlow 源码/GraphRAG | 已有解析、向量检索、图抽取、Web 和引用 | 主平台，可直接定开 | 主线 |
| Microsoft GraphRAG | global/local/DRIFT、Leiden 社区、社区摘要、增量 update 思路 | 可作为算法和任务设计参考，不直接替换 RAGFlow | 全局检索/增量设计参考 |
| LightRAG | local/global/hybrid/mix、增量 insert、按文档删除、多种图存储和可视化 | 131 已有代码；可做旁路验证或适配器 | 定开参考/备选引擎 |
| Neo4j / PostgreSQL AGE | 结构化图存储、关系查询、版本/来源属性 | RAGFlow 原生图谱不导出时的外置治理与查询后端 | 生产图存储候选 |
| RAGAS + JSONL 评测骨架 | 质量指标、延迟、失败记录、checkpoint | 131 已有，可直接复用 | 评估主线 |

开源方案的能力不能直接等同于已完成集成。尤其是 LightRAG 的 `source_id` 可以保存来源，但仍需自行实现面向最终答案的精确引用、业务版本权限和 RAGFlow Web 融合。

| 删除/修订文档 | 原生 GraphRAG 需重生成，版本治理不足 | A | 部分满足，需外置版本与重建编排 |
| RAGFlow 定开 | 可行，源码/API/SDK/容器均可改 | A | 可以在 RAGFlow 上定开，不必换栈 |
| 可视化 | `/graph` 返回 256 nodes / 128 edges；41 条社区报告通过落库和内容验收 | A+B | API 产物具备演示条件；Web 页面操作性仍需现场终验 |
| 来源/时序/置信度 | 普通引用可用；业务版本、时序节点、可解释置信度需定开 | A+B | 部分满足 |

## 10. 今日结论

**建议向项目经理汇报：RAGFlow 作为主平台可行，但当前只能给出“部分满足”，不能承诺原生 RAGFlow GraphRAG 已经具备 30 万份级别的稳定能力。**

满足的部分：RAGFlow + MinerU 的导入、解析、普通 RAG、GraphRAG 配置、图谱可视化、引用展示和 API/源码二次开发基础。

部分满足的部分：百份至上万份的容量、增量新增后的稳定完成、删除/修订后的图谱一致性、版本/时序/置信度治理。

当前不满足/未证实的部分：需求规定的 2 秒/5 秒端到端查询阈值；万份或 30 万份同规模压测；图谱导出；完整内容级版本回退和影响范围分析。单份 PTR 的社区报告内容有效性和 GraphRAG 社区问答接入已在修复后通过验收。

**现场 Demo 的正确叙事顺序：**

1. 用 RAGFlow Web 展示 PTR 文档已入库、普通 RAG 可问、引用可回溯。
2. 展示 GraphRAG 配置和图谱页面：256 个节点、128 条边；说明本次发现 43 个候选社区，最终 41 条有效社区报告成功落库。
3. 在 `demo_graph_v4` 依次问 Q5 和 Q6，展开首条 `Related content in Knowledge Graph` 引用，证明社区/KG 链路已进入 Chat 上下文。
4. 展示修复后的三层验收：41/41 唯一 ID、来源正确、污染词为 0；固定题集 7/7 成功，但 P1 长答案仍有完整性边界。
5. 展示四问题评估表：单文档 Demo 满足；2 秒/5 秒性能未满足；百份/万份未实测；删除/修订需重建或定开。
6. 给出定开路线：版本治理 + 增量任务编排 + 图谱分域/外置存储 + 检索融合 + 容量压测。
