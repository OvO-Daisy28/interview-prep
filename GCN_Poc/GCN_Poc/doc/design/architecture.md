## 〇、阶段二目标架构（7 子系统 + RAGFlow 定位）

### RAGFlow 在目标架构中的角色

- **不是**整个系统，**是**知识库与知识图谱子系统的后端引擎 + 检索/图谱能力供给方。
- 与内容数据库（PostgreSQL）形成"双写"：结构化参数入关系库，检索向量与图谱入 RAGFlow。
- 需二开的 RAGFlow 侧（改源码/扩展）：GraphRAG 实体/关系 Prompt 定制（10 类实体 + 6 类关系）、社区报告领域适配、检索结果增加 PBS/专业维度/置信度标注、知识节点审核与版本管理界面、批量导入断点续传、查询路由（局部→普通RAG，全局→GraphRAG）。
- 需新建（独立于 RAGFlow）：内容解析（参数提取+信息块+PBS）、内容数据库、内容治理、手册生成、规则梳理、AI 辅助编辑前端、系统管理/集成、LLM 私有化部署。

### 二开优先级与"做中才能定论"项

P0（T+1 需求设计）：拿到甲方存量文件样本（3-5 类设备手册）、内容数据库数据模型设计、RAGFlow GraphRAG 领域 Prompt 方案、LLM 私有化部署选型、与甲方确认 CUD4.0/4A/UAU/UBA 接口。

"做中才能定论"（不能用单份 PTR 外推的硬指标）：参数提取准确率≥95%、端到端延迟≤2s/5s（当前 E2E P50 15-23s，瓶颈在外部 LLM，待本地化后验证）、GraphRAG 规模化稳定性（1/10/100/1000 阶梯压测）、模板生成质量、规则梳理结论、PBS 对象识别准确率。

> 阶段二的开发优先级、里程碑（T+1/T+3/T+4）与逐条二开/新建判定，以 [二次开发范围分析.md](二次开发范围分析.md) 为 SSOT，本文不重复。

## 二、系统分层

| 层 | 当前使用 | 责任 | 验收重点 |
|---|---|---|---|
| 数据与版本层 | PTR 手册 + 外置元数据 | 文档 ID、设备、版本、生效时间、来源章节 | 新增/删除/修订可追溯 |
| RAGFlow 导入层 | Web/API + MinerU/DeepDoc | 批量上传、解析、分块、embedding、索引 | 单份成功；批量与失败隔离待测 |
| 普通检索层 | RAGFlow hybrid search | 向量、全文、重排、引用 | 常规检索 2 秒需求阈值待测 |
| GraphRAG 构建层 | RAGFlow worker `graphrag` | 实体、关系、消歧、社区、子图合并 | 四项健康检查 |
| GraphRAG 查询层 | RAGFlow chat + knowledge graph | 局部/全局上下文增强 | 关系题/全局题的覆盖与耗时 |
| 评估层 | 131 JSONL/RAGAS 骨架 + PTR 金标 | 质量、延迟、失败、资源留证 | 结果可复现、失败不包装 |
| 定开层 | 当前只做方案设计 | 版本治理、增量编排、外置图存储、Web 展示 | 作为后续实施路线，不冒充今日已完成 |

## 三、主问题与演示顺序

1. **平台入口**：展示 PTR 文档已入库、普通 RAG 解析完成、引用来源可回溯。
2. **GraphRAG 能力**：展示配置项、256 个节点、128 条边和社区产物；后端验收为 41 条有效社区报告、41 个唯一 ID、来源正确、污染词为 0。
3. **问题分层**：局部事实题说明普通 RAG 的适用范围；Q5 关系装配和 Q6 全局类别题展示 GraphRAG 的有效增益，P1 保留长答案截断边界。
4. **检索证据**：显式对照 `use_kg=false/true`，确认 KG 聚合块进入召回和 `demo_graph_v4` 引用，而不是只看图谱构建日志。
5. **规模外推**：说明普通索引、图谱抽取、社区报告、存储和查询的增长变量，不把单文档结果当压测。
6. **更新治理**：新增文档可触发普通索引和图谱更新；删除/修订仍需重建和外置版本治理。
7. **决策结论**：单份 PTR Demo 与社区/KG 链路满足；性能、上万份规模和删除/修订一致性为未满足或未验证，整体结论是“部分满足”。

## 四、核心技术判断

### 4.1 普通 RAG

文档数扩大后，倒排和向量索引承担候选定位，查询时间不应简单按文档数线性增长；但索引内存、缓存、磁盘 I/O、并发队列和生成模型仍会使长尾延迟上升。需按文档数阶梯记录 P50/P95，而不是只记录平均值。

### 4.2 GraphRAG

GraphRAG 的成本集中在离线构建：每个 chunk 的实体/关系抽取、embedding、子图合并、实体消歧和社区报告。图谱并非只增加一个向量字段，而是增加 LLM 调用、图结构存储、图组件 embedding 和社区上下文。RAGFlow 官方也明确警告其内存、计算和 token 成本较高。

### 4.3 查询路由

普通 RAG 作为默认主链路，处理参数、条文和局部事实；召回不足时增加 rerank。关系/故障因果链可路由到 KG local 或 Light；跨文档全局归纳才使用 General 社区报告。所有请求不应默认开启最重的 GraphRAG 路径，否则无法控制端到端延迟和外部模型成本。

RAGFlow Light 当前只证明同平台的抽取方法可切换，不证明完整 LightRAG 增量能力。PTR 建图耗时从 General 1255.11 秒降到 831.47 秒，但节点从 256 降到 36、边从 128 降到 27，必须以查询质量 A/B 决定是否用于关系题。

### 4.4 增量更新

- 新文档解析时可触发数据集图谱更新，但完成时间和一致性依赖 worker、超时、实体消歧和社区重算。
- 删除相关文件不会自动更新图谱，必须重新生成。
- 生产方案需要文档版本元数据、变更影响分析、删除/修订任务编排和回滚策略。

### 4.5 二次开发

RAGFlow 为 Apache-2.0 开源项目，具备源码、API、Python SDK、前端和容器部署资产。可在其上定开，不必先换平台。建议先做外置编排与治理层，只有确认 GraphRAG 核心瓶颈后再改 worker 和检索内核。

## 五、当前实测终态与边界

131 PTR GraphRAG 已在修复后完整重建并验收：`progress=1.0`、总耗时 1255.08 秒、Graph API 为 256 nodes / 128 edges；Elasticsearch 为 entity=614、relation=292、community_report=41、graph=1、subgraph=1。41 条有效社区报告 ID 全部唯一、来源正确，三个已知 Prompt 污染词命中为 0。

显式 KG retrieval 对照中，`use_kg=false` 返回 0 个社区块，`use_kg=true` 返回 1 个社区聚合块；固定题集 7/7 API/答案级成功，Q5/Q6 的修复后答案有效。三系统正式基准（2026-08-05）72/72 全部成功：普通 RAG E2E P50=15.61s、General P50=23.16s、Light P50=22.56s，均未达到采购要求的常规 2 秒、复杂 5 秒；独立检索 P50 仅 1.58～2.38 秒，生成残差占 E2E 约 86%～91%，主要瓶颈在外部 LLM 调用。普通 RAG 规则覆盖率 99.2% 最高，Light 仅 88.3%。

本结论只覆盖一份 PTR 手册和 131 当时的资源/模型组合，不能外推为百份、万份或 30 万份验证。服务器五处修复是已验证的运行时补丁，源码前后版本、diff 和哈希已归档，但尚未构建固定自定义镜像。任何再次删除图谱、重启 worker/容器或覆盖服务器源码的操作仍须显式授权、备份和回滚准备。

## 六、扩展和定开蓝图

```text
业务文档/版本元数据
        │
        ├── RAGFlow：解析、chunk、普通索引、答案与基础引用
        │
        ├── 增量编排服务：批量、断点、重试、限流、失败隔离、状态机
        │       │
        │       └── GraphRAG worker：子图增量、实体消歧、受影响社区重算
        │
        ├── 治理存储：版本、生效时间、审核、影响范围、回滚、时序标签
        │
        └── 检索适配：向量/BM25 + 图局部/全局 + 统一 citation/source_id
```

开源参考：Microsoft GraphRAG 的 global/local/update 思路；LightRAG 的 local/global/hybrid/mix、增量插入和按文档删除；Neo4j 或 PostgreSQL/AGE 作为外置图存储候选。它们是定开参考，不是今天已经集成进 RAGFlow 的能力。
