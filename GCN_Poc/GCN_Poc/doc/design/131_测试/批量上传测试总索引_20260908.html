五、发现的问题

1. RAGFlow 原生取消不生效（方案A硬伤）

DELETE /chunks 在文档多的串行场景下取消不彻底——实测跑到 30% 时取消，最终 0 份变 CANCEL，100 份全部正常 DONE。RAGFlow 的取消是软取消（Redis 标志 + worker 阶段边界检查），但串行 embedding 下检查点之间文档已被处理完。

影响：方案A 无法满足 PM"随时暂停/重试"需求。

2. 方案B MySQL 持久化并发 bug（反馈 mentor）

MySQLRepository 用 threading.local() 每线程一个连接，在 Scheduler 的 ThreadPoolExecutor 并发下连接断开，get_task 返回 None 导致 task 全失败（'NoneType' object has no attribute 'status'）。

复现：--persist --concurrency 3，10000 份 7 份成功后全卡死。InMemory 模式不受影响（50 份 c1/c3/c6 全成功）。
建议 mentor：MySQLRepository 加连接 ping 检查/自动重连机制。

3. embedding 长尾（两方案共性瓶颈）

bge-base 在 131 共享 CPU 上推理，单份 embed avg 11s（并发1）→ 30s（并发6），max 47s→118s。并发越高长尾越严重。提速正解是 GPU/独立部署，不是加并发。

131 是 34 容器混跑、load 22、无 GPU、embedding 服务跑 36 天。
