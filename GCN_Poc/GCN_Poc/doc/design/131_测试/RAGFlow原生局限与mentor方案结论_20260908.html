一、结论

RAGFlow 原生批量上传接口功能上能完成文档上传与解析（100 份 .docx 实测：上传 3.2s、解析 1104s、100% 成功），但存在六大局限：进度只能猜、无暂停、无重试、性能不由己控、状态不可控、升级耦合。其中取消能力实测不生效（DELETE /chunks 后 0 份变 CANCEL，100 份全部正常 DONE）。

项目经理要的「可管理批量上传」（每阶段计时、随时暂停/重试、读写队列状态、提供接口），RAGFlow 原生只满足 1/5（提供 HTTP 接口）。mentor 方案 B 通过绕过解析引擎、复用存储基础设施的自建流水线，一次性解决了全部局限——这是经实测验证的、唯一能同时满足 PM 全部需求的路径。

三、RAGFlow 原生批量上传六大局限

局限 1：进度只能猜（无分阶段计时）

RAGFlow 只给文档级单浮点 progress（0.0~1.0）+ 累积文本 progress_msg，不给 parse/chunk/embed/index 各阶段独立进度与计时。

实测证据：100 份文档全流程 progress_msg 只有 4 种文本——"Task is queued..." / "256 tasks are ahead in the queue..." / "254..." / "252..."。没有任何阶段关键词（OCR/embedding/entity）。前 483 秒 100 份全卡 RUNNING、progress 浮点 0.0049 几乎不动。
源码：task_executor.py:186 set_progress 只写单 progress+msg；document_service.py:1146 _sync_progress 聚合取平均。
文档：ingest-orchestration.md:82,105-110

局限 2：无暂停（只有取消，且不彻底）

task_executor 无 pause 状态，只有 cancel（DELETE /chunks 设 Redis 标志）。且 has_canceled 是阶段边界轮询非即时中断。

实测证据：跑到 30% 时发 DELETE /chunks，最终0 份变 CANCEL，100 份全部正常 DONE。取消在文档多的串行场景下不生效——软取消标志还没被 worker 看到，文档就跑完了。
源码：task_service.py:610 has_canceled 读 Redis key；task_executor.py 多处阶段边界检查。
文档：ingest-orchestration.md:88-89,132-140

局限 3：无重试（失败即终态）

Task 模型有 retry_count 字段，但task_executor 无自动重试消费逻辑。失败即 failed，重跑需重新 POST /chunks 全量入队。

源码：db_models.py:1015 retry_count 字段在；task_executor 主循环不消费该字段。
文档：ingest-orchestration.md:83,89,142-146

局限 4：性能不由己控（单 worker 串行）

task_executor 默认 MAX_CONCURRENT_CHUNK_BUILDERS=1，embedding 阶段串行。批量提交不限流会 Redis 队列堆积 + OOM（131 曾被 OOM 停 Docker daemon）。

实测证据：100 份解析 1104s，吞吐仅 0.091 份/s。前 483s 一份都没跑完（100 份在队列排队，串行 embedding 每份约 11s）。
源码：task_executor_limiter.py:20-28 MAX_CONCURRENT_CHUNK_BUILDERS 默认 1。
文档：ingest-orchestration.md:159-160

局限 5：状态不可控（无优先级/队列操作）

RAGFlow 原生无优先级调度、无队列读写接口。文档入 Redis Stream 后按队列顺序消费，无法插队、改优先级、查看具体排队位置。

源码：Redis Stream + 消费者组（redis_conn.py:415），严格 FIFO。GET /documents 只能查"前面还有 N 份"的模糊信息，不能操作队列。
文档：ingest-orchestration.md:22-32,155

局限 6：升级耦合（调解析 API 绑定内部流程）

调 RAGFlow 解析 API 就绑定了它的内部流程（Redis 队列、task_executor、progress 上报机制）。RAGFlow 升级改动这些内部实现，调用方就要跟着改。

文档：progress-board.md:39——"自建流水线只依赖存储契约（MinIO/ES/MySQL），升级不受影响"。

四、为什么 mentor 要自建（第一版撞墙记）

mentor 第一版就是方案 A（调 RAGFlow 原生解析 API），接真实 131 服务器后撞了上面 4 个问题（进度只能猜、无暂停、无重试、性能不由己控），设计重写时又发现 2 个设计假设错误（共 6 处 v1→v2 修正）。

v1 错误假设v2 修正
7 精确 stage5 子步骤对齐 PM 原型 + 映射自 progress
无 cancel endpoint，要 SSH有 DELETE /chunks，但仍无真暂停
暂停=软停，硬取消运维级默认软暂停 + force 硬停，行业惯例
/ingest 最灵活首选走 /chunks（/ingest 不适配 GraphRAG）
状态机自造直接对齐 RAGFlow run 5 态
无灵活性机制三层抽象（接口/映射/适配层）
文档：ingest-orchestration.md:284-293；批量导入规模验证_20260907.html:262-264——"PM 要的可管理批量上传，只有自建编排能实现"

五、mentor 方案 B 解决了什么

方案 B 核心：自己跑 parse→chunk→embed→index 全链路，把产物写进 RAGFlow 认识的存储（MinIO/ES/MySQL），绕过解析引擎 task_executor。复用基础设施，不碰解析——检索效果不打折（实测 sim=0.476 命中）。

PM 需求RAGFlow 原生方案 B 解决方式
每阶段计时不支持 单浮点+文本支持 每阶段 time.time() 精确计时，on_stage 回调写 duration_ms
随时暂停不支持 实测 0/70 生效支持 stage 边界检查 _cancelled 标志，软暂停+force 硬停
重试不支持 失败即终态支持 单份从 failed→pending 重跑，删旧 chunks 重来
读写队列状态弱 只能查模糊排队数支持 MySQL 三表（job/task/step），可查/改优先级/插队
提供接口支持 HTTP API支持 8 个 REST endpoint + /demo 评审页
性能可控不受控 0.091 份/s，串行可调 Scheduler max_concurrent，并发 3 最优（实测 0.25 份/s）
升级解耦耦合 绑定内部流程解耦 只依赖存储契约

七、最终结论

1. RAGFlow 原生定位

RAGFlow 原生批量上传接口是"能用但不可管"的——它适合轻量、一次性、不需暂停重试的文档导入场景。接口齐全（HTTP API），功能完整（上传→解析→检索），但可控性弱。

2. 方案 B 定位

mentor 方案 B 是"可管理的批量导入服务"——满足 PM 全部 5 项需求（计时/暂停/重试/队列/接口），性能更优（并发可调），解耦升级。代价是放弃 RAGFlow 解析引擎、自维护全链路。

3. 选型建议

场景推荐理由
批量导入（需暂停/重试/计时）方案 BPM 核心需求，原生满足 0/5
单文档/少量上传方案 A 原生简单、无需自维护
复杂版面/扫描件解析需评估方案 B 的 docx 解析较简单，复杂场景可能仍需 RAGFlow DeepDOC
embedding 提速独立二开两方案都调 bge-base，提速需 GPU/独立部署，非调并发
