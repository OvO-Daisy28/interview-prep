# RAGFlow 核心概念与规范书术语详解

> 用途：面向项目经理和开发团队，系统解释 RAGFlow 的技术实现细节和规范书术语
> 日期：2026-08-13
> 依据：RAGFlow v0.26.1 源码归档、131 服务器实测、二次开发范围分析、技术规范书

## 一、文档批量上传

### 1.1 RAGFlow 原生支持批量上传

- Web 界面：拖拽多份文档一次性上传
- API：`POST /api/v1/datasets/{kb_id}/documents` 支持批量

### 1.2 处理逻辑

```
上传 → 存MinIO → 创建MySQL文档记录 → 入Redis队列 → 
task_executor消费 → DeepDoc/MinerU解析 → chunk → embedding → ES索引
```

- 异步队列模型，上传不阻塞
- 默认单 worker，需配置多 worker 提升并发
- 无断点续传、无自动重试、无限流——需二开编排层

### 1.3 几百份文档的挑战

- 普通 RAG：排队解析，需要并发控制和失败隔离
- GraphRAG：单份 PTR 建图 1255 秒，几百份需要分域+分批+任务编排
- 二开判定：断点续传和失败重试 = 需二开

## 二、文档解析技术栈

### 2.1 章节层级识别

- DeepDoc：版面分析模型 + 字体/字号/缩进规则，支持四级+层级
- MinerU：LayoutLMv3 改进模型，更强版面分析，输出 Markdown/JSON

### 2.2 段落/表格/图片识别

- 段落：版面分析 + 换行/缩进特征
- 表格：版面定位 + 表格结构识别（含合并单元格），MinerU F1>90%
- 图片：版面分析识别区域 + 提取
- 注意框/警告框：原生不足，需定制开发

### 2.3 OCR

- RAGFlow 内置 OCR（DeepDoc 自带 + MinerU 自带）
- 文本检测 + 文本识别两阶段
- 内置于 Docker 容器，不需单独部署
- 无 GPU 时走 CPU 推理，较慢
- 技术规范书要求扫描版 PDF OCR ≥95%，需验证中文准确率

### 2.4 MinerU 是什么

- **不是单一模型，是完整文档解析流程**
- 组成：版面分析模型 + OCR模型 + 表格结构识别 + 公式识别 + 阅读顺序排序 + 输出转换
- MinerU 的 OCR/版面模型是固定的视觉模型，**不能切换大模型 key**
- MinerU 之后的 LLM 步骤（实体抽取、参数提取）**可以切换大模型 key**

## 三、规范书术语解释

### 3.1 "文档到结构化参数"

- 结构化参数 ≠ JSON 串本身
- 结构化参数 = 把自然语言段落拆成一条条可独立管理的参数记录
- 举例："额定流量640m³/h，额定扬程36m" → 两条独立参数记录
- RAGFlow 只做到"文档→chunk"，没做到"chunk→参数记录"

### 3.2 复合参数拆分

- 一句话含多个参数时，拆成多条独立记录

### 3.3 PBS（Plant Breakdown Structure）

- 设备分解结构，核电行业工程概念
- 从核电站到零件的层级树：系统→子系统→设备→部件→零件
- 每个参数/故障/操作/备件都要关联到 PBS 节点
- RAGFlow 完全没有 PBS 概念

### 3.4 信息块（Information Block）

- 规范书定义的知识管理单元，比 chunk 更结构化
- 包含：PBS对象 + 专业维度 + 信息类型 + 内容 + 来源 + 审核状态 + 版本
- RAGFlow 产出 chunk，规范书要求信息块——中间差了拆解+结构化+打标签

### 3.5 表格语义解析

- RAGFlow 能识别表格位置和结构（行列、合并单元格）
- 但不理解语义含义（如故障三元组：现象→原因→措施）
- 需 LLM 理解表格语义，将每行拆为结构化记录

### 3.6 AI审核界面

- 技术规范书确实要求
- 功能：左侧原文 vs 右侧 AI解析结果，逐条对照确认/修正
- 记录差异，审核通过后参数才生效
- RAGFlow 完全没有，需新建

## 四、知识库与知识图谱子系统

### 4.1 时序知识图谱

- 不是简单加时间节点
- 专业定义：
  - 节点和边带时间属性（Valid Time）
  - 同一实体不同时间有不同版本
  - 支持时间维度查询
  - 时序推理
- 学术概念：Valid Time + Transaction Time + Bitemporal Model + Time-decay
- RAGFlow 是静态快照图，不支持时序
- 判定：全新建

### 4.2 置信度

- RAGFlow 只有检索相似度（similarity score）
- 规范书要求多维度置信度：
  - 来源置信度（正式文件 > 草稿）
  - 审核置信度（人工确认 > AI提取）
  - 时间置信度（有效 > 过期）
  - 一致性置信度（多来源一致 > 冲突）
- 需二开

### 4.3 专业维度标注

- 每个知识节点标注：机械/电气/仪控/运行/维修/安全
- 作用：权限隔离 + 精准检索
- 需二开或新建标注系统

### 4.4 知识节点审核与版本管理界面

- 增删改查 + 审核流程 + 版本管理 + 影响范围分析 + 质量检查
- RAGFlow 只有基础文档管理，需二开扩展

## 五、语义检索与 Hybrid Search

### 5.1 Hybrid Search

- 词法检索（BM25）+ 向量检索 → 融合排序 → 可选 rerank
- 适合：精确匹配 + 语义理解兼顾

### 5.2 知识图谱可视化

- 后端 API 返回 JSON（nodes + edges）
- 前端：力导向图，基础可视化
- 不足：无高级布局、无路径追踪、无时序可视化、大图可能卡顿
- 专业级可视化建议集成 ECharts G6 / Cytoscape.js

### 5.3 知识推理

- 不是编排流程，是 GraphRAG 检索增强
- 利用图结构信息（直接边 + 社区报告）增强 LLM 上下文
- RAGFlow 负责检索+上下文组装，推理由 LLM 完成

### 5.4 知识库分层分类管理

- KB = Knowledge Base，RAGFlow 顶层组织单元
- 原生平铺列表，无层级
- 规范书要求层级分类：设备/参数/操作/故障/标准知识库
- 需二开加分类目录层

## 六、实体抽取与 Prompt

### 6.1 RAGFlow 实体抽取方式

- 通过配置 Prompt 模板 + 调用 LLM
- chunk → 合并批次 → LLM(Prompt) → JSON → 实体/关系 → NetworkX 子图
- method: general / light / ner

### 6.2 本项目实体类型（10类）

设备、系统PBS、部件、参数、操作、故障、标准、文件、信息块、时间节点

### 6.3 本项目关系类型（6类）

组成、特性、引用、从属、顺序、交叉引用

### 6.4 Prompt 核心结构

- 角色定义（核电设备领域专家）
- 实体类型列表（带定义）
- 关系类型列表
- 输出格式约束（严格JSON）
- 待抽取文本（{chunk_content}）

## 七、完整工作流程

```
文档上传
  ↓
MinerU/DeepDoc 版面分析+OCR → chunk
  ├─ 普通 RAG：embedding → 混合检索 → 问答
  └─ GraphRAG：LLM抽取 → 子图 → 合并 → 消歧 → 社区 → KG检索增强 → 问答
  
  ── RAGFlow 原生覆盖到此 ──
  
  ── 规范书要求但 RAGFlow 不覆盖 ──
  
  chunk → LLM参数提取 → 复合参数拆分 → 结构化参数
    → PBS关联 → 信息块建立 → AI审核界面 → 内容数据库(PostgreSQL)
    → 同步到RAGFlow（双写）
```

| 参数提取 | 需新建 | RAGFlow 无此能力 |
| 复合参数拆分 | 需新建 | RAGFlow 无 |
| 信息块建立 | 需新建 | RAGFlow 无 |
| 表格语义解析 | 需二开 | 有版面定位，无语义理解 |
| PBS关联 | 需新建 | RAGFlow 无 PBS 概念 |
| AI审核界面 | 需新建 | RAGFlow 无 |
| 时序知识图谱 | 需新建 | RAGFlow 是静态图 |
| 置信度标注 | 需二开 | 只有相似度 |
| 专业维度标注 | 需二开 | 无 |
| 知识节点审核界面 | 需二开 | 基础有，审核/版本不足 |
