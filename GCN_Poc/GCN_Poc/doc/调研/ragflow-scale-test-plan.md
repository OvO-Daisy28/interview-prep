# RAGFlow 万份级文档管理与阶梯压测方案

> 日期：2026-08-05
> 目标：回答“文档增长到几万份如何管理、如何验证查询效率与建库能力”
> 适用版本：RAGFlow v0.26.1；普通 RAG、GraphRAG General、GraphRAG Light

## 1. 结论先行

几万份文档不能用“单知识库全部上传 + 打开 GraphRAG”管理。正确边界是：

1. **按业务域/设备/版本分库**，单库控制 chunk 和图谱规模；跨库由查询路由层聚合。
2. **普通 RAG 做默认检索主链路**，关系/跨文档/全局问题才路由到 KG；不要让所有查询支付 GraphRAG 成本。
3. **文档索引与图谱索引分生命周期**：普通 chunk 增量实时，GraphRAG 分批/定时合并，删除或修订触发受影响域重建。
4. **规模用 chunk、token、图节点/边衡量，不只看文件数**。1 万个 2 页文件和 1 万本手册不可比较。
5. **压测必须阶梯推进**，每一级通过容量、吞吐、延迟、质量和恢复性门槛后再扩大；禁止从 100 份直接跳 1 万份。

## 2. 万份级管理模型

### 2.1 分域与命名

建议知识库主键：`业务域/系统/设备类型/资料类型/有效版本`。

示例：

```text
核岛/PTR冷却系统/泵/运行手册/现行
核岛/PTR冷却系统/泵/检修记录/2026Q3
常规岛/凝汽系统/泵/运行手册/现行
```

每个知识库保存以下治理字段：

- `document_id`：稳定业务 ID，不使用文件名作为唯一键；
- `source_uri` 与来源系统；
- `content_hash`：判定内容是否实际变化；
- `version`、`effective_from`、`effective_to`、`status`；
- `domain`、`system`、`equipment_type`、`document_type`；
- `ingestion_batch_id`、导入时间、索引状态、失败原因；
- `security_scope`：组织、角色、项目或设备权限；
- `supersedes_document_id`：新旧版本关系。

### 2.2 导入与更新

- 导入使用批次任务，建议每批 100–500 份；每批独立状态、可重试、可回滚。
- 普通 RAG：文档解析和 embedding 成功后即可上线。
- GraphRAG：先生成文件子图，再按域合并；合并任务离线运行，限制并发，失败不影响普通 RAG 服务。
- 新增：增量解析 → 文件子图 → 域图合并。
- 修改：以 `content_hash` 判定；新版本先建索引并验证，再切换生效状态。
- 删除：先逻辑下线检索，再重建受影响域图；RAGFlow 原生删除文件不会自动同步 KG，不能只删文件。
- 每晚做索引一致性核对：业务文档数、RAGFlow 文档数、成功 chunk 数、失败任务数、图谱任务版本。

### 2.3 查询路由

| 问题类型 | 默认路径 | 目标 |
|---|---|---|
| 单条事实、参数、明确条文 | 普通 RAG（BM25 + 向量） | 低延迟 |
| 召回不准但答案局部 | 普通 RAG + rerank | 提升精度 |
| 实体关系、故障因果链 | KG local/Light | 关系覆盖 |
| 跨文档全局汇总 | General + 社区报告 | 全局归纳 |
| 超长表格/全部清单 | 结构化查询或分页生成 | 避免单次 Prompt 截断 |

路由必须记录：判定类型、选择的知识库、是否使用 KG、检索候选数、引用、各阶段耗时，支持重放。

## 3. 测试数据设计

### 3.1 两种数据集都要测

1. **容量集**：从真实文档复制并做可控元数据变体，验证导入、存储、队列、索引容量。不能用于质量结论。
2. **质量集**：真实且去重的业务文档，保留人工标准答案，验证准确性、引用和版本生效。

仅复制同一 PTR 文件到 1 万份会造成实体高度重合，GraphRAG 合并成本与真实异构文档差异巨大。因此复制集只能给容量下界，不能代表真实建图能力。

### 3.2 规模阶梯

| 阶段 | 文档数 | 重点 |
|---|---:|---|
| S0 | 1 | 功能基线、逐阶段耗时 |
| S1 | 10 | 并发导入、重复实体合并 |
| S2 | 100 | 批次失败隔离、索引增长率 |
| S3 | 1,000 | 队列稳定性、磁盘/ES 容量、P95/P99 |
| S4 | 10,000 | 分库路由、跨库查询、长稳运行 |
| S5 | 30,000+ | 采购目标容量与灾备演练 |

每一级至少记录：文件数、总字节、页数、原始 token、chunk 数、embedding 数、节点/边/社区数。这些指标才允许跨阶段外推。

## 4. 测试矩阵

### 4.1 建库测试

- 单批 100/500 份导入吞吐（docs/min、chunks/min）；
- 1/2/4/8 个解析 worker 并发对吞吐和失败率的影响；
- embedding API 的吞吐、限流、重试和费用；
- General 与 Light 的建图耗时、LLM 调用数、Token、失败重试数；
- 中断后恢复、任务超时、单文档失败是否阻塞整批；
- 增加/修改/删除 1%、5%、10% 文档时的重建范围与耗时。

### 4.2 查询测试

固定问题集按五类分层：局部事实、关系、故障链路、全局汇总、复杂组合。每类至少 20 题，合计 ≥100 题。

负载分三档：

- 单用户：并发 1，测算法基线；
- 日常负载：并发 5/10/20；
- 峰值与极限：逐步加压到 P95 或错误率越界。

每轮至少 30 分钟，长稳测试 8–24 小时。记录：

- 检索 P50/P90/P95/P99；
- LLM 首 Token、生成总耗时、端到端耗时；
- QPS、超时率、5xx、限流率；
- CPU、内存、GC、磁盘 IOPS、ES heap/cache、Redis 队列；
- context precision/recall、faithfulness、factual correctness、引用可追溯率；
- 成本：embedding Token、建图 LLM Token、单问生成 Token。

### 4.3 版本与一致性测试

- 上传 v1 后问旧参数，应命中 v1；上传 v2 并切换生效后，应只回答 v2；
- 删除 v1 后，普通 RAG 与 KG 均不得再引用 v1；
- 构建过程中查询仍应使用上一稳定版本；
- 故障回滚后，答案和引用恢复到上一版本；
- 权限不同的用户检索结果和 KG 上下文都必须隔离。

## 5. 验收门槛与停止条件

采购阈值：常规检索 ≤2s、复杂组合检索 ≤5s。必须明确这是检索还是端到端；当前项目按端到端理解，现有实测不达标。

建议门槛：

- 导入/建图成功率 ≥99.5%，失败可单条重试；
- 检索服务错误率 <0.1%，端到端错误率 <1%；
- 普通 RAG P95 ≤2s（检索阶段），复杂 KG retrieval P95 ≤5s；
- 端到端目标另按模型吞吐设置，并拆出首 Token 与总生成时间；
- 引用可追溯率 100%；
- ES heap 长时 <75%，磁盘水位 <70%，保留至少 30% 扩容余量；
- 任一级出现磁盘 >80%、ES heap >85%、错误率 >1%、队列持续增长或 P95 超标 2 倍，立即停止扩量，先定位瓶颈。

## 6. 当前 131 的前置整改

2026-08-05 基线：64 核、246GiB 内存（约 206GiB 可用），主机 CPU/RAM 充足；但：

- 根盘仅剩 18GiB，使用率 82%；Docker/ES 数据实际位于独立 `/data` 文件系统（984GiB 总量、247GiB 可用、使用率 74%）；
- Elasticsearch 容器上限 7.519GiB，运行时占用约 4.9GiB；JVM heap 实际使用率 32%；
- 当前 RAGFlow ES 索引仅约 2,500 条 live docs、60.3MiB；
- 双查询任务并行时 RAGFlow CPU 约 0.67%、ES CPU 约 0.24%，主机没有饱和。

因此 131 可以继续做 S1/S2（10/100 份）并测单位成本，但**不应直接跳到 1 万份压测**。必须先：

1. 把 `/data` 使用率控制在 70% 以下或扩容，并配置 ES 磁盘水位；根盘也应清理到 70% 以下，避免系统日志/临时文件写满；
2. 根据 S2 实测 heap、缓存命中和 GC 决定是否将 ES 上限提高到 16–31GiB，并预留 OS page cache；不能仅凭容器占用率直接扩内存；
3. 配索引生命周期、快照和恢复；
4. 明确外部 LLM/Embedding 的并发额度和限流，它们是当前建库与端到端延迟的首要变量；
5. 先完成 S1/S2，再根据单位文档存储、Token 和耗时实测推算 S3/S4 资源。

## 7. 容量估算公式

阶梯 S2（100 份）后，用实测单位成本估算：

```text
预计 chunk 数 = 文档数 × 平均每文档 chunk 数
预计向量原始大小 = chunk 数 × embedding 维度 × 4 bytes
预计 ES 存储 = S2 实测索引大小 / S2 chunk 数 × 目标 chunk 数 × 1.3 安全系数
预计建图时长下界 = 目标原始 Token / S2 每分钟处理 Token
预计费用 = embedding Token 费用 + 抽取 Token 费用 + 社区摘要 Token 费用
```

GraphRAG 的图合并和社区发现不是严格线性，必须同时测重复实体率、平均度数、最大连通分量和社区数；不能只按文件数线性外推。
