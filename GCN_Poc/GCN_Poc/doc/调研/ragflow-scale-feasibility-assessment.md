# RAGFlow / GraphRAG 规模与可行性评估

> 面向：项目经理内部评审
> 日期：2026-08-05
> 评估对象：RAGFlow v0.26.1 容器环境、PTR 冷却泵手册、131 服务器现有资产
> 评估结论：部分满足

## 1. 一页结论

RAGFlow 适合继续作为客户指定的主平台：普通 RAG 的文档导入、解析、混合检索、问答、引用和 Web 演示链路已有基础；RAGFlow 也具备内置 GraphRAG、图谱和社区可视化，以及 API/源码二次开发基础。

但今天不能承诺“原生 RAGFlow 已经支持上万份甚至 30 万份文档的稳定 GraphRAG 生产能力”。原因有三层：

1. 需求背景规模是 30 万份以上，但当前只有 1 份 PTR 手册，未完成同规模压测。
2. 131 修复后实测中，PTR GraphRAG 已完成图谱构建，得到 256 个节点、128 条边、41 条有效社区报告，任务 `ok=1`；社区报告 41/41 ID 唯一、来源正确、已知污染词为 0，显式 KG 检索和 `demo_graph_v4` 均已接入社区聚合块。
3. 单文档 General 建图耗时 1255.11 秒，Light 建图 831.47 秒（快 33.76%但图更稀疏）；三系统正式基准 72 条（12 题 × 2 轮 × normal/general/light）全部成功，端到端 P50 分别为：普通 RAG 15.61s、General 23.16s、Light 22.56s，均未达到 2 秒/5 秒阈值；检索 P50 仅 1.58～2.38s，生成残差占 E2E 约 86%～91%，主要瓶颈在外部 LLM 调用而非 131 本地硬件。RAGFlow 官方也明确提示 GraphRAG 需要较多内存、计算资源和 token，删除相关文件不会自动更新，必须重新生成图谱。

因此建议汇报为：

- **普通 RAG：原生链路可行，规模性能需要阶梯压测。**
- **GraphRAG：单份 PTR 的图主体、社区报告和 KG 问答链路在修复后已通过；百份至上万份仍需要分域、分批、任务编排和容量设计，不能由单份成功外推。**
- **二次开发：可行，不必先换平台。** RAGFlow 为 Apache-2.0 开源项目，提供源码、API、Python SDK、前后端和容器部署资产。
- **增量更新：新增文档原生可触发；删除/修订后的图谱一致性原生不足，需要版本治理和重建编排。**
- **最终状态：部分满足。**

## 2. 对四个核心问题的回答

### 2.1 几百份、上万份文档是否支持？

**普通 RAG：原则上支持，但不能用单份 Demo 代替规模验证。** RAGFlow 已有批量导入、异步解析、分块、embedding、全文/向量检索和 API。文档数增加后，主要变量是 chunk 总量、embedding 吞吐、文档引擎容量、索引内存、磁盘 I/O、worker 数量和并发请求数。

**GraphRAG：架构上可以扩展，原生直接承诺不足。** RAGFlow 的 GraphRAG 不是简单为 chunk 加一个向量，而是增加实体/关系抽取、节点 embedding、子图合并、实体消歧、社区发现和社区报告。文档数和跨文档关系增加后，图谱合并、实体去重和社区重算会成为主要成本与失败点。

建议采用分层方案：

- 文档层：按设备、系统、专业或业务域分知识库。
- 图谱层：每个域维护相对可控的子图，跨域查询通过检索编排层聚合。
- 任务层：批量异步、断点、重试、限流、失败隔离和可观测。
- 存储层：RAGFlow 文档引擎继续承担普通检索；需要强图治理时，再评估 Neo4j 或 PostgreSQL/AGE。

上万份文档不是一个“打开 GraphRAG 开关”就能验收的问题，而是容量规划、分域策略、索引生命周期和任务调度问题。

### 2.2 文档规模增长后查询效率如何变化？

普通 RAG 的候选检索依赖倒排/向量索引，理论上不必随文档数线性扫描；但以下因素会推高长尾延迟：

- 向量索引和全文索引变大，缓存命中率下降。
- embedding、重排和文档引擎的资源竞争增加。
- worker 队列、数据库连接和磁盘 I/O 排队。
- 多知识库联合检索时，候选集合和融合排序变大。
- 最终生成耗时受上下文长度和 LLM 服务吞吐影响。

GraphRAG 在查询阶段还要组装实体、关系、局部邻居或社区摘要，通常会增加上下文准备和生成成本。局部实体问题更容易控制；全局汇总问题需要社区摘要和更大的上下文，查询 P95/P99 更值得关注。

当前硬件关联的结论是：131 本地资源不是 S0 的主瓶颈。Light 建图采样时 RAGFlow CPU 不足 1.2%、内存约 5GiB，ES CPU 约 0.2%–0.3%、JVM heap 使用率约 32%；PTR 基础解析 550.44 秒中 embedding 约 499.37 秒，占约 91%。因此直接给 131 增加 CPU 或本地 GPU，无法显著缩短当前通过外部 API 完成的 LLM/Embedding 等待。优先优化应是模型服务并发/限流、Prompt 与输出长度、查询路由、缓存、流式首 Token 和分阶段 Trace；只有将模型/embedding 本地化后，本地 GPU 才会成为直接性能变量。

采购需求给出的目标是：常规检索不超过 2 秒，复杂组合检索不超过 5 秒。三系统正式基准（72 条，12 题 × 2 轮 × 3 系统）端到端结果如下：

| 系统 | E2E P50 | P90 | P95 | P99 | 检索 P50 | 规则覆盖率 |
|---|---:|---:|---:|---:|---:|---:|
| 普通 RAG | 15.61s | 26.04s | 39.39s | 40.12s | 1.58s | 99.2% |
| General | 23.16s | 31.64s | 36.50s | 50.21s | 1.97s | 99.0% |
| Light | 22.56s | 52.93s | 58.86s | 76.23s | 2.38s | 88.3% |

三种模式端到端 P50 均超过 15 秒，未达到阈值。但独立检索 P50 仅 1.58～2.38 秒，生成残差（E2E 减独立检索）占 E2E 约 86%～91%，说明当前主要瓶颈不在 ES/图谱检索，而在 RAGFlow 上下文组装、外部模型排队、网络往返、首 Token 等待和答案逐步生成。`generation_residual` 来自两次独立顺序请求相减，仅作诊断方向，不能精确拆分为纯模型推理时间。

必须重新建立以下测量：

```text
按文档数：1 / 10 / 100 / 1,000 / 10,000
按问题类型：局部事实 / 关系 / 全局汇总 / 复杂组合
按系统：普通 RAG / GraphRAG
记录：P50 / P90 / P95 / P99、检索耗时、重排耗时、生成耗时、失败率
```

### 2.3 原生不支持时能否定开？有什么开源方法？

**可以定开。** RAGFlow 官方仓库是 Apache-2.0 开源项目，包含 API、Python SDK、前端、文档解析、RAG、GraphRAG、Docker 和 Helm 等代码。定开不等于随意改生产容器，建议通过受控分支、固定镜像和自动化测试管理。

优先级建议：

| 模块 | 建议内容 | 原因 |
|---|---|---|
| 版本治理 | 文档/设备/版本/生效时间/来源 ID、审核、回滚、影响范围 | 需求明确要求版本管理，RAGFlow 原生证据不足 |
| 导入编排 | 批量、断点、重试、限流、失败隔离 | 解决百份以上导入稳定性 |
| GraphRAG 任务 | 增量子图、删除后重建、实体消歧、受影响社区重算 | 解决更新和合并瓶颈 |
| 检索适配 | 向量/BM25 与图局部/全局融合、统一引用和置信度 | 对齐需求的混合检索与来源展示 |
| 观测与容量 | 队列、token、节点/边/社区、存储、P95、失败任务 | 支撑可行性而非只看 Demo 效果 |

开源参考：

- **Microsoft GraphRAG**：global/local/DRIFT 查询、Leiden 社区、社区摘要和增量 update 的算法与任务设计参考。
- **LightRAG**：local/global/hybrid/mix、多种图存储、增量插入、按文档删除、GraphML 可视化和 `source_id` 来源字段。131 已有法律域 LightRAG 资产，但不能把其结果直接外推到核电设备域或 RAGFlow。
- **Neo4j / PostgreSQL AGE**：外置图存储候选，适合保存关系、版本、来源和时序属性。
- **RAGAS 与 131 JSONL 评测骨架**：复用已有质量指标、延迟、checkpoint 和失败记录。

| 路线 | 主要优化对象 | 主要收益 | 明确代价/边界 |
|---|---|---|---|
| RAGFlow Light | 实体/关系抽取 Prompt 与建图成本 | 保留 RAGFlow 平台，配置切换成本低；PTR 建图快 33.76% | 图更稀疏；不具备完整 LightRAG 的增量/删除链路 |
| 独立 LightRAG | 图+文本双层检索、增量插入和按文档删除 | 索引更轻，适合高频增量和混合检索实验 | 独立服务与 Web/权限/引用适配成本；已有法律域延迟也未到 2 秒级 |
| Microsoft GraphRAG | 全局社区归纳、Local/Global/DRIFT 查询质量 | 跨文档全局问题能力强，算法资料成熟 | 建图 Token、社区摘要和查询上下文成本高 |
| LazyGraphRAG 类方法 | 推迟/按需执行全量社区摘要 | 降低前置索引成本，避免为未发生查询预付全部成本 | 首次复杂查询可能更慢；工程成熟度和 RAGFlow 集成需验证 |
| KAG / OpenSPG | Schema、逻辑形式、数值/时序/规则推理 | 规程符合性、参数越限和多跳严谨推理更强 | Java + Neo4j 第二平台；Schema 人力和查询延迟更高 |

这些方案不是同一维度的“加速版”。当前主矛盾是规模治理和端到端延迟，短期优先级应是查询路由、外部模型服务、异步/分域建图和可观测；只有出现强规则推理需求时，KAG 才值得独立 PoC。

推荐路线不是立刻替换 RAGFlow，而是“RAGFlow 主平台 + 外置版本治理/任务编排 + 必要时外置图存储”。这样满足客户指定平台，同时把原生短板放在可独立测试的边界。

### 2.4 新增文档是否容易更新？

分两种情况：

- **普通 RAG 新增**：上传后异步解析、分块、embedding 和索引，原生流程相对直接，适合增量导入；仍需验证批量失败隔离、索引刷新和引用一致性。
- **GraphRAG 新增**：官方说明新文件开始解析时数据集图谱会自动更新，但实际需要完成实体/关系抽取、节点 embedding、子图合并、消歧和社区处理。本次提高合并超时并修复链路后，单份 PTR 成功完成仍需 1255.08 秒，说明可触发不等于稳定、快速完成。
- **删除文件**：官方明确不会自动更新图谱，必须重新生成。
- **修订文件**：生产上应生成新版本，不建议直接覆盖；需要版本元数据、旧版本保留、生效时间和影响范围。

结论是：新增文档“可以接入”，但 GraphRAG 的增量更新属于**部分满足**；删除、修订、回滚和跨文档一致性需要定开治理层。

Light 的建图提速不能单独视为质量提升。它生成的图明显更稀疏，必须结合关系题、全局题、社区引用率和答案完整性判断。并且 RAGFlow `method=light` 只替换图谱抽取方法，图存储、KG retrieval 和 Chat 仍是 RAGFlow 链路，不能把该结果表述成“完整 LightRAG 已验证”。

### 3.2 不能外推的历史结果

实习生法律域 RAGFlow 结果包含延迟和 RAGAS 指标，但当时没有开启知识图谱，且普通 RAG、LightRAG、GraphRAG-SDK 的数据和参数不同。因此它们只用于复用评测骨架和说明测量方法，不作为 PTR 或 GraphRAG 的效果/规模证据。

## 5. 建议的下一步

1. 固化当前修复：Prompt 去示例污染、社区稳定 ID、Chat 复用当前模型、GraphRAG worker 移除硬编码模型；合入受控分支并构建固定镜像。
2. 在 RAGFlow Web 完成图谱、社区、Q5/Q6 和引用展开的人工终验；后端证据已经通过，不再重复触发图谱重建。
3. 执行 1/10/100 份最小阶梯实验；上千和上万份只在资源足够时执行，不用单份成功替代规模结论。
4. 拆分端到端延迟，分别测检索、重排、KG 上下文和生成；当前 2 秒/5 秒指标明确未满足。
5. 在最终方案中把 RAGFlow 作为主平台，把版本治理、增量编排、图谱外置、社区报告质量校验和容量观测列为定开模块。
6. 对项目经理明确说：当前结论为“部分满足”；单文档 Demo 和社区/KG 链路满足，规模性能与删除/修订一致性仍未满足或未验证。
