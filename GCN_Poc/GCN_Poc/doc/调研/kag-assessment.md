# KAG（OpenSPG/KAG）调研评估

> 面向：项目经理内部评审
> 日期：2026-08-05
> 评估对象：OpenSPG/KAG（蚂蚁集团 + 浙江大学开源，Apache-2.0），与 RAGFlow 主平台的关系
> 评估结论：技术先进、专业领域匹配度高，但现阶段建议列入观察/备选名单，不建议替换或并行引入主链路
> 信息来源：官方论文（arXiv 2409.13731）、GitHub OpenSPG/KAG、社区实践文章；标注"待验证"的为我们未实测项

## 1. 一页结论

KAG 是蚂蚁集团知识图谱团队面向**专业领域严谨问答**的框架，核心卖点是用 Schema 约束 + 逻辑形式推理解决传统 RAG"对数值、时序、规则不敏感"的问题，在蚂蚁政务（1.1 万份政务文档）和医疗场景有真实生产落地，多跳问答基准上显著超过 GraphRAG。

但它与我们的约束存在三点错位：

1. **延迟方向相反**：采购目标是常规 2 秒、复杂 5 秒；KAG 的逻辑形式求解链路比 GraphRAG 更重，社区实测单次问答约 40 秒（单机低配，待验证），不是为低延迟设计的。
2. **是独立平台而非插件**：KAG 强耦合 OpenSPG 引擎（Java 服务 + MySQL + Neo4j + MinIO），无法作为模块嵌入 RAGFlow，引入即意味着维护第二套平台、第二套技术栈（Java）。
3. **产品化成熟度不足**：知识库编辑、批量导入（目前单文件上传）、参数调优等工程功能不完善，社区规模明显小于 RAGFlow。

**建议**：不替换 RAGFlow 主平台；列入技术观察名单。触发重新评估的条件：需求侧出现强规则推理/合规审计类问题（如"某操作是否违反规程第 X 条"），且 RAGFlow GraphRAG/Light 路线在该类问题上实测不达标。

## 2. KAG 是什么

KAG（Knowledge Augmented Generation）= 知识图谱与向量检索双向增强的问答框架，基于蚂蚁开源的 OpenSPG 知识图谱引擎。架构分两个已开源模块：

| 模块 | 职责 |
|---|---|
| kg-builder | 知识构建：LLM 友好的知识表示（LLMFriSPG），兼容无 Schema 抽取与有 Schema 约束的专业知识构建，图结构与原文块双向互索引 |
| kg-solver | 问题求解：逻辑形式（Logical Form）引导的混合推理引擎，集成检索、图谱推理、语言推理、数值计算 |
| kag-model | 面向 KAG 的模型能力专项增强，官方称后续开源（截至本次调研未见完整发布，待验证） |

五大技术点：LLM 友好知识表示、图谱-文本互索引、逻辑形式混合推理、语义推理知识对齐、模型能力增强。

与 GraphRAG/LightRAG 的本质差异：后两者是"LLM 自由抽取实体关系 → 图增强检索"，KAG 是"Schema 约束的领域建模 + 符号逻辑推理"，更接近传统知识图谱工程与 LLM 的融合。

## 3. 效果与产业验证（均为官方/论文口径，非我们实测）

- 多跳问答基准：HotpotQA 上 F1 相对提升 19.6%，2WikiMultiHopQA 上相对提升 33.5%，超过 GraphRAG、HippoRAG 等。
- 产业落地：支付宝政务问答（约 1.1 万份政务文档，论文口径准确率 91.6%）、支付宝健康管家医疗问答。
- 适用领域：金融、医疗、法律、政务等需要规则推理、数值/时序敏感、答案可解释的专业场景。

对我们的参考价值：核电运行规程、检修记录恰恰是"规则 + 参数 + 因果链"密集型文档，KAG 的 Schema 约束抽取和逻辑推理在问题类型上高度匹配——这是它值得留在观察名单的原因。

## 4. 部署与资源要求

- 部署形态：docker-compose 一键部署，四个组件——openspg-server（Java/SOFABoot）、MySQL、Neo4j（图存储）、MinIO（对象存储）；管理后台 `http://<host>:8887`。
- 官方建议硬件：CPU ≥ 8 核、内存 ≥ 32 GB、磁盘 ≥ 100 GB；社区反馈 16 GB 内存可勉强运行（待验证）。
- 依赖外部 LLM/Embedding 服务（兼容 OpenAI 接口），向量模型可接硅基流动等免费 API 做验证。
- 技术栈：服务端 Java，Python 侧为 builder/solver 包；二次开发需要 Java 能力，与我们现有 RAGFlow（Python 为主）的调试经验不重合。

与 131 服务器的关系：已核实主机为 64 核、246GiB 内存、约 206GiB 可用，资源上具备启动隔离 KAG PoC 的余量；但 RAGFlow、ES 与 KAG/OpenSPG/Neo4j 长期共机仍需设置容器限额、独立数据目录和监控，不能用当前空闲内存代替生产容量评估。优先使用独立机器，避免第二套平台影响现有 Demo。

## 5. 与采购需求的对照

| 需求维度 | KAG 现状 | 判定 |
|---|---|---|
| 30 万份级文档规模 | 无公开大规模案例；政务场景为 1.1 万份；Neo4j 社区版水平扩展有限 | 不满足/待验证 |
| 常规 2s / 复杂 5s 延迟 | 逻辑形式求解链路重，社区实测单次问答约 40s（低配单机，待验证） | 大概率不满足 |
| 混合检索 | 图谱 + 向量 + 逻辑推理混合，能力强 | 满足且为强项 |
| 增删改后的索引/图谱更新 | 有 Schema 治理基础，但知识库编辑功能不完善，工程化需自行补齐 | 部分满足 |
| 版本治理、审核、回滚 | 无原生证据 | 需自研 |
| 权限、多租户、运维 | OpenSPG 平台级能力弱于 RAGFlow 产品化程度 | 待验证 |
| 与 RAGFlow 共存 | 无集成路径，只能双平台并行 + 上层路由 | 架构成本高 |

## 6. 风险与局限

1. **延迟**：逻辑形式推理把查询变成"规划 → 多步求解 → 生成"，Token 和耗时都显著高于普通 RAG，与 2s/5s 目标方向相反。
2. **Schema 设计成本**：需要领域专家参与建模（实体类型、关系、规则），前期投入远大于 GraphRAG/LightRAG 的自由抽取；Schema 质量直接决定上限。
3. **平台耦合**：强依赖 OpenSPG 全家桶（Neo4j 图存储、SPG 语义层），替换组件或嵌入现有系统成本高。
4. **产品化成熟度**：社区反馈知识库编辑修改、批量导入（单文件上传）、参数调优功能不完善，使用中会遇到 Bug。
5. **社区与文档**：社区活跃度中等，中文资料相对全（蚂蚁背景），但英文资料和生产案例披露有限；kag-model 尚未完整开源。
6. **团队技能**：Java 服务端栈与我们现有 Python/RAGFlow 调试经验不重合，问题分层定位成本上升。

## 7. 与现有路线的定位对比

| 维度 | RAGFlow GraphRAG（General，已实测） | RAGFlow Light（LightRAG prompts） | 独立 LightRAG | KAG |

## 8. 建议

**短期（本次汇报口径）**：KAG 列入观察名单，不投入 PoC。理由：与 2s/5s 延迟目标方向相反、双平台架构成本高、产品化不成熟；其价值点在"规则推理"，而我们当前题集的主要矛盾是延迟和规模，不是逻辑严谨性。

**触发重新评估的条件**（任一满足即可立项最小 PoC）：

1. 业务方明确提出"规程符合性判断""参数越限因果链"等强规则推理类需求，且 RAGFlow 路线实测不达标；
2. 有独立服务器资源（≥8C/32G/100G）且不影响 131 现有环境；
3. 有具备知识图谱 Schema 建模经验的人力投入。

**若立项，最小 PoC 设计**：取 PTR 手册同一域文档 + 复用现有固定题集，另补 5–10 道规则推理题；只测三项——规则题准确率、单次问答延迟、建库工时；与 RAGFlow General/Light 同题对比。预期 2–3 天出结论。
