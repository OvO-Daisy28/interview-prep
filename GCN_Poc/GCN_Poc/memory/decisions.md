# 关键决策记录（ADR）

> 本项目的重要决策及理由。每条决策记录"为什么这么选"，避免后续重复讨论。
> 最后更新：2026-08-21（任务队列选型与 Redis 演进方向）

---

## 决策 1：技术栈用 RAGFlow，不自搭

**背景**：中广核采购文件活化项目，甲方指定 RAGFlow + MinerU。实习生已部署 RAGFlow。

**决策**：直接用甲方已部署的 RAGFlow（http://10.126.2.131:9388），不自搭 RAG/GraphRAG。

**理由**：
1. 甲方硬约束：换栈须证明指标不低于 RAGFlow/MinerU 并经评审，半月内做不到
2. 招投标 demo 有时限，自搭调试成本高
3. RAGFlow 内置 GraphRAG（开关式），覆盖受控客户需求材料中的 GraphRAG 要求
4. 算法团队职责是"关键技术支撑"，非从零造轮子

**代价**：受限于 RAGFlow 的实现细节（如社区发现参数、checkpoint 机制），不能自由改算法。
**边界**：若 RAGFlow 的 GraphRAG 能力不达标，结论是"部分满足"，不强行换栈。

## 决策 2：模型选择以运行时真实可用和结构化输出为准

**背景**：原 `deepreasoning-ds-v4pro` 及多个同源模型实例因上游密钥禁用或欠费失效；GraphRAG worker 还存在硬编码模型覆盖，使知识库配置无法真正生效。

**决策**：PTR GraphRAG 知识库、对应文档和 `demo_graph_v4` 使用实测可用的 `deepreasoning-ds-v4flash@deepreasoning-ds-v4flash@ModelScope`，并删除 worker 中硬编码 `api_key/llm_name` 覆盖。租户默认模型和普通 RAG 库不随意修改。

**理由**：
1. 模型名称不能证明实例可用，必须通过真实最小调用和结构化输出验证。
2. 配置必须在知识库、文档、worker 和 Chat KG 链路中一致生效。
3. 本次完整重建已实测成功：256 nodes / 128 edges / 41 条有效社区报告。

**边界**：当前模型选择是 131 环境在 2026-08-04 的可用终态，不等于永久推荐；生产化需要模型健康检查、降级策略和凭据治理。

## 决策 3：GraphRAG 重跑用 DELETE /graph，不改源码

**背景**：之前改 RAGFlow 源码打补丁（force re-extract），但补丁不完整导致 edges 丢失（坑#5）。

**决策**：重跑 GraphRAG 时用官方 API `DELETE /api/v1/datasets/{kb}/graph` 清旧图谱，不改源码。

**理由**：
1. 改源码要完整追踪调用链（does_graph_contains + load_subgraph + merge_subgraph_attempt），容易漏
2. 官方 DELETE /graph 会清 phase marker + source_id，解决 "already merged" 跳过问题
3. 可复现、可追溯，不污染容器内代码

**例外**：max_tokens 注入（坑#2）仍需改源码，因为没有 API 可设。此补丁已落盘到 doc/learn/ragflow_operations.md。

## 决策 4：demo 范围只做检索对比，不做其他子系统

**背景**：需求文档有 7 个子系统（解析入库、治理、检索、手册生成等），demo 半月时限。

**决策**：demo 只聚焦"普通 RAG vs GraphRAG 检索效果对比"，不做其他 6 个子系统。

**理由**：
1. 项目经理核心诉求：评估 RAGFlow 能否满足"普通 RAG + GraphRAG"
2. 检索是 GraphRAG 的经典卖点，对比效果最能打动评审
3. 半月时限 + 1 份测试文档，做不了全量 30w 份的完整系统
4. 其他子系统（内容治理、手册生成）非算法团队职责

**demo 交付物**：
1. 对比问答截图（6 个问题：局部事实 / 故障诊断 / 关系推理 / 全局汇总）
2. 图谱可视化截图（Web 界面的知识图谱页面）
3. 评估结论文档（RAGFlow 满足度：满足 / 部分满足 / 不满足）

## 决策 5：按运行代码、验证代码和证据资产分层

**背景**：之前 `code/` 混放 API 客户端、一次性 debug、固定题集和验证脚本，项目根又新增了规范外的 `outputs/`，导致职责边界和凭据治理失控。

**决策**：
- `code/` 只保留可复用运行与运维工具：`ragflow_client.py`、`rebuild_graph.py`、`monitor_graphrag.py`、`ssh_ops.py`。
- `test/` 保存固定题集、GraphRAG 验收、KG retrieval 对照和 pytest。
- `code/patches/` 保存服务器源码前后版本、diff、哈希和回滚边界。
- `test/results/<YYYY-MM-DD>/` 保存不可变 JSON/JSONL 和质量摘要；项目根不设 `outputs/`。

**原则**：
- 一次性 debug 脚本和 `__pycache__` 不保留。
- 代码、文档和测试结果不保存真实 API Key、密码或私钥路径，统一由环境变量或受控秘密来源注入。
- `rebuild_graph.py` 的删除操作必须提供固定确认令牌；普通检查脚本默认只读。
- uv 项目元数据由 `code/pyproject.toml`、`uv.lock` 和 `.python-version` 统一管理。

## 决策 7：截止日改为“可行性评估优先”，问答演示降为证据

**背景**：用户于 2026-08-04 明确，项目经理主要要数据和可行性，重点是几百至上万份文档、查询效率、RAGFlow 定开和新增文档更新；截止日期就是当天，不需要截图，真实材料无需脱敏，允许“部分满足”。

**决策**：主交付改为 RAGFlow Web 可操作演示 + 规模/效率/定开/增量更新评估 + 满足度矩阵。原固定 6 题只作为普通 RAG/GraphRAG 界面证据，不再作为主评估中心；截图不作为交付物。

**理由**：单份 PTR 手册无法证明万份或 30 万份规模，且当前 GraphRAG 在 747 个节点合并时两次 180 秒超时。若继续把“GraphRAG 效果对比”作为主线，会把无效图谱结果误读成算法结论，无法回答项目经理真正的决策问题。

**结果**：允许结论为“部分满足”；必须区分官方事实、131 实测、工程外推和待验证实验。普通 RAG、GraphRAG 配置/图谱、问答、引用和失败证据保留为现场演示主线。

## 决策 8：规模化方案采用“RAGFlow 主平台 + 外置治理/编排 + 分域图谱”

**背景**：采购需求背景规模为 30 万份以上，并要求批量导入、版本管理、增删改查、来源/时序节点、GraphRAG 局部和全局检索。RAGFlow 官方支持 GraphRAG 和新文档触发更新，但删除相关文件不会自动更新，且官方警告 GraphRAG 资源成本高；131 当前 PTR 图谱合并超时。

**决策**：保留 RAGFlow 作为主平台和 Web 入口；在其外增加版本治理、批量任务编排、失败隔离、图谱健康检查、分域/分批构建和统一引用适配层。只有隔离实验验证确有必要时，才修改 GraphRAG worker 或引入 Neo4j/PostgreSQL AGE 等外部图存储。

**理由**：既满足甲方指定 RAGFlow 的约束，又把原生能力不足的部分放在可测试、可回滚的边界上；分域图谱比把所有文件立即合成一张统一图更容易控制构建超时、更新范围和查询上下文。

**结果**：今天交付方案和证据矩阵，不把外部开源组件已具备的能力写成 RAGFlow 已完成集成；后续按 1/10/100/1000/10000 份阶梯压测决定是否实施定开。

> ⚠️ **本决策的适用范围已被[决策 15](#决策-15开发阶段以交付好用系统为准ragflow-是手段不是约束)收窄（2026-08-19）**。决策 8 是 **POC 可行性评估阶段**的策略（当时要快速评估、不引入维护成本，故"能不改就不改"）。进入开发交付阶段后，"不改 RAGFlow 内核"**不再是前提**，改与不改按收益/成本判断。本条保留作为历史快照。

## 决策 9：社区产物验收拆为生成、落库、检索三层

**背景**：2026-08-04 PTR GraphRAG 任务日志显示生成并索引 24 个社区，但 ES 中仅命中 8 个 `community_report`，且正文出现 Prompt 示例中的 `Unity March` / `Verdant Oasis Plaza`；当前 Chat 也没有把社区报告稳定送入上下文。

**决策**：后续 GraphRAG 验收必须同时检查：
1. 社区生成数量与输入图谱数量一致；
2. ES 实际文档数、唯一 ID、`kb_id/source_id` 和正文领域一致；
3. 显式 KG 检索或 Chat reference 中出现有效社区报告；
4. 报告标题 ID 不得只依赖 LLM 生成标题，必须加入社区层级/社区 ID/节点集合哈希。

**理由**：单看 `progress=1`、`Graph indexed N communities` 或 `mind_map` 字段无法证明社区产物可用。当前代码中 `chunk_id` 由 `content_with_weight + kb_id` 生成，LLM 重复标题会覆盖文档；社区 Prompt 的完整示例还会诱发模型复制跨域文本。Chat 只有在 `parser_id=knowledge_graph` 或 `use_kg=true` 时才调用 KG 检索，当前 PTR KB 的 `parser_id` 为 `null`。

**结果（2026-08-04）**：三层验收已闭环。Leiden 发现 43 个候选社区，41 条报告成功生成并索引；ES 为 41 条、41 个唯一 ID、来源正确、污染词为 0；显式 KG retrieval 和 `demo_graph_v4` 均返回 `Related content in Knowledge Graph` 聚合块。该决策继续作为后续每次重建的强制验收标准。

## 决策 10：运行时补丁必须镜像化，Demo 成功不等于生产完成

**背景**：本次为恢复 131 真实 Demo，已在运行容器和宿主源码中修复社区 Prompt、社区稳定 ID、worker 模型覆盖和 Chat KG 模型复用，并保存补丁前后源码与 diff。Docker daemon 重启后补丁仍存在，但继续依赖容器内修改会造成版本漂移和不可复现。

**决策**：当前运行时补丁只作为受控恢复和实测证据；正式交付前必须合入源码分支、增加回归测试并构建固定版本镜像。镜像发布前保留现有备份和回滚路径。

**验收**：
1. Python 编译和相关分支测试通过；
2. GraphRAG 任务、图主体、社区落库、KG retrieval、Chat 五层通过；
3. 容器重启后配置和补丁可回读；
4. 不用单份成功外推百份、万份或 30 万份能力。

**结果**：单份 PTR Demo 满足；社区/KG 链路满足；2 秒/5 秒端到端性能未满足；规模和删除/修订一致性仍为部分满足。

## 决策 11：结构化归档作为唯一事实源，不保留重复 zip 和 outputs

**背景**：服务器修复资产曾同时存在于 `outputs/repair_2026-08-04/server_code_archive/`、早期 `patch/` 副本和 zip 中，测试证据也与源码补丁混放，既破坏根目录规范，又让后续更新容易产生多份漂移。

**决策**：容器五文件的 `before/after/diffs/metadata` 以 `code/patches/ragflow-v0.26.1-2026-08-04/container/` 为唯一审计事实源；宿主三文件同步范围单独放在 `host/`；运行证据放入 `test/results/2026-08-04/`。逐文件 SHA-256 和数量校验通过后删除旧 `outputs/` 及重复 zip。

**理由**：结构化目录可直接审查、diff 和复用；zip 只增加重复副本，不能替代受版本控制的文件树。删除旧位置前已验证 8 个测试证据全部哈希一致，容器归档 18/18 文件、0 个哈希差异。

**边界**：该归档证明运行时修复和当时服务器哈希，不等于已构建固定自定义镜像；宿主只归档有真实来源的三文件，不伪造 `task_executor.py` 或 `dialog_service.py` 的宿主版本。

## 决策 12：先测 RAGFlow 内置 Light，不把它等同于完整 LightRAG

**背景**：RAGFlow v0.26.1 的 `parser_config.graphrag.method` 支持 `general` 和 `light`；项目经理希望评估 LightRAG 路线，但甲方主平台仍是 RAGFlow。

**决策**：先在 RAGFlow 内复制同一 PTR 文档，以 `method=light` 重建图谱并与 General 做公平 A/B；独立 LightRAG 只作为后续旁路候选，不立即替换主平台。

**理由**：RAGFlow Light 复用 LightRAG 风格的实体/关系抽取 Prompt，但图存储、KG retrieval 和 Chat 仍走 RAGFlow 自有链路。它能低成本验证抽取速度和图谱稀疏度，不能代表完整 LightRAG 的双层检索、增量插入或按文档删除能力。

**验收**：建图必须同时满足 `progress=1.0`、日志无失败标记、图节点数大于 0；查询 A/B 必须统一文档、模型、`top_n/top_k`、题集和轮次。

## 决策 13：效率结论拆分检索与端到端，不用差值冒充服务端 Trace

**背景**：采购需求关注常规 2 秒、复杂组合 5 秒；单看 Chat 总耗时无法判断是 ES/KG、Rerank 还是外部 LLM 慢。

**决策**：每题先独立调用 retrieval，再调用非流式 Chat，分别记录检索和端到端 P50/P90/P95/P99，以及成功率、失败率和超时率；成功分位数只统计成功请求，超时样本仍计入失败/超时率。`端到端 - 独立检索` 只标为生成残差诊断值，不称为服务端精确生成耗时。

**理由**：两次请求是串行独立调用，检索缓存、模型排队和上下文可能不同。只有服务端 Trace 才能精确拆出 embedding、检索、rerank、KG 上下文、首 Token 和生成阶段。

**边界**：单用户串行 S0 结果用于算法和外部服务基线，不能替代并发 5/10/20、8–24 小时长稳或万份级容量结论。

## 决策 14：长基准必须逐行落盘、断点续跑并使用硬墙钟超时

**背景**：三系统正式基准在 Q10 General 非流式 Chat 上停留超过 30 分钟。`requests timeout` 只限制连接/单次读等待，服务端保活可使其无法形成总墙钟上限。

**决策**：基准以 `(round, question_id, system)` 为唯一键逐行 `flush + fsync`；中断后 `--resume` 跳过已有键。每个系统测量放到独立子进程，默认 180 秒硬墙钟超时；retrieval 阶段完成即回传，Chat 超时时保留检索指标并将 e2e 记为失败。Windows 子进程结果使用临时 JSON 原子文件回传，不用 `multiprocessing.Queue` 承载大答案。

**理由**：长测试不能因单题挂死丢失全部证据，也不能删除超时样本后只报告成功分位数。硬超时、失败率和断点唯一性都是性能验收的一部分。实测表明 Windows `spawn` 下队列 feeder 线程可能在大消息或终止场景死锁，使父进程收尾突破墙钟上限；文件回传消除了这条退出依赖。

## 决策 15：开发阶段以"交付好用系统"为准，RAGFlow 是手段不是约束

**背景**：[决策 8](#决策-8规模化方案采用ragflow-主平台--外置治理编排--分域图谱) 定的"保留 RAGFlow 主平台 + 只有确有必要才改 worker"，是 **POC 可行性评估阶段**的合理策略（当时目标是快速评估、不引入维护成本）。但进入**开发交付阶段**后，该策略被误当成"RAGFlow 内核一行不能改"的硬前提，导致设计时把 RAGFlow 的能力缺陷当成不可跨越的边界，绕着走出一堆次优方案。

典型症状（2026-08-19 M1 实测暴露）：
- RAGFlow 只给单浮点 progress + 累积文本日志 → 编排层被迫"猜"当前阶段，为此修了 4 个映射 bug，逻辑脆弱
- RAGFlow 无暂停能力 → 只能提供"软停（等当前跑完）"或"硬停（取消重跑）"，都不是真暂停
- RAGFlow 无自动重试（`Task.retry_count` 字段存在但无消费逻辑）→ 编排层重新触发
- 单 worker 吞吐 → 编排层限流迁就
- 单份 3.7MB docx 耗时 130~166s，其中 embedding 占 60%+（CPU 部署）→ 编排做得再好也是给慢引擎排队

**决策**：**核心目标是交付好用、鲁棒、符合业界规范的批量上传能力；RAGFlow 是实现手段，不是设计约束。**

- 改不改 RAGFlow（源码/worker/配置/部署形态/替换组件），一律按**收益 vs 维护成本**判断，不预设"不能改"。
- 判断标准：
  1. **收益大 + 改动局部** → 直接改（例：`set_progress` 上报结构化阶段与耗时，消灭猜阶段逻辑）
  2. **收益大 + 改动深** → 先隔离验证再改（例：worker 主循环加暂停检查点实现真暂停）
  3. **编排层能做好的** → 不改 RAGFlow（例：批量排队、优先级、失败隔离，本就是编排层职责）
- 改动必须满足决策 10 的工程约束：完整追踪调用链（避免坑#5 类漏改）、合入源码分支、回归测试、构建固定镜像、保留回滚路径。
- 二开候选清单与优先级由**真实性能数据**驱动（M2 批量实测后确定），不拍脑袋。

**理由**：
1. 甲方约束是"技术栈建议 RAGFlow + MinerU，换栈须证明指标不低于并经评审"——这约束的是**不要另起炉灶换平台**，不是"不能改 RAGFlow"。RAGFlow 是 Apache-2.0 开源，二开本就是其正当用法，也是项目经理明确要求的（沟通记录："如果不满足要在 ragflow 的基础上进行开发"）。
2. 死守不改会让交付物停留在"能用但不好用"：靠轮询猜状态、没有真暂停、无法优化性能瓶颈——这不符合业界对批量导入系统的基本要求。
3. 维护成本可控：改动进源码分支 + 固定镜像 + 回归测试（决策 10 已定义流程），不是运行时打补丁的野路子。

**边界**：
- 不换主平台（不因局部不满意就迁移到别的 RAG 框架）。
- 不做无收益的改动（能在编排层解决的不动内核）。
- 每笔内核改动都要有对应的回归测试和回滚方案。

**结果**：决策 8 的"外置编排"部分仍然有效（编排层该做的事不变），"不改内核"部分作废。二开候选清单见 `doc/design/ragflow-modification-candidates.md`。

## 决策 16：编排层用 MySQL，复用 131 现有实例——PostgreSQL 此前无依据

**背景**：`ingest-orchestration.md` §九、`interface-inventory.md`、`pbs-and-layering.md`、`architecture.md` 全都写着编排层/内容数据库用 **PostgreSQL**。2026-08-20 用户追问"为什么一定要 PG？哪里规定的？"，回溯发现**没有任何依据**。

**查证（2026-08-20，PDF 全文检索）**：

技术规范书《附件1+技术规范书.pdf》全文搜索 `PostgreSQL / Postgres / MySQL / Oracle / 达梦 / 人大金仓 / openGauss / GaussDB`——**命中数 0**。规范书只有两处泛指要求：

- p12：「本项目应以**关系型数据库**作为解析后的结构化数据的在线管理载体，以 JSON/JSONL…」
- p17：「数据库应采用**关系型数据库**，数据模型应涵盖文档级、设备级、参数级、信息块」

`doc/客户/` 下其余材料（功能需求 docx、项目经理沟通记录）同样无数据库产品要求。

**PostgreSQL 的来源**：`二次开发范围分析.md:213,231` 画阶段二架构图时，前一个 agent 自行填入了具体产品名，此后 architecture.md → interface-inventory.md → pbs-and-layering.md → ingest-orchestration.md 层层继承，被当成既定事实。**这与[决策 15](#决策-15开发阶段以交付好用系统为准ragflow-是手段不是约束)是同一类错误：把前人的一个选择当成了外部约束。**

**决策**：批量导入编排层用 **MySQL 8.0.39**，复用 131 已部署实例（`docker-mysql-1`），**建独立 database `gcn_ingest`，不混入 `rag_flow` 库**。

**131 MySQL 实测**（不凭旧记录）：版本 8.0.39、`utf8mb4` / `utf8mb4_unicode_ci`、默认引擎 InnoDB。JSON 类型、外键、事务、中文文件名均支持。

**理由**：
1. 规范书只要求"关系型数据库"，MySQL 满足，无合规风险。
2. 131 已在跑（RAGFlow 自用），复用现有实例/备份/监控，少一套运维。
3. 本层需求极简单：job/task/step 三张表 + 状态机 + 时间戳 + 计数，用不到 PG 的 JSONB 高级查询、AGE 图扩展等差异化能力。
4. 实习生部署的就是 MySQL，团队已有运维经验。

**边界**：
- 只定**本编排层**。组 3「内容数据库子系统」（PBS 树 / 信息块 / 枚举字典）如确有 PG 特性需求（如 AGE 图查询），可独立选型——两层本就该解耦。
- 独立 database，不与 RAGFlow 的 `rag_flow` 库混用，避免表名冲突与误删。
- 若后续甲方提出信创/国产化数据库要求，按 ORM 层抽象改造（当前 SQL 保持标准语法，不用 MySQL 方言特性）。

**MySQL 与原 PG 草案的语法差异**（`code/ingest/schema.sql` 已按此改写）：`BIGSERIAL`→`BIGINT AUTO_INCREMENT`、`JSONB`→`JSON`、`now()`→`CURRENT_TIMESTAMP`、`updated_at` 用 `ON UPDATE CURRENT_TIMESTAMP`、时间列用 `DATETIME`（避开 TIMESTAMP 的 2038 与时区问题）、TEXT 列不直接建索引。

**教训**：文档里的技术选型，若无客户文档/实测/决策记录支撑，就是待验证项而非事实。继承前先问一句"依据在哪"。

## 决策 17：任务队列先用 MySQL 表 + 轮询，Redis 是明确的演进方向而非当前选项

**日期**：2026-08-21

**背景**：向 PM 汇报时被问"批量上传背后是 Redis 队列吗"。当前实现是 `ingest_task` 表当队列，后台 worker 每 2s 轮询取 pending，`ThreadPoolExecutor(max_workers=3)` 并发执行。用户直觉"业界都用 Redis，MySQL 轮询是不是不规范"——这个直觉是对的，需要给出选择理由而不是辩解。

**决策**：**当前阶段维持 MySQL 表做队列**；规模到千份级或需要多机消费时换 Redis/RabbitMQ，**MySQL 保留为阶段耗时与状态的账本**（队列归队列、账本归账本），不是二选一替换。

**理由**：
1. **需求要的是可查询可修改的队列**，不是消息管道。PM 第 1 点明确要"读取和修改队列状态"（如查出所有失败任务重排优先级）。Redis List/Stream 做不了条件查询与随机修改，旁边仍要挂状态表 → 两处存储要保持一致。
2. **阶段耗时本就是要长期留存的业务数据**。四阶段的 started_at/finished_at/duration_ms/retry_count/error 要能事后查账，本就该在关系库。表已存在，再引队列反而多一层同步。
3. **当前单实例，Redis 的核心优势（多机安全消费同一队列）兑现不了**，而 MySQL 已在 131 上跑着，少运维一个组件。

**代价（如实记录，不回避）**：
- **空转轮询**：无任务时每 2s 一次查询。Redis 阻塞读能做到有活才醒。
- **最长 2s 取任务延迟**：REST 提交时会额外 `_kick_worker()` 叫醒，实际通常立刻开始；纯靠轮询最坏 2s。
- **只能单实例运行**（最实在的限制）：`pending_in_priority_order` → `run_batch` 之间没有跨进程抢锁，起两个服务进程会重复处理同一 doc。**横向扩容前必须先换队列。**

**换的时候要改哪**：取任务只集中在 `ingest/scheduler.py` 一个类——REST 接口、状态机、表结构都不动。这是三层灵活性设计（可替换适配器）的一次兑现。

**触发条件**：百份 → 千份级压测暴露单机吞吐不足时。**不为还没到来的规模提前付运维成本。**

**相关实测（2026-08-21，job 33，task 42/43）**：同一批两份文件 **02:22:17 同时开始**，docx 25.9s 完成、扫描 PDF 166.9s 完成——并发是真的，但快慢差 6.4 倍，界面上看起来像串行。批次总耗时 167s（= 最慢那份），串行需 193s，并发省 13%。耗时大头是两个 CPU 推理环节：MinerU 版面识别 96.8s + 向量化 68.8s，占 99%。**结论：要更快的方向是给这两个环节配 GPU，不是继续加并发。**
